# Changelog new entry — feat(exit-traffic): активные пробы exit-нод — TG-уведы «нода недоступна 📴 / тупит 🐌 / восстановлена 🔌» по TCP host:port (11 Nov 2026)

## Контекст: запрос владельца (11.11.2026, по деплою exit_traffic_watcher): «если нода RU1 деградирует (упадёт, начнёт тупить или станет неиспользуемой) — придёт ли уведа в TG?» Наблюдатель был ЧИСТО ПАССИВНЫМ (дельты счётчиков Stats API): смерть/деградация ноды видна лишь косвенно — трафик через неё молчит или перераспределяется на другие. В балансировочных режимах «молчащая» нода не порождает НИ ОДНОГО события: traffic_node_starved по умолчанию выключен (starve_hours=0) и смотрит только на selector; traffic_dominant_change приходит лишь когда трафик уже сконцентрировался в другом месте. Отказ единственной/закреплённой ноды вообще невидим (трафик просто пропадает). Вопрос владельца оставался без ответа.

## Решение — exit_traffic_watcher.py: АКТИВНЫЕ пробы (TCP host:port каждой chain-ноды, stdlib socket.create_connection + time.monotonic — модуль остаётся самодостаточным, без _core/chain_relay). Три новых события: 📴 traffic_node_down — проба не проходит probe_fails прогонов подряд (дефолт 2); текст: нода (алиас либо host:port) + причина (timeout/Connection refused/DNS) + контекст «последний трафик через ноду N мин/ч назад» (метки last_traffic_ts из дельт) + довесок «(Health Monitor: DOWN)» по вердикту node-health-state.json, если HM уже заметил; 🐌 traffic_node_degraded — проба проходит, но RTT выше probe_degraded_ms (дефолт 500, 0 = выкл) probe_degraded_fails прогонов подряд; 🔌 traffic_node_up — восстановление после отказа («после отказа») либо деградации («после деградации»). Машина состояний _tw_probe_update — чистая функция: ok+быстрая проба сбрасывает счётчики, ok+медленная → slow+1, отказ → fails+1, событие ТОЛЬКО на переходе статуса (флап не спамит); переходы одного типа за прогон агрегированы в ОДНО событие с несколькими нодами (одна TG-уведа на тип — min_gap friendly). Guard локальной проблемы: если ВСЕ ноды разом не отвечают — вероятна проблема на самом релее (сеть/DNS/исходящий трафик): персональные счётчики/статусы не трогаются, шлётся один «локальный» traffic_node_down («Все N exit-нод недоступны одновременно… Уведы по отдельным нодам подавлены») и один traffic_node_up с local_recovery при рассасывании («Связь восстановлена: M из N отвечают»). Пробы покрывают ВСЕ chain-ноды (не только selector — в отличие от starve) и идут ДО опроса Stats API: отказ Stats API (ранний выход run_once) не теряет probe-состояние прогона; события идут через общий _emit → фильтр notify/тихие часы/min_gap работают как у остальных. Прочее: EVENTS 4→7 (notify-фильтр добирает новые как ВКЛ — обратная совместимость), DEFAULT_TEMPLATES +3 (📴/🐌/🔌, плейсхолдер {node} — алиас первой затронутой ноды, паттерн {node_to} у смены ноды), tg_bot.py — иконки + event_labels + ev_keys/ev_labels (управляемость из меню «Telegram-уведомления»), TUI: пороги проб в [D] (вкл/выкл, таймаут 1-30 с, неудач 1-10, RTT-порог 0-5000 мс, медленных подряд 1-10), тумблеры трёх событий в [S] (нумерация фиксированных пунктов сдвинута 8-13), статусная строка «Пробы нод (TCP)», тест-уведа (T) шлёт все 7 типов. exit_switch_watcher/smart_balancer/b4/mieru не тронуты (node_health_monitor читается только как контекст).

# Changelog new entry — feat(exit-traffic): человекочитаемый заголовок уведы смены ноды — «Режим: активная нода X. Переключение ноды: Y → X» (10 Nov 2026)

## Контекст: запрос владельца (10.11.2026) по деплою exit_traffic_watcher: уведы traffic_dominant_change приходили строкой «Трафик окна переехал: old → new (72% окна, 1.1 ГБ из 1.5 ГБ)» — технично, но в заголовке (первая строка уведы, её строит tg_notify_event как «🧭 [host | ip] {detail}») не видно ни РЕЖИМА балансировки, ни того, ОТКУДА и КУДА переключился трафик. Владелец: «в названии — откуда переключилась нода, на какую переключилась — желательно, чтобы это было полностью указано, например: SmartBalancer: активная нода node-de.example.com:443. Переключение ноды: node-a.example.com:443 — сделай человекочитаемым».

## Решение — (1) новые чистые функции exit_traffic_watcher: _tw_strategy_label(live, sb) — метка режима для заголовка: «SmartBalancer», если SB включён (патчит selector и владеет ротацией); иначе красивое имя нативной стратегии chain-balancer (leastPing→«LeastPing», roundRobin→«RoundRobin», leastLoad→«LeastLoad», random→«Random», неизвестные — как есть); без балансировщика (pinned/single, failover) — «Каскад». _tw_dominant_change_text(strategy, old, new, share, bytes, total) — тело события: строка 1 «Режим: активная нода X», строка 2 «Переключение ноды: Y → X» (откуда и куда — полностью, имена — алиас либо host:port), строка 3 «Доминирование: N% окна (байт из байт)». (2) run_once: ветка смены доминирующей строит текст через эти функции; _tw_notify_event получил extra-плейсхолдеры ({strategy}/{node_from}/{node_to} — доступны в шаблоне при chat_id-override и curl-fallback). (3) DEFAULT_TEMPLATES: у traffic_dominant_change убран статический заголовок «Смена доминирующей exit-ноды» — первая строка detail теперь и есть человекочитаемый заголовок; основной путь tg_notify_event не менялся (заголовок = первая строка detail). (4) TUI: строка «Стратегия» в статусе меню показывает ту же метку (LeastPing/SmartBalancer/Каскад — раньше сырой тип); тест-уведомление T шлёт смену ноды РОВНО в боевом формате (режим + первая/последняя нода из живых, пометка «тест» отдельной строкой); подменю шаблонов M документирует новые плейсхолдеры. Существующие каналы и остальные 3 события не тронуты.

## Тесты: test_exit_traffic_watcher +7 (58→65): _tw_strategy_label (SB включён → SmartBalancer; SB выключен → нативная метка; все 4 нативные стратегии; неизвестная — passthrough; без балансировщика → «Каскад»; пустые входы); _tw_dominant_change_text (точный формат трёх строк: заголовок/переключение from→to/доля окна; алиасы подставляются как есть); test_full_cycle усилен ассертами на новый формат в run_once (RoundRobin-заголовок, «Переключение ноды: A → B», extra-плейсхолдеры события). # Changelog new entry — feat(exit-traffic): наблюдатель трафика exit-нод — TG-уведы «через какую ноду реально идёт трафик» во ВСЕХ режимах балансировки (10 Nov 2026)

## Контекст: запрос владельца: уведы о том, через какую ноду идёт трафик, раньше приходили (SmartBalancer слал node_connect при каждом переключении), после перехода ротации на нативный chain-balancer пропали — exit_switch_watcher (кейс окт.2026 №8) вернул уведы о СОСТАВЕ ротации и режимных переключениях, но в балансировочных режимах (roundRobin / leastPing / leastLoad / random) Xray выбирает outbound на каждое СОЕДИНЕНИЕ — «активной ноды» не существует, события молчат, пока состав не меняется; вопрос «через какую ноду реально идёт мой трафик?» остаётся без ответа в любом из 5 режимов.

## Решение: chimera/modules/exit_traffic_watcher.py — второй наблюдатель поверх той же точки, но источник данных не СОБЫТИЯ, а СЧЁТЧИКИ: Xray Stats API (127.0.0.1:10085; секции stats/api уже встраиваются в chain-конфиги `_apply_stats_to_config`) отдаёт накопленные байты по каждому outbound-тегу `outbound>>>chain-exit-N>>>traffic>>>uplink/downlink`; дельты счётчиков между прогонами = фактический трафик через каждую ноду за окно — режим-агностично по построению (roundRobin/leastPing/leastLoad/random/smartBalancer/pinned/single). События (4, все в фильтре меню «Telegram-уведомления» + иконки в tg_notify_event): 🧭 traffic_dominant_change — доминирующая нода сменилась (пороги: доля ≥ 60%, объём окна ≥ 50 МБ — равномерный roundRobin НЕ порождает доминирования, это корректно); 📈 traffic_snapshot — периодический дайджест: распределение по нодам (байты + %), стратегия, опционально per-user разбор «кто через какую ноду» (access.log, loglevel=info, топ-N, выключен по умолчанию); 💤 traffic_node_starved — нода в selector балансировщика без трафика N часов при живом окне (балансировщик скипает ноду — сигнал); ⚠️ traffic_stats_error — Stats API недоступен 3 прогона подряд (не чаще раза в сутки). Технически: рестарт xray (сброс счётчиков) → дельта = cur, не отрицательная; накопитель окна дайджеста (acc) сбрасывается после snapshot вместе с dominant_tag; starve-таймер перевзводится после уведа (не спамит); первый прогон — только базовая линия (пустой дайджест не шлётся), первый дайджест уходит на следующем прогоне. Кастомизация (максимум, /var/lib/xray-installer/exit_traffic_watcher.json): вкл/выкл каждого события, интервал cron 1–60 мин, пороги доминирования (доля 50–100%, объём МБ), starve-часы и мин. трафик окна, дайджест раз в N ч (0=выкл), проценты/байты в дайджесте, тихие часы (через полночь), анти-спам min_gap, chat_id override, шаблоны всех сообщений ({host}/{ts}/{detail}), алиасы нод (host:port → «RU1» в уведах), per_user + per_user_top. TUI: меню «[6] Безопасность и автоматизация → TW» (статус: cron/интервал/стратегия/Stats API/доминирующая нода/текущее распределение; прогоны C/T; подменю S/D/A/M — настройки, пороги, алиасы+пользователи, шаблоны; установка cron I/I5/I10/I30/U) + пункт [7] в меню «Telegram-уведомления». # Changelog new entry — FEAT(awg-mieru): аддон «AWG 3.1 поверх Mieru» — клиентский UDP-мост SOCKS5 UDP ASSOCIATE, выдача бандла пир+mita-юзер, TUI+CLI, откат (02 Nov 2026)

## Контекст: продолжение линии hybrid_addon (Mieru поверх Xray). Вопрос владельца: можно ли аналогично завернуть AWG 3.1 — клиент подключается по mieru, дальше весь трафик в туннеле AmneziaWG. Ключевой механизм — НЕ SOCKS5-CONNECT (как у Xray), а SOCKS5 UDP ASSOCIATE: сервер WireGuard/AWG отвечает пиру по адресу последней валидной датаграммы (endpoint roaming), mita держит UDP-сокет на время ассоциации → awg0 на Entry видит «пира с адресом mita» и работает штатно. Живая валидация на entry-ноде (02.11.2026, mita/mieru 3.38.0): UDP ASSOCIATE через mieru→mita доставляет датаграммы вплоть до 127.0.0.1 и до собственного публичного IP:порт awg0 — TCP CONNECT и UDP echo подтверждены end-to-end; на проводе 138x→EU mieru НЕ несёт TLS ClientHello вообще (tshark не находит handshake, первые байты high-entropy) — «маяк» MLKEM768/SNI/JA3 неприменим по построению. Схема клиентского mieru-профиля (profileName / user{name,password} / servers[].portBindings[{port,protocol}] / socks5Port) сверена оракулом `mieru replace config` на реальном бинарнике — легаси-поля port/protocols отвергаются, рабочая схема принята.

# Changelog new entry — FIX(tui): стрелки ↑↓ убивали меню выбора — _getch_raw не видел хвоста ESC-последовательности (sys.stdin.read(1) затягивал [B в буфер Python мимо select); раунд-2: всплеск-чтение + парсер CSI/SS3 + _KEY_PENDING (04 Nov 2026)

Как только нажимаю на стрелку вниз или вверх, сразу появляется надпись "Нажмите Enter…"» — любые терминалы, обычные и NumPad-стрелки; «в меню DPI Detector из Chimera стрелочки работают» (то меню на input() в cooked-режиме — стрелки там безвредны, потому и «работают»). Разбор: tui_select/tui_form/tui_input (меню выбора: routing_rules/dns_rules/_core, формы) читают клавиши через _getch_raw; тот читал первый символ через sys.stdin.read(1) — TextIOWrapper одним сисколом затягивал в буфер Python ВЕСЬ хвост последовательности ([B приходит из SSH одним пакетом), где его не видит select(2) на fd → таймаут 50 мс → «голый» ESC → tui_select трактовал его как Esc-отмену и закрывал меню, остаток [B эхом печатался. Воспроизведено pty-пробой на 138x до патча: _getch_raw([B) → '' (должен быть KEY_DOWN), tui_select(↓+Enter) → None (меню убито первым же байтом).

## Решение — два раунда, оба вскрыты pty-тестами на реальном терминале (как в SSH-сессии). Раунд-1: чтение через os.read(fd, 1) по байту из kernel-буфера — select сразу видел хвост, стрелки заработали; но pty-прогоны показали наследника: восстановление cooked-режима между нажатиями съедало байты, пришедшие ОДНИМ всплеском со стрелкой (↓+Enter одним пакетом: '
' повисал в kernel-очереди на границе raw→cooked→raw, второй _getch_raw блокировался навсегда), плюс SS3-стрелки (OB, application mode) не разбирались вовсе — ранний обрыв хвоста по isalpha ловил модификатор 'O' как финал ('O' вместо KEY_DOWN), дефект, наследованный от исходного кода. Раунд-2 (итоговая схема): _getch_raw читает ВЕСЬ всплеск одним raw-сеансом (блокирующий os.read + дочитывание до 50 мс тишины), первый кейстрок разбирает отдельный парсер _parse_key (CSI: ESC [ params до финала-буквы/~; SS3: ESC O финал — ровно 3 байта; UTF-8: продолжения по lead-байту 0xC0-0xF7 → 2-4 байта, кириллица в формах; / → KEY_BACKSPACE,   → KEY_TAB), остаток всплеска хранится в _KEY_PENDING и отдаётся следующим вызовам БЕЗ обращения к терминалу — все байты живут в Python, границы raw/cooked их не трогают. Одинокий Esc — всплеск из одного байта → '' (честная отмена, 50 мс тишины). Маппинг последовательностей и коды клавиш — без изменений; EOF/поведение — паритет со старым кодом.

## Решение: (1) креды Web UI на все три ноды с публичными b4-фронтами (62.x chimeravpn.pro:9743, RU1 chimeravpn.online:9743, RU2 chimeraprodcdn.online:9743): PUT /api/config {system.web_server.username/password} (b4 сам хеширует: reconcileWebPassword, bcrypt $2a$12) + MCP-токен (system.web_server.mcp.token) для MCP-клиента владельца; креды — secrets/b4_webui.json (вне репо). НЮАНС b4 1.90.x: логин-эндпоинт переименован /api/login → /api/auth/login (легаси-путь отдан auth-мидлварю с 401). WS-токен браузерный UI передаёт через ?token= (utils/common.ts wsUrl). (2) http2 ВОЗВРАЩЁН на все три b4-фронта (listen 9743 ssl http2) по требованию владельца и поскольку доказано: браузерный WS идёт http/1.1 независимо от http2-флага; генератор откачен revert-коммитом 85def4f (d9a390e снят). (3) ИЗВЕСТНЫЙ НЮАНС на будущее: chimera dpi_bypass._b4_api_token шлёт POST /api/login (в 1.90.x не существует) и читает креды из config.json (там теперь bcrypt-хеш, паролем не является) — REST-автопоток Chimera против 1.90.1+auth деградирует в легаси-путь (прямая запись config.json + restart), который продолжает работать; честный REST-логин требует отдельного решения (хранить plain-кредо в state Chimera) — не сделано здесь осознанно, вне скоупа инцидента.

## Тесты/валидация: e2e снаружи по всем трём фронтам (scripts/b4_front_e2e.py, путь браузера): /api/version 200; POST /api/auth/login OK; WS /api/ws/logs?token= + Origin → 101; WS без токена → 401; POST /api/mcp (Bearer MCP-токен) → 200 initialize; REST /api/sets без токена → 401 (ранее — открыт всем: попутно закрыта дыра публичного admin-API). На 62.x access-log после фикса: 101 на /api/ws/*. b4 не рестартился (hot-reload PUT), сеты не тронуты (10/12/10 на 62.x/RU1/RU2).
