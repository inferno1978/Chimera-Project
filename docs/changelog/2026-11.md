# Changelog new entry — FEAT(awg-mieru): аддон «AWG 3.1 поверх Mieru» — клиентский UDP-мост SOCKS5 UDP ASSOCIATE, выдача бандла пир+mita-юзер, TUI+CLI, откат (02 Nov 2026)

## Контекст: продолжение линии hybrid_addon (Mieru поверх Xray). Вопрос владельца: можно ли аналогично завернуть AWG 3.1 — клиент подключается по mieru, дальше весь трафик в туннеле AmneziaWG. Ключевой механизм — НЕ SOCKS5-CONNECT (как у Xray), а SOCKS5 UDP ASSOCIATE: сервер WireGuard/AWG отвечает пиру по адресу последней валидной датаграммы (endpoint roaming), mita держит UDP-сокет на время ассоциации → awg0 на Entry видит «пира с адресом mita» и работает штатно. Живая валидация на entry-ноде (02.11.2026, mita/mieru 3.38.0): UDP ASSOCIATE через mieru→mita доставляет датаграммы вплоть до 127.0.0.1 и до собственного публичного IP:порт awg0 — TCP CONNECT и UDP echo подтверждены end-to-end; на проводе 138x→EU mieru НЕ несёт TLS ClientHello вообще (tshark не находит handshake, первые байты high-entropy) — «маяк» MLKEM768/SNI/JA3 неприменим по построению. Схема клиентского mieru-профиля (profileName / user{name,password} / servers[].portBindings[{port,protocol}] / socks5Port) сверена оракулом `mieru replace config` на реальном бинарнике — легаси-поля port/protocols отвергаются, рабочая схема принята.

## Решение — новый модуль chimera/modules/awg_mieru_addon.py (самостоятельный, stdlib-only, паттерн hybrid_addon; все импорты chimera — ленивые внутри функций):
1. **Сервер: ноль изменений инфраструктуры.** Не трогает awg0, AWG-каскад, mita, порты, firewall. Добавляет только: AWG-пир (штатный awg_peer_add) и mita-юзер awg_<имя> (регенерация server.json через примитивы mieru.py — _build_server_config/_apply_server_config, те же, что в ensure_user_full).
2. **Клиентский бандл** /root/awg-mieru/<name>/: awg-client.conf (штатная сборка awgs_qr_build_client_conf + патч Endpoint=127.0.0.1:<gw_port>, MTU=1100 — консервативно как AWG31_MTU в wpp_awg: mieru MTU 1400 − padding ≤128 − заголовки), mieru-client.json (оракул-сверенная схема), mieru-udp-gw.py (мост), start-linux.sh, start-windows.bat, README.txt (стек, порядок запуска, компромисс TCP-over-TCP, откат).
3. **Мост mieru-udp-gw.py** — UDP→SOCKS5(UDP ASSOCIATE), только stdlib, selectors-петля: сессия per client-addr (TCP control + relay UDP), обёртка RSV/FRAG/ATYP/DST, разворот ответов с корректным парсом ATYP 1/3/4, idle-GC 180 c (keepalive 25 с держит живые тёплыми). E2E протестирован локально: mock-SOCKS5 с UDP ASSOCIATE + fake-AWG-echo → 5/5 датаграмм клиент→мост→SOCKS5→«awg0»→обратно.
4. **CLI**: --status / --issue NAME [--gw-port --socks-port --entry] / --regen NAME (смена IP/домена Entry — пересборка бандла) / --revoke NAME / --list / --rollback-all. **TUI**: do_awg_mieru_menu() — пункт [M] в меню управления пирами AWG (do_manage_awg_peers). State: /var/lib/xray-installer/awg_mieru.json (schema 1, права 0600).
5. **Идемпотентность и откаты**: issue откатывает mita-юзера при падении awg_peer_add; revoke удаляет пир+юзер+бандл; rollback-all — всех; regen не трогает ключи (только бандл). Лог в /var/log/chimera.log.

**Компромиссы (задокументированы в README бандла):** TCP-over-TCP для TCP-нагрузки внутри туннеля (браузение терпимо, торренты плохо; UDP-нагрузка страдает меньше); MTU 1100; синхронизация времени ±30 с (требование mieru). Сегмент клиент→Entry при этом полностью теряет TLS-отпечаток И UDP-ногу (UDP-квоты/шейпинг неприменимы — нога TCP); AWG 3.1-обфускация (I1-I5, HeaderProtectionKey, padding, trailers) сохранена как есть.

**Не входит (намеренно, возможные следующие шаги):** интеграция с TG-ботом (/config-сегмент), rest_api-синк в WPP-портал, QR для mierus-части (мобильный стек mieru+AWG не собирается одним приложением — Karing/NekoBox не умеют AWG I1-I5).

# Changelog new entry — FEAT(routing_rules)+FIX(dns_rules): кастомные routing-правила — любой матч → любой outbound (приоритет/расположение/чанки), импорт РФ-подсетей RIPE; починка молчаливой потери dns_rules при regenerate (03 Nov 2026)

## Контекст: две задачи одним пакетом. ## Контекст: NL-выход (qwins; порт 16.5 Gbps — Ookla CLI: DL 16526 / UL 19675 Mbps) при однопотоковой пробе curl 10/95 MB стабильно показывал 578-681 Mbps — занижение в 27 раз. Три причины: (1) одиночный TCP-поток физически не наполняет порт > 1 Gbps (Ookla гоняет ~16 параллельных соединений), (2) 100 MB на 16 Gbps = 0.05 c «по проводу» — весь замер происходит внутри slow start, (3) стабильная полоса ~600 Mbps — потолок источника загрузки, а не порта. Бонус-слепота: абсолютные пороги normal≥100/degraded≥50 Mbps не видят обрез гигабитного+ порта — обрез 16.5G→1G выглядел бы «🟢 normal» при 950 Mbps, т.е. мониторинг пропускал свой главный кейс «хостер silently урезал канал».

## Решение: (1) параллельный движок: _parallel_download_one/_parallel_download — N потоков (лёгкая проба 6×10 MB / полный замер 8×95 MB; бюджеты probe_mb_light/probe_mb_big в конфиге, таймкапы 15/30 c на поток) на stdlib http.client (HTTPSConnection, один GET на поток, чтение до бюджета или таймкапа — хвостовое добивание не качаем), события (t, cum_bytes) в общий список под lock; _steady_and_peak — средняя с отбросом первых 0.5 c разгона TCP + пик в скользящем окне 1 c; PARALLEL_DOWNLOAD_SOURCES (cloudflare первым — точный {size}, cachefly/testdebit запасом, {size_mb} округляется к существующим файлам); отказ всех источников или parallel_streams=1 → откат на легаси-однопотоковый curl (старый _try_download сохранён как fallback). (2) _ookla_test (opt-in use_ookla, только полный замер): speedtest --accept-license --accept-gdpr -f json → dl/ul/latency/server — единственный источник настоящего числа на порту > 1 Gbps (десятки GB трафика за прогон, потому opt-in, не дефолт). (3) _classify_level с level_mode=auto (дефолт): normal/degraded/critical относительно МЕДИАНЫ download_mbps за 24ч (≥50% / ≥20%, настраивается baseline_normal_ratio/baseline_degraded_ratio; <5 сэмплов за окно → fallback на абсолютные пороги; level_mode=absolute — прежнее поведение). (4) _check_alert consecutive-check переведён с абсолютного Mbps на level сэмплов — иначе auto-режим не алертил бы обрез гигабитного порта; текст алерта различает «ниже 50 Mbps» и «падение > 80% от базлайна». (5) Отчёты TG честно подписаны: «≥ X Mbps (нижняя оценка)» для многопотоковых замеров + «Пик (окно 1 с)» + блок Ookla (Upload/Server); сэмплы несут streams/probe_mb/peak_mbps/ookla_ul_mbps/ookla_server; меню и CLI показывают режим порогов/потоки/ookla.

## Тесты: tests/test_bandwidth_monitor.py 19→38: TestMeasureOnce переведён на мок _run_download_probe (классификация без базлайна → absolute, семантика прежняя) + протаскивание ookla-полей в сэмпл; новые классы: TestSteadyAndPeak (отброс разгона: 150MB/0.9c; дегенерация короткого замера → простое среднее), TestParallelDownloadOne (бюджет делится по потокам с ранним стопом, пустой источник → None; герметично — фейковый HTTPSConnection, без сети), TestOoklaParser (парсинг JSON/нет бинаря/ненулевой exit), TestRunDownloadProbe (диспетчер: ookla только для полного, лёгкая всегда параллельная, parallel_streams=1 → легаси, отказ параллельных → curl-fallback), TestBaselineClassification (кейс №16: 950 при базлайне 9000 → critical; границы 50%/20%; fallback без базлайна; absolute не трогает базлайн; медиана по jsonl сэмплам + окно 24ч + min_samples), TestAlertFastPortCut (сквозной: 950 Mbps при базлайне 9000 → critical-алерт с «КРИТИЧНО» в тексте). verify.py 407 ✓ (готовность 10/10), leak_guard LEAK 0 (только WARN домены публичных CDN-источников, как до правки), PEP 701-скан 0, const-default чисто. # Changelog new entry — fix(dpi_response): скоринг DPI-зондов честным окном — хвост лога по ВРЕМЕНИ вместо «последних 2000 строк» + уже забаненные файрволом источники не раздувают score; fix(system_doctor): «цель не задана» — честный info вместо молчаливого ok (08 Nov 2026)

## Контекст (кейс DMZHOST 07.11.2026, RU-entry): сканер дал 91 REALITY-пробу за минуту → probe_score 310 (порог атаки 300) → level 2 + два TG-алерта, хотя fail2ban уже отрезал источник минутой раньше. Две системные причины: (1) collect_signals читал «последние 2000 строк» error.log — при живом логе 150-250 строк/мин это лишь ~8-13 мин из заявленного окна window_min=30 → короткий всплеск занимал весь хвост и выглядел «атакой»; (2) строки от IP, уже отрезанных файрволом (fail2ban / ipset xray_manual_ban*), продолжали раздувать score — пакеты оттуда дропаются до Xray, угроза нейтрализована, алертить по её хвосту в окне не нужно. Бонус (кейс chexit4): chk_xray_version при НЕзаданной цели писал молчаливое «ok» — маскировка того, что дрифт версий вообще не сверяется.

## Решение: (1) dpi_response: _tail_covering_window(path, cutoff, max_bytes=32MB) — чтение блоками с КОНЦА файла до реальной границы окна (первая датированная строка старее cutoff = стоп; флуд-щит по байтам), бездатные строки — прежняя семантика «считать свежей» (продолжение стека); _banned_sources() — ip_network'ы из fail2ban-client banned (все jail) + ipset xray_manual_ban/xray_manual_ban6, fail-open (любой сбой = пустой список = прежнее поведение); _line_source_banned() — матч «from <ip>» (v4/v6) по бан-сетям; collect_signals считает score БЕЗ строк от забаненных источников (пропущенное пишется в лог INFO — audit-trail сохраняется), сигналы несут skipped_banned/window_lines, run_once логирует их. (2) system_doctor: chk_xray_version — цель задана и совпала → ok «= цели»; цель НЕ задана → info «цель не задана — дрифт не сверяется; задайте xray_target_version» (видно в ежедневном отчёте, не дёргает TG-фильтры).
