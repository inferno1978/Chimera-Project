## 1. Что случилось с GitHub в РФ и почему это «частичная» блокировка

С 2026 года ТСПУ (технические средства противодействия угрозам)
получили задачу ограничивать доступ к инфраструктуре GitHub — прежде
всего к **скачиванию исходников**: `raw.githubusercontent.com`,
`codeload.github.com` (тарбалы/зипы), `objects.githubusercontent.com`
и `release-assets.githubusercontent.com` (бинарники релизов).

«Частичная» — ключевое слово. Полный блок (как с Facebook) не
включили: разработка в РФ завязана на GitHub, и запрет целиком
ударил бы по слишком многим. Вместо этого наблюдаются три мягких
режима, которые провайдеры применяют по-разному:

| Режим | Как выглядит у пользователя | Что видит зонд |
|---|---|---|
| **SNI-фильтрация** | «Сайт недоступен» / вечная загрузка на одних доменах, другие работают | TLS сбрасывается после ClientHello с SNI `*.githubusercontent.com` |
| **Троттлинг** | Скачивание ползёт на 5–50 КБ/с, страница GitHub при этом живая | Соединение устанавливается, но скорость придушена |
| **DNS-отравление** | «Сайт не найден», пинг идёт не туда | Резолв выдаёт мусорные адреса |

На домашнем роутере (с которого писался этот FAQ) на момент
диагностики 2026-09-06 замер discovery показал: `github.com` 694 КБ/с,
`raw` 373 КБ/с, `codeload` 253 КБ/с — то есть в тот момент блок был
отложен. Сет построен **заранее**: когда ТСПУ включит SNI-фильтр,
роутер уже будет резать и подменять ClientHello, и скачивание
исходников не прервётся.

> **Урок:** «сейчас работает» не значит «сеть готова». Душение
> включают и выключают волнами — сет должен стоять до того, как
> это произойдёт.

## 2. Диагностика: как отличить SNI-фильтр от IP-душения от DNS-отравления

Прежде чем строить сет, выясните, ЧТО именно блокирует. Иначе сет
будет лечить не ту болезнь. Порядок диагностики:

**Шаг 1 — Discovery (главный инструмент).**
```
Web UI → Discovery → домены: github.com, raw.githubusercontent.com,
codeload.github.com, objects.githubusercontent.com,
release-assets.githubusercontent.com → Start
```
Discovery брутфорсит стратегии и честно говорит: «works without
b4 — do not create a set for it» (работает и так) либо находит
победившую стратегию. Каждому домену он сообщает скорость
(`best_kb_per_sec`) — **троттлинг вскрывается именно здесь**,
сравнением с эталонной скоростью сети.

**Шаг 2 — интерпретация артефактов зонда.** Зонд `b4_test_domain_now`
ходит на **корневой путь** домена. У CDN-хостов корень часто отдаёт
мусор:

- `https://objects.githubusercontent.com/` → S3 отвечает XML-ошибкой
  объёмом **~425 байт** — зонд честно рапортует `insufficient data`,
  хотя сайт живой. Это НЕ блок.
- `https://raw.githubusercontent.com/` → 301-редирект на `github.com`
  — зонд не принимает междоменные редиректы, рапортует ERROR.
  Тоже НЕ блок.

**Правило:** если домен «падает» одинаково **и через b4, и без b4**
(`mode: both`), а на корне у него CDN — сначала проверьте, не
артефакт ли это, реальным запросом из браузера/`curl`.

**Шаг 3 — DNS-проверка.** Если `dig github.com @1.1.1.1` (внешний
резолвер) и резолв от провайдера дают **разные** IP — у вас
DNS-отравление, и в сет включается секция `dns` (DoH).

## 3. Архитектура сета GitHub-Fat-v1

Сет собран как зеркало боевого `Youtube-Fat-v1` (та же ТСПУ,
проверенная связка) с заменой таргетов на инфраструктуру GitHub.
JSON сета: `vendor/b4/set-artifacts/GitHub-Fat-v1.json` в этом репо
и `download/b4-set_GitHub-Fat-v1.json` в delivery.

```json
{
  "name": "GitHub-Fat-v1",
  "enabled": true,
  "fragmentation": { "strategy": "combo", "middle_sni": true,
    "combo": { "first_byte_split": true, "extension_split": true,
               "shuffle_mode": "full", "first_delay_ms": 30 } },
  "faking": { "sni": true, "strategy": "timestamp", "sni_type": 8,
              "timestamp_decrease": 600000, "ttl": 7 },
  "tcp": { "seg2delay": 20, "seg2delay_max": 60,
           "rst_protection": { "enabled": true } },
  "dns": { "enabled": true, "doh_url": "https://1.1.1.1/dns-query",
           "strict": false },
  "escalate": { "to": "<id GitHub-Heavy-v1>" }
}
```

**Таргеты — три слоя покрытия:**

| Слой | Объём | Что ловит |
|---|---|---|
| `sni_domains` | 19 суффиксов | `github.com` (плюс api/gist/codeload/ssh — суффикс-матч), `githubusercontent.com` (raw/objects/avatars/release-assets), `githubassets.com`, `github.io`, `github.dev`, `ghcr.io`, `npmjs.com`, … |
| `geosite_categories` | `github` (64 записи) | S3-бакеты релиз-ассетов `github-production-release-asset-*.s3.amazonaws.com`, 20 Azure-блобов артефактов Actions, `npm` registry, Copilot-эндпоинты |
| `ip` | 87 CIDR | Официальные диапазоны из `api.github.com/meta`: web+api+git+pages+copilot, IPv4 (`<ip>/20`, `<ip>/22`, `<ip>/22`, …) и IPv6 (`2a0a:a440::/29`, `2606:50c0::/32`) — ловит соединения **без SNI** |

**Почему именно такие настройки:**

- **combo + first_byte_split + extension_split** — SNI разрезается
  на два сегмента в разных местах; ТСПУ не собирает цельный SNI и
  пропускает пакет. Выбор семейства подтверждён на этом провайдере
  сетом Youtube-Fat-v1.
- **faking `timestamp` (sni_type 8, decrease 600000)** — перед
  настоящим ClientHello летит фейковый с тем же SNI, но «протухшим»
  TCP-таймстампом: DPI читает его, сервер отбрасывает. Google/YouTube
  инфраструктура это прощает, Azure/S3 — тоже (проверено боем).
- **seg2delay 20–60 мс** — второй сегмент чуть задерживается, чтобы
  DPI не склеил фрагменты пересборкой. На скорость скачивания почти
  не влияет (замер: 79 КБ/с без b4 против 52 КБ/с с b4 на тестовой
  странице; на больших файлах разница размывается).
- **rst_protection** — ТСПУ любит «стрелять» поддельными TCP RST.
  b4 сверяет TTL и отбрасывает фальшивки (за первые минуты на
  GitHub-трафике отсеяно 114 RST).
- **dns + DoH 1.1.1.1** — DNS-запросы доменов сета резолвятся через
  DoH: отравление резолва отключается как класс.
- **escalate → GitHub-Heavy-v1 (strategy: tcp)** — если ТСПУ
  адаптируется и начнёт душить combo, b4 сам (по RST/stall-порогам)
  переключит домены на tcp-десинхронизацию. Тяжёлый сет — пустой
  каркас с другой стратегией, как `Youtube-Heavy-v1`.

> **Суффикс-матчинг:** запись `github.com` в b4 покрывает и точное
> совпадение, и ВСЕ поддомены (`api.github.com`, `ssh.github.com`…).
> Wildcard `*.github.com` писать не нужно — движок так не умеет,
> Chimera нормализует вилдкарды в суффикс при импорте.

<a id="4"></a>
## 4. Установка сета на роутер (три способа)

### Способ 1 — ИИ-агент по MCP (как было сделано в этом кейсе)

Роутер с включённым MCP-сервером b4 (`b4 Web UI → Settings → API →
MCP → Enable` + токен). Агент проходит handshake по
`http://<роутер>:7000/api/mcp` и вызывает инструменты:

```
b4_manage_set      action=create, name=GitHub-Fat-v1, position=first
b4_edit_set_targets  set=GitHub-Fat-v1, kind=geosite_categories, add=github
b4_edit_set_targets  set=GitHub-Fat-v1, kind=sni_domains, add=github.com,...
b4_edit_set_targets  set=GitHub-Fat-v1, kind=ip, add=<87 CIDR чанками>
b4_set_config_value  sets[GitHub-Fat-v1].faking.strategy=timestamp ...
b4_manage_set      action=create, name=GitHub-Heavy-v1
b4_set_config_value  sets[GitHub-Heavy-v1].fragmentation.strategy=tcp
b4_set_config_value  sets[GitHub-Fat-v1].escalate.to=<id Heavy>
```

Всё применяется live, без рестарта демона. Добавление домена в сет
автоматически **вынимает его из других сетов** (домен принадлежит
одному сету) — b4 рапортует, что «переехало».

### Способ 2 — импорт JSON через Web UI

1. Откройте `https://<домен>:9743` (nginx front) → вкладка **Sets**.
2. Три точки на карточке любого сета → **Edit** → **Import/Export**.
3. Вставьте JSON из `vendor/b4/set-artifacts/GitHub-Fat-v1.json`
   (секция `sets[0]`) → применить.

### Способ 3 — импорт через TUI Chimera

```
Главное меню → 3 (Настройки сети) → B (DPI Bypass) →
3 (Импортировать кастомный сет JSON) → вставить JSON
```

Chimera при импорте нормализует вилдкарды, выставит `enabled: true`
и пропишет `system.geo.sitedat_path` для работы `geosite_categories`
(см. [DPI_BYPASS_FAQ.md](DPI_BYPASS_FAQ.md), раздел 7).

> **После импорта любым способом** проверьте эскалацию: `escalate.to`
  должен указывать на реальный id вашего `GitHub-Heavy-v1` (id живёт
  в вашем конфиге, в артефакте оставлен реальный id кейс-роутера —
  при импорте b4 выдаст Heavy новый id, поправьте).

## 5. Проверка работоспособности

**Watchdog — главный вердикт** (без генерации трафика, статус по
последнему чеку):

```
Web UI → Watchdog (или MCP: b4_watchdog action=status)
```

Кейс-роутер, живой вывод через 20 минут после установки:

```
github.com                  matched_set=GitHub-Fat-v1  healthy  71 KB/s
raw.githubusercontent.com   matched_set=GitHub-Fat-v1  queued
```

`matched_set` — доказательство, что реальный трафик GitHub
матчится сетом. Добавление домена в watchdog:

```
MCP: b4_watchdog action=add domain=github.com
     b4_watchdog action=add domain=raw.githubusercontent.com
```

**Живая проба парой** (генерирует трафик): `b4_test_domain_now`
mode=both — сравнить через b4 и без. Помните про артефакты корня
CDN (раздел 2): github.com — валидный зонд, objects/release-assets —
нет.

**Метрики пакета:** `b4_metrics` — `rst_dropped` (RST-защита
работает), `connections_seen` (растёт — сет в деле),
`blocked_total`.

**Персистентность:** перезагрузите роутер (или рестарт b4) и
повторно проверьте watchdog — сеты живут в `/etc/b4/config.json`
и переживают рестарт (проверено: после случайного рестарта демона
uptime 9м, сет на месте, трафик матчится).

<a id="6"></a>
## 6. Тонкая настройка под своего провайдера

Сет откалиброван на провайдера кейс-роутера. Если у вас ТСПУ
жёстче/мягче:

- **Прожимает всё равно** → запустите Discovery только на
  `raw.githubusercontent.com` и `codeload.github.com` (2–5 доменов,
  НЕ все 5+ — discovery идёт минутами и гонит трафик). Победившую
  стратегию примените к сету: `b4_set_config_value
  sets[GitHub-Fat-v1].fragmentation.strategy=<найденная>`.
- **Ломает скачивание** (S3/Azure капризничают к фейкам) →
  отключите фейк, оставьте чистую фрагментацию:
  `sets[GitHub-Fat-v1].faking.sni=false`. Фрагментация одна
  обычно достаточна против SNI-чтения.
- **Медленно на больших файлах** → поднимите `seg2delay` в ноль
  (`0/0` — без задержки) — combo останется, задержка уйдёт:
  `sets[GitHub-Fat-v1].tcp.seg2delay=0`,
  `...seg2delay_max=0`.
- **Escalate-пороги**: при агрессивном ТСПУ ужесточите
  `escalate.rst_threshold=2` (быстрее переключит на Heavy),
  при ложных срабатываниях — ослабьте `rst_window_sec=60`.
- **IPv6 у провайдера** — диапазоны v6 уже в сетах (`2a0a:a440::/29`,
  `2606:50c0::/32`, pages `/128`). Если v6 нет и не планируется —
  можно не трогать: unmatched не мешает.

**Обновление IP-диапазонов.** GitHub иногда расширяет сеть.
Актуальный список — всегда `curl https://api.github.com/meta`
(ключи web/api/git/pages/copilot). Пролить в сет:

```
MCP: b4_edit_set_targets  set=GitHub-Fat-v1  kind=ip
     remove=<старые>  /  add=<новые>
```

<a id="7"></a>
## 7. Что сет НЕ может обойти (честные ограничения)

- **IP-шный rate-limit на магистрали.** Если провайдер душит полосу
  до конкретных подсетей GitHub (не по SNI, а по маршруту) —
  пакетные трюки бессильны: TCP-окно не расширить фрагментацией.
  Симптом: скорость ~const (например, ровно 5 КБ/с) на ВСЕХ ресурсах
  GitHub, SNI-трюки не меняют ничего. Лечение — только маршрутизация
  через прокси: `sets[GitHub-Fat-v1].routing.enabled=true` +
  `routing.upstream` (ваш VLESS/Xray-нод) — трафик сета уйдёт в
  туннель и душитель останется не у дел.
- **Блок по IP целиком** (TCP SYN до сервера не доходит). Тоже
  лечится только routing→upstream.
- **HTTP/3 (QUIC).** UDP-кворум: GitHub на QUIC не работает
  всерьёз (браузер откатывается на TCP) — сет не критичен, но при
  желании QUIC блокируется per-set (Web UI → карточка сета → UDP →
  «Блокировать QUIC»), чтобы браузер не залипал в QUIC-ревери.

<a id="8"></a>
## 8. Решение проблем

### «Сет импортировался, но github.com не матчится»
Проверьте позицию: `b4_list_sets` — `GitHub-Fat-v1` должен стоять
ВЫШЕ других сетов в списке (первый включённый матч выигрывает;
кейс-роутер держит его позицией 1). Переставить:
`b4_manage_set action=move set=GitHub-Fat-v1 position=first`.

### «geosite_categories не разворачивается (дом=0 в списке)»
b4 не находит geosite-базу — `system.geo.sitedat_path` не задан.
Импортируйте сет через TUI Chimera (он пропишет путь), либо задайте
вручную: `b4_set_config_value system.geo.sitedat_path=/etc/b4/geosite.dat`.

### «npm/pypi качается, а GitHub-релизы — нет»
Релизы идут с S3/Azure-блобов — они в `geosite_categories: github`,
но их SNI может не покрыться, если база geosite устарела. Проверьте:
`b4_check_domain domain=github-production-release-asset-2e65be.s3.amazonaws.com`
— если не covered, добавьте суффикс вручную в `sni_domains`.

### «После импорта пропали домены из другого сета»
Так и задумано: домен принадлежит одному сету. `b4_edit_set_targets`
при добавлении рапортует, что «moved» — верните, если не хотели.

### «MCP не отвечает / таймауты»
Домашний WAN флапает — MCP-вызовы ретраятся. Проверка порта:
`bash -c "echo > /dev/tcp/<роутер-ip>/7000"`. Если порт закрыт —
b4-демон или роутер перезагружается; подождите минуту.

### «После установки сета GitHub «вообще не открывается», потом сам ожил»
Реальный инцидент 2026-09-06: через несколько минут после ввода сета в
прод GitHub перестал открываться совсем, а затем восстановился без
вмешательства. Причина — не сет: b4 на роутере авто-апгрейднулся
(v1.80.4 → v1.81.0) и рестартовал; в окно рестарта nft-правила
сбрасываются и применяются заново, и трафик, который уже ходит через
сет (а GitHub после установки сета ходит именно через него),
разово рвётся. Как отличить «рестарт-окно» от настоящего жёсткого
блока — три проверки по MCP:
1. `b4_status` — поле `uptime`: если минуты, b4 только что
   перезапускался/обновлялся; заодно сверьте `version` с ожидаемой.
2. `b4_test_domain_now` (mode=both) — если **baseline тоже жив**,
   блока нет вовсе; если baseline сломан, а through_b4 нет — наоборот,
   сет вас спасает.
3. `b4_watchdog` (action=status) — `consecutive_failures=0` и
   healthy-чеки в «простойное» окно означают: со стороны роутера всё
   работало, проблема была на клиенте/в окне рестарта.
Показатели того инцидента: uptime ~1 ч (апгрейд), watchdog 5/5 healthy
(github.com 66 КБ/с, raw 42 КБ/с), тест github.com baseline 103 КБ/с /
through_b4 64 КБ/с, `rst_dropped=373` за час — РКН-инжектор RST
продолжал работать, rst_protection их отшивал. Вывод: лечится
ожиданием пары минут, сет трогать не надо. Роутер после апгрейда
ходит на v1.81.0 — вендоренный в репо снапшот исходников при
сверке оказался содержимым v1.81.0 байт-в-байт (снимался с master
HEAD, а тег v1.81.0 стоит на том же коммите; изначально ошибочно
маркирован v1.80.4 — см. CHANGELOG). Совместимость полная.

<a id="9"></a>
## 9. MCP-управление сетом из ИИ-агента

Роутер с b4 — полноценный MCP-сервер (Streamable HTTP, 19
инструментов). Агент (Claude, Cursor, Z.ai и др.) подключается:

```json
{
  "b4": {
    "url": "http://<роутер-ip>:7000/api/mcp",
    "headers": { "Authorization": "Bearer <MCP-токен из Web UI>" }
  }
}
```

Ключевые инструменты для работы с GitHub-сетом: `b4_list_sets`,
`b4_get_set`,`b4_edit_set_targets`, `b4_set_config_value`,
`b4_check_domain`, `b4_test_domain_now`, `b4_find_bypass_strategy`
(discovery), `b4_watchdog`, `b4_metrics`, `b4_recent_connections`,
