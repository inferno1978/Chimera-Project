# DNSCrypt-proxy — FAQ по зашифрованному DNS в Chimera

Это подробный гайд по DNSCrypt-proxy в проекте Chimera. Описаны все
нюансы: зачем нужен, какая конфигурация предлагается и почему, как
настраивать резолверы, как диагностировать утечки DNS, как работает
анонимизация DNS-запросов, и типовые проблемы с решениями.

> **DNSCrypt-proxy** — локальный зашифрованный DNS-резолвер. Шифрует
> все DNS-запросы между вашим сервером и upstream-резолверами
> (Cloudflare, Google, Quad9 и др.), предотвращая перехват и
> модификацию DNS-трафика провайдером или DPI. В Chimera работает
> на `127.0.0.1:5300` и используется Xray-ядом для резолвинга доменов.

## 1. Зачем нужен DNSCrypt-proxy в Chimera

### Проблема: открытый DNS

По умолчанию DNS-запросы идут в **открытом виде** (UDP порт 53, без
шифрования). Любой узел между вашим сервером и upstream-DNS
(провайдер, магистральный оператор, DPI-система) может:

1. **Читать** запрашиваемые домены — даже если дальнейший трафик
   зашифрован HTTPS/TLS.
2. **Модифицировать** ответы — подменять IP-адреса, перенаправлять
   на заглушки.
3. **Блокировать** запросы к определённым доменам.
4. **Логировать** историю запросов для последующего анализа.

В России эту возможность использует **ТСПУ** (DPI-система РКН) —
именно через DNS-блокировки закрывается большинство запрещённых
ресурсов.

### Решение: DNSCrypt-proxy

DNSCrypt-proxy — локальный резолвер, который:
1. Принимает DNS-запросы от Xray и системных процессов на `127.0.0.1:5300`.
2. **Шифрует** их по протоколу DNSCrypt (на основе Curve25519) или
   DoH (DNS-over-HTTPS, порт 443).
3. Отправляет зашифрованные запросы к upstream-резолверу
   (Cloudflare, Google, Quad9, и т.д.).
4. Получает ответ, расшифровывает, отдаёт обратно.
5. Провайдер видит только зашифрованный трафик к `1.1.1.1:443` —
   он не может прочитать, какой домен запрашивался.

### Что DNSCrypt-proxy НЕ делает

- **Не шифрует трафик пользователей VPN** — он стоит на сервере
  (entry/exit-ноде), а не на клиенте. Для клиентского DNS
  используется DNSCrypt/DNS-over-HTTPS в самом клиентском приложении
  (v2rayN, Nekoray, Hiddify).
- **Не блокирует рекламу** — для этого есть AdGuard Home (если
  установлен) или клиентские блокировщики.
- **Не ускоряет интернет** — наоборот, добавляет ~1-5 мс задержки
  на шифрование/расшифровку. Но защищает от подмены и блокировки.
- **Не работает как кеширующий DNS для локальной сети** — он
  слушает только на `127.0.0.1` (loopback), не на всех интерфейсах.

### Аналогия

| Без DNSCrypt | С DNSCrypt |
|---|---|
| Отправляешь открытую открытку — почтальон читает | Пишешь письмо в запечатанном конверте — почтальон видит только адресата |

## 2. Архитектура: как DNS-запрос проходит через Chimera

```
   клиент (браузер, curl, Xray-клиент)
                    ↓
        DNS-запрос на домен example.com
                    ↓
   ┌────────────────────────────────────────────────────┐
   │  Сервер Chimera                                    │
   │                                                    │
   │  Xray config.json:                                 │
   │    dns.servers = ["127.0.0.1:5300"]                │
   │                  ↓                                 │
   │  ┌─────────────────────────────────┐               │
   │  │  DNSCrypt-proxy (127.0.0.1:5300)│               │
   │  │                                 │               │
   │  │  шифрует запрос                 │               │
   │  │  → DoH (443) или DNSCrypt (443) │               │
   │  └────────────┬────────────────────┘               │
   │               ↓                                    │
   │  [опционально] Anonymized DNS Relay                │
   │  (relay видит IP, не видит запрос)                 │
   │               ↓                                    │
   │  upstream-резолвер (Cloudflare/Google/Quad9/...)   │
   │  (видит запрос, не видит IP клиента, видит relay)  │
   │               ↓                                    │
   │  → ответ зашифрован обратно                        │
   └────────────────────────────────────────────────────┘
                    ↓
        Xray получает IP и подключается к example.com:443
```

### Уровни фильтрации DNS

| Уровень | Где | Что делает |
|---|---|---|
| 1. Системный DNS | `/etc/resolv.conf` → `127.0.0.1` | glibc (curl, dig, apt) → dnscrypt-proxy |
| 2. Xray DNS | `config.json` → `dns.servers` | Xray резолвит домены через dnscrypt-proxy |
| 3. DNSCrypt-proxy | `127.0.0.1:5300` | Шифрует и отправляет upstream |
| 4. Anonymized relay (опц.) | relay-сервер | Скрывает IP от upstream |
| 5. Upstream-резолвер | Cloudflare/Google/etc | Резолвит домен, возвращает IP |

## 3. Когда ставить DNSCrypt, а когда — нет

### ✅ Когда нужно ставить

- **Сервер в РФ** (entry-нода) — провайдер режет DNS, подменяет
  ответы. Без DNSCrypt невозможно нормально резолвить заблокированные
  домены.
- **Сервер с cascade exit-нодой в РФ** — exit-нода обращается к
  заблокированным ресурсам, нужен корректный DNS.
- **ТСПУ блокирует DNS-запросы** — DNSCrypt обходит это, т.к.
  зашифрованный трафик на 443 неотличим от обычного HTTPS.
- **Сервер с AWG-туннелем** — DNSCrypt должен запускаться от uid
  `dnscrypt`, чтобы его трафик уходил через AWG (см. раздел 16).
- **Тестируете утечки DNS** — без DNSCrypt почти гарантированно
  будет утечка через провайдерский DNS.
- **Нужен доступ к доменам, заблокированным по DNS** —
  DNSCrypt + выбор резолвера не из РФ решает проблему.

### ❌ Когда НЕ нужно ставить

- **Тестовый сервер для себя** — лишняя нагрузка, если вам не
  важна приватность.
- **Сервер за Cloudflare WARP full-tunnel** — WARP уже шифрует
  весь трафик, включая DNS. Дублирование не нужно.
- **У вас уже стоит Pi-hole / AdGuard Home на другом сервере** —
  DNSCrypt будет лишним звеном (но может работать upstream-резолвером
  для AdGuard Home — см. раздел 15).
- **Сервер без домена и без Xray** — DNSCrypt бесполезен без
  потребителя DNS-запросов.

### Рекомендация по умолчанию

При установке Chimera в **Режиме A** (прямой интернет) или
**Режиме B** (каскад) — **всегда выбирайте установку DNSCrypt**.
Это базовая защита, которая работает автоматически и не требует
обслуживания. Отказ от DNSCrypt имеет смысл только если вы точно
знаете, что делаете.

## 4. Установка и конфигурация по умолчанию

### Когда устанавливается

DNSCrypt-proxy предлагается к установке во время первичной настройки
Chimera. В меню установки есть пункт «DNSCrypt-proxy» — если
выбрать `[Y]`, параметр `PARAM_USE_DNSCRYPT = true` сохраняется в
`state.json`, и модуль `dnscrypt_setup.py::install_dnscrypt()`
запускается автоматически.

### Что делает `install_dnscrypt()`

1. **Определяет архитектуру** сервера (`x86_64`, `aarch64`, `armv7l`,
   `i386`) и выбирает соответствующий бинарник.
2. **Проверяет**, не установлен ли DNSCrypt-proxy уже (через
   `systemctl is-active dnscrypt-proxy`). Если активен — пропускает.
3. **Запрашивает последнюю версию** через GitHub API
   (`https://api.github.com/repos/DNSCrypt/dnscrypt-proxy/releases/latest`).
4. **Скачивает tarball** через `fetch_package(DNSCRYPT_SPEC, tag, arch)`
   из `download_manager.py`. Используется 10 зеркал (GitHub + jsDelivr
   + зеркала Chimera) — если GitHub недоступен, скачивание продолжается.
5. **Распаковывает** tarball, находит бинарник `dnscrypt-proxy`,
   копирует в `/usr/local/bin/dnscrypt-proxy` (chmod 0o755).
6. **Создаёт конфиг** `/etc/dnscrypt-proxy/dnscrypt-proxy.toml`
   (см. раздел 5).
7. **Создаёт пользователя** `dnscrypt` (см. раздел 16).
8. **Создаёт systemd-юнит** `/etc/systemd/system/dnscrypt-proxy.service`.
9. **Запускает сервис** и ждёт до 30 секунд, пока он станет active.
10. **Проверяет**, что порт 5300 слушается (через `ss -ulnp`).

### Конфигурация по умолчанию

Файл: `/etc/dnscrypt-proxy/dnscrypt-proxy.toml`

```toml
listen_addresses = ['127.0.0.1:5300']

max_clients = 250

ipv4_servers = true
ipv6_servers = true             # если сервер поддерживает IPv6
dnscrypt_servers = true
doh_servers = true
odoh_servers = false

require_dnssec = false
require_nolog = true
require_nofilter = false

force_tcp = false
server_names = ["cloudflare", "cloudflare-ipv6", "google", "google-ipv6"]
lb_strategy = 'p2'
lb_estimator = true
timeout = 5000
keepalive = 30

log_level = 1
use_syslog = true

cert_refresh_delay = 240

bootstrap_resolvers = ['1.1.1.1:53', '8.8.8.8:53']
ignore_system_dns = true
fallback_resolvers = ['1.1.1.1:53', '8.8.8.8:53']

netprobe_timeout = 5
netprobe_address = '1.1.1.1:53'

offline_mode = false
reject_ttl = 10

cache = true
cache_size = 32768
cache_min_ttl = 300
cache_max_ttl = 86400
cache_neg_min_ttl = 60
cache_neg_max_ttl = 600

[sources]
  [sources.public-resolvers]
    urls = [
      'https://raw.githubusercontent.com/DNSCrypt/dnscrypt-resolvers/master/v3/public-resolvers.md',
      'https://download.dnscrypt.info/resolvers-list/v3/public-resolvers.md'
    ]
    cache_file = '/etc/dnscrypt-proxy/public-resolvers.md'
    minisign_key = 'RWQf6LRCGA9i53mlYecO4IzT51TGPpvWucNSCh1CBM0QTaLn73Y7GFO3'
    refresh_delay = 72

  [sources.relays]
    urls = [
      'https://raw.githubusercontent.com/DNSCrypt/dnscrypt-resolvers/master/v3/relays.md',
      'https://download.dnscrypt.info/resolvers-list/v3/relays.md'
    ]
    cache_file = '/etc/dnscrypt-proxy/relays.md'
    minisign_key = 'RWQf6LRCGA9i53mlYecO4IzT51TGPpvWucNSCh1CBM0QTaLn73Y7GFO3'
    refresh_delay = 72
```

### Почему именно такие настройки

| Параметр | Значение | Почему |
|---|---|---|
| `listen_addresses` | `127.0.0.1:5300` | Только loopback — DNSCrypt не доступен снаружи. Порт 5300 (не 53) — чтобы не конфликтовать с systemd-resolved. |
| `server_names` | cloudflare + google | Самые быстрые и надёжные. IPv6-варианты включаются автоматически при наличии IPv6. |
| `require_dnssec` | `false` | DNSSEC добавляет задержку и может ломать некоторые домены. Включается через `[RA]`. |
| `require_nolog` | `true` | Cloudflare и Google логируют запросы (для аудита). Этот параметр выбирает только серверы, которые обещают не логировать. |
| `require_nofilter` | `false` | Разрешает серверы с фильтрацией (AdGuard, NextDNS). Иначе мы бы отрезали все «семейные» резолверы. |
| `force_tcp` | `false` | UDP быстрее. TCP включается только если UDP блокируется. |
| `lb_strategy` | `'p2'` | «P2» = выбирает 2 самых быстрых сервера из пула. Оптимальный баланс скорости и отказоустойчивости. |
| `timeout` | `5000` (5 сек) | Если upstream не ответил за 5 сек — переключаемся на следующий. |
| `bootstrap_resolvers` | `1.1.1.1:53`, `8.8.8.8:53` | Для первичного резолвинга DNSCrypt-серверов (до установки шифрованного канала). Открытый DNS, но только для bootstrap. |
| `ignore_system_dns` | `true` | Игнорируем `/etc/resolv.conf` — он может указывать на провайдерский DNS. |
| `fallback_resolvers` | `1.1.1.1:53`, `8.8.8.8:53` | Если все upstream-серверы недоступны — fallback на публичные DNS. |
| `cache_size` | `32768` | 32k записей в кеше. Для VPS с 1 ГБ RAM — оптимально. |
| `cache_min_ttl` | `300` (5 мин) | Минимальный TTL записей в кеше. Если upstream отдаёт TTL 60 сек — кешируем минимум 5 минут. |
| `cache_max_ttl` | `86400` (1 день) | Максимальный TTL. Если upstream отдаёт TTL 7 дней — кешируем максимум 1 день. |

### После установки: тюнинг `apply_dnscrypt_tuning()`

После базовой установки Chimera вызывает `apply_dnscrypt_tuning()` —
она применяет оптимизированные параметры:

```toml
timeout = 1500              # было 5000 — быстрее переключаемся
cache_min_ttl = 300         # без изменений
lb_strategy = 'p2'          # без изменений
```

Цель: уменьшить задержку на переключение между серверами (timeout
1.5 сек вместо 5 сек). На стабильном сервере это незаметно, но при
плохом канале — ускоряет отклик.

## 5. Параметры конфига: что значит каждый

### `listen_addresses`

```toml
listen_addresses = ['127.0.0.1:5300']
```

Где DNSCrypt-proxy принимает запросы. В Chimera — только loopback,
порт 5300. Это означает:
- Только приложения на этом же сервере могут использовать DNSCrypt.
- Снаружи DNSCrypt недоступен (правильно — он не для публичного
  использования).

**Можно изменить** на `['0.0.0.0:53']` если хотите, чтобы DNSCrypt
слушал все интерфейсы на стандартном DNS-порту — но это нужно только
если у вас局域ная сеть и вы хотите, чтобы все устройства использовали
этот DNS. В контексте Chimera это **не рекомендуется**.

### `server_names`

```toml
server_names = ["cloudflare", "google"]
```

Список upstream-резолверов. Имена берутся из `public-resolvers.md`
(скачивается с GitHub). DNSCrypt-proxy выбирает из этого списка по
стратегии `lb_strategy`.

**Важно:** эти имена — НЕ домены, это идентификаторы в списке
public-resolvers. Полный список доступен через `[R]` в меню Chimera.

### `doh_servers`, `dnscrypt_servers`, `odoh_servers`

```toml
dnscrypt_servers = true    # протокол DNSCrypt (Curve25519)
doh_servers = true         # DNS-over-HTTPS (порт 443)
odoh_servers = false       # Oblivious DoH (через relay)
```

- **DNSCrypt** — оригинальный протокол, шифрование Curve25519. Порт
  443, но не маскируется под HTTPS.
- **DoH** — DNS-over-HTTPS, полноценный HTTPS-трафик. Маскируется
  под веб-трафик, лучше проходит через DPI.
- **ODoH** — Oblivious DoH, запросы идут через relay, который не
  видит содержимое. Максимальная приватность, но медленнее.

В Chimera по умолчанию включены `dnscrypt_servers` и `doh_servers`,
`odoh_servers` выключен (его можно включить через `[RA]`).

### `require_dnssec`, `require_nolog`, `require_nofilter`

Эти фильтры определяют, какие серверы из пула будут использоваться:

| Параметр | Что требует | По умолчанию |
|---|---|---|
| `require_dnssec` | Сервер поддерживает DNSSEC (валидация подписей) | `false` |
| `require_nolog` | Сервер не логирует запросы | `true` |
| `require_nofilter` | Сервер не фильтрует контент (без блокировки рекламы/мальвары) | `false` |

**Почему `require_dnssec = false`:** DNSSEC добавляет ~50-100 мс к
каждому запросу и может ломать домены с неправильной конфигурацией.
Для большинства пользователей это лишнее.

**Почему `require_nolog = true`:** приватность важнее скорости. Без
этого флага DNSCrypt может выбрать сервер, который логирует все
ваши запросы (например, для «улучшения сервиса»).

**Почему `require_nofilter = false`:** некоторые хорошие серверы
(Quad9) блокируют malicious-домены. Мы не хотим их исключать.

### `force_tcp`

```toml
force_tcp = false
```

Если `true` — все запросы идут по TCP. По умолчанию `false` — DNSCrypt
использует UDP, что быстрее.

**Когда включать:** только если UDP-трафик на порт 443 блокируется
провайдером (редкость). TCP добавляет handshake-задержку.

### `lb_strategy` и `lb_estimator`

```toml
lb_strategy = 'p2'
lb_estimator = true
```

Стратегия балансировки нагрузки между upstream-серверами:

| Стратегия | Описание |
|---|---|
| `'fastest'` | Всегда использовать самый быстрый сервер |
| `'p2'` | Использовать 2 самых быстрых сервера (рекомендуется) |
| `'ph'` | Использовать все серверы, но с приоритетом по скорости |
| `'random'` | Случайный выбор |

`lb_estimator = true` — DNSCrypt постоянно измеряет RTT до каждого
сервера и обновляет порядок.

### `bootstrap_resolvers` и `fallback_resolvers`

```toml
bootstrap_resolvers = ['1.1.1.1:53', '8.8.8.8:53']
fallback_resolvers = ['1.1.1.1:53', '8.8.8.8:53']
```

- **bootstrap** — открытые DNS-серверы, через которые DNSCrypt
  первично резолвит домены upstream-серверов (например,
  `cloudflare-dns.com` → IP). Нужен только при старте.
- **fallback** — открытые DNS-серверы, используемые если все
  upstream-серверы недоступны.

В обоих случаях используются Cloudflare и Google — это плата за
надёжность при старте. После установки шифрованного канала они
не используются.

### `ignore_system_dns`

```toml
ignore_system_dns = true
```

Игнорировать `/etc/resolv.conf` при выборе upstream. Это критично:
если `/etc/resolv.conf` указывает на провайдерский DNS (например,
`77.88.8.8` от Yandex.DNS или `5.3.x.x` от Ростелекома), без этого
флага DNSCrypt мог бы его выбрать как upstream — и все запросы
утекли бы провайдеру.

### `cache_*`

```toml
cache = true
cache_size = 32768
cache_min_ttl = 300
cache_max_ttl = 86400
cache_neg_min_ttl = 60
cache_neg_max_ttl = 600
```

- `cache_size` — количество записей в кеше (32k = ~32k доменов).
- `cache_min_ttl` — минимальное время жизни записи (5 мин). Если
  upstream отдаёт TTL 30 сек — кешируем 5 минут.
- `cache_max_ttl` — максимальное TTL (1 день). Если upstream отдаёт
  TTL 7 дней — кешируем 1 день.
- `cache_neg_*` — TTL для негативных ответов (NXDOMAIN, т.е. домен
  не существует). 1-10 минут.

**Зачем кешировать дольше, чем отдаёт upstream:** для популярных
доменов (google.com, youtube.com) TTL 5 минут — избыточно. Кеширование
дольше снижает нагрузку на upstream и ускоряет отклик.

### `[sources]`

```toml
[sources.public-resolvers]
  urls = [
    'https://raw.githubusercontent.com/DNSCrypt/dnscrypt-resolvers/master/v3/public-resolvers.md',
    'https://download.dnscrypt.info/resolvers-list/v3/public-resolvers.md'
  ]
  cache_file = '/etc/dnscrypt-proxy/public-resolvers.md'
  minisign_key = 'RWQf6LRCGA9i53mlYecO4IzT51TGPpvWucNSCh1CBM0QTaLn73Y7GFO3'
  refresh_delay = 72
```

Список всех доступных DNSCrypt-серверов в мире. Обновляется каждые
72 часа. Подписан minisign-ключом — DNSCrypt проверяет подпись, чтобы
злонамеренно изменённый список не подсунул фейковый сервер.

Аналогично для `[sources.relays]` — список relay-серверов для
анонимизации DNS.

## 6. Выбор резолверов: [R] — замер latency

### Что делает

Меню → **Сеть → [R] DNSCrypt: выбор резолверов**.

`do_dnscrypt_selector_menu()` запускает:
1. Временно создаёт конфиг без `server_names` — чтобы DNSCrypt
   «увидел» весь пул серверов.
2. Запускает `dnscrypt-proxy -list -sort rtt` — получает список всех
   доступных серверов, отсортированных по RTT (времени отклика).
3. Показывает топ-100 серверов постранично (по 20 на страницу) с
   указанием RTT.
4. Пользователь выбирает нужные по номерам (через запятую: `1,2,3`).
5. Прописывает `server_names` в `/etc/dnscrypt-proxy/dnscrypt-proxy.toml`.
6. Перезапускает DNSCrypt-proxy.
7. Делает быстрый DNS-тест и показывает время ответа.

### Почему именно так

`server_names` зависит от географии VPS. Оптимальные резолверы для
Европы (Cloudflare, Google, Quad9 в Германии) отличаются от
оптимальных для Азии (Cloudflare Singapore, Google Tokyo) или
Латинской Америки. Автоподбор по RTT даёт пользователю актуальные
данные с его конкретного сервера.

### Когда использовать

- После первичной установки — чтобы выбрать самые быстрые серверы
  для вашей географии.
- После изменения провайдера/хостинга — старые серверы могут стать
  медленными.
- Если DNS-запросы стали медленными — возможно, текущие upstream
  деградировали.

### Что выбрать

- **2-3 сервера** из топ-10 по RTT. Больше — не нужно, `lb_strategy='p2'`
  всё равно использует только 2.
- **Из разных провайдеров** — Cloudflare + Google, или Cloudflare +
  Quad9. Если один провайдер упадёт — второй продолжит работать.
- **С поддержкой IPv6** если у сервера есть IPv6 — это ускорит
  резолвинг AAAA-записей.

## 7. Расширенная настройка: [RA] — 245 серверов, динамический пул и анонимизация

### Что делает

Меню → **Сеть → [RA] DNSCrypt: расширенная настройка**.

`do_dnscrypt_advanced_menu()` открывает доступ к расширенной
конфигурации, недоступной из базового меню:

1. **245 серверов в 51 стране** — курируемый список в
   `dnscrypt_advanced.py::_SERVER_NAMES`, синхронизированный с живым
   официальным `public-resolvers.md` (129 IPv4 / 116 IPv6; 221 через
   релеи, 24 DoH-напрямую). Включает серверы из:
   - Европы: FI, PL, DE, SE, CH, NL, CZ, AT, FR, IT, ES, GR, PT,
     UK, IE, BE, LU, IS, BG, DK, RO, HU, RS, SK, MD, NO, TR, GE, AL
   - Балтии и СНГ: UA, EE, LV, LT (RU-серверы исключены — юрисдикция)
   - Азии: JP, SG, KR, HK, TW, TH, ID, IN, BD, PK, LA
   - Америки: US, CA, BR, AR, CL
   - Африки: ZA, NG; Океания: AU, NZ

2. **180 анонимизированных маршрутов** — `_ANON_ROUTES` в
   `dnscrypt_advanced.py`: 179 персональных (4 relay из разных стран)
   + wildcard из 30 живых релеев для серверов без персонального
   маршрута (см. раздел 8). DoH-серверы не маршрутятся (протокол
   не анонимизируется — вместо ERROR-строк в логах ходят напрямую).

3. **Динамический пул**: cron каждые 6 ч
   `/usr/local/bin/chimera-dnscrypt-pool-sync.py`: пул ∩ живой
   список + воскрешения из кладбища `_POOL_GRAVEYARD` (37 имён,
   выселенных в), ребилд маршрутов по живым релеям. Конфиг
   перезаписывается только при фактическом дрейфе (нет изменений —
   нет рестарта).

4. **Включение ODoH** (Oblivious DoH) — максимальная приватность.

5. **Включение DNSSEC** — валидация подписей DNS-записей.

6. **Ручная настройка параметров** — timeout, cache, lb_strategy.

7. **Обновление и синк** — меню **Сеть → [DU]**: версия/обновление
   бинарника (ручное + авто timer 04:10), синк пула, проверка цепочки
   xray → AGH → dnscrypt. Единый state-файл — все DNS-меню показывают
   одну и ту же актуальную информацию.

### Почему Yandex исключён

В `_SERVER_NAMES` комментарий:
```
# Yandex ИСКЛЮЧЁН (утечка DNS). RU-серверы — через EU relay.
```

Yandex.DNS (77.88.8.8) логирует все запросы и передаёт данные в
РКН по запросу. Использование Yandex как upstream = гарантированная
утечка. То же самое касается других российских DNS-провайдеров
(Облачный DNS от Mail.ru, и т.д.).

RU-география закрывается через соседей: UA (kyiv/kyiv02), EE, LV,
LT, PL, FI — живые серверы с минимальным RTT из РФ, анонимизированные
через EU relay (запросы идут: клиент → EU relay → upstream, провайдер
в РФ видит только зашифрованный трафик к relay). `dnscry.pt-moscow`
исключён с RU-юрисдикция/хостер — риск hoster-level отравления
рекурсии, а голова пула = де-факто основной резолвер при
`lb_strategy p2`.

### Когда использовать [RA]

- **Нужна максимальная приватность** — включаете анонимизацию и ODoH.
- **Не устраивает скорость дефолтных Cloudflare/Google** — выбираете
  ближайший сервер из 245.
- **Нужен DNSSEC** — для защиты от DNS-spoofing.
- **Хотите диверсификацию** — не полагаться только на Cloudflare.

### Когда НЕ использовать

- **Базовая защита достаточна** — дефолтные Cloudflare + Google
  работают в 95% случаев.
- **Не понимаете, что делаете** — расширенная настройка может
  сломать DNS, если выбрать неправильные серверы.
- **Нужна максимальная скорость** — анонимизация добавляет ~10-30 мс
  задержки (через relay).

## 8. Anonymized DNS: как это работает

### Принцип

```
   ваш сервер (клиент DNSCrypt)
        ↓ (зашифрованный DNS-запрос)
   relay-сервер (видит IP клиента, НЕ видит запрос)
        ↓ (передаёт зашифрованный запрос)
   upstream-сервер (видит запрос, НЕ видит IP клиента)
        ↓ (ответ)
   relay → клиент
```

**Без анонимизации:**
```
клиент → upstream: видит и IP клиента, и запрос
```

**С анонимизацией:**
```
клиент → relay → upstream: relay видит IP, upstream видит запрос
                   никто не видит оба
```

### Реализация в Chimera

В `dnscrypt-proxy.toml` секция `routes`:
```toml
routes = [
  { server_name='cloudflare', via=['anon-cs-de', 'anon-cs-finland', 'anon-cs-poland', 'anon-cs-nl'] },
  { server_name='google',     via=['anon-cs-de', 'anon-cs-finland', 'anon-cs-poland', 'anon-cs-nl'] },
  ...
]
```

Для каждого upstream-сервера указано 4 relay-сервера. DNSCrypt
выбирает один из них случайно (для каждого запроса — новый relay).

### Правила составления маршрутов

В `dnscrypt_advanced.py::_ANON_ROUTES` маршруты составлены по
правилам:

1. **Relay в другой стране, чем upstream** — если upstream в DE,
   relay НЕ в DE. Иначе анонимизация теряет смысл (одна юрисдикция).
2. **Relay не в соседней стране** — если upstream в FI, relay НЕ в
   EE/RU (соседи). Чтобы один ордер на логи не покрыл обе страны.
3. **4 relay на каждый сервер** — для отказоустойчивости. Если один
   relay упал — есть 3 запасных.
4. **Relay в ЕС/Швейцарии** — у этих стран строгие законы о
   приватности, журналы не хранятся по умолчанию.
5. **Никогда relay в РФ/СНГ** — эти страны могут принудительно
   заставить хранить логи.

### Что анонимизация НЕ скрывает

- **Сам факт DNS-запроса** — провайдер видит зашифрованный трафик
  к relay. Он не знает, какой домен запрашивается, но знает, что
  вы делаете DNS-запрос.
- **Время запроса** — по таймингу можно сделать корреляцию с
  последующим HTTPS-соединением.
- **Объём трафика** — провайдер видит размер DNS-ответа (большой =
  много записей, маленький = одна запись).

### Когда включать

- **Максимальная приватность от upstream** — если не хотите, чтобы
  Cloudflare/Google знали ваш IP.
- **Защита от корреляции** — если один upstream скомпрометирован,
  relay в другой стране усложняет de-anonymization.
- **Сервер в РФ** — relay в EU добавляет слой защиты от российских
  ордеров на логи.

### Когда НЕ включать

- **Нужна максимальная скорость** — relay добавляет 10-30 мс.
- **Relay недоступны** — если все relay-серверы упали, DNS не работает.
  Без relay fallback на прямой запрос.

## 9. ODoH и DNSSEC: включать или нет

### ODoH (Oblivious DoH)

**Что это:** развитие DoH, где запросы идут через relay, как в
анонимизированном DNSCrypt. Но ODoH стандартизирован (RFC 9231),
тогда как DNSCrypt anonymization — проприетарный.

**Плюсы:**
- Стандартный протокол, поддерживается Cloudflare ODoH, Fastly.
- Скрывает IP от upstream.

**Минусы:**
- Меньше relay-серверов, чем у DNSCrypt.
- Медленнее (двойное шифрование).
- В Chimera по умолчанию выключен.

**Включать:** если нужна максимальная приватность и вы понимаете
риски. Через `[RA]` → «Включить ODoH».

### DNSSEC

**Что это:** криптографическая подпись DNS-записей. Резолвер
проверяет подпись и отбрасывает подделанные ответы.

**Плюсы:**
- Защита от DNS-spoofing (подмены ответов).
- Гарантия, что ответ от Cloudflare — действительно от Cloudflare,
  а не от провайдера, который вклинился в канал.

**Минусы:**
- Добавляет 50-100 мс к каждому запросу (проверка подписи).
- Может ломать домены с неправильной DNSSEC-конфигурацией
  (таких ~5% всех доменов).
- Увеличивает размер DNS-ответов (signature + DNSKEY + DS).

**Включать:** если вы опасаетесь подмены DNS-ответов (например,
находитесь в сети с агрессивным DPI). Через `[RA]` → «Включить
DNSSEC».

**Не включать:** если важна скорость и вы доверяете upstream.
Дефолтные Cloudflare и Google уже проверяют DNSSEC на своей стороне.

## 10. Принудительный DNS REDIRECT: [DR] — anti-leak для VPN-клиентов

### Проблема

Без этого правила клиент AmneziaWG (AWG) может вручную прописать
свой DNS-сервер (8.8.8.8, 1.1.1.1, провайдерский DNS) — и его
DNS-запросы уйдут напрямую, минуя DNSCrypt-proxy. Это:

- Сводит на нет защиту от DNS-leak.
- Позволяет провайдеру видеть запрашиваемые домены.
- Может использоваться для DPI-блокировки по DNS.

### Решение

Меню → **Сеть → [DR] Принудительный DNS REDIRECT**.

Модуль `dns_redirect.py` добавляет iptables-правила в `nat/PREROUTING`:

```bash
iptables -t nat -A PREROUTING -i awg0 -p udp --dport 53 -j REDIRECT --to-ports 5300
iptables -t nat -A PREROUTING -i awg0 -p tcp --dport 53 -j REDIRECT --to-ports 5300
```

Что это делает:
1. Перехватывает ВСЕ пакеты с портом 53 (UDP + TCP), приходящие
   через интерфейс `awg0`.
2. Перенаправляет их на локальный `dnscrypt-proxy` (порт 5300).
3. Клиент не может обойти это на уровне приложения — даже если
   прописал `8.8.8.8` в настройках, его запрос всё равно придёт
   к DNSCrypt.

### Когда использовать

- **AWG standalone / cascade** — обязательная защита от DNS-leak
  для VPN-клиентов.
- **Режим A (без AWG)** — НЕ применяется. Клиенты подключаются по
  VLESS TCP:443 напрямую, DNS уходит через Xray dns-spoofing, а не
  через отдельный интерфейс. REDIRECT не имеет смысла.

### Когда НЕ использовать

- **Режим A** — нет VPN-интерфейса, правило бесполезно.
- **DNSCrypt-proxy не запущен** — REDIRECT создаст «чёрную дыру»
  (клиент не получит ответ). Модуль проверяет это перед apply.

### Health-check

Меню → **Диагностика → [DN] DNS Redirect health-check**.

Проверяет:
1. `dnscrypt-proxy` активен и слушает порт 5300.
2. iptables-правила существуют в `nat/PREROUTING`.
3. State-файл `/var/lib/xray-installer/dns_redirect.json` существует.
4. systemd-юнит `dns-redirect-restore.service` установлен для
   восстановления после reboot.

### Persist после reboot

Модуль создаёт systemd-юнит `dns-redirect-restore.service`, который
запускается после `network-online.target` и повторно применяет
iptables-правила. Это нужно, потому что iptables-правила не
сохраняются между перезагрузками.

## 11. Кастомные DNS-правила: [D] — hosts и dns-routing

### Что делает

Меню → **Сеть → [D] Кастомные DNS правила**.

Модуль `dns_rules.py` позволяет управлять двумя механизмами Xray:

1. **hosts** — статическое сопоставление домен → IP. Xray использует
   это вместо DNS-запроса.
   ```json
   "dns": {
     "hosts": {
       "example.com": "1.2.3.4",
       "blocked.com": "127.0.0.1"
     }
   }
   ```

2. **dns-routing** — правила маршрутизации DNS-запросов. Например,
   домены `.ru` резолвить через direct, остальные — через proxy.
   ```json
   "routing": {
     "rules": [
       {"domain": ["geosite:category-ads-all"], "outboundTag": "block"},
       {"domain": ["domain:ru"], "outboundTag": "direct"}
     ]
   }
   ```

### Когда использовать

- **Нужно жёстко прописать IP домена** — например, если DNS-запрос
  блокируется, но вы знаете IP.
- **Нужно заблокировать домен на уровне DNS** — добавьте его в
  hosts с IP `127.0.0.1`.
- **Нужно разные домены резолвить через разные DNS** — например,
  `.ru` через провайдерский DNS, остальное через DNSCrypt.

### Совместимость с DNSCrypt-proxy

DNSCrypt-proxy имеет собственный блок-лист (`blocked-names.txt`),
но он работает только для запросов, проходящих через DNSCrypt.
`dns_rules.py` работает на уровне Xray — это срабатывает раньше,
до DNSCrypt. Два механизма не конфликтуют, но `dns_rules` имеет
приоритет.

## 12. Исправление /etc/resolv.conf: авто-фикс утечек

### Проблема

На Ubuntu 20.04/22.04/24.04 по умолчанию работает `systemd-resolved`.
Он получает DNS от DHCP (например, `77.88.8.8` — это Yandex.DNS,
или `5.3.x.x` — Ростелеком) и отправляет запросы к нему параллельно
с другими DNS. Результат: DNS Leak Test видит Yandex или
провайдерский резолвер.

Даже если `/etc/resolv.conf` указывает на `127.0.0.1` (DNSCrypt),
systemd-resolved всё равно шлёт запросы на свой DHCP-DNS.

### Решение

Меню → **Диагностика → [N] DNS Leak Test** → если найдена утечка →
prompt «Исправить автоматически? [Y/n]».

Или вручную: **Сеть → DNSCrypt → [resolv.conf fix]**.

Модуль `resolv_conf_fix.py` делает (БЕЗ перезапуска сети):

1. `/etc/resolv.conf` → `nameserver 127.0.0.1`
   - glibc (curl, dig, apt, ssh) использует этот файл напрямую,
     НЕ через systemd-resolved.
2. `/etc/nsswitch.conf` → убирает `resolve` из строки `hosts:`
   - nss-resolve модуль отключён, glibc использует `dns` (читает
     `/etc/resolv.conf`).
3. `/etc/systemd/resolved.conf.d/chimera-dns.conf` → drop-in
   (опционально)
4. `resolvectl dns LINK 127.0.0.1` + `default-route LINK false`
   - Для приложений, которые используют D-Bus API systemd-resolved
     напрямую.

### Принцип безопасности

Модуль **НЕ вызывает** ни одной команды, которая может затронуть
сетевой интерфейс:

| Команда | Используется? | Почему |
|---|---|---|
| `networkctl reconfigure` | ❌ | УБИВАЕТ SSH — сбрасывает IP |
| `networkctl reload` | ❌ | То же |
| `.network` файлы / drop-in'ы | ❌ | То же |
| `nmcli connection up/down` | ❌ | То же |
| `dhclient` | ❌ | Может повесить сеть |
| `ifconfig` / `ip link` | ❌ | Тронет интерфейсы |
| `/etc/resolv.conf` (текстовый) | ✅ | glibc читает напрямую |
| `/etc/nsswitch.conf` (текстовый) | ✅ | glibc читает напрямую |
| `resolvectl dns` (runtime) | ✅ | Не трогает интерфейсы |
| `resolvectl flush-caches` | ✅ | Очистка кеша, безопасно |

### Проверка

После fix:
```bash
cat /etc/resolv.conf
# должно быть: nameserver 127.0.0.1

resolvectl status
# должно быть: Current DNS Server: 127.0.0.1

dig example.com | grep SERVER
# должно быть: ;; SERVER: 127.0.0.1#53
```

### Rollback

Если что-то пошло не так — `rollback_resolv_conf()` восстанавливает
из бэкапов (`/etc/resolv.conf.chimera.bak`, `/etc/nsswitch.conf.chimera.bak`).

## 13. DNS Leak Test: [N] — диагностика утечек

### Что делает

Меню → **Диагностика → [N] DNS Leak Test**.

Функция `do_dns_leak_test()` проверяет, через какие DNS-серверы

1. **Метод 1/4: dnsleaktest.com API** — генерирует уникальный

2. **Метод 2/4: ipleak.net API** — аналогично, через другой сервис.

3. **Метод 3/4: browserleaks.com/dns** — третий сервис для
   кросс-проверки.

После сбора данных:
- Определяет GeoIP каждого найденного резолвера через `ip-api.com`.

  страна сервера если Режим A).
- Если найден резолвер в RU — предупреждение об утечке.
- Проверяет, что настроенный DNS (DNSCrypt / 1.1.1.1) совпадает с

### Что считается утечкой

| Сценарий | Утечка? |
|---|---|
| Найден резолвер в RU (при exit-ноде вне РФ) | ✅ ДА |
| Найден резолвер провайдера (МГТС, Ростелеком) | ✅ ДА |
| Найден Yandex.DNS (77.88.8.8) | ✅ ДА |
| Найден Cloudflare (1.1.1.1) в стране exit-ноды | ❌ нет |
| Найден Google (8.8.8.8) в стране exit-ноды | ❌ нет |
| Найден резолвер в стране exit-ноды, но не провайдерский | ❌ нет |

### Что делать при утечке

1. **Проверьте, что DNSCrypt-proxy активен:**
   ```bash
   systemctl is-active dnscrypt-proxy
   ```

2. **Проверьте /etc/resolv.conf:**
   ```bash
   cat /etc/resolv.conf
   # должно быть: nameserver 127.0.0.1
   ```

5. **Перезапустите DNSCrypt:**

## 15. Интеграция с AdGuard Home: [A] — DNS :53 + фильтры + DoH/DoT

> **✅ Статус:** модуль AdGuard Home **реализован** (Chimera v37).
> Управление: `Сеть → AdGuard Home` (пункт **A**). Установка — через
> мастер установки (шаг после DNSCrypt) или через меню.

### Что такое AdGuard Home

AdGuard Home — DNS-сервер с веб-интерфейсом, который фильтрует
рекламу, трекеры и malicious-домены на уровне DNS. В отличие от
клиентских блокировщиков (uBlock Origin в браузере), AdGuard Home
работает на сервере и фильтрует трафик для **всех** устройств,
использующих этот DNS — без установки расширений на каждом
устройстве.

### Архитектура в Chimera

AdGuard Home работает **поверх** DNSCrypt-proxy:

```
   приложения (glibc) + Xray + VPN-клиенты
        ↓
   AdGuard Home (127.0.0.1:53) — кеш 4MB, фильтры, DoH/DoT/DoQ
        ↓
   DNSCrypt-proxy (127.0.0.1:5300) — шифрует, отправляет upstream
        ↓
   Cloudflare/Google (DNSCrypt/DoH)
        + fallback 9.9.9.9 / 1.1.1.1 (как на роутере)
```

**Цепочка:**
1. Приложение/Xray делает DNS-запрос к `127.0.0.1:53` (AGH).
2. AGH проверяет запрос по блок-листам (AdGuard DNS filter + AdAway
   + OISD Big — все три включены). Реклама → `0.0.0.0`.
3. Чистый запрос уходит в кеш (4MB, optimistic — отдаёт устаревший
   ответ мгновенно и обновляет в фоне).
4. Промах кеша → upstream `127.0.0.1:5300` (DNSCrypt) → шифрование.
5. Если dnscrypt недоступен → fallback `9.9.9.9:53`, `1.1.1.1:53`.

Bootstrap AGH — тоже `127.0.0.1:5300` (улучшение относительно
роутерного скрипта: нет plain-DNS утечки при резолве имён
DoH-upstream'ов).

**Порядок запуска (systemd):** `dnscrypt-proxy.service` →
`AdGuardHome.service` → `xray.service` → `nginx.service` →
`chimera-dns-fix.service` (порядок задан через After=/Before= в
unit-файлах).

### Health-check Xray → AGH (`agh_probe.py`)

Генераторы xray-конфига переключают `dns.servers[0]` на `127.0.0.1:53`
только после **глубокой проверки** AGH — трёх обязательных условий:

1. Сервис активен (`systemctl is-active adguardhome/AdGuardHome`).
2. Именно AGH слушает `127.0.0.1:53/udp` (`ss -ulnp`; отсечены
   `:5300` и systemd-resolved `127.0.0.53:53`).
3. **Живая проба резолва** — DNS A-запрос `www.example.com` напрямую
   в `127.0.0.1:53` (собственный DNS-клиент, без зависимостей):
   проверяет end-to-end всю цепочку AGH → DNSCrypt → интернет
   (валидация txid, QR-бита, RCODE, answer-записей).

Любой сбой → Xray остаётся на `DNSCrypt:5300` (как раньше), DNS не
умирает. При успехе в конфиг пишется лестница с живым fallback:
`AGH:53 → DNSCrypt:5300 → 1.1.1.1 → 8.8.8.8` — если AGH упадёт
**после** генерации, Xray сам перейдёт на DNSCrypt.

Проба также **нейтрализует вредный iptables redirect 53→5300**
(который молча уводил glibc/Xray/B4 с AGH на DNSCrypt) — с
rollback'ом: если проба резолва провалилась, redirect
восстанавливается, и системный DNS продолжает работать через
dnscrypt-обход, пока AGH чинят. Аварийное восстановление
(`do_emergency_repair`) поднимает остановленный AGH **до** пересборки
xray-конфига — чтобы health-check успел его увидеть.

### Порты (все через port_registry)

| Порт | Назначение | Доступ снаружи |
|------|-----------|----------------|
| 53/udp+tcp | DNS (AGH) | ❌ закрыт (нет open resolver) |
| 3000/tcp | Web UI (HTTP) | по выбору (обычно loopback) |
| 30443/tcp | DoH + Web UI HTTPS | ✅ при TLS-режиме |
| 853/tcp | DoT | ✅ при TLS-режиме |
| 853/udp | DoQ | ✅ при TLS-режиме |
| 5300 | dnscrypt (upstream) | ❌ loopback |

**Почему :53 закрыт снаружи:** AGH биндится на loopback + публичный
IP (нужно для DoT/DoQ/DoH на 853/30443), но UFW **не открывает** 53
снаружи — иначе сервер стал бы open resolver (amplification-абуз).
Loopback-трафик (glibc, Xray) ходит на 127.0.0.1:53 свободно.

### Установка и мастер первого запуска

1. Мастер установки: после вопроса DNSCrypt появляется вопрос
   **«Установить AdGuard Home?»** (требует DNSCrypt — это upstream).
2. AGH скачивается (GitHub + gh-прокси + официальный CDN
   `static.adtidy.org` — работает при блокировках GitHub), ставится
   как systemd-служба от пользователя `adguard`
   (CAP_NET_BIND_SERVICE, без root).
3. **Миграция с нулевым даунтаймом:** если dnscrypt держал :53
   (ручной фикс старых версий) — listen_addresses переписывается на
   `127.0.0.1:5300`, dnscrypt рестартится. Пока AGH поднимается —
   redirect 53→5300 продолжает обслуживать DNS.
4. **Мастер первого запуска** (пароль задаёте ВЫ — не admin/admin):
   AGH стартует без конфига → откройте `http://IP:3000` (временный
   UFW-доступ только с вашего IP SSH-клиента), задайте логин/пароль.
   В мастере: Веб-интерфейс — все интерфейсы, DNS-сервер —
   127.0.0.1 (Loopback) — Chimera перенастроит адреса сама.
5. **Финализация** (автоматически после мастера): секции
   dns/tls/http/filters/querylog/statistics YAML заменяются на
   канонические Chimera (upstream=dnscrypt, фильтры, DoH/DoT),
   redirect 53→5300 **снимается** (AGH теперь владеет :53),
   конфиг Xray перегенерируется с DNS → `127.0.0.1:53`.

### Режимы Web UI / TLS

При установке (и позже через `Сеть → A → 4`) выбирается режим:

1. **HTTPS + Let's Encrypt** (рекомендуется) — сертификат домена
   сервера (тот же, что у Xray). Web UI + DoH на
   `https://домен:30443`. Renewal — certbot deploy-hook автоматически
   синкает сертификат в AGH.
2. **HTTPS + self-signed** — по IP, браузер предупредит.
3. **HTTP публично :3000** — без TLS (пароль открытым текстом —
   только для доверенных сетей).
4. **Локально 127.0.0.1:3000** — только SSH-туннель
   (`ssh -L 3000:127.0.0.1:3000 root@SERVER`).

DoH/DoT/DoQ эндпоинты (TLS-режимы):
- DoH: `https://домен:30443/dns-query`
- DoT: `домен:853` (tcp)
- DoQ: `домен:853` (udp)

Приватность: query log и statistics **включены** (ретенция 90 дней,
затем ротация) — логи запросов видны в Web UI (Настройки → Журнал
запросов). Отключаются штатно в UI AGH.

### Меню «Сеть → A»

| Пункт | Действие |
|-------|----------|
| 1 | Установить/переустановить (wizard + финализация) |
| 2 | Статус + завершить настройку (если мастер не завершён) |

| 5 | Переприменить конфиг (фильтры/DoH/DoT по канону) |
| 9 | Удалить AGH (полный откат к dnscrypt:5300) |

### Сосуществование с resolv.conf / redirect 53→5300

`chimera-dns-fix` (iptables OUTPUT redirect 53→5300) **понимает**
AGH (AGH-aware):

- **AGH активен и слушает :53** → redirect **снимается** (иначе он
  перехватывал бы запросы к 127.0.0.1:53 и уводил мимо фильтров AGH).
- **AGH в режиме мастера / удалён** → redirect ставится как обычно
  (dnscrypt страхует системный DNS).
- Persist-скрипт после ребута сам выбирает ветку: ждёт до 20 сек
  поднятия AGH, если тот включён; при падении AGH на буте redirect
  возвращает DNS на dnscrypt — black-hole исключён.

### Что AdGuard Home НЕ даст

- **Блокировку рекламы внутри приложений** — Spotify, YouTube и
  другие приложения с server-side рекламой обходят DNS-блокировку.
- **Блокировку YouTube-рекламы** — YouTube раздаёт рекламу с тех же
  доменов, что и видео (`googlevideo.com`). DNS-блок = блок видео.
- **Ускорение интернета** — фильтрация добавляет ~1-5 мс на запрос
  (компенсируется кешем — обычно итог быстрее).

| Аспект | Роутер | Chimera |

### Когда использовать

- **Нужна фильтрация рекламы на уровне DNS** — все устройства без

- **Нужен веб-интерфейс для управления DNS** — логи, блок-листы,

## 16. Запуск от отдельного пользователя: зачем uid dnscrypt

### Проблема

При AWG (AmneziaWG) iptables mangle маркирует трафик по
`--uid-owner`. Если dnscrypt-proxy работает от root (uid=0), его
исходящие соединения к DNS upstream-серверам (например,
`138.124.98.4:443`) НЕ получают AWG fwmark и уходят через дефолтный
маршрут провайдера, где DoT/DNSCrypt может блокироваться.

### Решение

`install_dnscrypt()` создаёт отдельного пользователя:
```bash
useradd -r -s /usr/sbin/nologin -d /var/lib/dnscrypt-proxy -m dnscrypt
```

И запускает сервис от этого пользователя:
```ini
[Service]
User=dnscrypt
Group=dnscrypt
```

Теперь AWG может добавить правило:
```bash
iptables -t mangle -A OUTPUT -m owner --uid-owner dnscrypt -j MARK --set-mark 0x...
```

И трафик DNSCrypt пойдёт через AWG-туннель, как и должно быть.

### Дополнительные меры безопасности

- `AmbientCapabilities=CAP_NET_BIND_SERVICE` — позволяет слушать
  порты <1024 (если понадобится).
- `CapabilityBoundingSet=CAP_NET_BIND_SERVICE` — ограничивает
  capabilities только этой одной.
- `NoNewPrivileges=yes` — запрещает повышение привилегий.
- `User=dnscrypt` + `Group=dnscrypt` — запуск от непривилегированного
  пользователя.

Это делает DNSCrypt-proxy устойчивым к компрометации — даже если
атакующий получит RCE в dnscrypt, он не получит root.

## 17. Сосуществование с AWG, WARP, Xray routing

### С AWG (AmneziaWG)

DNSCrypt-proxy запускается от uid `dnscrypt` (раздел 16). AWG
маркирует его трафик и отправляет через туннель к exit-ноде.
DNS-запросы резолвятся через DNSCrypt → upstream — это правильно,
потому что:

- Exit-нода находится за границей, DNSCrypt-серверы там доступны.
- Если бы DNSCrypt резолвил через провайдера РФ — ТСПУ блокировал
  бы запросы к «нежелательным» доменам.

**Важно:** если AWG-туннель падает, DNSCrypt тоже перестаёт работать
(трафик не уходит). Используйте AWG Watchdog (`[W]` в меню
безопасности) для автоматического перезапуска.

### С Cloudflare WARP

Если включён WARP full-tunnel — весь трафик (включая DNS) идёт через
WARP. DNSCrypt становится избыточным:

```
без WARP:  Xray → DNSCrypt (127.0.0.1:5300) → upstream
с WARP:    Xray → WARP → Cloudflare DNS (внутри туннеля)
```

Chimera автоматически обнаруживает WARP и не настаивает на
DNSCrypt. Но DNSCrypt можно оставить как fallback — если WARP
упадёт, DNSCrypt продолжит работать.

### С Xray routing

Xray в `config.json` имеет секцию `dns`:
```json
"dns": {
  "servers": [
    "127.0.0.1:5300",       // DNSCrypt
    "1.1.1.1",              // fallback если DNSCrypt упал
    {
      "address": "8.8.8.8",
      "port": 53,
      "domains": ["geosite:google"]  // Google-домены через Google DNS
    }
  ]
}
```

Xray сначала спрашивает у DNSCrypt (127.0.0.1:5300). Если тот не
ответил за 5 секунд — fallback на 1.1.1.1. Для определённых доменов
можно указать отдельный DNS (например, Google-домены через Google
DNS для совместимости).

**Важно:** не удаляйте `127.0.0.1:5300` из `dns.servers` — иначе
Xray будет резолвить напрямую, в обход DNSCrypt.

## 18. Диагностика: DNSCrypt не запускается

### Симптом

```bash
systemctl is-active dnscrypt-proxy
# failed или inactive
```

### Причина 1: бинарник не найден

```bash
ls -la /usr/local/bin/dnscrypt-proxy
# No such file or directory
```

**Решение:** переустановите через меню Chimera → **Сеть → [3]
DNSCrypt-proxy → Переустановить**.

### Причина 2: конфиг с ошибкой синтаксиса

```bash
journalctl -u dnscrypt-proxy -n 30 --no-pager
# Syntax error in /etc/dnscrypt-proxy/dnscrypt-proxy.toml
```

**Решение:**
```bash
# Проверка синтаксиса
/usr/local/bin/dnscrypt-proxy -config /etc/dnscrypt-proxy/dnscrypt-proxy.toml -check

# Если ошибка — восстановить из бэкапа
ls /etc/dnscrypt-proxy/dnscrypt-proxy.toml.*.bak
cp /etc/dnscrypt-proxy/dnscrypt-proxy.toml.20260812120000.bak /etc/dnscrypt-proxy/dnscrypt-proxy.toml
systemctl restart dnscrypt-proxy
```

### Причина 3: порт 5300 занят

```bash
ss -ulnp | grep 5300
# Если что-то уже слушает — конфликт
```

**Решение:** найдите, кто занял порт, и остановите. Обычно это
ранее запущенный dnscrypt-proxy, который не завершился:
```bash
pkill -f dnscrypt-proxy
systemctl start dnscrypt-proxy
```

### Причина 4: нет доступа к upstream

```bash
journalctl -u dnscrypt-proxy -n 30 --no-pager
# [FATAL] Unable to retrieve server certificates
# [FATAL] Timeout while resolving cloudflare-dns.com
```

**Решение:**
1. Проверьте доступность bootstrap-resolvers:
   ```bash
   dig @1.1.1.1 cloudflare-dns.com
   ```
2. Если не работает — провайдер блокирует DNS. Используйте DoH
   bootstrap:
   ```toml
   bootstrap_resolvers = ['https://1.1.1.1/dns-query']
   ```

### Причина 5: права на конфиг-директорию

```bash
ls -la /etc/dnscrypt-proxy/
# Файлы должны принадлежать dnscrypt:dnscrypt
```

**Решение:**
```bash
chown -R dnscrypt:dnscrypt /etc/dnscrypt-proxy
systemctl restart dnscrypt-proxy
```

## 19. Диагностика: утечка DNS через systemd-resolved

### Симптом

DNS Leak Test показывает российские DNS (`77.88.8.8` — Yandex.DNS,
`8.8.4.4` — Google через Ростелеком/МГТС, `5.3.x.x` — провайдерский),
хотя `/etc/resolv.conf` указывает на `127.0.0.1`.

### Причина

`systemd-resolved` игнорирует `/etc/resolv.conf` и использует DNS
из DHCP. glibc-приложения (curl, dig) используют `/etc/resolv.conf`,
но приложения через D-Bus API (NetworkManager, некоторые Python-
библиотеки) — используют systemd-resolved напрямую.

### Решение

1. Запустите авто-фикс из меню Chimera → **Диагностика → [N] DNS
   Leak Test** → «Исправить автоматически? [Y/n]».

2. Или вручную:
   ```bash
   # 1. /etc/resolv.conf → 127.0.0.1
   echo "nameserver 127.0.0.1" > /etc/resolv.conf

   # 2. Убрать 'resolve' из /etc/nsswitch.conf
   sed -i 's/hosts:.*/hosts: files dns/' /etc/nsswitch.conf

   # 3. Указать systemd-resolved использовать локальный DNS
   mkdir -p /etc/systemd/resolved.conf.d
   cat > /etc/systemd/resolved.conf.d/chimera-dns.conf << 'EOF'
   [Resolve]
   DNS=127.0.0.1
   Domains=~.
   EOF
   systemctl restart systemd-resolved

   # 4. Очистить кеш
   resolvectl flush-caches
   ```

3. Проверьте:
   ```bash
   resolvectl status | grep "DNS Server"
   # должно быть: 127.0.0.1

   dig example.com | grep SERVER
   # должно быть: ;; SERVER: 127.0.0.1#53
   ```

4. Повторите DNS Leak Test через 5 минут (кеш мог остаться на
   стороне тестового сервиса).

## 20. Диагностика: Yandex / провайдерский DNS в DNS Leak Test

### Симптом

DNS Leak Test показывает:
- `77.88.8.8` (Yandex.DNS)
- `77.88.8.1` (Yandex.DNS)
- `8.8.4.4` (Google, но маршрутизируется через Ростелеком/МГТС)
- `5.3.x.x` / `78.x.x.x` (провайдерский DNS Ростелекома)

### Причина

Это DHCP-DNS от провайдера (Ростелеком, МГТС как дочка Ростелекома,
и т.д.). Yandex.DNS (`77.88.8.8`) часто прописывается провайдером
по умолчанию или наследуется от старой настройки роутера — это
российский публичный DNS, и провайдер считает его «безопасным».
`systemd-resolved` получил эти адреса при подключении к сети и
использует параллельно с DNSCrypt.

### Решение

Раздел 19 — авто-фикс `/etc/resolv.conf` + `nsswitch.conf` +
systemd-resolved drop-in.

### Дополнительно

Если у вас AWG — включите принудительный DNS REDIRECT (раздел 10).
Это перехватит DNS-запросы клиентов, даже если они прописали
свой DNS.

## 21. Диагностика: DNSCrypt работает, но Xray не резолвит

### Симптом

```bash
systemctl is-active dnscrypt-proxy
# active

dig @127.0.0.1 -p 5300 google.com
# работает, отдаёт IP

# Но в Xray:
journalctl -u xray -n 30 | grep -i dns
# failed to resolve domain
```

### Причина 1: Xray не настроен на DNSCrypt

Проверьте `config.json`:
```bash
python3 -c "import json; c=json.load(open('/etc/xray/config.json')); print(c.get('dns',{}).get('servers'))"
```

Должно быть:
```json
["127.0.0.1:5300", "1.1.1.1", ...]
```

Если `dns.servers` пуст или не содержит `127.0.0.1:5300` — Xray
не использует DNSCrypt.

**Решение:** добавьте `127.0.0.1:5300` первым элементом:
```bash
python3 -c "
import json
cfg_path = '/etc/xray/config.json'
c = json.load(open(cfg_path))
c.setdefault('dns', {})['servers'] = ['127.0.0.1:5300', '1.1.1.1']
json.dump(c, open(cfg_path, 'w'), indent=2)
"
systemctl restart xray
```

### Причина 2: Xray использует domainStrategy, который обходит DNS

В `config.json`:
```json
"routing": {
  "domainStrategy": "AsIs"
}
```

`AsIs` = Xray не резолвит домены, отправляет их как есть. Это
нормально для VLESS+REALITY (где dest указывается IP), но ломает
routing по доменам.

**Решение:** измените на `IPIfNonMatch` или `UseIP`:
```json
"domainStrategy": "IPIfNonMatch"
```

### Причина 3: DNSCrypt слушает не на том порту

```bash
ss -ulnp | grep dnscrypt
# должно быть: 127.0.0.1:5300
```

Если порт другой — обновите `config.json` или приведите конфиг
DNSCrypt к стандарту:
```toml
listen_addresses = ['127.0.0.1:5300']
```

## 22. Логи, файлы состояний и ротация

### Файлы

| Файл | Назначение | Ротация |
|---|---|---|
| `/etc/dnscrypt-proxy/dnscrypt-proxy.toml` | основной конфиг | нет |
| `/etc/dnscrypt-proxy/public-resolvers.md` | кеш списка серверов (72ч) | автообновление |
| `/etc/dnscrypt-proxy/relays.md` | кеш списка relay (72ч) | автообновление |
| `/etc/dnscrypt-proxy/blocked-names.txt` | локальный блок-лист доменов | вручную |
| `/etc/dnscrypt-proxy/blocked-ips.txt` | локальный блок-лист IP | вручную |
| `/var/log/dnscrypt-proxy-blocked.log` | лог заблокированных запросов | нет |
| `/etc/systemd/system/dnscrypt-proxy.service` | systemd-юнит | нет |
| `/var/lib/xray-installer/dns_redirect.json` | state DNS REDIRECT | нет |
| `/var/lib/xray-installer/resolv_conf_fix.json` | state resolv.conf fix | нет |
| `/etc/systemd/system/dns-redirect-restore.service` | restore после reboot | нет |
| `/usr/local/bin/xray-dns-redirect-restore.sh` | скрипт restore | нет |
| `/etc/systemd/resolved.conf.d/chimera-dns.conf` | drop-in для resolved | нет |
| `/etc/resolv.conf.chimera.bak` | бэкап resolv.conf | нет |
| `/etc/nsswitch.conf.chimera.bak` | бэкап nsswitch.conf | нет |

### Логирование

DNSCrypt-proxy пишет логи в journald (`use_syslog = true`):
```bash
journalctl -u dnscrypt-proxy -n 50 --no-pager
journalctl -u dnscrypt-proxy -f    # follow
journalctl -u dnscrypt-proxy --since '1 hour ago'
```

### Ротация логов

`/var/log/dnscrypt-proxy-blocked.log` растёт бесконечно. Добавьте
в `/etc/logrotate.d/dnscrypt-proxy`:
```
/var/log/dnscrypt-proxy-blocked.log {
    weekly
    rotate 4
    compress
    missingok
    notifempty
}
```

Или используйте модуль Chimera **logrotate** (`[L]` в меню
диагностики) — он настраивает ротацию для всех логов Chimera.

### Очистка кеша

```bash
# Очистить кеш DNSCrypt (без перезапуска)
kill -USR1 $(pidof dnscrypt-proxy)

# Очистить кеш systemd-resolved
resolvectl flush-caches

# Очистить кеш nscd (если установлен)
nscd -i hosts
```
