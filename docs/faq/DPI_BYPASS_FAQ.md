# DPI Bypass (b4) — FAQ по обходу ТСПУ для YouTube и любых заблокированных ресурсов

Полное руководство по DPI Bypass через b4 (Bye Bye Big Bro) — интеграция в
Chimera Project. Охватывает YouTube (специализированный модуль) и централизованный
модуль для любых ресурсов.

> **b4** — Linux-демон (Go, статически слинкованный), перехватывает исходящий
> TCP/UDP трафик через NFQUEUE и применяет DPI-обход: фейковый SNI, фрагментацию
> ClientHello, fake RST. ТСПУ не может сопоставить SNI → пропускает трафик.
> Репозиторий: https://github.com/DanielLavrushin/b4
>
> Семантика настроек описана по b4 ≥ 1.79 (включая 1.80rc1): QUIC-блок —
> per-set, значения `filter_quic` — только `sni`/`all`.

## 1. Что такое DPI Bypass и зачем он нужен

### Контекст: история проблемы YouTube в Chimera

**ТСПУ** (Технические средства противодействия угрозам) — DPI-система
на уровне российских провайдеров. Она:

- Видит SNI в TLS ClientHello → блокирует/троттлит соединения к
  заблокированным доменам (например, `youtube.com`).
- Блокирует QUIC (UDP/443) — браузер не может установить соединение.
- Отвечает forged RST — рвёт соединение.

### Ранние попытки решения в Chimera (и почему они не сработали)

В Chimera Project было **два предыдущих подхода** к починке YouTube
на entry-нодах, ни один из которых не решил проблему полностью:

**Попытка 1: TCP-фрагментация ClientHello (freedom outbound + fragment)**

Chimera имеет 12 модулей фрагментации (`fragment_*.py`) и серверную
фрагментацию (`server_fragment.py`). Идея: разбить TLS ClientHello на
несколько TCP-сегментов, чтобы ТСПУ не смог собрать полный SNI.

**Почему не сработало:**
- Xray `freedom` outbound умеет **только базовую фрагментацию по смещению
  байтов** (`packets:"1-3"` + `length` + `interval`). Он не умеет:
  - Отправлять фейковый ClientHello с decoy-SNI (DuckDuckGo/Google),
    который ТСПУ читает, а сервер отбрасывает.
  - Разрезать ClientHello в середине SNI (SNI-aware split).
  - Инжектить fake RST для corrupt DPI per-flow state.
  - Перехватывать QUIC (UDP/443) — только TCP.
- На серверах без IPv6 `routeOnly=True` ломал `domainStrategy=UseIPv4` —
  freedom outbound получал IP от клиента вместо домена → dial падал.
- Патч `patch_inbounds_for_fragment` был **выключен** из-за этого бага.
- Результат: «работает урывками», «без IPv6 не работает совсем».

**Попытка 2: YouTube через Cloudflare WARP (`youtube_warp_route.py`)**

Маршрутизация YouTube-трафика через Cloudflare WARP (WireGuard-туннель
от entry VPS к Cloudflare). Xray `freedom` outbound с `sendThrough`
отправляет YouTube-трафик через интерфейс `wg-warp`.

**Почему не сработало:**
- WARP сам по себе не обходит ТСПУ — он меняет маршрут (через Cloudflare),
  но ТСПУ всё равно видит SNI `youtube.com` в ClientHello на пути к WARP.
- Cloudflare WARP имеет **лимиты трафика** (free tier ~1GB/день) — для
  видео это неприемлемо.
- Добавляет лишний хоп: entry VPS → Cloudflare WARP → YouTube, вместо
  entry VPS → YouTube напрямую.
- Не решает QUIC-блокировку (WARP не перехватывает UDP/443).

### Почему выбран b4

**b4 (Bye Bye Big Bro)** — Linux-демон от DanielLavrushin, который
работает на сетевом уровне (L3/L4) через NFQUEUE + raw sockets. Он
делает то, чего не могут ни Xray fragment, ни WARP:

| Возможность | Xray fragment | WARP | **b4** |
|---|---|---|---|
| Fake SNI (decoy ClientHello) | ❌ | ❌ | ✅ 9 типов payload |
| SNI-aware split (в середине SNI) | ❌ | ❌ | ✅ |
| QUIC-перехват (UDP/443) | ❌ | ❌ | ✅ |
| Fake RST (corrupt DPI state) | ❌ | ❌ | ✅ |
| RST protection (отбрасывать forged RST) | ❌ | ❌ | ✅ |
| Discovery (автоподбор сета) | ❌ | ❌ | ✅ |
| Не добавляет лишний хоп | ✅ | ❌ (через Cloudflare) | ✅ |
| Без лимитов трафика | ✅ | ❌ (free tier 1GB) | ✅ |
| Не требует remote server | ✅ | ❌ | ✅ |

**Ключевое решение:** b4 ставится **на entry VPS** (не на роутер юзера, не
на exit-ноду). Entry VPS находится в РФ и сам ходит к YouTube CDN напрямую.
b4 перехватывает **исходящий** трафик от Xray к YouTube и мутирует пакеты
так, что ТСПУ не может сопоставить SNI → пропускает. Юзер не ставит b4
на свой роутер — он просто подключается по VLESS, и YouTube работает.

### Дополнительный бонус: YouTube без рекламы

Поскольку entry VPS находится в РФ, YouTube видит российский IP-адрес.
YouTube не показывает рекламу пользователям из РФ (с 2022 года). Таким
образом, **весь YouTube-трафик через Chimera + b4 идёт без рекламы** —
видео загружается сразу, без pre-roll и mid-roll рекламы. Это было одной
из целей всего проекта — обеспечить стабильный доступ к YouTube без
троттлинга и без рекламы, через единый VLESS-туннель без необходимости
настраивать отдельные инструменты на клиенте.

### Как b4 обходит ТСПУ

1. **Фейковый SNI** — отправляет decoy ClientHello с SNI другого сайта
   (например, `staticcdn.duckduckgo.com` или `www.google.com`). ТСПУ читает
   фейк и думает, что соединение к разрешённому сайту. Реальный сервер
   отбрасывает фейк (по TTL или TCP-seq).
2. **Фрагментация ClientHello** — разбивает реальный ClientHello на 3-4
   TCP-сегмента с паузами 20-60ms. ТСПУ не может собрать полный SNI.
3. **QUIC-перехват** — b4 перехватывает UDP/443 (QUIC) и применяет
   тот же DPI-обход.
4. **Fake RST** — инжектит фейковые RST/FIN с плохими checksums для
   corrupt DPI per-flow state.

**Результат:** ТСПУ не может сопоставить SNI → пропускает → YouTube работает.

## 2. Архитектура: как b4 работает в Chimera

```
Клиент (без изменений)
    ↓ VLESS Reality (ТСПУ не видит — TLS-handshake замаскирован)
Entry VPS (panel.example)
    ↓ Xray inbound (port 443)
    ↓ Xray routing: geosite:youtube → outbound:direct
    ↓ freedom outbound открывает TCP к youtube.com:443
    ↓ iptables mangle OUTPUT → NFQUEUE 537
    ↓ b4 daemon (Go, systemd):
    ↓   SNI=youtube.com? → DROP + inject fake Google SNI + фрагментация
    ↓   raw socket (SO_MARK=32768) → YouTube CDN
    ↓ ТСПУ не видит SNI → пропускает → YouTube работает
YouTube CDN
```

**Ключевые принципы:**

- b4 ставится **только на entry VPS** (не на exit, не на клиенте).
- b4 перехватывает **исходящий** трафик от Xray к YouTube CDN.
- b4 не требует изменений в конфиге Xray — работает поверх routing
  `geosite:youtube → direct`.
- b4 не конфликтует с UFW/iptables/ingress_geoip (mangle vs filter таблицы).
- b4 работает на L3 — не важно, IPv4 или IPv6.

## 3. DPI Bypass для YouTube — полный путь из главного меню

**ВАЖНО:** Для работы b4 необходимо, чтобы в Xray было включено
`geosite:youtube → outbound:direct` (YouTube через RU entry).
Без этого YouTube-трафик идёт через exit-ноды (зашифрованный туннель),
и b4 его не видит (SNI зашифрован внутри туннеля).

```
python3 main.py
→ Главное меню → 3 (Настройки сети)
→ Меню «Настройки сети» → Y (YouTube через RU)
→ Меню «YouTube маршрутизация» → 1 (YouTube через RU entry)
   (включает geosite:youtube → outbound:direct в Xray — ОБЯЗАТЕЛЬНО)
→ Вернуться назад → B (b4 DPI bypass)
→ Меню b4 → 1 (Установить)
```

После установки b4:
- YouTube-трафик с entry VPS перехватывается b4.
- Применяется fake SNI + фрагментация.
- ТСПУ пропускает → YouTube работает.

**Дополнительно в меню b4:**
- Пункт 2 — переключить preset (default / aggressive / light)
- Пункт 3 — импорт кастомного сета
- Пункт 4 — Discovery (автоподбор)
- Пункт 5 — Health check
- Пункт 6 — Логи
- Пункт 7 — Web UI (SSH-туннель инструкция)
- Пункт 8 — nginx front (прямой доступ к Web UI по HTTPS)
- R — удалить b4

**Альтернативный запуск (без главного меню):**
```bash
python3 -m chimera.modules.youtube_b4
```

## 4. Централизованный DPI Bypass — полный путь из главного меню

```
python3 main.py
→ Главное меню → 3 (Настройки сети)
→ Меню «Настройки сети» → B (DPI Bypass)
→ Меню «DPI Bypass (b4) — централизованный»
```

**Что показывает меню:**
- Статус: active/stopped + версия + проверка обновлений
- Список всех set'ов с доменами
- Кнопки управления

**Пункты меню:**
- 1 — Запуск/остановка b4
- 2 — Переключить preset
- 3 — Импорт кастомного сета (JSON) — добавляет к существующим
- 4 — Discovery (автоподбор сета под провайдера)

- S — Синхронизация доменов b4 → Xray routing
- U — скрытый алиас: открывает раздел обновления (как [5])

**Альтернативный запуск:**
```bash
python3 -m chimera.modules.dpi_bypass
```

## 5. Установка b4

**Способ 1 — через YouTube меню:**
```
Главное меню → 3 (Настройки сети) → Y (YouTube) → 1 (RU entry) → B (b4) → 1 (Установить)
```

**Способ 2 — через централизованное меню:**
```
Главное меню → 3 (Настройки сети) → B (DPI Bypass)
```
Если b4 не установлен — будет предложено установить.

**Способ 3 — через CLI:**
```bash
python3 -m chimera.modules.youtube_b4 install
```

**Что происходит при установке:**
1. Скачивается b4 binary с GitHub releases (linux-amd64, ~7MB).
2. Создаётся ПУСТОЙ конфиг `/etc/b4/config.json` (без сетов — пресет
   выбирается позже через [2] или Discovery):
   ```json
   {
     "sets": [],
     "system": {
       "geo": {
         "sitedat_path": "/usr/share/xray/geosite.dat",
         "ipdat_path": "/etc/b4/geoip.dat",
         "ipdat_url": "https://github.com/DanielLavrushin/b4geoip/..."
       }
     }
   }
   ```
   `system.geo.sitedat_path` — путь к geosite.dat Xray: сеты с
   geosite-категориями (в т.ч. из Discovery) валидируются b4 только при
   заданном пути.
3. Создаётся systemd-unit `/etc/systemd/system/b4.service`.
4. iptables-правила Chimera НЕ ставятся: b4 сам создаёт свою таблицу
   `b4_mangle` в nftables (IPv4+IPv6, перехват первых пакетов соединения).
5. Регистрируются порты в port_registry:
   - 9700 (Web UI, loopback)
   - 5453 (DNS TCP, internal)
6. Сервис запускается и включается в автозагрузку.

## 6. Переключение пресетов (default / aggressive / light)

**Путь:**
```
Главное меню → 3 (Настройки сети) → Y (YouTube) → B (b4) → 2 (Переключить preset)
```

**3 пресета:**

| Preset | Fake SNI | seg2delay | QUIC-блок |
|---|---|---|---|
| Default | DuckDuckGo (sni_type=3) | 20-60ms | reject/all |
| Aggressive | Google (sni_type=2) | 10-30ms | reject/all |
| Light | Нет (sni=false) | 30-80ms | reject/all |

Во все пресеты встроен QUIC-блок — per-set секция
`"udp": {"filter_quic": "all", "mode": "reject"}` (см. раздел 11).
Если YouTube перестал работать — переключите на другой preset.
ТСПУ постоянно обновляет правила — то, что работало вчера, может не работать сегодня.

## 7. Импорт кастомных сетов из Discovery

> **⚠ ВАЖНО:** сет, созданный через Web UI b4 (Discovery → Create Set),
> может содержать `geosite_categories` — для них валидация b4 требует
> настроенный путь к geosite-базе (`system.geo.sitedat_path`). Если сет
> с категориями не загружается (видео не крутится, стратегия не
> применяется) — импортируйте его через TUI Chimera (пункт [3]):
> Chimera прописывает `system.geo.sitedat_path` (geosite.dat Xray) при
> установке и миграции конфига.

### Полный путь импорта сета из Discovery (Web UI → TUI)

Для того, чтобы импортировать сет из Discovery - сделайте следующее:
1. Найдите рабочую стратегию обхода в Web-UI B4
2. Нажмите Use This Strategy
3. Create Set
4. На странице с сетами нажмите на три точки на карточке сета, затем нажмите Edit
5. Перейдите в Import/Export
6. Нажмите Copy JSON
7. Удалите созданный сет
8. Перейдите в TUI Chimera по пути Главное меню->3->Y->B
9. Нажмите 3 - Импортировать кастомный сет (JSON)
10. Вставьте содержимое скопированного сета из п.6 и нажмите Enter.
11. Перейдите в Web-UI во вкладку "Sets", нажмите F5, чтобы перезагрузить страницу и убедитесь, что сет импортирован успешно.

**Что делает Chimera при импорте:**
- Нормализует wildcard-домены (`*.example.com` → `example.com` — движок b4
  матчит поддомены суффикс-матчингом, wildcard-записи не поддерживает).
- Выставляет `enabled: true`, если поле отсутствует (Go-декодер b4
  считает отсутствующее поле = false).
- Удаляет legacy-поле `b4_version` (не поле SetConfig — b4 его игнорирует).
- Основной путь — REST API b4 (hot-reload, без рестарта сервиса). Если
  REST недоступен — прямая запись config.json с мёржем (queue/ui/system
  сохраняются) и чисткой legacy-полей старого конфига (верхнеуровневые
  `udp`/`routing`, `system.geosite_path` → `system.geo.sitedat_path`).
- Сохраняет `active_preset: "custom"` в state.json.
- QUIC-блок в импортируемый сет НЕ добавляется — это per-set настройка
  сета (см. раздел 11): включается в Web UI (карточка сета → UDP →
  «Блокировать QUIC») или задаётся в самом JSON сета.

**Почему сеты из Discovery иногда не работают без импорта через TUI?**
Сет, созданный в Web UI, может содержать `geosite_categories` — для них
валидация b4 требует настроенный `system.geo.sitedat_path`. Chimera
прописывает путь к geosite.dat Xray при установке и миграции конфига,
поэтому после импорта через TUI (и починки секции system) сеты с
geosite-категориями загружаются корректно.

## 8. Discovery — автоподбор рабочего сета

Discovery — встроенная функция b4, которая перебирает сотни комбинаций
(fake SNI типы, TTL, стратегии фрагментации, delay) и находит рабочую
под текущего провайдера хостера.

**Запуск Discovery:**

**Через Web UI (рекомендуется):**
1. Включите nginx front для Web UI:
   ```
   Главное меню → 3 (Настройки сети) → Y (YouTube) → B (b4) → 8 (nginx front)
   → порт 9743 → Let's Encrypt → ваш домен
   ```
2. Откройте `https://<домен>:9743` в браузере.
3. Перейдите на вкладку Discovery → Start.

**Через TUI:**
```
Главное меню → 3 (Настройки сети) → Y (YouTube) → B (b4) → 4 (Discovery)
```

**После Discovery:**
- Скопируйте найденный рабочий сет (JSON).
- Импортируйте через TUI (пункт 2 или 3).

## 9. Обновление b4 (раздел «Обновление Bye Bye Big Bro»)

**Путь (централизованный модуль):**
```
Главное меню → 3 (Настройки сети) → B (DPI Bypass) → 5 (Обновление Bye Bye Big Bro)
```

**Путь (модуль YouTube):**
```
Главное меню → 3 (Настройки сети) → Y (YouTube) → B (b4) → 5 (Обновление Bye Bye Big Bro)
```

**Раздел содержит два подраздела:**
- 1 — Обновление до последней release версии
- 2 — Обновление до prerelease версии (нестабильно!)

**Что показывает раздел:**
- Установленную версию binary
- Последнюю release-версию на GitHub
- Последнюю pre-release версию на GitHub

**Принудительное обновление:**
Если установленная версия совпадает с выбранной (release или pre-release) —
Chimera предлагает принудительную переустановку `[y/N]`. Это полезно, когда:
- бинарник повреждён (частые падения b4);
- нужно откатиться с pre-release на стабильную версию;
- b4 был обновлён мимо Chimera (из Web UI b4 или через install.sh).

**Синхронизация версии между модулями:**
Модули «YouTube через B4» и «DPI Bypass» работают с одним binary
(`/usr/local/bin/b4`) и одним общим state-файлом. При входе в раздел
обновления фактическая версия binary синхронизируется с state
(`sync_b4_version_state()`) — оба меню всегда показывают одну версию,
из какого бы модуля ни выполнялось обновление.

**Последовательность обновления:**
1. Проверка последней версии на GitHub API.
2. Сравнение с установленной.
3. Если есть обновление (или подтверждено принудительное):
   a. Скачивание `b4-linux-amd64.tar.gz`.
   b. Проверка SHA256 (через `.sha256` файл).
   c. Остановка сервиса.
   d. Backup старого binary.
   e. Замена binary.
   f. Запуск сервиса.
   g. Проверка что active (если нет — восстановление из backup).
4. **Конфиг и set'ы не затрагиваются.**

**CLI:**
```bash
python3 -m chimera.modules.dpi_bypass update        # до последней release
python3 -m chimera.modules.dpi_bypass update-pre    # до pre-release
python3 -m chimera.modules.dpi_bypass sync-version  # синхронизация версии в state
```

## 11. Web UI b4 и nginx front (прямой доступ по HTTPS)

b4 имеет встроенный Web UI на порту 9700 (только HTTP, только loopback).

### Доступ через SSH-туннель (простой, но требует SSH)

```bash
ssh -L 9700:127.0.0.1:9700 root@<server>
# В браузере: http://localhost:9700
```

### Доступ через nginx front (прямой HTTPS из браузера)

Chimera умеет ставить nginx с TLS перед Web UI b4 — аналогично User Portal
и подписке. Два режима:

**Режим 1: Let's Encrypt (домен, доверенный сертификат)**

Если при установке VLESS вы указали домен (например, `panel.example`),
Chimera переиспользует уже выпущенный LE-сертификат для nginx front b4.
Новый сертификат не выпускается — используется существующий.

```
Главное меню → 3 (Настройки сети) → Y (YouTube) → B (b4) → 8 (nginx front)
→ порт 9743 (default) → 1 (Let's Encrypt) → ваш домен
```

После: `https://panel.example:9743` — Web UI с доверенным LE-сертификатом.
Браузер не ругается. Доступ напрямую, без SSH-туннеля.

**Важно:** Chimera автоматически подгружает домен из `state.json`
(даже если вызов идёт из меню без `_load_state_into_globals`). Если домен
не найден — предлагается self-signed режим.

**Режим 2: Self-signed (по IP, без домена)**

Если домена нет (доступ по IP) — Chimera генерирует self-signed
сертификат. Браузер предупредит («недоверенный сертификат»), нужно
подтвердить вручную. После — работает.

```
Главное меню → 3 (Настройки сети) → Y (YouTube) → B (b4) → 8 (nginx front)
→ порт 9743 → 2 (Self-signed)
```

После: `https://<IP-сервера>:9743` — Web UI с self-signed сертификатом.

**Что происходит при включении nginx front:**
1. nginx ставит vhost на порту 9743 с TLS (LE или self-signed).
2. Проксирует `https://<host>:9743` → `http://127.0.0.1:9700`.
3. Прямой доступ к порту 9700 закрывается (UFW deny) — только через nginx.
4. Порт 9743 регистрируется в port_registry.
5. При выключении — nginx vhost удаляется, порт 9700 открывается обратно.

**В Web UI можно:**
- Управлять set'ами (включить/выключить)
- Запустить Discovery (автоподбор сета)
- Смотреть статистику в реальном времени
- Импортировать кастомные сеты

### QUIC блокировка (b4 1.79+)

**QUIC-блок — per-set настройка.** У каждого сета своя вкладка UDP с двумя
независимыми полями:
- `udp.filter_quic` — какие QUIC-пакеты матчатся сетом:
  - `sni` (default) — только те, где SNI из QUIC ClientHello совпал с
    доменами сета;
  - `all` — плюс любые long-header QUIC-пакеты к адресам, которые сет
    уже знает по IP/порту (без читаемого SNI).
- `udp.mode` — что делать с матчнутым пакетом:
  - `off` — пропустить без изменений (сет продолжает изучать адреса);
  - `fake` (default) — декой-пакеты + фрагментация Initial;
  - `drop` — молча дропнуть (браузер откатится на TCP после таймаута);
  - `reject` — дропнуть + ICMP port unreachable → мгновенный откат
    на TCP/HTTP2.

**Канонический QUIC-блок** — то, что ставит переключатель «Блокировать
QUIC» в Web UI (карточка сета → UDP):

```json
"udp": { "filter_quic": "all", "mode": "reject" }
```

Все три пресета Chimera уже содержат эту пару. Для кастомных сетов
включите переключатель в Web UI или пропишите пару в JSON сета.

**Почему QUIC блокируют, а не обходят.** SNI в QUIC зашифрован в Initial
packet, всё после — под AEAD: переписать или порезать нельзя так, чтобы
обе стороны приняли. Fake-режим для QUIC — декой-шторм + IP-фрагменты,
которые душатся middlebox'ами → зависания при открытии видео. `drop`
даёт «вечный спиннер» — браузер ждёт таймаут. `reject` отвечает сразу
— фоллбэк на TCP незаметен. Браузер к тому же помнит `alt-svc`
advertisement и без отказа продолжает пробовать QUIC.

**Историческая справка (не используйте).** Прежние версии Chimera писали
`"udp": {"filter_quic": "block"}` на верхнем уровне конфига b4. Это
мёртвый ключ: у Config b4 вообще нет верхнеуровневой секции `udp`
(только version/queue/system/sets/ui) — ключ игнорировался при
загрузке и выкидывался при сохранении самим b4. И значения `"block"`
не существует: NormalizeQUICFilter переписывает всё, кроме `"all"`, в
`"sni"` — т.е. даже внутри сета `"block"` молчно превращался в «матч
по SNI», а не в блок. Актуальная Chimera пишет канонический per-set
блок и при переключении пресета / импорте сета вычищает legacy-ключи
из старого конфига (`udp`, `routing`, `system.geosite_path`,
`b4_version` в сетах).

## 13. Синхронизация между YouTube b4 и централизованным DPI Bypass

## 15. Решение проблем

### YouTube показывает «Нет подключения к интернету» / вечный спиннер

**Причина:** QUIC (UDP/443) не блокируется сетом — браузер бьётся в QUIC
к заблокированному ТСПУ адресу вместо мгновенного отката на TCP.

QUIC-блок per-set (b4 1.79+): UDP/443 всегда попадает в очередь b4, но
вердикт зависит от полей сета. Сет без udp-секции работает на дефолтах
b4 (`mode:"fake"`, `filter_quic:"sni"`) — fake-режим для QUIC даёт
декой-шторм и IP-фрагменты → зависания.

**Решение:**
1. Убедитесь, что в сете есть QUIC-блок (переключатель «Блокировать
   QUIC» в Web UI, карточка сета → UDP; в JSON это
   `"udp": {"filter_quic": "all", "mode": "reject"}`).
2. Для пресетов Chimera — просто переключите пресет заново
   (Главное меню → 3 → Y → B → 2): актуальные пресеты уже содержат
   QUIC-блок, заодно конфиг вычищается от legacy-полей.
3. Проверьте, что b4 вообще перехватывает трафик:
   ```bash
   journalctl -u b4 -f
   # Откройте YouTube → должны увидеть строки с youtube.com
   ```

### Видео открывается с задержкой / микрофризы

**Причина:** сет работает на QUIC `fake`-режиме (декой-пакеты +
IP-фрагментация Initial) вместо reject.

**Решение:** включите «Блокировать QUIC» для сета (см. выше) — браузер
получит ICMP port unreachable и мгновенно уйдёт на TCP/HTTP2, где
работают fake SNI + фрагментация.

### YouTube работал, потом перестал

**Причина:** ТСПУ обновил правила.

**Решение:** Переключите preset:
```
Главное меню → 3 → Y → B → 2 (Переключить preset)
→ 2 (Aggressive) или 3 (Light)
```

Если не помогает — запустите Discovery (пункт 4 или через Web UI).

### b4 запускается, но YouTube не работает

**Проверьте:**
1. `geosite:youtube → direct` включён в Xray:
   ```
   Главное меню → 3 → Y → 1 (RU entry)
   ```
2. b4 видит YouTube-трафик:
   ```bash
   journalctl -u b4 -f
   # Откройте YouTube → должны увидеть строки с youtube.com
   ```
3. Health check:
   ```bash
   python3 -m chimera.modules.youtube_b4 health
   ```

### «Unknown key name 'StartLimitIntervalSec'» в логах

Это безобидное предупреждение (устаревший systemd). Уже исправлено в
последних версиях Chimera — обновитесь:
```bash
cd /opt/chimera && git pull
python3 -m chimera.modules.youtube_b4 uninstall
python3 -m chimera.modules.youtube_b4 install
```

### Как добавить DPI bypass для Discord / Instagram / других сайтов

1. Установите b4 (через YouTube меню).
2. Запустите Discovery в Web UI для нужного домена.
3. Скопируйте найденный сет (JSON).
4. Импортируйте через централизованное меню:
   ```

   ```
5. Set добавится к существующему YouTube set — оба будут работать одновременно.
