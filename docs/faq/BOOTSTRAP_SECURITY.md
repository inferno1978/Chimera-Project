# BOOTSTRAP SECURITY — безопасная установка Chimera (мульти-зеркало + Ed25519)

> Документ описывает: модель доверия установки, команду, требования к инструментам,
> процесс публикации и подписи релизов, ротацию ключей и действия при компрометации.

## 1. Схема установки (кратко)

Установка — один copy-paste блок («Безопасная установка» в [README](../../README.md#-быстрый-старт)).
Блок делает следующее:

1. Проверяет наличие `openssl` и поддержку Ed25519 (без этого — отказ, ничего не скачивается и не исполняется).
2. Для каждого зеркала по порядку (Forgejo → GitLab → GitHub):
   - скачивает `bootstrap.sh` **во временный файл** (`curl -fsSL`, `--connect-timeout 10 --max-time 60`);
   - проверяет размер (пустой файл или > 512 KiB → зеркало отбрасывается);
   - скачивает `bootstrap.sh.sig` (detached-подпись Ed25519, 64 байта; не 64 байта → отбрасывается);
   - проверяет подпись закреплённым публичным ключом (`openssl pkeyutl -verify -rawin`);
   - **только при успешной проверке** — запускает проверенный файл (`bash "$tmp" "$@"`, код возврата сохраняется).
3. Ошибка загрузки ИЛИ проверки → переход к следующему зеркалу (каждое проверяется независимо, без ослабления требований).
4. Все зеркала исчерпаны → понятная ошибка на русском (различаются «ничего не скачалось» и «скачалось, но не прошло проверку»), код возврата 1, временные файлы удалены. **Fail-closed: неотверифицированный код не исполняется ни при каком сценарии.**

Публичный ключ закреплён в самой команде установки (trust anchor) и дублируется ниже.

## 2. Модель доверия

**Anchor (источник доверия):** Ed25519 публичный ключ, вшитый в команду установки,
которую пользователь копирует из README / этого документа / надёжного канала автора
(TG-канал, сайт). Приватный ключ существует в двух защищённых копиях вне git:
у релизера и на сервере Forgejo (`/etc/chimera-mirror/`, root:600).

**Публичный ключ (текущий):**

```
-----BEGIN PUBLIC KEY-----
MCowBQYDK2VwAyEA+6KSAskfo+LBzW/io8q376wAULspfGTik674H1o8Gu4=
-----END PUBLIC KEY-----
```

Отпечаток (sha256 DER): `6accc3b58de02d7a873caa52fd9ea66158865b094816947a95bcbf61e2a433d4`

**Что схема защищает (атаки, которые НЕ работают):**

- подмена/повреждение `bootstrap.sh` на любом одном или нескольких зеркалах
  (включая откат на старую версию — подпись не сойдётся, если она не от того же файла);
- компрометация GitLab или GitHub (зеркала) — подпись не подделать без приватного ключа;
- MITM при условии честного TLS (дополнительно подпись закрывает и скомпрометированный CA);
- подмена только raw-URL (кэши CDN, «тот же путь — другой файл»);
- частичная/битая загрузка, HTML-заглушки прокси вместо скрипта (не сойдётся подпись/размер);
- исполнение «злого» файла при недоступности основного зеркала (fallback не ослабляет проверку);
- обновление `.sig` без `.sh` или наоборот — pre-commit hook блокирует рассинхрон в репозитории.

**Что схема НЕ защищает (честные ограничения):**

- подмена команды установки ВМЕСТЕ с ключом в канале, откуда пользователь её копирует
  (например, злоумышленник контролирует то, что пользователь читает). Закрепление работает,
  только если команда получена из независимого от зеркал источника; поэтому ключ
  дублируется в README, этом документе и каналах автора;
- компрометация машины пользователя до/во время установки (локальный малварь подменит и команду);
- «freeze»-атака: зеркало честно отдаёт СТАРУЮ подписанную версию (свежесть не гарантируется,
  гарантируется только подлинность). Смягчение: bootstrap при обновлении репозитория
  дополнительно сверяет `bootstrap.sh.sha256` из репозитория;
- приватный ключ не защищён от кражи с машины релизера (защита — права 600, отсутствие
  ключа в git/логах; процедура ротации — ниже);
- устойчивость квантового компьютера к Ed25519 (академический риск, общий для всей
  индустрии на 2026 год).

**Почему не «sha256 из README»:** закреплённый хеш пришлось бы менять при каждом коммите,
ломая автоматизацию и разрывая доверие «команда из старого сообщения → новый файл».
Подпись позволяет одной командой (и одним ключом) верифицировать произвольное число
релизов. Почему не GPG: тяжёлая цепочка доверия (web of trust) и слабая предустановленность
`gpgv` на минимальных VPS; `openssl` есть везде (требование — 1.1.1+).

## 3. Требования к инструментам

| Инструмент | Версия | Зачем |
|---|---|---|
| bash | 4+ (Ubuntu 20.04+/Debian 11+ штатно) | блок установки (subshell-функция) |
| curl | любой с `-fsSL` | загрузка файла и подписи |
| openssl | >= 1.1.1 (Ed25519 + `-rawin`) | проверка подписи |

Ubuntu 20.04/22.04/24.04, Debian 11/12 — всё уже в базе. Alpine: `apk add bash curl openssl`.
Нет openssl / старый openssl → установка честно откажется (fail-closed), а не запустит непроверенное.

## 4. Ручная установка (wget / air-gap)

```bash
wget -O /tmp/bootstrap.sh     https://git.chimeraprodvpn.online/inferno1978/chimera/raw/branch/main/bootstrap.sh
wget -O /tmp/bootstrap.sh.sig https://git.chimeraprodvpn.online/inferno1978/chimera/raw/branch/main/bootstrap.sh.sig
# Публичный ключ — из раздела 2 ЭТОГО документа (не с зеркала!)
printf '%s\n' '-----BEGIN PUBLIC KEY-----' 'MCowBQYDK2VwAyEA+6KSAskfo+LBzW/io8q376wAULspfGTik674H1o8Gu4=' '-----END PUBLIC KEY-----' > /tmp/bootstrap.pub
openssl pkeyutl -verify -pubin -inkey /tmp/bootstrap.pub -rawin -in /tmp/bootstrap.sh -sigfile /tmp/bootstrap.sh.sig \
    && bash /tmp/bootstrap.sh
```

Файл `scripts/bootstrap-release/bootstrap.pub` в репозитории — справочная копия ключа
(используется pre-commit hook и тестами). Как источник доверия при ручной проверке
использовать его НЕЛЬЗЯ (лежит на тех же зеркалах, что и подписываемый файл).

## 5. Процесс публикации релиза

1. Изменения `bootstrap.sh` готовятся в ветке/рабочей копии как обычно.
2. Релизер подписывает:
   ```bash
   CHIMERA_SIGN_KEY=/root/.signing/chimera-bootstrap-ed25519.pem \
       bash scripts/bootstrap-release/sign_bootstrap.sh
   ```
   Скрипт: подписывает raw-Ed25519 (`openssl pkeyutl -sign -rawin`), сразу проверяет
   парность с `scripts/bootstrap-release/bootstrap.pub`, печатает sha256 и отпечаток ключа,
   отказывается работать, если приватный ключ лежит внутри репозитория.
3. `git add bootstrap.sh bootstrap.sh.sig && git commit` — pre-commit hook:
   - перегенерирует `bootstrap.sh.sha256`;
   - требует `bootstrap.sh.sig` в staged и проверяет подпись **staged-блобов** относительно
     staged (или HEAD) публичного ключа;
   - без подписи коммит блокируется (обход `CHIMERA_ALLOW_UNSIGNED_BOOTSTRAP=1` — только
     dev-ветки, не для main).
4. `git push forgejo HEAD:main` — hook фан-аута на сервере Forgejo разливает один и тот же
   коммит (значит, и `.sh`, и `.sig` из одного снимка) в GitLab (`chimera-v5`) и GitHub (`main`).
   Атомарность: оба файла всегда из одного коммита, «старый скрипт + новая подпись» на зеркалах
   невозможна (это один и тот же push).
5. Проверка после релиза (обязательный контроль):
   ```bash
   for u in \
     https://git.chimeraprodvpn.online/inferno1978/chimera/raw/branch/main/bootstrap.sh \
     https://gitlab.com/netwalker071778/chimera-project/-/raw/chimera-v5/bootstrap.sh \
     https://raw.githubusercontent.com/inferno1978/Chimera-Project/main/bootstrap.sh; do
     curl -fsSL "$u" -o /tmp/bs && curl -fsSL "$u.sig" -o /tmp/bs.sig \
       && openssl pkeyutl -verify -pubin -inkey /tmp/bootstrap.pub -rawin -in /tmp/bs -sigfile /tmp/bs.sig
   done
   ```
   (плюс тест `tests/test_secure_bootstrap.py::TestLiveMirrors` при явном запуске с доступом в сеть).

**Восстановление после частично завершившейся синхронизации:** если фан-аут упал после
успешного пуша в GitLab, но до GitHub — зеркала на разных коммитах; каждое всё ещё
внутренне консистентно (своя пара `.sh`+`.sig` из своего коммита), установка работает
с любого. Починка: повторный запуск `systemctl start chimera-mirror` на сервере Forgejo
(идемпотентный push обоих файлов).

## 6. Ротация ключей

1. Сгенерировать новую пару (на машине релизера, вне репозитория):
   ```bash
   openssl genpkey -algorithm ed25519 -out /root/.signing/chimera-bootstrap-ed25519-v2.pem
   openssl pkey -in /root/.signing/chimera-bootstrap-ed25519-v2.pem -pubout -out bootstrap-v2.pub
   ```
2. Заменить `scripts/bootstrap-release/bootstrap.pub` на новый; обновить PEM в команде
   установки во всех четырёх местах (README, INSTALL.md, VLESS_FAQ.md, VK_BYPASS_FAQ.md) —
   тест `test_secure_bootstrap.py::test_pubkey_consistency` не пустит рассинхрон.
3. Переподписать: `CHIMERA_SIGN_KEY=…-v2.pem bash scripts/bootstrap-release/sign_bootstrap.sh`.
4. Коммит + пуш + верификация всех зеркал (раздел 5). Новая команда установки — в каналы автора.
5. Старый приватный ключ уничтожить (`shred -u`), старый отпечаток внести в список отозванных
   (список ниже), чтобы сообщество могло отличить «подписано старым ключом» = подозрительно.

**Отозванные (retired) отпечатки:** (пока пусто — ключ №1 активен)

## 7. Действия при компрометации

**Компрометация зеркала (подмена файлов):**
1. Не паниковать: подпись не сойдётся, пользователи в безопасности (fail-closed).
2. Восстановить консистентность: force-push канонического коммита через фан-аут
   (`systemctl start chimera-mirror` на Forgejo-сервере) — перезапишет зеркальные ветки.
3. Проверить все зеркала верификацией из раздела 5.

**Компрометация приватного ключа (подпись могла уйти злоумышленнику):**
1. Немедленная ротация (раздел 6) — новый ключ, переподпись, новая команда установки.
2. Публикация advisory в каналах автора с отпечатком старого ключа (внести в retired).
3. Усиление: пока пользователи не скопировали новую команду, старая команда + ключ
   злоумышленника остаются валидными — поэтому advisory должен быть заметным (закреп в TG,
   issue на всех хостингах).
4. Расследование, как утёк ключ (машина релизера/сервер Forgejo), закрыть вектор.

## 8. FAQ

**Почему команда стала многострочной?** Однострочник `bash <(curl …)` физически не может
проверить подпись до исполнения: поток уже уходит в bash. Верификация требует, чтобы файл
сначала лёг на диск. Это единственный способ сохранить «одну команду» и не жертвовать безопасностью.

**Можно ли по-прежнему `bash <(curl …)`?** Нет. Прежние однострочники удалены из всех
документов проекта: они исполняют непроверенный сетевой поток. Если увидели такой где-то —
это устаревший скриншот/совет, не используйте.

**Почему подпись лежит на том же зеркале, что и скрипт?** Подпись — не секрет: её подделка
без приватного ключа невозможна. Зеркало может отдать ЛЮБУЮ подпись — проверка всё равно
провалится, если файл изменён. Критично лишь то, чтобы ПУБЛИЧНЫЙ ключ был закреплён в команде,
а не скачивался.

**Что если зеркало отдаёт старую, но подписанную версию?** Установится старая версия
(целостность есть, свежести нет). Это осознанный компромисс; обновление самого репозитория
внутри bootstrap дополнительно сверяет `bootstrap.sh.sha256` из репозитория.
