# AdGuard Home — FAQ по DNS-серверу с фильтрацией в Chimera

Это подробный гайд по AdGuard Home (AGH) в проекте Chimera. Описаны все
нюансы: зачем Chimera ввела ещё один DNS-слой поверх DNSCrypt, что даёт
связка Xray + AdGuard Home + DNSCrypt и в чём её минусы, как проходит
установка (миграция с нулевым даунтаймом, мастер первого запуска,
финализация), какие режимы Web UI и порты предлагаются, как устроен
канонический конфиг, как пользоваться AGH после установки и как
с DNS-стеком соседствует DPI-обход b4.

> **AdGuard Home** — DNS-сервер с веб-интерфейсом от AdGuard Team.
> Фильтрует рекламу, трекеры и вредоносные домены на уровне DNS, кеширует
> ответы и раздаёт шифрованные DNS-эндпоинты (DoH/DoT/DoQ). В Chimera
> работает на `127.0.0.1:53` поверх DNSCrypt-proxy (`127.0.0.1:5300`),
> который отвечает за шифрование запросов к upstream-резолверам.

## 1. Зачем Chimera ввела AdGuard Home

### Что было до AGH

До появления AGH DNS-стек Chimera состоял из двух участников:

```
приложения (glibc) + Xray
        ↓
DNSCrypt-proxy (127.0.0.1:5300) — шифрование
        ↓
Cloudflare / Google / Quad9 (DoH/DNSCrypt)
```

DNSCrypt-proxy решает ровно одну задачу — **шифрование**. Он прячет
DNS-запросы от провайдера и DPI, защищает от подмены ответов и не даёт
утечек к провайдерскому DNS. Всё это подробно описано в
[DNSCRYPT_FAQ.md](DNSCRYPT_FAQ.md).

### Чего не хватало

У «голого» DNSCrypt-proxy есть принципиальные ограничения, которые
с ростом проекта стали ощущаться всё сильнее:

1. **Нет фильтрации.** Рекламные и трекинговые домены спокойно
   резолвятся. Каждый баннер, каждая аналитика мобильного приложения,
   каждый телеметрический зонд — всё это проходит через DNS без
   препятствий. Блокировать приходилось на каждом клиенте отдельно
   (uBlock Origin в браузере, AdGuard на телефоне) — а клиенты Xray
   (SmartTV, IoT, чужие приложения) блокировать вообще не умели.
2. **Нет кеша.** DNSCrypt умеет кешировать, но его кеш скромнее, а
   главное — при перезапуске службы он остаётся без накопленного
   состояния. Повторяющиеся запросы от glibc-процессов (а их на живом
   сервере тысячи) каждый раз упираются в полный цикл
   шифрование → upstream → расшифровка.
3. **Нет интерфейса.** Управление — правкой TOML-конфига. Посмотреть,
   «какой домен резолвился и почему», невозможно: нет журнала запросов,
   нет статистики, нет кнопки «заблокировать этот домен».
4. **Нет публичных шифрованных DNS-эндпоинтов.** DNSCrypt слушает
   только loopback. Использовать сервер как личный зашифрованный DNS
   для телефона или ноутбука (мимо блокировок публичных DoH/DoT) было
   нечем.

### Решение: слой AGH поверх DNSCrypt

Chimera добавляет AdGuard Home **вторым слоем** — между клиентами и
DNSCrypt:

```
приложения (glibc) + Xray
        ↓
AdGuard Home (127.0.0.1:53) — фильтры + кеш + Web UI + DoH/DoT/DoQ
        ↓
DNSCrypt-proxy (127.0.0.1:5300) — шифрование
        ↓
Cloudflare / Google / Quad9 (DoH/DNSCrypt)
```

Ключевая идея: **роли разделены**. AGH не занимается шифрованием —
он получает уже готовый к использованию upstream на loopback и сам
остаётся простым локальным DNS-сервером. DNSCrypt не занимается
фильтрацией — он остаётся узкоспециализированным шифровальным
прокси. Каждый слой делает одно дело и делает его хорошо.

### Происхождение решения

Связка AGH + DNSCrypt не придумана с нуля — она обкатана годами на
роутерах (скрипт `install-dnscrypt-v7.23-usb.sh`). В Chimera эта связка
переработана под VPS: шифрованный bootstrap, отдельный пользователь
вместо root, UFW-политика «нет open resolver», интеграция с
port_registry, гарантии живости DNS и headless-установка без браузера.

### Почему именно AdGuard Home, а не альтернативы

| Решение | Web UI | DoH/DoT/DoQ сервер | Фильтры из коробки | Язык | Вердикт для Chimera |
|---|---|---|---|---|---|
| **AdGuard Home** | ✅ встроенный | ✅ нативно, один TLS-порт | ✅ встроенный менеджер списков | Go, один бинарник | **выбран** |
| Pi-hole | ✅ (PHP+FTL) | ❌ нужен отдельный слой | ✅ | PHP/Shell | тяжелее стек, нет нативного DoH/DoT |
| Blocky | ❌ только конфиг | ✅ | ✅ списки в YAML | Go | нет UI — не подходит для TUI-проекта |
| unbound + блок-листы | ❌ | ✅ (DoT/DoQ) | ⚠️ ручная сборка | C | рекурсор вместо форвардера; lists вручную |

AGH выигрывает по совокупности: один статический бинарник, нативный
Web UI, один сертификат и один TLS-порт сразу на DoH + DoT + DoQ +
HTTPS-панель, встроенное управление списками фильтров с обновлением.

### Что AGH НЕ делает

- **Не шифрует DNS сам.** Шифрование — задача нижнего слоя
  (DNSCrypt). AGH общается с upstream по loopback в plain — это
  нормально, трафик не покидает сервер.
- **Не блокирует рекламу внутри HTTPS-страниц.** DNS-фильтрация
  отсекает целые домены (doubleclick.net, telemetry.example), но
  баннер, загружаемый с того же домена, что и контент, DNS не увидит.
  Для этого нужны клиентские блокировщики в браузере.
- **Не ускоряет первый запрос к редкому домену.** Промах кеша —
  полный цикл AGH → DNSCrypt → upstream. Ускоряются повторные запросы.
- **Не фильтрует трафик Xray-клиентов напрямую.** Клиенты VPN
  резолвят домены через Xray, а Xray уже идёт на `127.0.0.1:53` —
  то есть фильтрация работает для них автоматически, но сам AGH про
  VPN ничего не знает.

### Аналогия

| Без AGH | С AGH |
|---|---|
| Консьержка (DNSCrypt) принимает письма в запечатанных конвертах и передаёт курьеру — но пропускает и рекламные каталоги, и счёт за чужой ремонт | Перед консьержкой появился фильтр на входе (AGH): макулатура — сразу в корзину, обычные письма — в запечатанный конверт и к консьержке; повторные адреса — из картотеки, не спрашивая курьера |

## 2. Архитектура: связка Xray + AGH + DNSCrypt

### Общая схема

```
                ┌──────────────────────────────────────────────┐
                │                VPS (Chimera)                 │
                │                                              │
  glibc-процессы│   Xray (VPN-ядро)                            │
  (curl, apt,   │        │ dns-запросы клиентов                 │
  git, python)  │        │                                      │
        │       │        │                                      │
        └───────┴──┬─────┘                                      │
                   ▼                                            │
        AdGuard Home (127.0.0.1:53)                             │
          • фильтры: AdGuard DNS + AdAway + OISD Big            │
          • кеш 4 MB, optimistic                                │
          • Web UI + DoH :30443 / DoT :853/tcp / DoQ :853/udp   │
                   │                                            │
                   ▼                                            │
        DNSCrypt-proxy (127.0.0.1:5300)                         │
          • шифрование: DNSCrypt / DoH                          │
          • upstream: Cloudflare, Google, Quad9 …                │
                   │                                            │
                   ▼                                            │
        Интернет (зашифрованный DNS-трафик)                     │
                └──────────────────────────────────────────────┘
```

### Цепочка запроса по шагам

1. Приложение (или Xray, резолвящий домен для VPN-клиента) отправляет
   DNS-запрос на `127.0.0.1:53` — это адрес из `/etc/resolv.conf`.
2. AGH проверяет домен по блок-листам (AdGuard DNS filter + AdAway +
   OISD Big). Реклама/трекер → мгновенный `0.0.0.0`, upstream не
   беспокоится.
3. Чистый домен → просмотр кеша (4 MB, ~десятки тысяч записей).
   Свежая запись отдаётся мгновенно; устаревшая (TTL истёк) — отдаётся
   сразу (optimistic cache), а обновление уходит в фон.
4. Промах кеша → запрос на единственный upstream `127.0.0.1:5300`.
5. DNSCrypt шифрует запрос и отправляет к выбранному резолверу
   (Cloudflare и др.). Провайдер видит зашифрованный трафик.
6. Ответ возвращается по цепочке, кешируется в AGH, отдаётся клиенту.

Параллельно работают публичные TLS-эндпоинты AGH: DoH на
`:30443/tcp` (тот же порт, что и Web UI HTTPS), DoT на `:853/tcp`,
DoQ на `:853/udp`. Внешние клиенты (телефон, ноутбук вне VPN) могут
использовать сервер как личный шифрованный DNS.

### Разделение ролей

| Слой | Зона ответственности | Чего НЕ делает |
|---|---|---|
| **Xray** | Маршрутизация VPN-трафика; DNS-запросы клиентов отправляет на `127.0.0.1:53` | Не резолвит сам (кроме служебных нужд), не фильтрует |
| **AdGuard Home** | Фильтрация, кеш, Web UI, DoH/DoT/DoQ для внешних клиентов, статистика | Не шифрует upstream, не видит VPN-клиентов |
| **DNSCrypt-proxy** | Шифрование запросов к публичным резолверам, анонимизация (опционально) | Не фильтрует, не кеширует для glibc, не принимает внешний трафик |

### Порядок запуска systemd

```
dnscrypt-proxy.service
        ↓ (After=)
AdGuardHome.service
        ↓ (Before=)
xray.service → nginx.service → chimera-dns-fix.service
```

Порядок задан в unit-файле AGH: `Wants=dnscrypt-proxy.service`,
`After=network.target network-online.target dnscrypt-proxy.service`,
`Before=xray.service nginx.service chimera-dns-fix.service`.
Логика: upstream (dnscrypt) поднимается раньше AGH, клиенты AGH
(xray) — позже. Служба работает от выделенного системного
пользователя `adguard` с `CAP_NET_BIND_SERVICE` (право слушать
привилегированный :53) и `NoNewPrivileges=yes` — **не от root**.
Рестарт — `Restart=on-failure` через 5 секунд.

## 3. Что даёт установка

### Фильтрация рекламы и трекеров на уровне сервера

Главный эффект. Все три списка (AdGuard DNS filter, AdAway, OISD Big)
включены сразу и покрывают миллионы доменов: рекламные сети,
трекеры, метрики, телеметрию, фишинг. Фильтрация работает для
каждого, кто использует этот DNS — glibc-процессы сервера, Xray (а
значит, и все VPN-клиенты), внешние клиенты DoH/DoT/DoQ. Не нужно
ставить блокировщик на каждое устройство: SmartTV, IoT-железо и
чужие приложения, которые нельзя настроить, фильтруются просто
потому, что их DNS-запросы проходят через сервер.

### Кеш 4 MB с optimistic-режимом

AGH кеширует до 4 MB записей (десятки тысяч доменов). Повторный
запрос обрабатывается за микросекунды, не выходя из процесса.
`cache_optimistic: true` — ключевая опция: когда TTL записи истёк,
AGH всё равно мгновенно отдаёт устаревший ответ и параллельно
обновляет его в фоне. Для пользователя это выглядит как «DNS стал
быстрее», хотя физически запрос просто перестал блокировать
ожиданием upstream.

### Web UI — управление и наблюдение

Панель на `https://домен:30443` (или по выбранному режиму из
раздела 9): дашборд со статистикой (запросов/заблокировано за
24 часа, top-домены, top-клиенты), журнал запросов с поиском и
фильтрами, управление списками фильтров и пользовательскими
правилами, настройки службы. Из журнала запросов домен блокируется
или разблокируется одним кликом — правило попадает в `user_rules`.

### Личный шифрованный DNS для внешних устройств

Установка AGH поднимает публичные эндпоинты:

- **DoH:** `https://домен:30443/dns-query`
- **DoT:** `домен:853` (TCP)
- **DoQ:** `домен:853` (UDP, QUIC)

Телефон или ноутбук вне VPN получает личный зашифрованный DNS с
фильтрацией и без блокировок публичных резолверов. Android
подключается через «Частный DNS» (это DoT), iOS — через профиль
DoH, браузеры — через Secure DNS.

### Валидация DNSSEC

`enable_dnssec: true` — AGH проверяет электронные подписи DNSSEC и
отбрасывает подделанные ответы. Подмена DNS-ответа злоумышленником
(кэш-отравление, атака на upstream) становится обнаруживаемой.

### Защита от абьюза

Сервер не превращается в open resolver: `:53` закрыт снаружи UFW.
Плюс встроенные ограничения: `ratelimit: 20` запросов в секунду с
одной подсети (/24 IPv4, /56 IPv6), `refuse_any: true` (отказ на
тяжёлые ANY-запросы — классика DNS-amplification), блокировка
CHAOS-запросов `version.bind` / `id.server` / `hostname.bind`
(не раскрываем версию и имя сервера).

### Единая точка управления DNS

Раньше поведение DNS настраивалось в трёх местах: TOML dnscrypt,
iptables-redirect и resolv.conf. Теперь профиль «что блокировать,
что кешировать, кого пускать» живёт в одном месте — Web UI AGH,
а инфраструктурные гарантии (шифрование, живость) — в Chimera.

## 4. Плюсы связки Xray + AGH + DNSCrypt

### Шифрование и фильтрация одновременно

Классическая дилемма DNS — «либо зашифровано, либо фильтруется» —
здесь решена послойно: DNSCrypt даёт первое, AGH — второе. Никаких
компромиссов вроде «фильтруем только то, что видно в plain» или
«шифруем, но без блок-листов».

### DNS-фильтрация для VPN-клиентов «из коробки»

Xray отправляет резолвинг доменов клиентов на `127.0.0.1:53`.
Установили AGH — и каждый VPN-клиент автоматически получает
DNS без рекламы, независимо от того, что у него настроено на
устройстве. На стороне клиента менять ничего не нужно.

### Личный шифрованный DNS вместо публичного

Публичные DoH/DoT-эндпоинты (Cloudflare, Google, AdGuard DNS)
в некоторых сетях деградируют или блокируются целиком. Свой
эндпоинт на собственном VPS: DoH на нестандартном порту `:30443`
(мимо типовых блокировок :443/:853), DoT/DoQ на `:853`, сертификат
домена сервера, фильтрация и статистика — ваши.

### Разделение ответственности

Поломка фильтров не ломает шифрование, а перенастройка dnscrypt
не трогает пользовательские правила AGH. Диагностика проще:
каждый слой тестируется независимо (`dig @127.0.0.1` — AGH,
`dig @127.0.0.1 -p 5300` — dnscrypt).

### Миграция и откат с нулевым даунтаймом

Установка AGH не останавливает DNS ни на секунду: пока AGH
поднимается, трафик :53 обслуживает iptables-redirect на
dnscrypt (подробнее в разделе 7). Удаление — обратный откат
к redirect за один пункт меню. DNS жив на каждом шаге обеих
операций — это проектная гарантия, а не удача.

### Гарантии живости DNS

Chimera обволакивает связку защитами: проверка фактическим
запросом перед/после каждой фазы установки, watchdog каждую
минуту, persist-сервис с AGH-aware логикой после ребута
(раздел 16). Смерть любого одного компонента не оставляет
систему без DNS дольше пары минут.

### Интеграция с port_registry

Все порты AGH (:53, :3000, :30443, :853 tcp/udp, :5300) заведены
в реестр портов Chimera. Установка/активация открывает нужные
порты в UFW автоматически, удаление/деактивация — закрывает
(раздел 13). Нет «забытых» открытых портов после удаления.

### Headless-установка без браузера и туннелей

Мастер первого запуска завершается прямо в SSH-сессии: логин и
пароль вводятся в TUI, конфиг пишет сам AGH через свой API на
loopback. Не нужны ни браузер, ни SSH-туннель, ни временные
дыры в фаерволе (раздел 8).

### Изоляция привилегий

AGH работает от системного пользователя `adguard` с минимальным
набором возможностей (`CAP_NET_BIND_SERVICE` только для :53/:853,
`NoNewPrivileges`), а не от root. Вздумайте сравнить с типовой
установкой `curl | sh` из документации AGH, которая стартует
службу от root.

### Идемпотентная финализация

Финализацию можно запускать сколько угодно раз (пункт 5 меню):
она приводит конфиг к каноническому виду Chimera, не ломая то,
что уже правильно. После ручных экспериментов в Web UI один
пункт меню возвращает канон.

### Observability

Журнал запросов (retention 90 дней) + статистика по доменам,
клиентам и типам блокировок. Можно увидеть, какой именно домен
сломал приложение, найти и разблокировать его за секунды.

## 5. Минусы и ограничения связки

Честный список — без прикрас. Часть минусов Chimera компенсирует
механизмами, часть остаётся свойством архитектуры.

### Лишний слой задержки на промахе кеша

Первый запрос к редкому домену проходит на одну пересадку больше:
AGH → DNSCrypt → upstream. На практике это единицы миллисекунд на
loopback, и для повторных запросов связка быстрее голого dnscrypt
за счёт кеша — но синтетический «холодный» DNS-бенчмарк проиграет
однослойной схеме.

### +1 служба = +1 точка отказа

Схема из двух DNS-служб статистически отказывает чаще, чем из
одной: у AGH свои конфиг, сертификаты и процесс. Chimera
компенсирует это watchdog-ом (раздел 16) и лестницей self-heal
(раздел 10) — отказ самовосстанавливается за минуты. Но сложность
системы выросла объективно: понять, «кто сломал DNS», теперь
значит проверить два слоя.

### False positives фильтров

OISD Big — агрессивный список: вместе с рекламой периодически
отсекаются CDN-домены, платежные виджеты, части мобильных
приложений. Симптом — «сайт открывается наполовину» или «приложение
не логинится». Лечение — журнал запросов в Web UI → найти
заблокированный домен → «Разблокировать» (правило попадает в
`user_rules`). При консервативном сценарии можно отключить OISD Big в
Web UI и оставить AdGuard DNS filter.

### Приватность: журнал запросов на 90 дней

Query log и statistics включены по решению владельца сервера: кто
пользуется сервером — тот и видит, что резолвилось (включая домены
VPN-клиентов). На сервере для семьи это фича; на сервере с
недоверенными пользователями — вопрос. Отключается штатно:
Web UI → Настройки → Журнал запросов (retention/выключение).

### Открытые TLS-порты видны сканерам

:30443 и :853 отвечают всему интернету — неизбежная цена публичных
DoH/DoT/DoQ. Сканеры находят их за часы. Защита: TLS + пароль на
Web UI, кастомный plain-порт (раздел 9), ratelimit. Отдельный нюанс:
:853 — стандартный DoT-порт, который некоторые сети блокирует
нацело; DoH на :30443 обычно выживает лучше.

### Потребление памяти

AGH с загруженными списками (сотни тысяч правил в трёх фильтрах)
занимает заметно больше RAM, чем простой dnscrypt — ориентируйтесь
на десятки–сотню МБ RSS. На VPS с 512 MB это уже фактор; на 1 GB+
— незаметно.

### Сложность отладки для новичка

«DNS не работает» теперь имеет в два раза больше причин: AGH
(конфиг, фильтры, сертификаты) и dnscrypt (upstream, шифрование).
Chimera частично снимает боль статус-боксом и diagnostic-командами
(раздел 21), но понимать двухслойность всё равно придётся.

### Тонкости plain-порта :3000

В TLS-режимах AGH биндит `http.address` на `0.0.0.0:3000` — это
свойство AGH: HTTPS-порт :30443 наследует хост из секции `http`.
Chimera закрывает :3000 изнутри UFW, так что снаружи он не отвечает —
но знать об этом бинде стоит: любой локальный процесс на сервере
может открыть Web UI без TLS.

### Кому связка не подойдёт

- Минималистам: «хочу только шифрованный DNS, ничего больше» —
  не ставьте AGH, оставьте чистый DNSCrypt (вопрос N на шаге 12/12).
- Серверам под тяжестью DNS-фильтрации сотен клиентов: AGH
  справляется, но односерверный DNS для организации — уже другая
  задача.
- Тем, кому нельзя логировать запросы даже локально: сначала
  отключите query log в UI, потом решайте.

## 6. Когда ставить AGH, а когда — нет

### ✅ Когда нужно ставить

- **Сервер для себя/семьи** — максимальная выгода: фильтрация,
  статистика, личный DoH для всех устройств.
- **Клиенты Xray жалуются на рекламу в приложениях** — DNS-слой
  отсекает рекламные SDK без настройки клиентов.
- **Нужен личный шифрованный DNS вне VPN** — телефон в кафе,
  ноутбук в отеле: DoT/DoH на вашем домене.
- **Нужна диагностика DNS** — «какой домен ломается» решается
  журналом запросов за секунды.
- **Мало RAM на клиентских устройствах** — фильтрация переехала
  на сервер, клиентам не нужен свой блокировщик.
- **Хочется кеша** — стабильные сервисы перестают ходить к upstream.

### ❌ Когда НЕ нужно ставить

- **Минимализм / дефицит RAM** — каждый компонент должен
  оправдывать своё существование; dnscrypt-only проще и легче.
- **Категорическое нежелание логировать** — query log включён
  по умолчанию (отключается, но AGH без него теряет половину
  пользы).
- **Страх лишнего слоя** — если двухслойность пугает, поддержка
  будет раздражать.
- **DNS-абуз-сценарии** (организация с сотнями пользователей) —
  нужен специализированный кластер, не VPS-стек.

### Рекомендация по умолчанию

В мастере установки Chimera AGH предлагается как рекомендуемый
вариант (Y по Enter). Для персонального/семейного VPN-сервера
ответ почти всегда «да»: связка отработана, откат тривиален,
а выгода накапливается каждый день. Если сомневаетесь — начните
без AGH; поставить позже можно в любой момент: `Сеть → A → 1`,
миграция займёт пару минут и не уронит DNS.

## 7. Установка: процесс по шагам

### Два пути установки

| Путь | Где | Когда |
|---|---|---|
| Мастер установки | Шаг [12/12] «AdGuard Home» — сразу после вопроса про DNSCrypt | Свежий сервер, ставим всё с нуля |
| TUI-меню | `Сеть → A → 1` — Установить/переустановить | На живом сервере в любой момент |

Оба пути вызывают одну функцию `install_aghome()` — разница только
в контексте.

### Предусловие: DNSCrypt-proxy активен

AGH в Chimera не имеет собственных шифрованных upstream — его
единственный upstream это `127.0.0.1:5300`. Поэтому установка
проверяет: если dnscrypt-proxy не активен — отказ с подсказкой
сначала установить DNSCrypt. Без dnscrypt AGH не ставится вовсе.

### Шаг 0: проверка живости DNS

Перед любыми действиями Chimera делает **фактический** DNS-запрос
к `127.0.0.1:53` (dig/getent). Мёртвый системный DNS — стоп-сигнал:
без него не скачается бинарник (GitHub «недоступен»), а сервер
останется без резолвинга. Если probe не прошёл — выполняется
восстановление: redirect 53→5300 + resolv.conf, и только потом
установка продолжается.

### Шаг 1: скачивание бинарника

1. Определение архитектуры (`uname -m` → amd64/arm64/armv7/armv6/armv5/386).
2. Запрос последнего release-тега к GitHub API (3 попытки).
3. Если API недоступен — pinned-версия `v0.107.62` + зеркала:
   GitHub-прокси и официальный CDN AdGuard `static.adtidy.org`
   (работает при блокировках GitHub).
4. Скачивание через общий download-менеджер Chimera
   (`fetch_package`): tar.gz, распаковка, установка в
   `/usr/local/bin/AdGuardHome`.

Уже установленный бинарник не перетирается — версия показывается,
скачивание пропускается.

### Шаг 2: пользователь и директории

Создаётся системный пользователь `adguard` (без shell, без home в
обычном смысле), рабочая структура:

```
/usr/local/bin/AdGuardHome          — бинарник
/opt/AdGuardHome/                   — рабочая директория (working dir)
/opt/AdGuardHome/AdGuardHome.yaml   — конфиг (chmod 640, owner adguard)
/opt/AdGuardHome/data/              — служебные данные
/opt/AdGuardHome/certs/             — TLS-сертификаты (agh-tls.crt/key)
```

### Шаг 3: миграция dnscrypt с :53 (нулевый даунтайм)

Ключевой трюк установки. Исторически dnscrypt мог слушать
`127.0.0.1:53` (старые ручные фиксы). Чтобы AGH забрал :53, dnscrypt
переводится на `127.0.0.1:5300`:

1. `listen_addresses` в TOML переписывается на `127.0.0.1:5300`,
   dnscrypt рестартуется.
2. **До** этого в nat-таблицу добавляется redirect: локальный
   `:53` (udp + tcp) → `:5300`. Системный DNS не прерывается ни
   на один запрос — трафик :53 просто переезжает на новый порт
   dnscrypt.
3. Redirect живёт с комментарием `chimera-dns-fix` и будет снят
   финализацией, когда :53 займёт AGH.

### Шаг 4: systemd-unit и старт в режиме мастера

Пишется `/etc/systemd/system/AdGuardHome.service` (порядок запуска
и изоляция — раздел 2), служба enable + restart. Дальше развилка:

- **Конфига нет** (свежая установка) → AGH стартует в режиме
  мастера первого запуска: поднимается только web-интерфейс на
  `:3000`, DNS-сервер не запускается. :53 в это время держит
  redirect → dnscrypt. Дальше — раздел 8.
- **Конфиг есть** (переустановка) → мастер не нужен, сразу
  финализация (раздел 10) каноническим конфигом поверх
  существующего.

### Что видно по завершении

```
✓ AGH: бинарник установлен: /usr/local/bin/AdGuardHome
✓ AGH: служба активна (мастер первого запуска)
✓ AGH: администратор создан — мастер завершён без браузера
✓ AGH: DNS слушает :53 (udp+tcp)
✓ AGH: DoH+HTTPS слушает :30443/tcp
✓ AGH: DoT слушает :853/tcp
✓ AGH: DoQ слушает :853/udp
✓ AGH: redirect 53→5300 снят, системный DNS → AGH :53
✓ AGH: финализация завершена — DNS: AGH:53 → dnscrypt:5300
```

## 8. Мастер первого запуска: headless или браузер

### Семантика первого запуска AGH

AGH при старте без конфиг-файла входит в режим first-run
(проверено по исходникам, `internal/home/home.go::detectFirstRun`):

- поднимается **только** web-интерфейс на `0.0.0.0:3000` с мастером;
- DNS-сервер не стартует, пока мастер не завершён;
- мастер отправляет `POST /control/install/configure` — AGH сам
  пишет yaml с учёткой администратора (пароль — bcrypt) и стартует
  DNS;
- пустой `users` в существующем конфиге = lockout (любой логин
  отклонён) — поэтому пароль задаётся мастером, а не пустым users.

Из этого следует главное: **пока мастер не завершён, :53 держит
redirect → dnscrypt**. Системный DNS жив, спешки нет.

### Путь 1: headless (рекомендуется)

Установщик спрашивает: «Без браузера (рекомендуется)» или
«Веб-мастер http://IP:3000». Headless-путь:

1. Логин и пароль администратора вводятся прямо в TUI
   (пароль дважды, без эха, минимум 6 символов).
2. Chimera отправляет `POST /control/install/configure` на
   **loopback** `127.0.0.1:3000` — те же самые endpoints, что
   дергает кнопка «Далее» в браузерном мастере.
3. AGH пишет конфиг с users и запускает DNS на `127.0.0.1:53`.
4. Установщик дожидается секции `users` в yaml — мастер завершён.

Ничего не требуется кроме SSH-сессии: ни браузера, ни SSH-туннеля,
ни временно открытого порта в UFW, ни публичного IP. Путь не
зависит от сетевой обстановки между вами и сервером.

### Путь 2: веб-мастер (fallback)

Если headless не подошёл (неинтерактивный запуск, желание всё
видеть глазами):

1. Порт `:3000` временно открывается в UFW **для всех** — туннели
   не нужны (доступ только с IP SSH-клиента ломался при CGNAT,
   смене IP и прокси, поэтому выбран универсальный вариант).
2. TUI печатает инструкцию: откройте `http://IP-СЕРВЕРА:3000`,
   задайте логин/пароль. В самом мастере выбирайте: веб-интерфейс —
   «Все интерфейсы», DNS-сервер — «Только 127.0.0.1 (Loopback)» —
   Chimera перенастроит адреса сама.
3. Установщик ждёт до 5 минут (`AGH_WIZARD_WAIT_SEC = 300`),
   полля конфиг на появление `users`.
4. По завершении порт :3000 закрывается финализацией.

### DNS во время мастера

Ожидание мастера не ослабляет гарантий: в цикле ожидания
периодически пробится системный DNS (`127.0.0.1:53`) и активность
самой службы AGH. Redirect чинится на лету, если отвалился.

### Если мастер так и не завершён

Установка не считается провалом: служба стоит, DNS работает через
redirect, состояние — `phase: wizard`. Завершить позже:
`Сеть → A → 2` (статус + «Ждать завершения сейчас?»). Или сменить
пароль позже — `Сеть → A → 3`.

## 9. Режимы Web UI и кастомный порт

### Четыре режима Web UI

При установке (и в любой момент через `Сеть → A → 4`) выбирается
режим доступа к панели управления:

| # | Режим | Адрес панели | TLS | Доступ снаружи | Кому подходит |
|---|---|---|---|---|---|
| 1 | **HTTPS + Let's Encrypt** (рекомендуется) | `https://домен:30443` | ✅ сертификат домена | ✅ | Домен есть — дефолт |
| 2 | HTTPS + self-signed | `https://IP:30443` | ⚠️ браузер предупредит | ✅ | Нет домена, но нужен доступ |
| 3 | HTTP публично | `http://IP:3000` (или кастомный порт) | ❌ пароль открытым текстом | ✅ | Только доверенные сети |
| 4 | Только локально | `http://127.0.0.1:3000` | ❌ | ❌ (SSH-туннель) | Максимальная паранойя |

Если домен не задан (или пустой ввод) — режим 1 автоматически
переключается на режим 2.

### Один TLS-порт на всё: почему :30443

Внутреннее свойство AGH: HTTPS-порт (`port_https`) обслуживает
**одновременно** DoH-эндпоинт (`/dns-query`) и Web UI, и биндится
на тот же хост, что указан в `http.address`. Отдельной настройки
«хост для TLS» у AGH нет. Поэтому:

- в TLS-режимах (1 и 2) секция `http` биндится на `0.0.0.0:3000`,
  иначе :30443 остался бы loopback-only и панель была бы недоступна
  без туннеля;
- plain-порт :3000 при этом **закрыт изнутри UFW** — снаружи он не
  отвечает, публично живёт только TLS :30443;
- DoH и панель делят один порт и один сертификат — никаких
  дополнительных портов и сертификатов.

### Кастомный порт Web UI (plain)

Режимы 3 и 4 слушают plain-HTTP порт. По умолчанию это :3000, но
при установке (и через `Сеть → A → 4`) Chimera спрашивает порт —
можно задать любой свободный.

**Что управляет кастомный порт:**
- адрес панели в режиме «HTTP публично» — `http://IP:ВАШ_ПОРТ`;
- локальный вход в режиме «Только локально» —
  `http://127.0.0.1:ВАШ_ПОРТ`.

**Что НЕ меняет:** основной вход в TLS-режимах остаётся
`https://домен:30443` — он не кастомизируется.

**Правила валидации порта:**

| Правило | Причина |
|---|---|
| Диапазон 1024–65535 | Привилегированные порты требует root |
| Не из служебного набора {22, 53, 80, 443, 853, 5300, 30443} | SSH, DNS-стек, веб-стандарты и TLS-порт AGH — заняты |
| Свободен по port_registry (`port_is_free`) и `ss` | Порт не должен конфликтовать с другими службами Chimera |

Валидация идёт через port_registry с исключением собственного тега
`aghome_web` — смена порта самой панелью конфликтом не считается.

**Механика применения:** wizard-фаза мастера всегда живёт на
дефолтном :3000 (AGH без конфига слушает только его). Кастомный
порт записывается в payload мастера и применяется финализацией.
При смене порта на уже работающей установке старый порт закрывается
в UFW и снимается с регистрации — порты не «текут».

### Смена режима позже

`Сеть → A → 4` — выбирается режим (и порт), значение сохраняется
в state, конфиг переприменяется финализацией немедленно (если
мастер завершён). Сертификат LE подтянется автоматически, self-signed
сгенерируется на лету.

## 10. Финализация: канонический конфиг Chimera

### Что это

Мастер первого запуска пишет минимальный конфиг (users + адреса).
Финализация (`finalize_aghome_config()`) приводит его к канону
Chimera — хирургически, заменяя отдельные секции yaml, не трогая
остальное:

| Секция | Что ставится |
|---|---|
| `http` | адрес/порт Web UI по выбранному режиму |
| `dns` | upstream dnscrypt:5300, bind_hosts, кеш, ratelimit (раздел 11) |
| `tls` | порт 30443/853/853 + путь к сертификату (или disabled) |
| `filters` | три списка (раздел 12) |
| `whitelist_filters` | пусто — наполняется из Web UI |
| `user_rules` | пусто — наполняется из Web UI |
| `querylog` | включён, ретенция 90 дней |
| `statistics` | включена, ретенция 90 дней |
| `dhcp` | отключён (VPS — не роутер) |
| `language` | `ru` |

Перед записью — бэкап текущего конфига в
`/root/aghome-backups/AdGuardHome.yaml.<время>.bak`, после записи —
`chown adguard:adguard`, `chmod 640`, рестарт.

### Полный конвейер финализации

1. Чтение yaml; требование: непустой `users` (мастер завершён).
2. Подготовка TLS-сертификата: копия Let's Encrypt домена или
   генерация self-signed (раздел 17).
3. Хирургическая замена секций (таблица выше).
4. Перезапись yaml + права + рестарт + ожидание active.
5. Верификация портов **по имени процесса** AdGuardHome:
   :53/udp, :53/tcp, :30443/tcp, :853/tcp, :853/udp (с retry —
   AGH биндит порты на 1–3 секунды позже, чем systemd помечает
   службу активной).
6. Снятие redirect 53→5300 — теперь :53 держит AGH. Вызывается
   `fix_resolv_conf_to_localhost(force=True)` с AGH-aware веткой:
   она же перегенерирует persist-скрипт, чтобы redirect не вернулся
   после ребута.
7. Закрытие временных wizard-правил UFW + регистрация финальных
   портов в port_registry (раздел 13).
8. Перегенерация конфига Xray: DNS Xray → `127.0.0.1:53` (через
   AGH, кеш и фильтры).
9. Запись state: `phase: finalized`, режим, порт, домен, метка
   времени.

### Лестница self-heal

Если AGH не поднялся после записи канонического конфига:

1. **Self-heal 1:** переписать секцию `dns` с bind_hosts без
   публичного IP (loopback-only) — типовая причина падения,
   если IP изменился. Рестарт.
2. **Self-heal 2:** откат к yaml мастера (бэкап из шага перед
   записью) — DNS работает на дефолтных секциях, канон можно
   повторить позже.
3. **Self-heal 3 (критично):** вернуть redirect 53→5300 —
   системный DNS не должен умирать даже ценой отказа финализации.

Для TLS-портов — свой heal: если :30443/:853 не поднялись,
снимается точная причина из journalctl, проверяется пара
сертификат/ключ и права пользователя adguard, чинится
(chown / self-signed fallback / рестарт), tls-секция
перезаписывается в live-конфиге.

### Идемпотентность

Все шаги финализации безопасно выполняются повторно: сертификат
уже на месте — копия пропускается, redirect уже снят — не трогается,
UFW-правила дубликаты не плодит. Поэтому пункт 5 меню
(«Переприменить конфиг») — штатный способ вернуть канон после
ручных экспериментов в Web UI или ручной правки yaml.

## 11. Параметры конфига: что значит каждый

Каноническая секция `dns:` — что и почему. Файл:
`/opt/AdGuardHome/AdGuardHome.yaml`.

### `upstream_dns` — `['127.0.0.1:5300']`

Единственный upstream — локальный DNSCrypt. Весь исходящий DNS
шифруется нижним слоем. Прямых публичных upstream у AGH нет
принципиально — иначе появлялась бы plain-утечка мимо DNSCrypt.

### `bootstrap_dns` — `['127.0.0.1:5300', '9.9.9.9:53', '1.1.1.1:53']`

Bootstrap нужен, чтобы резолвить имена DoH-upstream'ов. Основной
bootstrap — тоже dnscrypt (улучшение относительно роутерного скрипта,
где bootstrap был plain 9.9.9.9). Plain-адреса 9.9.9.9/1.1.1.1 —
страховка на случай мёртвого dnscrypt; при живом слое они не
используются: наш upstream — IP-адрес, резолвить нечего.

### `fallback_dns` — `['9.9.9.9:53', '1.1.1.1:53']`

Куда идёт запрос, если основной upstream не ответил (dnscrypt
умер/завис). Осознанный компромисс «DNS важнее шифрования»:
лучше plain-ответ, чем таймаут. Уровень защиты тот же, что был
на роутере годами.

### `upstream_mode: parallel` + `fastest_timeout: 1s`

Параллельный режим актуален при нескольких upstream (с fallback) —
запрос уходит одновременно всем, побеждает самый быстрый. С одним
upstream поведение вырождается в обычный запрос.

### `cache_size: 4194304`, `cache_optimistic: true`, `cache_ttl_min/max: 0`

Кеш 4 MB (~десятки тысяч записей). TTL границы не искажаются
(`0/0` — уважать upstream), но устаревшая запись всё равно
отдаётся мгновенно с фоновым обновлением (optimistic) — компромисс
«микросекундная свежесть» вместо «полный круг к upstream».

### `ratelimit: 20` (+ subnet /24 IPv4, /56 IPv6)

Лимит запросов в секунду с одной подсети — защита от абьюза и
зацикленных клиентов. 20 qps с /24 — с огромным запасом для
легитимного трафика.

### `refuse_any: true` и `blocked_hosts`

ANY-запросы (используются в DNS-amplification атаках) — отказ.
CHAOS-запросы `version.bind`/`id.server`/`hostname.bind` — блок:
не раскрываем версию и имя сервера сканерам.

### `enable_dnssec: true`

Валидация DNSSEC-подписей: подделанные ответы отбрасываются.

### `trusted_proxies: ['127.0.0.0/8', '::1/128']`

Кому верить заголовки X-Forwarded-For — только loopback (тот же
сервер). Чужие прокси не подменят IP-клиента в статистике.

### `serve_http3: true`, `serve_plain_dns: true`

HTTP/3 (QUIC) для DoH-эндпоинта — включён. Plain DNS на :53 —
включён (это и есть основной служебный вход).

### `querylog` / `statistics` — enabled, `interval: 2160h`

Журнал запросов и статистика: ретенция 90 дней (2160 часов),
затем ротация файлов. `size_memory: 1000` — буфер записи.
Отключается штатно в Web UI → Настройки.

### `dhcp: enabled: false`

DHCP-сервер AGH отключён — VPS не раздаёт адреса в LAN.

### `language: ru`

Язык Web UI.

приложений). По умолчанию пусто.

## 13. Порты, UFW и port_registry

### Карта портов AGH

| Порт | Прото | Тег port_registry | Назначение | Снаружи (UFW) |
|---|---|---|---|---|
| 53 | udp+tcp | `aghome` | DNS — вход для glibc и Xray | ❌ закрыт |
| 3000* | tcp | `aghome_web` | Web UI plain (wizard, режимы 3/4) | по режиму; в TLS-режимах ❌ |
| 30443 | tcp | `aghome_doh` | DoH + Web UI HTTPS (native TLS AGH) | ✅ при TLS-режиме |
| 853 | tcp | `aghome_dot` | DoT | ✅ при TLS-режиме |
| 853 | udp | `aghome_doq` | DoQ (QUIC) | ✅ при TLS-режиме |
| 5300 | udp+tcp | `dnscrypt` | dnscrypt-proxy — upstream AGH | ❌ loopback |

\* :3000 — если выбран кастомный порт, в реестре фигурирует он
(старый закрывается и снимается).

### Почему :53 закрыт снаружи

AGH биндится на `127.0.0.1` **и** публичный IP (второй нужен для
DoT/DoQ/DoH на :853/:30443), но UFW **не открывает** :53 наружу:
иначе сервер стал бы open resolver — бесплатным участником
DNS-amplification атак и целью абуз-жалоб. Loopback-трафик
(glibc, Xray) ходит на 127.0.0.1:53 свободно, внешним клиентам
предназначены шифрованные DoH/DoT/DoQ.

### Как port_registry управляет портами AGH

Реестр портов Chimera (`chimera/modules/port_registry.py`) — единая
точка учёта: кто какой порт занимает. API: `port_register`,
`port_unregister`, `ufw_open_port`, `ufw_close_port`,
`port_list_for_service`, `port_is_free`.

**Установка/финализация** (`_register_aghome_ports`) — идемпотентно:

```
port_register(dnscrypt, 5300, udp+tcp, force)    — loopback upstream
port_register(aghome, 53, udp+tcp, force)         — UFW не открываем
port_register(aghome_web, WEB_ПОРТ, tcp, force)
   + ufw_open/aghome_web  — только в режиме «HTTP публично»
   + ufw_close            — в остальных режимах (loopback/TLS)
при TLS-режиме:
   port_register + ufw_open — aghome_doh 30443/tcp
                              aghome_dot 853/tcp
                              aghome_doq 853/udp
при смене web-порта: старые записи тега aghome_web закрываются
в UFW и снимаются с регистрации (порт не течёт)
```

**Удаление** (`_unregister_aghome_ports`):

```
для каждого тега (aghome, aghome_doh, aghome_dot, aghome_doq):
    ufw_close_port + port_unregister
для aghome_web: ВСЕ порты тега из реестра + дефолт 3000 + порт из
state (кастомные порты прошлых установок не остаются висеть)
dnscrypt :5300 НЕ трогается — он продолжает служить системе
```

Итог: после `Сеть → A → 9` в UFW не остаётся ни одного AGH-правила,
а в реестре — ни одной AGH-записи.

## 14. Клиенты: как пользоваться AGH

### Серверные клиенты — ничего настраивать не надо

После финализации все резолверы сервера уже идут через AGH:

- **glibc** — `/etc/resolv.conf` указывает на `127.0.0.1`
  (поддерживается resolv-фиксом Chimera);
- **Xray** — конфиг перегенерирован: dns-сервер `127.0.0.1:53`.
  Значит, и все VPN-клиенты, чей трафик резолвится на сервере,
  получают фильтрованный DNS автоматически;
- **systemd-resolved** — при наличии работает как stub и
  форвардит на 127.0.0.1.

Проверка без инструментов: `curl ya.ru` работает, а в журнале
AGH появились запросы — значит, цепочка живая.

### Внешние клиенты: личный шифрованный DNS

Телефон, ноутбук, планшет вне VPN подключаются к эндпоинтам AGH:

| Протокол | Адрес | Где настраивать |
|---|---|---|
| DoH | `https://домен:30443/dns-query` | Браузер (Secure DNS → свой провайдер), iOS (профиль описания), Android-приложения, любые DoH-клиенты |
| DoT | `домен:853` | Android: Настройки → Сеть → «Частный DNS» → имя хоста. iOS — через профиль. Десктоп-клиенты |
| DoQ | `домен:853` (UDP/QUIC) | Поддерживается немногими клиентами (AdGuard for Android, digq) |

Нюансы:
- DoT/DoQ требуют валидный сертификат (режим Let's Encrypt) —
  Android Private DNS отклоняет self-signed;
- :853 — стандартный DoT-порт; если сеть его режет, используйте
  DoH на :30443;
- для DoH в браузере порт указывается прямо в URL провайдера.

### Клиенты VPN (Xray)

Ничего не меняется: клиент отправляет домены в туннель, Xray
резолвит их на сервере через AGH. Фильтрация применяется к
браузерному трафику клиента без установки чего-либо на его
устройстве. Если клиент хочет «свой» DNS даже вне VPN — выдаёте
ему DoH/DoT-эндпоинт сервера.

## 15. B4 (DPI-обход): сосед в стеке Xray + AGH + DNSCrypt

### Зачем эта секция

На entry-VPS рядом с DNS-стеком может жить ещё один сетевой механизм —
**b4 (Bye Bye Big Bro)**: DPI-обход для YouTube и других
заблокированных ресурсов. b4 не входит в DNS-стек: он не фильтрует
рекламу и не шифрует запросы — его работа в другом, мутировать
исходящие TLS-пакеты так, чтобы ТСПУ не смогла сопоставить SNI. Но
b4 и DNS-стек делят одно ядро: одни цепочки nftables, одни и те же
порты :53 и :443. Эта секция описывает, как связка
Xray → AGH → DNSCrypt → Интернет работает при включённом b4: где b4
вмешивается, где принципиально нет и что проверить в настройках.
Полное руководство по самому b4 — [DPI_BYPASS_FAQ.md](DPI_BYPASS_FAQ.md).

### Полная цепочка: от клиента до интернета

Клиент подключается по VLESS Reality (ТСПУ такой трафик не видит —
handshake замаскирован под обычный TLS к разрешённому сайту) и
отправляет в туннель запросы к доменам. На entry-VPS одновременно
работают две плоскости — DNS и трафик:

```
Клиент (VLESS Reality — ТСПУ не видит)
    │
    ▼
Xray inbound (entry-VPS)
    │ routing: geosite:youtube → direct, остальное → exit-ноды
    │
    │ ПЛОСКОСТЬ DNS: freedom нужен IP для direct-выхода
    ▼
AdGuard Home (127.0.0.1:53, UDP)      ← b4 НЕ перехватывает:
    │ фильтры → кеш → upstream          loopback исключён из правил
    ▼
DNSCrypt-proxy (127.0.0.1:5300)       ← b4 НЕ перехватывает:
    │ шифрование                        порт вне правил (:53/:443)
    ▼
Cloudflare / Google / Quad9 (:443)    ← проходит ТРАНЗИТОМ через
    │                                   очередь b4, SNI не совпадает
    ▼                                   с сетами → без изменений
IP-адрес → Xray → freedom открывает TCP к IP:443
    │
    │ ПЛОСКОСТЬ ТРАФИКА: исходящее соединение
    ▼
nftables mangle OUTPUT → NFQUEUE 537 → b4   ← ЗДЕСЬ b4 активен
    │ SNI youtube.com совпал с сетом:
    │ decoy-ClientHello + фрагментация + fake RST
    ▼
ТСПУ не может собрать SNI → пропускает
    ▼
YouTube CDN → Интернет
```

### Прогон по шагам (запрос youtube.com от VPN-клиента)

1. Клиент отправляет домен прямо в туннеле — DNS на его стороне
   не нужен.
2. Routing Xray отправляет `geosite:youtube` в outbound `direct`
   (freedom); всё остальное уходит зашифрованным на exit-ноды.
   SNI внутри туннеля b4 недоступен, поэтому «YouTube через RU
   entry» — обязательное условие работы b4.
3. Freedom нужен IP: Xray спрашивает свой DNS — `127.0.0.1:53`
   (UDP; запись появляется при финализации AGH). Это loopback-пакет,
   а первая строка output-цепочки b4 — `oifname "lo" return`:
   **весь loopback выведен из-под перехвата**, запрос доходит до
   AGH нетронутым.
4. AGH проверяет блок-листы (реклама/трекер → `0.0.0.0`), кеш,
   промах отправляет на единственный upstream `127.0.0.1:5300`.
   Порт 5300 в правила b4 не входит — DNSCrypt получает запрос
   напрямую.
5. DNSCrypt шифрует запрос и открывает соединение к публичному
   резолверу на :443 (DoH — TCP, DNSCrypt-протокол — UDP). Эти
   пакеты попадают в очередь b4, но SNI `cloudflare-dns.com` /
   `dns.google` не совпадает ни с одним сетом — пакеты пропускаются
   без изменений. Цена — микросекунды на первые пакеты соединения.
6. IP возвращается в Xray, freedom открывает TCP к `IP:443`.
7. Начало соединения попадает в NFQUEUE: b4 читает SNI, находит
   `youtube.com` в сете → отправляет decoy-ClientHello с чужим SNI,
   режет реальный ClientHello на фрагменты, при необходимости
   инжектит fake RST.
8. ТСПУ не может собрать SNI → соединение проходит → видео грузится.
   Ответ идёт обратно обычным путём.

### Кто чем владеет: карта пересечений

| Путь на сервере | Владелец | Роль b4 |
|---|---|---|
| glibc / Xray → `127.0.0.1:53` (UDP) | **AGH** | нет — loopback исключён |
| glibc / Xray → `127.0.0.1:53` (TCP, редкий путь) | b4 :5453 → AGH | перехват + пересылка (ниже) |
| AGH → `127.0.0.1:5300` | **DNSCrypt** | нет — порт вне правил |
| DNSCrypt → резолверы :443 | Интернет | транзит через очередь, без изменений |
| Xray → YouTube CDN :443 | Интернет | **активный DPI-обход (fake SNI)** |
| Xray → exit-ноды :443 | VLESS-туннель | транзит, без изменений |
| Внешний клиент → DoH :30443 / DoT :853 / DoQ :853 | **AGH** | нет — порты вне правил |
| Внешний клиент → :53 plain | закрыт UFW | перехват в PREROUTING (нюанс ниже) |

### Правила b4: что реально стоит в системе

b4 управляет правилами сам (native nftables, IPv4 + IPv6, таблица
`inet b4_mangle`). Упрощённо, но с сохранением сути:

```
table inet b4_mangle {
    chain output {
        oifname "lo" return                       # loopback выведен
        meta mark & 0x8000 == 0x8000 accept       # собственные пакеты b4
        jump b4_mangle                            # стратегии сетов
        udp dport 53 counter queue num 537 bypass # исходящий plain-DNS
        udp sport 53 counter queue num 537 bypass # ответы plain-DNS
    }
    chain prerouting {
        udp dport 53 counter queue num 537 bypass # входящий plain-DNS
        udp sport 53 counter queue num 537 bypass
        # + SYN-ACK/RST-фазы TCP-соединений (reply-side)
    }
    chain b4_mangle {
        tcp dport 443 ct original packets < 20 … queue  # первые ~20
        udp dport 443 ct original packets < 9  … queue  # первые ~9
    }
}
table ip b4_dnsnat {          # существует, пока у включённого сета
    chain dnstcp_pre { tcp dport 53 redirect to :5453 }  # задан
    chain dnstcp_out { tcp dport 53 redirect to :5453 }  # DNS-резолвер
}
```

Три свойства, на которых держится совместимость со стеком:

1. **`oifname "lo" return`** — loopback-трафик (весь внутренний
   DNS-обмен: Xray → AGH, AGH → DNSCrypt) не попадает в перехват.
   DNS-плоскость AGH + DNSCrypt работает так, как будто b4 нет.
2. **`ct original packets < 20`** — в очередь уходит только начало
   соединения (ClientHello и несколько пакетов дальше), установленный
   поток ядро пропускает само. Накладные расходы транзитного :443
   (upstream DNSCrypt, туннели к exit-нодам) — микросекунды на
   установку соединения, а не на каждый пакет.
3. **`bypass` в queue-правилах** — если очередь без слушателя (b4
   остановлен или упал, а правила остались), ядро **принимает**
   пакеты, а не роняет. Падение b4 не рвёт ни трафик, ни DNS —
   просто исчезает DPI-обход.

### DNS-плоскость: что b4 перехватывает, а что нет

**Не перехватывает (основной путь — 99% запросов):**

- Xray → AGH по UDP (loopback);
- AGH → DNSCrypt `:5300` (порт вне правил);
- публичные DoH `:30443` / DoT `:853` / DoQ `:853` — шифрованные
  клиенты AGH с b4 вообще не встречаются (порты не :443/:53).

**Перехватывает (побочные пути):**

- **TCP:53 с самого сервера.** nat-правило b4 заворачивает такие
  соединения в собственный слушатель `:5453`. Домены, совпавшие с
  сетом (при включённом в сете перенаправлении DNS), b4 резолвит
  сам; остальные пересылает по исходному адресу назначения — то
  есть в AGH (с mark, минуя собственные правила). На практике Xray
  обращается к TCP-DNS редко: запись `tcp` в его dns.servers —
  резервная.
- **Внешний UDP:53.** Перехватывается в PREROUTING — раньше, чем
  фильтр UFW отбросит пакет. Для чужих клиентов это не открывает
  резолвер: несовпавшие с сетами запросы идут транзитом и гибнут в
  UFW; совпавшие — см. нюанс ниже.
- **Служебные plain-запросы наружу**: bootstrap DNSCrypt
  (`1.1.1.1:53`, `8.8.8.8:53`), bootstrap/fallback AGH
  (`9.9.9.9:53`, `1.1.1.1:53`), инертные fallback-записи Xray
  (`skipFallback: true` — фактически не используются). Все они
  проходят через очередь b4 и продолжают путь без изменений.

### Микро-нюанс: :53 «приоткрывается» для доменов сетов

Если у сета включено «Перенаправление DNS» и задан резолвер
(DoH-адрес или IP), b4 на перехваченных запросах доменов этого сета
отвечает сам — от имени сервера, до UFW. Наружу сервер отвечает на
закрытом :53 по доменам активных сетов: сканер увидит, что
`youtube.com` и прочие домены сетов «резолвятся». Это не open
resolver — все остальные домены молчат (транзит роняет UFW). Если
такое поведение нежелательно — выключите перенаправление DNS в
сетах: без него b4 прозрачен для DNS.

### Что прописать в настройках b4: чек-лист

| # | Правило | Зачем |
|---|---|---|
| 1 | Ставить b4 только через меню Chimera (`Сеть → Y → B` или `Сеть → B`) | Chimera пишет совместимый конфиг и регистрирует порты в port_registry |
| 2 | Включить «YouTube через RU entry» (`Сеть → Y → 1`) | Без `geosite:youtube → direct` SNI зашифрован в туннеле — b4 нечего перехватывать |
| 3 | Не создавать сет-заглушку `regexp:.*` с перенаправлением DNS или Block | Catch-all перехватит весь plain-DNS в зоне видимости b4: уведёт его с AGH или убьёт |
| 4 | Не добавлять домены DNS-резолверов (`cloudflare-dns.com`, `dns.google`, `dns.quad9.net`) в сеты — и тем более в Block | Upstream DNSCrypt и так зашифрован; Block на таком домене рвёт upstream |
| 5 | Не использовать домены сетов как REALITY dest/SNI для exit-нод | Туннели к exit-нодам идут через очередь b4: совпадение SNI включит стратегии на собственном туннеле |
| 6 | В сете «Перенаправление DNS» → обычный DNS `127.0.0.1`, а не внешний DoH | b4 остаётся прозрачным: домены сетов идут через AGH → DNSCrypt, единая DNS-плоскость |
| 7 | Импорт кастомных сетов — только через TUI Chimera (пункт 3), не через Web UI | Chimera нормализует wildcard-домены, выставляет `enabled`, прописывает `system.geo.sitedat_path` и чистит legacy-поля (DPI_BYPASS_FAQ §7) |

По пунктам 1–2 Chimera позаботилась бы и сама, а вот пункты 3–6 —
зона ручной дисциплины: их нарушение не ломает стек сразу, но
меняет DNS-картину незаметно (запросы начинают обходить AGH).

### Нюансы сетов в Web UI b4

- **Вкладка Sets** — включение/выключение сетов, Discovery,
  Import/Export. После импорта сета через TUI обновите страницу
  (F5) — сет появится в списке.
- **DNS & Маршрутизация сета → Перенаправление DNS**: выключено
  (b4 прозрачен для DNS) / DoH-адрес (b4 резолвит сам) / обычный
  DNS (рекомендуется `127.0.0.1` — через AGH). Если заполнены оба
  поля, приоритет у DoH-адреса.
- **Режим Block** — sinkhole: домены сета получают NXDOMAIN на
  перехваченных запросах. Никогда не совмещать с catch-all.
- **Закреплённые адреса (pins)** — работают только для доменов,
  уже входящих в цели сета; TTL ответа — 60 секунд.
- Сет, созданный прямо в Web UI (Discovery → Create Set), может
  содержать `geosite_categories` — для них валидация b4 требует
  `system.geo.sitedat_path` (Chimera прописывает путь к geosite.dat
  Xray). Рабочий путь при проблемах: Discovery → Use This Strategy →
  Create Set → три точки на карточке → Edit → Import/Export →
  Copy JSON → удалить сет → импорт через TUI Chimera (пункт 3).
  QUIC-блок — per-set: включается переключателем «Блокировать QUIC»
  (карточка сета → UDP).
- Модули «YouTube через B4» и «DPI Bypass» работают с одним конфигом
  `/etc/b4/config.json` и одним сервисом — изменения видны в обоих
  меню (подробно — DPI_BYPASS_FAQ §13).

### Отказоустойчивость: кто чью смерть переживает

| Сценарий | Что происходит |
|---|---|
| Умер AGH | Watchdog за минуту ставит redirect 53→5300. UDP-loopback идёт напрямую — b4 в пути нет; TCP:53 попадает в b4 и пересылается на исходный адрес, где его подхватывает redirect Chimera. DNS жив при любом порядке nat-правил (b4: 53→5453, Chimera: 53→5300 — разные таблицы) |
| Умер / перезапускается b4 | Флаг `bypass`: пакеты очереди без слушателя принимаются ядром. Трафик и DNS идут дальше — без DPI-обхода. AGH и DNSCrypt этого даже не замечают |
| b4 удалён | Chimera убирает правила, binary, конфиг, nginx front и порты из port_registry (9700/5453/9743). DNS-стек не затрагивается |
| Ребут | b4 стартует после xray (`After=xray.service`); зависимостей с AGH/DNSCrypt нет — плоскости независимы |

### Плюсы и минусы четвёртого слоя

**Плюсы:**

- Заблокированные ресурсы (YouTube) идут напрямую с entry-VPS, а не
  через exit-ноды: меньше нагрузка на туннели, ниже задержка.
- Клиенту ничего ставить не надо — обход живёт на сервере.
- Нулевое пересечение с DNS-плоскостью на основном пути: фильтрация
  и кеш AGH продолжают работать, b4 их не замечает.
- Fail-open (`bypass`): смерть b4 не роняет ни трафик, ни DNS.

**Минусы:**

- +1 служба, +1 слой в каждом исходящем :443-соединении (начало
  соединения обрабатывается в userspace).
- ТСПУ адаптируется: пресеты и сеты надо периодически обновлять
  через Discovery — это отдельная забота.
- DNS-картина усложняется: на побочных путях (TCP:53, внешний :53)
  появляется ещё один резолвер — b4 с per-set политикой.
- Правила b4 живут в mangle/nat до UFW (filter): поведение «до
  фаервола» нужно держать в голове при отладке.

### Диагностика связки

```bash
# Правила b4 живы? (пустой вывод/ошибка = таблицы нет, b4 не запущен)
nft list table inet b4_mangle

# Ключевая строка совместимости — первая в output-цепочке:
nft list chain inet b4_mangle output | head -3
# ожидаемо: oifname "lo" return

# DNS-over-TCP редирект (появляется при DNS-резолвере в сете)
nft list table ip b4_dnsnat

# DNS-стек работает при живом b4
dig @127.0.0.1 ya.ru +short
dig @127.0.0.1 doubleclick.net +short      # 0.0.0.0 — фильтры живы
dig @127.0.0.1 -p 5300 ya.ru +short        # dnscrypt жив

# Статус и логи b4
systemctl status b4 --no-pager
journalctl -u b4 -n 30 --no-pager
```

Если `dig @127.0.0.1` отвечает, а YouTube через VPN не грузится —
проблема не в DNS-стеке: смотрите журнал b4, переключите пресет
(`Сеть → Y → B → 2`) или запустите health check
(`python3 -m chimera.modules.youtube_b4 health`).

## 16. Надёжность DNS: защиты Chimera

### Философия

**Живость важнее фильтрации.** Redirect 53→5300 при живом AGH
лишь обходит фильтры для локальных процессов (внешние клиенты
всё равно попадают в AGH), а мёртвый DNS означает: git pull
не работает, пакеты не ставятся, сертификаты не обновляются,
сервер «слепой». Поэтому все механизмы ниже нацелены на одно:
`127.0.0.1:53` отвечает всегда.

### Проверка фактом, а не правилом

Ключевой принцип: успешный код возврата фикса ≠ работающий DNS.
Во всех критичных точках Chimera делает **фактический запрос**
(dig `@127.0.0.1` / getent) и верит только ему. Любой DNS-ответ
(NOERROR или NXDOMAIN) = путь жив; таймаут/refused = мёртв.

### DNS-alive гарантия (`_ensure_system_dns_alive`)

Вызывается перед/после каждой фазы: перед установкой, после
провала скачивания, после провала миграции, после провала старта,
во время ожидания мастера, после удаления. Лестница восстановления
(после каждой ступени — фактический probe):

1. Полный resolv-фикс: resolv.conf + nsswitch + redirect обоих
   протоколов + persist-сервис (AGH-aware — не мешает живому AGH).
2. Рестарт AdGuardHome, если он активен и должен держать :53.
3. Рестарт dnscrypt (если лежит) + прямые iptables-redirect
   53→порт dnscrypt, оба протокола.

Если лестница не помогла — красный бокс с ручными командами
(iptables + dig), чтобы администратор чинил руками.

### Watchdog: `chimera-dns-watchdog`

Постоянный надзор, когда никто не сидит в меню:

- `chimera-dns-watchdog.timer` срабатывает **каждые 60 секунд**;
- probe `127.0.0.1:53`; при отказе — повтор через 3 секунды
  (анти-флап: транзиентная нагрузка смертью не считается);
- не отвечает → ветка AGH: если AdGuardHome активен — рестарт
  службы, снова probe;
- всё ещё не отвечает → ветка dnscrypt: рестарт dnscrypt-proxy
  (если лежит) + redirect 53→порт dnscrypt (idempotent, оба
  протокола), снова probe;
- все действия пишутся в journal: `journalctl -t
  chimera-dns-watchdog`.

Итог: смерть AGH (креш, OOM, зависание) самовосстанавливается
не дольше чем за минуту + время рестарта, а в самом тяжёлом
случае DNS переезжает на redirect к dnscrypt — система остаётся
с резолвингом, теряя только фильтры.

### Persist после ребута

`chimera-dns-fix.service` (проверяется при загрузке) —
**AGH-aware**: при живом AGH redirect не ставится (AGH сам
владеет :53), при мёртвом — ставится. Ребут не может оставить
систему без DNS и не может «затопить» AGH лишним redirect-ом.

### Строгий YAML-парсер AGH

Конфиг AGH валидируется жёстко: дубли top-level ключей = отказ
стартовать. Хирургия секций Chimera защищена от этого тремя
барьерами: генераторы секций пишут каждый ключ ровно один раз;
безопасная дедупликация перед записью; GATE перед записью — при
обнаружении дублей живой конфиг не трогается вовсе.

## 17. Сертификаты: Let's Encrypt и self-signed

### Режим HTTPS + Let's Encrypt (рекомендуется)

Используется сертификат домена сервера — тот же, что у Xray
(выпускается при установке Chimera). Финализация копирует пару
в `/opt/AdGuardHome/certs/agh-tls.crt` + `agh-tls.key`,
выставляет владельца `adguard` и прописывает пути в секцию
`tls:`.

**Обновление без участия человека:** certbot при каждом renew
запускает deploy-hook
`/etc/letsencrypt/renewal-hooks/deploy/chimera-aghome.sh`, который
синхронит свежий сертификат в AGH и рестартует службу. Хук ставится
при финализации и снимается при удалении.

### Режим HTTPS + self-signed

Если домена нет, Chimera генерирует self-signed пару (CN = IP или
localhost) прямо в `/opt/AdGuardHome/certs/`. DoH/DoT/DoQ и панель
работают, но:
- браузер показывает предупреждение (придётся «Дополнительно →
  перейти»);
- Android Private DNS (DoT) self-signed не принимает — этот
  клиентский сценарий недоступен;
- переключиться на LE можно в любой момент: `Сеть → A → 4` →
  режим 1 → указать домен.

### Проверка сертификата

```bash
# Какой сертификат обслуживает :30443:
openssl s_client -connect 127.0.0.1:30443 </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates

# Пара сертификат/ключ совпадает (сравнить pubkey):
openssl x509 -in /opt/AdGuardHome/certs/agh-tls.crt -noout -pubkey
openssl pkey -in /opt/AdGuardHome/certs/agh-tls.key -pubout
```

## 18. Web UI: повседневная работа

### Дашборд

Главная страница: счётчики за 24 часа (запросы, заблокированные,
среднее время обработки), круговая диаграмма типов блокировок,
топ-домены, топ-клиенты, топ-блокировщики. Быстрая проверка
«всё живое»: цифры крутятся — DNS идёт через AGH.

### Журнал запросов

Список всех DNS-запросов: время, клиент, домен, статус
(заблокирован/кеширован/upstream), тип, ответ, правило. Фильтры по
домену/клиенту/статусу. Главный рабочий инструмент при «что-то
сломалось»: ищете домен, смотрите статус. Если заблокирован не
тем, чем нужно — кнопки «Заблокировать»/«Разблокировать» прямо
из журнала создают правило в `user_rules`.

### Фильтры

Списки блокировок: статус, число правил, дата обновления.
«Проверить обновления» — принудительный рефреш. «Добавить
фильтр» — свой URL (любой hosts/adblock-формат). Пользовательские
правила — редактор `user_rules` списком.

### Клиенты

Если в сети есть постоянные клиенты (по IP), им можно задать
индивидуальные теги и правила — например, «детский» профиль с
дополнительным списком или, наоборот, отключение фильтрации для
конкретного устройства.

### Настройки

- Общие: язык, порт панели, статистика/журнал (включение,
  ретенция, игнор-листы).
- DNS: upstream, кеш, ratelimit — **осторожно**: ручные правки
  здесь живут до следующей финализации (`Сеть → A → 5` вернёт
  канон Chimera).
- Шифрование: сертификаты, TLS-порты.
- Служебное: обновление AGH (рекомендуется обновляться через
  меню Chimera, чтобы сохранился канон).

### Что менять руками НЕ стоит

Upstream DNS (сломает шифрование через dnscrypt), порт :53
(сломает resolv.conf/Xray), bind_hosts (сломает DoT/DoQ на
публичном IP). Всё это — управляемые Chimera параметры; ручные
правки конфликтуют с каноном.

## 19. Удаление, сброс пароля, переприменение конфига

### Удаление (`Сеть → A → 9`)

Полный откат DNS-стека к состоянию «до AGH»:

1. Остановка и отключение службы, удаление unit-файла.
2. Бэкап `/opt/AdGuardHome` → `/root/aghome-backups/aghome-<дата>.tar.gz`
   (конфиг, фильтры, статистика — можно вернуть руками позже).
3. Удаление рабочей директории и бинарника.
4. Удаление пользователя `adguard`.
5. Снятие certbot deploy-hook.
6. Закрытие всех портов: UFW + port_registry — все теги AGH,
   включая кастомные web-порты прошлых установок (раздел 13).
7. Восстановление redirect 53→5300 — системный DNS снова через
   dnscrypt напрямую.
8. Перегенерация конфига Xray: DNS → `127.0.0.1:5300`.

В конце — фактическая проверка живости DNS (probe), при отказе
автовосстановление и, если не помогло, красный бокс с командами.
DNSCrypt :5300 не удаляется — он остаётся служить системой.

### Сброс пароля админа (`Сеть → A → 3`)

Пароль AGH — bcrypt; в окружении сервера нет инструментов его
подделать, поэтому сброс делается повторным мастером:

1. Стоп AGH, текущий yaml → бэкап (`.pre-reset.bak`), yaml удаляется.
2. Старт AGH → нет конфига → режим мастера (web :3000).
3. Новый логин/пароль: headless-API (по умолчанию, без браузера)
   или веб-мастер.
4. Финализация восстанавливает канонические секции из state —
   режим Web UI, домен, TLS, порт и фильтры не теряются.

Потеряны будут только изменения, сделанные руками в Web UI после
последней финализации (пользовательские правила живут в yaml —
они попадают в бэкап, но в новый конфиг не переносятся).

### Переприменение конфига (`Сеть → A → 5`)

Повторный запуск финализации с параметрами из state: канонические
секции, сертификат, redirect, UFW/реестр, Xray. Сценарии:
- после ручных правок yaml/Web UI «всё сломалось» — вернуть канон;
- после обновления AGH — убедиться, что конфиг валиден;
- профилактика — раз в сезон, чтобы конфиг не дрейфовал.

| 9 | 🗑️ Удалить AdGuard Home | Полный откат к dnscrypt:5300, порты закрыты, бэкап создан |

Бейдж в заголовке меню показывает фазу: `[OK]` — финализировано,
`[МАСТЕР НЕ ЗАВЕРШЁН]` — DNS держит redirect, завершить через
пункт 2.

## 21. Диагностика

### Статус из меню (`Сеть → A → 2`)

Бокс показывает: версию, состояние службы, DNS :53 (udp+tcp),
upstream dnscrypt, Web UI (порт + режим + слушается ли), TLS
(домен/self-signed), DoH/DoT/DoQ по портам, число фильтров,
query log/stats, путь конфига и бэкапов. Плюс предупреждение,
если мастер не завершён.

### Послойная проверка руками

```bash
# Слой 1 — AGH отвечает на :53? (должен вернуть IP)
dig @127.0.0.1 ya.ru +short +time=2 +tries=1

# Фильтры работают? (должен вернуть 0.0.0.0)
dig @127.0.0.1 doubleclick.net +short

# Слой 2 — dnscrypt отвечает на :5300?
dig @127.0.0.1 -p 5300 ya.ru +short

# Слушатели портов (по имени процесса — только AdGuardHome считается)
ss -tulnp | grep -E ':(53|3000|30443|853|5300)\b'

# Служба и её логи
systemctl status AdGuardHome --no-pager
journalctl -u AdGuardHome -n 50 --no-pager

# Логи watchdog (что чинил и когда)
journalctl -t chimera-dns-watchdog --since "1 hour ago"

# UFW-правила AGH
ufw status | grep -i adguard
```

### Типовые симптомы

| Симптом | Вероятная причина | Куда смотреть |
|---|---|---|
| DNS не отвечает на :53, `dig` таймаут | Служба лежит или зависла | `journalctl -u AdGuardHome`; watchdog должен был среагировать — его лог |
| :53 жив, :30443/:853 нет | TLS-секция не поднялась (сертификат/права) | journalctl по tls-ошибкам; раздел 17; `Сеть → A → 5` |
| Сайт «наполовину открывается» | Фильтр зарезал нужный домен | Журнал запросов → разблокировать |
| Web UI не открывается | Режим loopback; порт закрыт; не тот порт | `Сеть → A → 2` (порт и режим); UFW |
| Xray-клиенты без DNS | Конфиг Xray не перегенерирован | `Сеть → A → 5` (финализация перегенерирует) |
| git pull на сервере падает | Системный DNS мёртв | Раздел 16; watchdog-лог; красный бокс с командами |

### port_registry

Реестр хранит JSON с записями «сервис → порт/прото → комментарий».
Просмотр записей AGH — через список служб реестра (`port_list_for_service`
для тегов `aghome`, `aghome_web`, `aghome_doh`, `aghome_dot`,
`aghome_doq`). Полезно после переустановок: в реестре не должно
оставаться портов, которые никто не слушает.

## 22. Шпаргалка по командам

```bash
# ── Статус ─────────────────────────────────────────────────
systemctl status AdGuardHome --no-pager      # служба
ss -tulnp | grep AdGuardHome                 # слушатели по процессу
ufw status | grep -i adguard                 # правила фаервола

# ── DNS-проверки ───────────────────────────────────────────
dig @127.0.0.1 ya.ru +short                  # AGH жив?
dig @127.0.0.1 doubleclick.net +short        # фильтры живы? (0.0.0.0)
dig @127.0.0.1 -p 5300 ya.ru +short          # dnscrypt жив?

# ── Логи ───────────────────────────────────────────────────
journalctl -u AdGuardHome -n 100 --no-pager  # лог службы
journalctl -t chimera-dns-watchdog -n 50     # что чинил watchdog

# ── Служба ─────────────────────────────────────────────────
systemctl restart AdGuardHome                # рестарт
systemctl enable AdGuardHome                 # автозапуск (уже включён)

# ── Конфиг и бэкапы ────────────────────────────────────────
cat /opt/AdGuardHome/AdGuardHome.yaml        # конфиг (владелец adguard, 640)
ls /root/aghome-backups/                     # бэкапы yaml + tar.gz

# ── Внешние эндпоинты ──────────────────────────────────────
# DoH: https://домен:30443/dns-query
# DoT: домен:853 (tcp)
# DoQ: домен:853 (udp)
curl -s "https://домен:30443/dns-query?name=ya.ru" \
  -H 'accept: application/dns-json'

# ── Сертификат ─────────────────────────────────────────────
openssl s_client -connect 127.0.0.1:30443 </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates

# ── Экстренное восстановление DNS (если watchdog не успел) ──
iptables -t nat -A OUTPUT -p udp -d 127.0.0.1 \
  --dport 53 -j REDIRECT --to-ports 5300
iptables -t nat -A OUTPUT -p tcp -d 127.0.0.1 \
  --dport 53 -j REDIRECT --to-ports 5300
dig @127.0.0.1 github.com +time=2 +tries=1
```
