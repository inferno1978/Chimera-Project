# ИИ-агент на роутере + разблокировка Telegram: MCP, REST и живой кейс — FAQ

Это полный гайд по подключению ИИ-агента (Claude, GLM, любой CLI-ассистент
или приложение с поддержкой MCP) к b4, работающему на вашем роутере.
Описано всё: от включения MCP-сервера в b4 и открытия доступа по WAN до
разделения ролей «что делает ИИ / что делаете вы», встроенных защит и
сравнения этого подхода с классическими VLESS-туннелями. А во второй
половине — живой кейс: как этот же ИИ-агент за двое суток разобрался,
почему Telegram «отвалился», выстроил эшелон каналов и починил всё:
родной WS-edge, CF-пул Flowseal, socat-релей через VPS и CF Worker —
с объяснением, почему Discovery здесь бессилен и что включается при
отказе каждого слоя.

> **TL;DR:** b4 умеет говорить по протоколу MCP (Model Context Protocol) —
> стандарту, на котором внешние ИИ-приложения читают его состояние и
> (по вашему разрешению) меняют настройки. Ваша задача — включить
> MCP-сервер, сгенерировать токен и открыть сетевой путь до роутера.
> Дальше диагностика DPI-обхода, подбор сетов, переключение апстримов и
> чтение логов происходят без вашего участия — ИИ делает это сам, за
> минуты, с возможностью отката. Если сомневаетесь, зачем всё это
> нужно, — сразу листайте §5: реальная история «Переподключение через
> 4 секунды…» и её развязка средствами одного REST-доступа.

## 1. Что это такое: ИИ-агент у руля b4

b4 (см. [DPI_BYPASS_FAQ.md](DPI_BYPASS_FAQ.md)) — DPI-обход на вашем
роутере или VPS: перехватывает соединения к заблокированным сайтам и
пропускает их через рабочие стратегии (фрагментация, fake-пакеты, DNS).
У b4 есть Web UI, REST API и — с недавних версий — **встроенный
MCP-сервер**.

MCP (Model Context Protocol) — открытый протокол, через который внешние
ИИ-приложения (Claude Desktop, VS Code, Cursor, LM Studio, Jan, любой
CLI-агент) читают состояние программ и вызывают их инструменты.
Говоря проще: **b4 сам рассказывает ИИ, что он умеет, и ИИ может это
вызывать**. Никаких «научи модель командам» — список инструментов b4
отдаёт сам, при подключении.

Включаете MCP-сервер в b4 → генерируете токен → даёте ИИ endpoint и
токен → ИИ получает возможность:

- смотреть статус, сеты, конфиг, логи, метрики, недавние соединения;
- проверять, какой сет покрывает домен и дошла ли до него трафика;
- (если разрешили) менять настройки сетов и MTProto/SOCKS5-подсистем,
  с автоматическим откатом на «поставь как было».

Сам b4 никуда не ходит: он не обращается к провайдерам ИИ, не требует
API-ключей, ничего не отправляет наружу. Модель работает внутри вашего
ИИ-приложения, b4 только обслуживает его запросы на `/api/mcp`.

Важное следствие: «ИИ-агент на роутере» = **канал управления и
диагностики**, а не туннель для трафика. Он не возит ваши байты в
интернет — им по-прежнему занимаются сеты b4, VLESS-транспорт или
MTProto-мост. Он позволяет **обслуживать** всё это хозяйство без ручного
тыканья по меню.

## 2. Кому это нужно и что оно даёт

Типовой цикл без ИИ: «YouTube тормозит» → вы открываете Web UI →
смотрите соединения → копаетесь в логах → гуглите → меняете пресет →
ждёте → откатываете, потому что стало хуже. Каждый шаг — минуты, а
вечером, когда CF-пул дохнет и фризы у всех, вы уже не инженер, а
диспетчер аварий.

С ИИ-агентом тот же цикл выглядит так: вы пишете «видео на таком-то
сайте открывается по 30 секунд» — и через несколько минут получаете
разбор: какой сет покрывает домен, долетает ли до него трафик, что
говорит лог, какая стратегия сейчас активна, что изменено и что
откачено. Со скриптами, которые остались сохранёнными и воспроизводимыми.

Что конкретно это даёт:

| Возможность | Как это выглядит |
|---|---|
| Диагностика в минутах, не в часах | ИИ читает статус, покрытие домена, конфиг и хвост лога за один заход |
| Безопасное щупание дорог | probe-запросы к /api/mtproto/test-ws с одноразовыми оверрайдами: проверка любой стратегии без записи в конфиг |
| Живое наблюдение | подписка на WS-поток логов: «какой сет сматчил этот домен прямо сейчас» |
| Управление с откатом | b4_set_config_value меняет одну настройку, b4_revert_last_change возвращает как было |
| Воспроизводимость | удачные последовательности команд остаются скриптами и runbook-документами — повторяются одной командой |
| Работа 24/7 | ИИ не спит: ночной флап CF-пула, мигающий фильтр на VPS — всё ловится пробами по расписанию или по запросу |
| Разгрузка пользователя | вы делаете только то, что требует рук: SSH на роутер, ufw на VPS, тест телефона |

Кому подходит: тем, у кого b4 стоит на роутере/VPS и кто не хочет быть
круглосуточным оператором собственного обхода. Кому не подходит: тем, кто
не готов открыть сетевой путь до панели b4 и доверить третьей стороне
чтение состояния сети (см. §9 и §20 — риски и как их зажимают).

## 3. Архитектура: как ИИ добирается до роутера

Карта целиком (пути A/B/C — разделы ниже):

```
                        ИИ-приложение (модель работает ЗДЕСЬ)
                        Claude Desktop / VS Code / CLI-агент в песочнице
                                        │
                                        │  POST /api/mcp  (JSON-RPC 2.0)
                                        │  Authorization: Bearer <token>
                                        │  Accept: application/json, text/event-stream
                ┌───────────────────────┼───────────────────────┐
                │                       │                       │
        путь A: LAN            путь B: WAN-порт         путь C: nginx front на VPS
        (тот же Wi-Fi,         (файрволл роутера         (домен + TLS, ufw,
         провод)                пускает только            проксирует на b4)
                                 IP ИИ)
                │                       │                       │
                ▼                       ▼                       ▼
        ┌───────────────────────────────────────────────────────────┐
        │  роутер: b4, web-сервер на порту 7000 (по умолчанию)      │
        │  ├── Web UI (то же, что вы открываете в браузере)         │
        │  ├── REST API (/api/...)                                   │
        │  ├── MCP endpoint /api/mcp (выключен по умолчанию)        │
        │  └── WS-поток логов /api/ws/logs                           │
        └───────────────────────────────────────────────────────────┘
```

Три пути, по возрастанию сложности:

- **Путь A (LAN):** ИИ-приложение стоит на домашнем компьютере. Ничего
  открывать наружу не надо, токен не покидает дом. Самый безопасный
  вариант и минимум работы.
- **Путь B (WAN):** ИИ-клиент — CLI-агент, работающий в облаке/песочнице.
  Открываете порт web-сервера b4 на файрволле роутера, жёстко ограничив
  по Source IP. Трафик — HTTP, поэтому обязателен TLS (см. §12).
- **Путь C (nginx front на VPS):** если b4 стоит на VPS с Chimera —
  публикуете панель через nginx с нормальным сертификатом (уже входящий в
  Chimera механизм, см. [DPI_BYPASS_FAQ.md, §15](DPI_BYPASS_FAQ.md)).
  Рекомендуется и для роутерного b4 «на вырост»: front умеет TLS и
  ограничение доступа лучше, чем открытый порт.

Технический факт, который сберегает час отладки: **b4 слушает wildcard**
(в netstat это выглядит как `:::7000` — dual-stack, все интерфейсы), то
есть сам web-сервер доступен и с LAN, и с WAN. Всё, что отделяет
интернет от вашей панели, — файрволл роутера. Если «снаружи не
подключается» — в 9 случаях из 10 это firewall, а не b4 (см. §23).

> **Nota bene для Merlin (ASUSWRT):** firewall Merlin по умолчанию дропает
> все входящие с WAN. Правило для порта b4 добавляется через GUI или SSH
> (§14) и живёт до перезагрузки, если не позаботиться о персистенции.

## 4. MCP и REST: два языка ИИ с b4

У ИИ два способа говорить с b4, и они дополняют друг друга.

### MCP (`/api/mcp`) — основной путь

- JSON-RPC 2.0 поверх HTTP: `initialize` → `notifications/initialized` →
  `tools/call`.
- b4 сам рекламирует список инструментов (§18) — ИИ-приложению не нужно
  знать b4 заранее; протокол сам расскажет.
- Аутентификация — постоянный Bearer-токен (§12).
- Токен действует **только** на `/api/mcp`: на остальных маршрутах он
  отклоняется, т.е. скомпрометированный MCP-токен не даёт REST-доступа.
- Гранулярные права: чтение — всегда; запись — отдельным переключателем
  «Allow configuration changes» (§20).
- Транспорт Streamable HTTP: обслуживается только `POST`; `GET`/`DELETE`
  возвращают 405 — это норма, не ошибка.

### REST (`/api/...`) — для тонкой диагностики

- Те же маршруты, что использует Web UI: конфиги, пробы, статистика.
- Аутентификация — как у Web UI (login-токен, если задан пароль).
- Позволяет то, чего нет в MCP-инструментах: например, probe-прогоны
  `POST /api/mtproto/test-ws` с одноразовыми оверрайдами (§19) и подписку
  на WS-поток логов.
- ⚠️ Основной REST-грабель: `POST /api/<section>/config` у b4 заменяет
  конфиг целиком, без merge. Курс: сначала `GET`, потом изменить в памяти,
  потом `POST` весь объект (§19).

Практический вывод: ИИ-приложениям с нативным MCP (Claude, VS Code,
LM Studio) — путь MCP; CLI-агентам, которые просто умеют HTTP, — MCP
вручную (это 30 строк скрипта, см. §16) плюс REST для проб.

## 5. Живой кейс: два дня «ремонта» Telegram руками ИИ-агента

Разделы выше описывали архитектуру в теории. Здесь — что происходит,
когда теория встречается с цензурой: у пользователя «отвалился»
Telegram, и ИИ-агент, подключённый к роутерному b4 по рецептам §11–16,
за двое суток разобрался в причине, собрал эшелон резервных каналов и
починил всё — с шестью короткими SSH-вставками со стороны человека и
сотнями probe-запросов со стороны ИИ. Это не придуманный сценарий: ниже
— реальный ход событий, решения и объяснение каждого «почему». Читается
как разбор инцидента; матчасть вынесена в §6, дороги — в §7, итоговая
карта — в §8.

### 5.1. Что случилось (постановка задачи)

Домашняя сеть за TSPU (см. §6.1). На роутере уже работал сет
`Telegram-WS-Bridge` (режим `mtproto-ws`, §6.3): все устройства дома
ходили в Telegram прозрачно, без настроек. Вечером десктоп показал
«Переподключение через 4 секунды…» и зациклился в ретраях.

Первый же заход ИИ в состояние b4 (статус, конфиг MTProto, хвост
WS-логов — всё через REST, без единой ручной команды) показал картину
«умерло всё сразу»:

| Дорога до DC (см. §7) | Состояние в момент инцидента |
|---|---|
| Прямой TCP до дата-центров ТГ (v4 и v6) | `dial timeout` — соединение не устанавливается вообще |
| Родной WS-edge Telegram (`kws2.web.telegram.org`) | флип-флоп: то 179 мс и живой hold, то dial timeout |
| CF-пул (20 доменов Flowseal, §7.3) | массово `503 Service Unavailable` — за час живых стало 2 из 20 |
| `web.telegram.org` в браузере | `TLS_DROP` в обе стороны, 15/15 падений — отдельный IP-блок |
| DNS на домены ТГ | отравление: провайдерские резолверы отдают фейковые A-записи |

Дополнительная вводная: в WS-логах моста (дамп 120 секунд — 860 строк)
видно, как мост churn-ит апстримы, а через родной edge идут ответы
`-404 (auth key not found)` — часть релеев несла данные, но сессия не
удерживалась, и клиент циклил реконнекты каждые 1–3 секунды, после чего
ушёл в бэкофф.

### 5.2. Что и в каком порядке делал ИИ

Ключевая особенность кейса: **ни одного вслепую**. Каждый шаг — проба
(probe-only, §19), чтение логов или чтение исходников b4; каждый
изменяющий шаг — с верификацией round-trip. Порядок был такой:

| Шаг | Действие ИИ | Зачем / что дало |
|---|---|---|
| 1 | Дамп WS-логов 120 с + расшифровка паттернов | увидел churn апстримов и `-404` от родного edge → мост жив, но лишился дорог |
| 2 | Пер-мостовое зондирование: `POST /api/mtproto/test-ws` по каждому апстриму + `ws_custom_domain`-оверрайд | поймал смерть CF-пула (503) и флип-флоп edge — гипотеза «мост сломан» снята, сломаны дороги |
| 3 | Пробы из зарубежной песочницы ИИ (те же эндпоинты) | сравнил картину «изнутри цензуры» и «снаружи» → блок адресный (TSPU), не протокольный |
| 4 | Чтение исходников b4 (`transparent.go`, `obfuscated2.go`) | понял механику моста и планировщика дорог до конца — что можно безопасно крутить |
| 5 | Проба VPS №1: `tcp://<DC2>:443` с самой ноды | **прорыв**: провайдер VPS №1 пускает прямой TCP до DC за 7 мс → VPS = новая дорога |
| 6 | Ре-включение MTProto-прокси на VPS №1 (секрет сбросился в `enabled=false` при прошлых конфиг-циклах) | вернул tg://-канал для телефона; round-trip через REST подтверждён |
| 7 | Runbook резервных каналов + флип-скрипты | воспроизводимость: следующий инцидент закрывается выполнением готовых файлов |
| 8 | socat DC-Relay на VPS №1 (юнит собрал ИИ, вставил юзер) + флип `dc_relay` через REST | мост прозрачно ожил для всей LAN — основная дорога |
| 9 | Разведка VPS №2 (CF-пул с неё 20/20) + развёртывание третьего прокси через CF | канал, независимый и от роутера, и от VPS №1 |
| 10 | Диагностика «из дома глухо все порты VPS №2» по трём источникам | нашёл автобан домашнего IP на самой VPS №2 — лечится одной вставкой (§8.5) |

Чему этот порядок учит: диагностика шла от наблюдений к гипотезам и от
гипотез к пробам, а не наоборот. Каждая гипотеза проверялась с двух
независимых точек (из-под цензуры и снаружи), каждая замена — с
контрольной пробой после. Именно это отличает «ИИ у руля» от
человека с форумом: агент не тыкает наугад, а сужает пространство
поиска, и у него хватает терпения на 860 строк лога.

### 5.3. Что делал пользователь (честная арифметика ролей)

| Задача | Кто | Сколько занимает |
|---|---|---|
| Прочитать логи, пробы, исходники, REST-флипы, runbook | ИИ | сотни запросов, ноль внимания юзера |
| Установить socat-релей на VPS №1 (одна SSH-вставка готового блока) | юзер | 1 минута |
| Открыть порт 3128 для сотовой (`ufw allow 3128/tcp`) | юзер | 1 команда |
| Вставить socat-блок на VPS №2 | юзер | 1 минута |
| Разбан своего IP + whitelist автобана на VPS №2 (готовый блок) | юзер | 1 минута |
| Проверить tg://-ссылку на телефоне (Wi-Fi и сотовая) | юзер | 2 тапа |

Граница ролей — та же, что в §17: всё, что требует SSH, рук и владельца
секрета, делает человек; всё, что делается по HTTP, — ИИ. Человек ни
разу не выполнял диагностических действий руками: даже проверка
«доходят ли байты с моей VPS до дата-центра» сделана ИИ через probe-only
запрос к роутеру и через REST самой VPS.

### 5.4. Чем закончилось

Итог — карта из трёх «дверей» (как устройство попадает в b4) и пяти
«дорог» (как b4 добирается до дата-центров Telegram), см. §8. Телефон
ходил через tg://-прокси, вся LAN — прозрачным мостом через socat-релей,
а на случай смерти каждого из слоёв остался заряженный резерв: второй
релей, третий прокси и рецепты WEB-канала и CF Worker. Ни один канал не
одноразовый: все переключается либо автоматически (планировщик дорог,
§7.1), либо одним полем в Web UI / одним REST-вызовом.

## 6. Почему Discovery не помог: природа блокировки Telegram

Прежде чем читать про дороги, важно понять, почему «обычный» путь b4 —
Discovery со стратегиями DPI-обхода — в этом кейсе не применялся вообще.
Это самый частый вопрос к кейсу §5, и ответ лежит не в «так вышло»,
а в фундаментальной разнице типов блокировок.

### 6.1. Два разных типа блокировок

b4 — прежде всего DPI-обход: он лечит ситуации «TCP до сайта жив, но
цензор рвёт TLS-сессию по SNI на середине хендшейка». Для этого
существуют стратегии (фрагментация ClientHello, fake-пакеты, смена
порядка записей) и Discovery — автоматический перебор этих стратегий
(подробнее — [DPI_BYPASS_FAQ.md](DPI_BYPASS_FAQ.md)).

С Telegram в этом кейсе всё было иначе:

| Признак | DPI-блокировка «обычного» сайта | Блокировка Telegram у нас |
|---|---|---|
| Что происходит | TCP устанавливается, TLS-хендшейк обрывается или подменяется | TCP-хендшейк до DC **не завершается**: `dial timeout` |
| Уровень | L7 (анализ содержимого) | L3/L4 (чёрная дыра по IP-префиксам) |
| Что лечится сменой формы пакетов | да — фрагментация ломает сигнатуру | **нет — если SYN не доходит, фрагментировать нечего** |
| DNS | обычно чистый | отравление фейковыми A-записями |
| Диагностика | Discovery находит рабочую стратегию | Discovery на `web.telegram.org` = `TLS_DROP` 15/15 — чистый IP-блок |

Вывод из таблицы: набор стратегий бессилен против адресной чёрной дыры.
Discovery здесь использовался только как диагност — его 15/15 падений
подтвердили, что веб-морда ТГ заблокирована по IP (и не лечится ничем,
кроме смены маршрута целиком). Клиентский же трафик — MTProto, и для
него в b4 есть отдельная подсистема.

### 6.2. Почему MTProto не «проксируется» как сайт

Три свойства Telegram, из-за которых «просто прокинуть его через
стратегию» не выйдет:

1. **Клиенты говорят не HTTPS.** Telegram-приложения ходят протоколом
   MTProto к дата-центрам (DC1–5 + медиа-DC203) по портам 443/80/5222.
   Стратегии DPI-обхода заточены под TLS/HTTP-флоу; здесь перехватывать
   «форму хендшейка» нечего — нужен терминатор, который понимает
   MTProto и пере-диалирует его вверх по другой дороге.
2. **Целевые адреса — IP, не домены.** Клиент сначала ломится по
   захардкоженным префиксам `149.154.160.0/20`, `91.108.0.0/16` и др.
   Блокировать их просто, и TSPU это делает; значит, лечится только
   сменой маршрута — куда угодно, лишь бы не «напрямую».
3. **Часть трафика чинить нельзя в принципе.** Веб-морда
   `web.telegram.org` блокирована отдельным IP-блоком; звонки и
   прочие транспорты, которые b4 не может смапить на DC, мост
   пропускает напрямую (fail-open) — там их и душит цензор. Это
   осознанное ограничение, а не баг.

Поэтому инструментом стала встроенная MTProto-подсистема b4: мост
`mtproto-ws` для LAN + MTProto-прокси для ручных клиентов + планировщик
дорог §7. Discovery при этом никуда не делся — он остался делать свою
работу для «обычных» сайтов (YouTube, соцсети), просто у этой задачи
другой слой.

### 6.3. Матчасть: MTProto, DC, obfuscated2, fake-TLS, мост

Минимальный словарик, без которого §7 не читается:

- **MTProto** — клиентский протокол Telegram. **DC** — его дата-центры:
  DC1–5 (IP-префиксы из гео-базы: `149.154.160.0/20`, `91.108.0.0/16`,
  `95.161.64.0/20` и др.) и DC203 — медиа-DC, делящий слот DC2.
- **obfuscated2** — обфускация MTProto-потока: клиент шлёт 64-байтный
  init-пакет, ключ выводится из секрета через HMAC, дальше поток
  шифруется в CTR-режиме. Для цензора это выглядит случайным байтом.
- **fake-TLS** — если в конец секрета дописан домен, прокси отвечает
  псевдо-TLS-хендшейком с SNI этого домена (например,
  `storage.googleapis.com`): на TSPU выглядит как невинный заход в
  Google Cloud. Секрет вида `ee…` в `tg://`-ссылке — это hex-ключ +
  домен маскировки.
- **Прозрачный мост** — сет b4 с routing-режимом `mtproto-ws`: ядро
  роутера через iptables mangle/ipset помечает пакеты к IP-диапазонам
  ТГ и заворачивает их в TPROXY-порт b4; мост терминирует MTProto и
  пере-диалирует DC по плану дорог (§7.1). Не-MTProto трафик на те же
  IP пропускается напрямую (fail-open). DNS доменов ТГ резолвится самим
  b4 — обходит отравление.

Минимальный конфиг сета (официальный формат):

```json
{
  "name": "telegram-ws",
  "targets": {
    "geosite_categories": ["telegram"],
    "geoip_categories": ["telegram"]
  },
  "enabled": true,
  "routing": { "enabled": true, "mode": "mtproto-ws" }
}
```

Симптомы и их перевод на язык диагнозов (из живого кейса §5):

| Симптом | Диагноз |
|---|---|
| «Переподключение через N секунд…» циклом | мост жив, дороги дохнут; смотреть WS-логи и test-ws (§7.1) |
| `-404 auth key not found` в логах моста | родной edge отверг resume-пакет — TG убирает старые эндпоинты; не ваша ошибка |
| `503` от CF-доменов | шаренный пул перегружен — на него вечерний пик; лечится другой дорогой |
| `dial timeout` до `149.154.x.x` | адресный блок TSPU; лечится только сменой маршрута |
| Фото/видео не грузятся, текст ходит | медиа-DC недоступен — типично для CF-пула; лечится CF Worker или релеем |
| `web.telegram.org` не открывается вообще | IP-блок веб-морды; не лечится ни одной схемой моста |

## 7. Дороги до DC: WS-edge, CF-пул Flowseal, socat, CF Worker

Как b4 добирается до дата-центров Telegram. Здесь — вся механика
пяти дорог: как устроена каждая, как разворачивается, почему стоит
именно на этом месте в очереди.

### 7.1. Планировщик дорог: сердце подсистемы

За выбор дороги отвечает планировщик транспортов (в исходниках b4 —
`planTransports`/`dialObfuscatedDC`). Он работает так:

- **Каждое новое соединение** перебирает дороги по очереди в пределах
  бюджета времени (`dialBudget`). Диал не удался — берётся следующий
  план. Сессия живёт, пока жив коннект.
- Порядок планов зависит от режима **upstream_mode** (Settings →
  MTProto):

| Режим | Порядок дорог |
|---|---|
| `tcp` | только TCP: DC-Relay (если задан) → прямые адреса DC |
| `ws` | только WS: родной edge → кастомный домен → CF-пул → воркеры |
| `auto` без dc_relay | родной edge → кастомный домен → CF-пул → воркеры → в конце TCP |
| `auto` с dc_relay (наш случай) | **релей →** прямые DC → родной edge → кастомный домен → CF-пул → воркеры |

- **Кулдауны гасят штормы ретраев**: CF-домен ответил 429/503 → пауза
  60 с; молчит → 90 с; родной edge охлаждается per-DC и оживает
  фоновой пробой. Если остыли ВСЕ TCP-адреса — режим «last resort»:
  диал даже по остывающему (лучше медленно, чем шторм).
- Есть **предразогретые пулы**: WS-пул держит тёплые коннекты до edge,
  worker-пул — до воркеров; новое соединение может получить готовый
  коннект мгновенно.
- Отдельного «скрипта фейловера» **не нужно и не надо**: `auto` +
  `dc_relay` уже даёт автоматическое переключение в обе стороны.

Чем ИИ проверяет дороги: `POST /api/mtproto/test-ws {"dc":2}` — это не
«пинг порта», а полный obfuscated2-хендшейк с реальным DC + удержание
2 с (`hold_ms ~ 2000` = коннект жив). Оверрайды в пробе (`dc_relay`,
`upstream_mode`, `cfproxy_enabled`, `ws_custom_domain`) **не
сохраняются** в конфиг — можно безопасно щупать любые дороги (§19).

### 7.2. Родной WS-edge Telegram

Telegram сам держит WebSocket-edge: `kws1…kws5.web.telegram.org`
(по одному на DC, порты 443/80). MTProto поверх WS выглядит как
обычный HTTPS к домену — до поры до времени это работает даже из-под
TSPU. Слабое место: TSPU научился «дышать» по конкретным пинам edge
(флип-флоп жив/мёртв на одном и том же адресе), а свежие
`wss://kws2.web.telegram.org/apiws` с актуального DNS-edge отвечают
`404` — TG периодически убирает старые эндпоинты. Поэтому edge —
первая попытка, но не опора: в кейсе §5 он умирал на глазах (за час
живость 15 → 2).

### 7.3. CF-пул Flowseal: что это такое и почему так называется

Дорога, которая спасает, когда edge зажат: MTProto-мост через
**Cloudflare**. У Cloudflare есть сервис проксирования WS-трафика: если
у владельца домена в CF прописать A-записи `kws1…kws5`, `kws203`,
указывающие на IP дата-центров Telegram, то WebSocket-соединение на
`kws2.ваш-домен` приедет на `149.154.167.51:443` — но для цензора это
будет выглядеть как трафик к Cloudflare (а резать Cloudflare целиком —
колоссальный collateral: половина интернета живёт на тех же IP).

**tg-ws-proxy** — известный open-source-проект автора **Flowseal**
(GitHub, ~9,6 тыс. звёзд, начат в марте 2026). Изначально это локальный
MTProto-прокси для Telegram Desktop: приложение поднимает MTProto на
`127.0.0.1:1443`, перехватывает коннекты к IP ТГ, извлекает DC-ID из
obfuscation-init и выносит их в WebSocket к DC через домены ТГ;
если WS недоступен — переключается на CF-прокси или прямой TCP. В
проекте есть рецепт CfProxy (свой домен в CF + те самые A-записи) и
свой WS-релей на Workers (§7.5). Идея восходит к Nekogram/WSProxy.

**CF-пул** — шаренный список из ~20 публичных CF-доменов, которые
кто-то заботливо настроил по этому рецепту для всех. b4 скачивает его
раз в час:

```
cfproxy_url = https://raw.githubusercontent.com/Flowseal/tg-ws-proxy/main/.github/cfproxy-domains.txt
```

Тонкости, без которых пул непонятен:

- **Список обфусцирован.** Строки вида `virkgj.com` — это не домены, а
  Caesar-сдвиг настоящих имён (+ замена `.com` → `.co.uk`). `virkgj.com`
  декодируется в `pclead.co.uk`. Обфускация защищает список от простого
  парсинга блок-листами. **Резолвить строки из файла не нужно** — b4
  декодирует сам. В бинарь зашит встроенный запасной пул — b4 работает,
  даже если GitHub недоступен.
- Новый список принимается, только если в нём ≥3 валидных доменов,
  иначе держится старый. Мёртвые домены — в кулдаун (60/90 с).
- Балансер делает per-DC pinning (успешный домен запоминается для DC),
  остальные перемешиваются.
- **Почему пул регулярно дохнет:** он шаренный. Вечером в него валит
  весь российский Telegram → домены упираются в лимиты CF → `503`. Это
  не «пул сломался», а «пул перегружен»: часы спустя он оживает. Для
  надёжности домен можно (и желательно) сделать своим по рецепту CfProxy.

В кейсе §5 пул умирал дважды: в первый вечер (2/20 живых) — после этого
мост переехал на socat-релей; потом ночами оживал на 14–20/20 и вернулся
в роль запасной дороги.

### 7.4. socat DC-Relay: «тупая труба» через вашу VPS

Самая предсказуемая дорога — через собственную VPS. **socat** —
универсальная утилита-«труба»: слушает TCP-порт и пересылает байты в
заданный адрес. Никакого протокола, никакого секрета — чистый перенос.
Рецепт называется **DC Relay**: пять труб на VPS, каждая ведёт в свой
дата-центр:

```
порт = база + DC − 1   (база 7007; медиа-DC203 делит слот DC2)

7007 → 149.154.175.50:443    (DC1)
7008 → 149.154.167.51:443    (DC2 и DC203)
7009 → 149.154.175.100:443   (DC3)
7010 → 149.154.167.91:443    (DC4)
7011 → 149.154.171.5:443     (DC5)
```

Почему это работает против TSPU: цензор душит IP-префиксы Telegram, а
IP вашего хостинг-провайдера не трогает — внутри трубы идут обычные
байты между роутером и VPS. Порог для блокировки такой схемы на порядок
выше (это уже не «заблокировать ТГ», а «заблокировать VPS-провайдера»).

В Web UI b4 у поля **DC Relay** есть кнопка «?» — диалог «DC Relay
socat setup» сам сгенерирует команды под выбранное семейство адресов
(v4/v6) и список портов для фаервола. Юнит под systemd (с автоперезапуском
пятёрки при смерти любой трубы):

```ini
# /etc/systemd/system/tg-dcrelay.service — на VPS
[Unit]
Description=Telegram DC relays 7007-7011 (for home B4 bridge)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/bin/bash -c 'socat TCP-LISTEN:7007,fork,reuseaddr TCP:149.154.175.50:443 & socat TCP-LISTEN:7008,fork,reuseaddr TCP:149.154.167.51:443 & socat TCP-LISTEN:7009,fork,reuseaddr TCP:149.154.175.100:443 & socat TCP-LISTEN:7010,fork,reuseaddr TCP:149.154.167.91:443 & socat TCP-LISTEN:7011,fork,reuseaddr TCP:149.154.171.5:443 & wait -n; exit 1'
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Нюансы, добытые в бою: `fork` — на каждое соединение свой процесс (мост
держит десятки коннектов); `wait -n; exit 1` вместо наивного `wait` —
смерть любого socat перезапускает пятёрку за 5 секунд (иначе порт мог
молча висеть мёртвым); `reuseaddr` — переживает перезапуск. Дальше:
`systemctl enable --now tg-dcrelay` + открыть 7007–7011 в фаерволе VPS
(или только для WAN-IP роутера: `ufw allow from 203.0.113.10 to any
port 7007:7011 proto tcp`). В b4: Settings → MTProto → **DC Relay** =
`<IP-или-домен-VPS>:7007`, режим `auto` — и релей станет первой
дорогой (§7.1).

В кейсе §5 у этой дороги нашёлся только один недостаток: весь трафик
дома пошёл через VPS — на лимитных тарифах смотреть счётчик (`vnstat`).

### 7.5. CF Worker: личный релей на edge Cloudflare

**Cloudflare Workers** — serverless-платформа: вы размещаете
JavaScript-код на тысячах точек присутствия CF, и он выполняется на
ближайшем edge. Для Telegram пишется маленький воркер-релей: принимает
WebSocket, устанавливает TCP-сокет до нужного DC (через `connect()`
из `cloudflare:sockets`) и перекачивает байты в обе стороны. Домен
вида `random-symbols-1234.username.workers.dev` — ваш личный,
бесплатный, не зависящий ни от шаренного пула, ни от ваших VPS.

Развернуть (полчаса, по гайду Flowseal — [CfWorker.md](https://github.com/Flowseal/tg-ws-proxy/blob/main/docs/CfWorker.md)):

1. Аккаунт Cloudflare (бесплатного тира достаточно).
2. Compute → Workers & Pages → Create application → Hello World → Deploy.
3. Edit code → заменить код воркера на релей-скрипт → Deploy.
4. Скопировать домен `*.workers.dev` в настройки b4: **Cloudflare
   Worker domain** (Settings → MTProto; несколько воркеров — через
   запятую). Compatibility date ≥ 2026-04-07.
5. Убедиться, что `workers.dev` вообще резолвится и доступен из вашей
   сети (если CF-подсети под фильтром — не судьба, увы).

Честное ограничение (и почему воркер — **последний** в очереди WS-планов
b4, после edge и пула): воркер не хранит состояние, и Cloudflare
«реклеймит» его посреди длинной сессии. Замеры из цензурной сети: воркер
ответил 8 раундов хендшейка и замолчал на 8,7-й секунде; домен из
шаренного пула на той же машине — 100 раундов за две минуты. Воркер
проходит тестовый коннект, но до видео ему далеко (лечение длинных
сессий — Durable Objects с WebSocket hibernation, это уже не про
пятиминутный рецепт). b4 знает об этом и ранжирует молчащего воркера
ниже на 10 минут. Отсюда роль в архитектуре: не основа, а **последний
эшелон** — когда и edge, и CF-пул, и обе VPS мертвы. В кейсе §5 до него
не дошло: он остался заряженным рецептом.

### 7.6. dc_fallback: актуальная карта DC

Не дорога, а «картограф»: b4 сверяет список IP дата-центров ТГ с
`https://proxy.b4core.app/telegram/getProxyConfig` (Telegram иногда
меняет адреса). Включается галкой `dc_fallback_enabled`; принудительное
обновление — `POST /api/mtproto/refresh-dcs`. Страховка от устаревания
карты, не обход блокировок.

## 8. Итоговая карта каналов: двери, дороги, отказоустойчивость

### 8.1. Двери × дороги

Главное разделение: **дверь** — как устройство попадает в ваш b4;
**дорога** — как b4 добирается до DC Telegram.

```
                 ДВЕРИ (вход в b4)                     ДОРОГИ (b4 → DC Telegram)
┌──────────┐   ┌──────────────────────────────┐   ┌───────────────────────────────────────┐
│ телефон  │──►│ A. MTProto-прокси :3128      │──►│ 1. прямой TCP до DC      (TSPU: мёртв)│
│ десктоп  │   │    tg://-ссылка, секрет      │   │ 2. socat-релей через VPS (основная)   │
│ (tg://)  │   │    роутер / VPS №1 / №2      │   │ 3. родной WS-edge ТГ     (флип-флоп)  │
├──────────┤   ├──────────────────────────────┤   │ 4. CF-пул Flowseal, ~20 д., hourly    │
│ вся LAN  │──►│ B. Прозрачный мост (TPROXY)  │──►│ 5. CF Worker             (последний)  │
│ (ноль    │   │    ничего не настраиваешь    │   └───────────────────┬───────────────────┘
│ настроек)│   ├──────────────────────────────┤                     │
├──────────┤   │ C. WEB-канал t.me/webproxy   │   ┌───────────────────▼───────────────────┐
│ TG Desk. │──►│    (резерв, рецепт готов)    │   │  DC1..DC5 + медиа-DC203               │
│ 7.1.1+   │   └──────────────────────────────┘   │  (149.154.x.x и др., :443)            │
└──────────┘                                      └───────────────────────────────────────┘
```

Двери в кейсе §5 развёрнуты три штуки (прокси на роутере, на VPS №1 и
на VPS №2 — все три со своим секретом `ee…` и fake-TLS-маскировкой);
четвёртая (WEB-канал) — заряженный рецепт: MTProto поверх
HTTPS-WebView для TG Desktop 7.1.1+ (`https://t.me/webproxy?server=…`),
спасает в сетях, где пускают только HTTPS к «нормальным» сайтам;
требует голого домена с TLS:443 за вашим b4.

### 8.2. Что было развёрнуто и что это страхует

| Канал | Дорога | Что страхует |
|---|---|---|
| tg://-прокси VPS №1 | прямой TCP до DC (провайдер VPS №1 пускает) | смерть CF, смерть роутера, смерть моста — самый живучий |
| tg://-прокси роутера (Wi-Fi) | планы моста (= релей/WS) | телефоны/десктоп дома без настроек мостов |
| tg://-прокси VPS №2 | CF-пул (плюс edge/TCP резервом) | фильтр ТГ у провайдера VPS №1, смерть роутера; умирает вместе с глобальной смертью CF |
| Мост LAN (TPROXY) | релей VPS №1 → WS-планы | вся квартира, включая устройства без прокси-настроек |
| socat-релеи на VPS №1 и №2 | — (это сами дороги) | смерть WS-апстримов у моста (флип одним REST-вызовом) |
| WEB-канал, CF Worker | рецепт | корпоративные/гостевые сети; глобальная смерть CF-пула и VPS |

Как выглядит ссылка MTProto-прокси (секрет берётся в Web UI кнопкой
Generate Secret; домен в конце включает fake-TLS):

```
tg://proxy?server=192.0.2.10&port=3128&secret=<SECRET-hex>746f726167652e676f6f676c65617069732e636f6d
```

Три инстанса прокси — три разные точки входа с независимыми путями:
обе внешние ссылки стоит держать в списке клиента, переключение —
два тапа (автопрыжков между прокси в клиентах TG нет).

### 8.3. Фейловер: что включается само, а что руками

**Автоматически (ниже уровня пользователя):** планировщик дорог §7.1 —
умерла дорога, следующее соединение уйдёт по живой; кулдауны возвращают
оживших; клиенты TG сами агрессивно реконнектятся, поэтому смена дороги
незаметна. Заданный `dc_relay` + `auto` = релей первичный, WS запасной;
стёрли поле — вернулись к WS-планам. **Руками остаются:** переключение
tg://-ссылок на телефоне (клиент ретраит только один прокси) и
осознанный выбор «жить на релее постоянно или на CF» (авто-возврата к
выздоровевшему CF-пулу нет — и это правильно: релей стабильнее и
быстрее, лишний watchdog — лишняя точка отказа).

Как переключает ИИ: probe-only проба (§19) → выбор → флип одной командой
— поле DC relay в Web UI (или GET → изменить → POST **весь** конфиг:
`POST /api/mtproto/config` — замена целиком, не merge, §19.2).

### 8.4. Матрица отказов

| Сценарий | Что умирает | Что остаётся | Действия |
|---|---|---|---|
| Вечерний 503-шторм CF-пула | дорога 4 | всё остальное | ничего: релей уже первичный |
| TSPU зажал родной WS-edge | дорога 3 | всё остальное | ничего: edge сам в кулдауне |
| Провайдер VPS №1 включил фильтр ТГ | релеи + прокси VPS №1 (один сетевой путь!) | мост падает на WS-планы; телефон — на прокси VPS №2 (CF-апстрим) | флип `dc_relay` на VPS №2; перевод прокси VPS №1 на WS (один REST) |
| Умер мост целиком (WS + релеи) | двери B и A(роутер) | tg://-прокси обеих VPS | сидеть через tg://, мост чинит ИИ по логам |
| Двойная смерть: CF-глобально + VPS №1 | все развёрнутые каналы | — | CF Worker (§7.5) / VPS вне фильтра / публичные MTProto-прокси |
| Ребут роутера | — | всё (сет + TPROXY поднимутся сами) | WAN-доступ к REST требует персистенции firewall (§14.3) |
| Сменился WAN-IP дома | ufw-вайт на VPS | прокси-порты, открытые всем | обновить вайт (или перевести на домен+DDNS) |

### 8.5. Грабли, пойманные в кейсе (учёные уроки)

1. **Автобан xray может забанить ваш собственный дом.** Симптом в кейсе:
   «из дома глухи ровно наши новые порты на VPS №2, при живых старых».
   Причина: `xray-autoban` (каждые 5 мин, ≥10 TLS-ошибок за 10 мин —
   включая `connection reset` и `broken pipe`) вписал `ufw deny from
   <WAN-IP роутера>` в середину списка правил: старые allow (22/443)
   стояли выше бана, новые порты (3128/7007–7011) — ниже. Одна строка
   объясняла всё. Лечение и профилактика — в §21. Правило номер один
   при любой аномалии доступности: **сначала `ufw status numbered`**.
2. **POST /api/mtproto/config — полная замена.** Сырой curl с одним
   полем затирает секреты и порт. Правильно: GET → изменить → POST
   весь JSON, затем GET-проверка, что `secrets[].enabled=true` (баг
   кейса: deploy без поля `enabled` выключал секрет — прокси резал все
   хендшейки, ссылка была чёрной дырой).
3. **REST роутера флапает.** Запросы могут зависать на 300 с и проходить
   со второй-третьей попытки — все клиентские скрипты ИИ ходят с ретраями.
4. **«Порт-точечная глухота» — почти всегда фаервол**, а не «TSPU вырезал
   порты». До проверки ufw гипотезы про блок-листы — спекуляция.
5. **Пробы из зарубежной песочницы ≠ пробы из дома.** Egress песочницы —
   другая страна: «у меня работает» ничего не говорит о пути из РФ.

## 9. Сравнение с VLESS-туннелями: плюсы и минусы

Сразу главное: **это не конкурирующие решения, а разные слои**.
VLESS-туннель — транспорт: он возит трафик ваших приложений через Entry-
и Exit-ноды (см. [VLESS_FAQ.md](VLESS_FAQ.md)). ИИ-агент — канал
эксплуатации: он управляет и диагностирует b4, который этот транспорт
обслуживает. Сравнивать их «что лучше» — как сравнивать машину и
механика-диагноста. Но осознанный выбор требует понимать, что вы
получаете и чем платите. А чтобы сравнение не было умозрительным,
раздел написан сразу после живого кейса §5–§8: там, где весь вопрос
«обхода» свёлся к пяти дорогам до дата-центров Telegram и переключению
между ними, различие «транспорт против эксплуатации» видно невооружённым
глазом.

| Критерий | ИИ-агент с доступом к b4 | VLESS-туннель (Xray) |
|---|---|---|
| Назначение | управление, диагностика, автоматизация обхода | провод трафика приложений |
| Что открывается наружу | порт web-сервера b4 (MCP/REST) | порт Xray-ноды |
| Криптография канала | HTTPS опционально; токен в заголовке | TLS/REALITY по умолчанию, маскировка под чужой сайт |
| Поверхность атаки | доступ к **управлению** системой обхода (зажимается правами MCP) | только к проксированию байтов |
| Кто может навредить при компрометации | сменить настройки сетов (read-only режим закрывает полностью) | посмотреть/проксировать трафик |
| Скорость реакции на «всё сломалось» | минуты: ИИ уже в логах и конфиге | ручная диагностика владельцем |
| Автоматизация | probe-пробы, флипы дорог, откаты, runbook-скрипты | нет (статическая конфигурация) |
| Стоимость ошибки ИИ | зажата guard'ами b4: большинство опасных путей запрещено, изменения откатываемы | к ИИ доступа нет — ошибки только человеческие |
| Зависимости | доступность ИИ-сервиса + путь до роутера | только живость ваших нод |
| Приватность | b4_diagnostics отдаёт hostname/интерфейсы/правила — ИИ «видит» вашу сеть | трафик инкапсулирован, управление не раскрыто |
| Настройка | включить MCP, токен, открыть путь (30–60 мин) | полноценная установка каскада (часы) |

**Плюсы предприятия «ИИ у руля», которых нет у чистого VLESS:**

1. Диагностика не требует вас: вечером умирают CF-мосты — ИИ сам гоняет
   пробы, находит живую дорогу и переключает, пока вы смотрите кино
   (ровно это произошло в §5: каскад смерти апстримов за час пойман и
   обезврежен без единого ручного действия).
2. probe-only культура: у b4 есть запросы с одноразовыми оверрайдами —
   ИИ проверяет гипотезы, ничего не записывая в конфиг (§19). Ручной
   эквивалент — каждый раз открывать Web UI и молиться.
3. Память процесса: скрипты и runbook-документы копятся; повторный инцидент
   закрывается выполнением готового файла, а не археологией в чатах.
4. Guard'ы проектировались именно под ИИ: b4 отдаёт модели описание
   каждого сеттинга (ресурсы MCP) — она не угадывает по названиям полей,
   а читает документацию изнутри. Плюс стриппинг всех кредов из ответов.

**Минусы и риски, о которых честно:**

1. **Открытый порт.** Любый WAN-порт — поверхность атаки. Смягчение:
   Source IP-ограничение в правиле файрволла + токен + TLS + read-only.
2. **Токен в заголовке каждого запроса.** Без HTTPS его видит каждый
   посредник на пути. Правило: наружу — только через TLS (§12, §15).
3. **Доверие к ИИ-сервису.** Диагностика раскрывает устройство вашей
   сети (интерфейсы, правила, hostname). Смягчение: read-only, точечные
   вопросы, свой локальный LLM для параноиков (LM Studio говорит MCP).
4. **Одиночная точка «ИИ недоступен».** Песочница агента легла — вы
   временно снова ручной оператор. VLESS-туннелю всё равно, работает сам.

### А мог ли VLESS спасти тот самый Telegram?

Честный вопрос после §5–§8: не проще было вообще не строить MTProto-
эшелон, а завернуть Telegram в VLESS-туннель (как YouTube и остальное)?
Мог бы — и в некоторых сетях это самый короткий путь. Разница в том,
что именно вы покупаете каждой технологией:

| Критерий | MTProto-стек b4 (мост + дороги §7) | Telegram через VLESS-туннель |
|---|---|---|
| Прозрачность для устройств | ноль настроек: TPROXY-мост ловит трафик LAN сам | на каждом устройстве нужен Xray-клиент — либо свой шлюз на роутере |
| Число независимых дорог | пять, планировщик переключает сам (§7.1) | дорога одна: туннель Entry→Exit; умерла — всё умерло |
| Exit внутри РФ | не важно: релей/CF-пул не требуют «не-РФ» | бесполезен: TSPU режет ТГ и с Exit-ноды |
| Медиа-DC, звонки, веб-морда | гранулярно: медиа лечится отдельной дорогой, звонки честно fail-open | всё или ничего одним туннелем |
| Маскировка от DPI | obfuscated2 + fake-TLS «под Google» (протокол ТГ) | REALITY «под чужой сайт» (свой транспорт) — тоже хорошо |
| Эксплуатация при сбое | ИИ видит каждую дорогу отдельно (test-ws, кулдауны) и лечит точечно | диагностика сводится к «туннель жив/мёртв», причин не видно |

Когда VLESS для ТГ удобнее: у вас уже есть рабочий каскад за границей
и клиенты с Xray — тогда телефонный трафик ТГ можно просто маршрутизировать
в туннель и не заводить MTProto-подсистему вовсе. Когда MTProto-стек
удобнее: устройства «не умеют» VPN (ТВ-приставки, чужие телефоны гостей),
Exit-ноды в РФ, или хочется живучести из нескольких независимых дорог с
автопереключением. Идеальная конфигурация большинства не выбирает — а
совмещает: VLESS тянет сайты, b4-мост — Telegram, ИИ обслуживает оба
слоя (и снова см. §5: в реальном инциденте эти слои не мешали друг
другу ни разу).

**Вывод:** связка «VLESS-транспорт + b4-обход + ИИ-эксплуатация» — это
слои одной системы. VLESS не умеет чинить сам себя, ИИ не заменяет
шифрование, а MTProto-мост не отменяет туннели — он закрывает тот класс
блокировок, до которого туннелю «нужен весь ваш трафик целиком». Начинать
можно с любого слоя, но режим «ИИ следит за b4» наиболее окупается, когда
у вас уже есть и мосты, и сеты, и истории «вечером всё отвалилось» — как
в кейсе §5, где вся авральная работа свелась к шести SSH-вставкам
человека и сотням рутинных проб, сделанных ИИ.

## 11. Шаг 1 — включаем MCP-сервер в b4

Действие выполняет: **пользователь** (5 минут, в Web UI).

1. Откройте Web UI b4: `http://<LAN-IP-роутера>:7000`.
2. Перейдите **Settings → Integrations → MCP server**.
3. Включите переключатель **Enable MCP server** в шапке карточки.
   Эндпоинт `/api/mcp` поднимается на web-сервере b4.
4. Решите, нужен ли ИИ режим записи:
   - **Allow configuration changes = OFF** (по умолчанию): ИИ читает
     статус/логи/конфиг, но не может изменить ни байта. Начинайте с этого.
   - **ON**: ИИ дополнительно меняет сеттинги сетов, MTProto/SOCKS5 и
     уровень логирования (список и ограничения — §20).
5. Нажмите **Generate** в поле Access token (§12) и **Save**.
6. Кнопка **Copy** у Client configuration скопирует готовый блок:
   URL эндпоинта + заголовок `Authorization: Bearer <token>` — это и есть
   «паспорт» для ИИ-приложения.

Проверка, что MCP поднялся (с любой машины в LAN):

```bash
# «обычный» curl без MCP-заголовков висит и отваливается по таймауту —
# это НОРМА (см. §23). Правильная проверка:
curl -sS -m 10 -X POST "http://192.168.1.1:7000/api/mcp" \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"manual-check","version":"1.0"}}}'
```

Ответом придёт JSON с `serverInfo` и capabilities — значит, сервер жив и
токен принят.

> **Если выключен web-сервер b4** (порт 0 в Security) — `/api/mcp`
> недоступен, b4 при старте пишет предупреждение в лог. Включите
> web-сервер, порт по умолчанию 7000.

## 12. Шаг 2 — токен: генерация и правила обращения

- **Generate** создаёт 64-символьный токен; он не сохраняется, пока вы
  не нажмёте Save. **Regenerate** заменяет его (старый мгновенно умирает
  — способ мгновенного отзыва доступа, см. §22).
- Пока токен задан, это **единственный** кред, принимаемый на `/api/mcp`.
  И он больше ничего не даёт: на любом другом маршруте REST его отклоняют.
- Пустое поле токена переключает `/api/mcp` на авторизацию Web UI —
  login-токен живёт сутки и сбрасывается при каждом рестарте b4:
  ИИ-приложение «молча умирает». Не полагайтесь на это — задайте токен.

> **⚠️ Главное правило:** токен передаётся в заголовке **каждого**
> запроса. Без HTTPS его читает любой узел на пути (провайдер, транзит,
> точка Wi-Fi). Пока трафик не выходит из доверенной сети — терпимо;
> как только путь идёт через интернет — обязателен TLS:
> - путь A (LAN) — достаточно HTTP;
> - путь B (WAN-порт) — включите HTTPS в b4 (Security) или используйте
>   путь C;
> - путь C (nginx front) — TLS уже там (Let's Encrypt / self-signed).

Ещё два правила обращения:

1. Токен для ИИ — как пароль: передаётся по защищённому каналу (или из
   рук в руки в конфиге), не коммитится в git, не попадает в скриншоты.
   Приложения без защищённого хранилища держат его в файле в открытом
   виде — VS Code умеет спрашивать токен при запуске (см. §16).
2. Один токен — один агент. Завели второго ИИ — отдельный токен не
   завести (поле одно), но зато Regenerate одной кнопкой отзывает доступ
   у всех сразу (§22).

## 13. Шаг 3 — вариант A: ИИ внутри LAN (рекомендуется)

Подходит: Claude Desktop / VS Code / Cursor / LM Studio, работающие на
домашнем ПК в той же сети, что и роутер.

Что делаете вы: ничего сверх §11–§12 — доступ из LAN уже открыт, порт
наружу не пробрасывается, токен не покидает дом.

Конфигурация клиента — VS Code (`.vscode/mcp.json` в проекте или
пользовательский `mcp.json`):

```json
{
  "inputs": [
    {
      "id": "b4-token",
      "type": "promptString",
      "description": "b4 MCP token",
      "password": true
    }
  ],
  "servers": {
    "b4-router": {
      "type": "http",
      "url": "http://192.168.1.1:7000/api/mcp",
      "headers": {
        "Authorization": "Bearer ${input:b4-token}"
      }
    }
  }
}
```

Claude Desktop / LM Studio — тот же смысл, верхний ключ `mcpServers`
(полный пример — §16). После сохранения в панели **Integrations** вашего
приложения появится сервер `b4-router` с тумблером — включаете и
спрашиваете: «Is b4 running, and which capture engine is active?»

> **Почему это рекомендуемый старт:** нулевая поверхность атаки извне,
   нулевая настройка сети, пять минут от идеи к первому вопросу ИИ.
   Неудобство одно — агент «привязан» к дому (клеточные/корпоративные
   сценарии требуют путей B/C).

## 14. Шаг 4 — вариант B: ИИ снаружи через WAN-порт роутера

Подходит: CLI-агент в облаке/песочнице, которому вы хотите дать руль,
находясь где угодно. Делаете вы; ИИ потом только стучится в endpoint.

### 14.1. Проверить, что b4 слушает все интерфейсы

По SSH на роутер:

```bash
netstat -tlnp | grep 7000
# ожидаемо: tcp6  :::7000  LISTEN  <pid>/b4  — wildcard, dual-stack
```

b4 из коробки слушает wildcard — если строка такая, WAN-сторону закрывает
только firewall, переходим к правилу. (Если вдруг b4 прибит только к
LAN-адресу — правьте bind-адрес web-сервера в настройках b4.)

### 14.2. Открыть порт (Merlin / ASUSWRT) — два способа

**Способ 1, GUI (проще):** веб-морда роутера → **Firewall → General →
Enable IPv4 inbound firewall rules = Yes** → Add rule:

| Поле | Значение |
|---|---|
| Source IP | IP вашего ИИ (например `198.51.100.50`) — НЕ «Any» |
| Port Range | `7000` (порт web-сервера b4) |
| Protocol | TCP |

**Способ 2, SSH (точнее):** правило iptables с подсетью источника:

```bash
# на роутере по SSH; /16 — если у песочницы ИИ гуляет IP внутри подсети
iptables -I INPUT -p tcp --dport 7000 -s 198.51.100.0/24 -j ACCEPT
```

> **Всегда указывайте Source IP.** Правило без `-s` (или «Any» в GUI)
> открывает панель управления обходом всему интернету. Токен — вторая
> линия обороны, не единственная.

### 14.3. Персистенция (иначе после ребута правило умрёт)

SSH-правило выше — runtime, живёт до перезагрузки роутера. Персистентный
вариант на Merlin — стартовый скрипт файрволла:

1. Administration → System → **Enable JFFS custom scripts and configs = Yes**
   (и Partition JFFS, если ещё не размечена; перезагрузка).
2. Создать/дополнить `/jffs/scripts/firewall-start`:

```bash
cat >> /jffs/scripts/firewall-start <<'EOF'
# b4 MCP access for AI agent (insert AFTER firewall setup)
iptables -I INPUT -p tcp --dport 7000 -s 198.51.100.0/24 -j ACCEPT
EOF
chmod +x /jffs/scripts/firewall-start
```

3. GUI-правило (способ 1) переживает ребут само — если делали через GUI,
   этот пункт не нужен.

### 14.4. OpenWrt и другие платформы

На OpenWrt то же самое делается через firewall UCI:

```bash
uci add firewall rule
uci set firewall.@rule[-1].name='allow-b4-mcp-ai'
uci set firewall.@rule[-1].src='wan'
uci set firewall.@rule[-1].dest_port='7000'
uci set firewall.@rule[-1].proto='tcp'
uci set firewall.@rule[-1].src_ip='198.51.100.50'
uci set firewall.@rule[-1].target='ACCEPT'
uci commit firewall && /etc/init.d/firewall restart
```

(Keenetic/Mikrotik — аналогично штатными средствами платформы; b4
ставится туда по [докам установки b4](https://github.com/DanielLavrushin/b4).)

### 14.5. Контроль снаружи

С машины ИИ (или любой внешней с тем же IP):

```bash
curl -sS -m 10 -X POST "http://203.0.113.10:7000/api/mcp" \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{...initialize...}'
```

Ответ с `serverInfo` — путь открыт. Таймаут — firewall (§23). И помните
про TLS (§12): по голому HTTP через интернет токен светится; либо
включайте HTTPS на web-сервере b4, либо переходите на путь C.

## 15. Шаг 5 — вариант C: публикация через nginx front на VPS

Если b4 живёт на VPS с Chimera (или вы хотите Publish endpoint с нормальным
TLS для роутера через проброс), используйте штатный механизм Chimera —
nginx front (полный разбор — [DPI_BYPASS_FAQ.md, §15](DPI_BYPASS_FAQ.md)):

```
Главное меню → 3 (Настройки сети) → Y (YouTube) → B (b4) → 8 (nginx front)
→ порт 9743 (default) → 1 (Let's Encrypt, если есть домен) → ваш домен
```

или self-signed по IP (режим 2). Что происходит:

1. nginx ставит vhost с TLS на выбранном порту;
2. `https://<host>:<port>` проксируется на `http://127.0.0.1:9700`
   (loopback web UI b4 — порт может отличаться от 7000, это порт VPS-инсталляции);
3. прямое попадание в loopback-порт закрывается (ufw deny) — только через front;
4. порт регистрируется в port_registry Chimera.

Для ИИ это просто другой URL в конфиге клиента:

```json
"url": "https://router.example.net:9743/api/mcp"
```

— TLS доверенный, ufw ограничивает по Source IP (правило «allow from
<IP-ИИ> to any port 9743» вместо широкого), и revoke = одно удаление
правила/выключение front (§22). Из коробки здесь же живёт REST и WS-логи
— front прозрачен для всех маршрутов b4.

> **Комбо для роутера:** VPS с доменом делает front, nginx проксирует
> не локальный b4, а LAN-адрес роутера по SSH-туннелю/VPN. Это уже
> продвинутый сценарий — базовый выбор для роутера остаётся путь A/B.

## 16. Подключение ИИ: конфиги клиентов и ручной HTTP

### Claude Desktop / LM Studio (`mcpServers`)

```json
{
  "mcpServers": {
    "b4-router": {
      "url": "https://router.example.net:9743/api/mcp",
      "headers": {
        "Authorization": "Bearer <TOKEN>"
      }
    }
  }
}
```

У LM Studio несколько серверов перечисляются в одном файле; в панели
**Integrations** каждый появляется как `mcp/<name>` с отдельным тумблером.

### VS Code — см. §13 (структура с `inputs`/`promptString`, чтобы токен
не хранился в файле).

### CLI-агент / любой язык — «ручной» MCP-клиент

Транспорт — Streamable HTTP, три просьбы b4:

```bash
#!/bin/bash
# mcp-call.sh <TOOL> <ARGS-JSON> — минимальный MCP-клиент для b4
URL="https://router.example.net:9743/api/mcp"   # путь A: http://192.168.1.1:7000/api/mcp
TOKEN="<TOKEN>"
DIR="$HOME/.mcp-b4"; mkdir -p "$DIR"

# 1) initialize (один раз; сессия живёт, пока b4 не перезапущен)
SESS=""
[ -f "$DIR/session" ] && SESS=$(cat "$DIR/session")

call() {
  local extra=()
  [ -n "$SESS" ] && extra=(-H "Mcp-Session-Id: $SESS")
  curl -sS -m 30 -D "$DIR/headers" -X POST "$URL" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    "${extra[@]}" \
    -d "{\"jsonrpc\":\"2.0\",\"id\":$RANDOM,\"method\":\"$1\",\"params\":$2}"
}

if [ -z "$SESS" ]; then
  call initialize '{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"my-agent","version":"1.0"}}' >/dev/null
  grep -i "mcp-session-id:" "$DIR/headers" | head -1 | tr -d '\r' | awk '{print $2}' > "$DIR/session"
  SESS=$(cat "$DIR/session")
  call notifications/initialized '{}' >/dev/null
fi

# 2) сам вызов инструмента
call tools/call "{\"name\":\"$1\",\"arguments\":$2}"
echo
```

Использование: `./mcp-call.sh b4_status '{}'`, `./mcp-call.sh b4_check_domain '{"domain":"youtube.com"}'`.

> **Три обязательных заголовка, без которых «ничего не работает»:**
> `Authorization: Bearer …` (иначе 401), `Accept: application/json,
> text/event-stream` (иначе запрос МОЛЧА ВИСИТ до таймаута — это
> Streamable HTTP, сервер ждёт согласования формата), `Mcp-Session-Id`
> (для последующих вызовов после initialize). GET на `/api/mcp`
> возвращает 405 — так и задумано.

### На что ИИ способен сразу после подключения

Спросите у него «какие инструменты b4 тебе доступны?» — клиент
запросит `tools/list` и перечислит §18. Промпт `diagnose_domain` (b4
публикует его рядом с инструментами) проводит модель по цепочке
статус → покрытие → конфиг → фаервол для конкретного домена — готовый
сценарий диагностики из коробки.

## 17. Разделение ролей: что делает пользователь, что делает ИИ

Граница проходит по простому принципу: **всё, что требует рук на железе
или секретов, делает человек; всё, что делается по HTTP, может ИИ.**

| Задача | Кто | Почему |
|---|---|---|
| Установка b4 на роутер/VPS | пользователь (руками по [DPI_BYPASS_FAQ §9](DPI_BYPASS_FAQ.md)) | SSH, systemd, бинарники |
| Включение MCP, генерация токена | пользователь (Web UI, §11) | секрет не должен рождаться у ИИ |
| Открытие firewall-порта, персистенция | пользователь (SSH на роутер, §14) | и ИИ не должен уметь открывать себе двери |
| Передача токена ИИ | пользователь | по защищённому каналу, в конфиг клиента |
| Диагностика «почему не работает X» | ИИ | MCP-инструменты + REST-пробы + логи |
| Подбор/импорт сетов, Discovery | ИИ (предлагает и применяет) — пользователь (согласует) | запись разрешается переключателем §11.4 |
| Переключение дорог/апстримов (probe-only) | ИИ | оверрайды не пишутся в конфиг (§19) |
| Изменение конфига REST'ом | ИИ (GET→правка→POST целиком, §19) | с осторожностью и проверкой после |
| SSH-команды на роутере | пользователь | у ИИ обычно нет и не должно быть вашего SSH |
| ufw/автобан/whitelist на VPS | пользователь (ИИ пишет готовый блок команд) | то же |
| Финальный тест «глазами пользователя» (телефон, видео) | пользователь | ИИ не смотрит видео (пока) |
| Скрипты, runbook-документация | ИИ | сохраняются у ИИ, воспроизводятся по запросу |

Рабочий цикл при инциденте выглядит так: вы пишете симптом → ИИ
сам собирает факты (инструменты §18, пробы §19) → если нужно действие —
либо применяет сам (если запись разрешена и путь безопасен), либо
присылает вам 3 строки для вставки в SSH → проверяет результат пробами →
фиксирует в runbook.

> **Про trust-границы с обеих сторон:** не давайте ИИ SSH на роутер и
> root на VPS, если не понимаете последствий; не давайте b4-режим записи,
> пока не убедились в адекватности агента на read-only. Токен MCP
> отзывается одной кнопкой Regenerate (§22) — это ваша «красная кнопка».

## 18. Инструменты ИИ через MCP (справочник)

Что b4 отдаёт через `tools/list` (актуальный состав — в Web UI, список
ниже — обзор; имена могут пополняться новыми версиями b4):

### Чтение (доступно всегда)

| Инструмент | Отвечает на вопрос |
|---|---|
| `b4_status` | b4 жив? версия, движок захвата, бекенд файрволла, сколько сетов/включено, uptime |
| `b4_check_domain` | какой сет покрывает домен, как сматчился, включён ли |
| `b4_list_sets` | все сеты по приоритету, число доменов, основная стратегия |
| `b4_get_set` | полный конфиг одного сета |
| `b4_get_config` | конфиг целиком или секция |
| `b4_recent_connections` | какие соединения обработал b4 и какой сет сматчил каждый |
| `b4_logs_tail` | хвост error/system-лога |
| `b4_metrics` | счётчики пакетного движка, скорость соединений, память |
| `b4_diagnostics` | ОС, ядро, интерфейсы, бекенд firewall и установленные b4 группы правил |

### Запись (только при Allow configuration changes = ON)

| Инструмент | Что делает |
|---|---|
| `b4_list_writable_paths` | какие настройки вообще можно менять, с типами и допустимыми значениями |
| `b4_set_config_value` | меняет одну настройку и применяет на лету; ответ содержит старое и новое значение |
| `b4_revert_last_change` | откат последнего изменения (повтор — откат ещё на шаг назад) |

Рядом публикуется готовый промпт `diagnose_domain` (цепочка диагностики
домена) и ресурсы-описания каждого сеттинга: модель читает их вместо
того, чтобы угадывать семантику полей.

> **Классическая пара вопросов, которую путают:** `b4_check_domain`
> отвечает «домен НАСТРОЕН в сете?», `b4_recent_connections` — «трафик
> домена ДОШЁЛ и сматчился?». Домен может быть настроен и не видеть
> трафика — это разные поломки: ошибка таргетинга vs ошибка маршрутизации.

> **Что вычищается из ответов:** web-логин/пароль, креды SOCKS5, секреты
> MTProto, ipinfo-токен, сам MCP-токен, прокси-креды апстримов. А вот
> `b4_diagnostics` сознательно содержит hostname, адреса интерфейсов и
> живой ruleset — этого достаточно, чтобы опознать сеть (см. §9,
> приватность).

## 19. REST-методы: probe-only пробы и правила выживания

Помимо MCP, ИИ говорит с b4 тем же REST, что и Web UI. Три приёма,
которые делают это безопасным и мощным.

### 19.1. Probe-only: щупать без записи

Ряд POST-методов принимает оверрайды и **не сохраняет** их в конфиг.
Флагман — проба транспортов MTProto:

```bash
POST /api/mtproto/test-ws {"dc":2}
POST /api/mtproto/test-ws {"dc_relay":"<хост>:7007","upstream_mode":"tcp","cfproxy_enabled":false,"dc":3}
```

Проба прогоняет не «пинг порта», а полный путь байтов: диал → хендшейк →
удержание соединения 2 с. Оверрайды (`dc_relay`, `upstream_mode`,
`cfproxy_enabled`) живут ровно один запрос — конфиг не трогается. ИИ
может гонять любые комбинации дорог, ничего не ломая. Проверка
до/после (`GET /api/mtproto/config`) — хорошая привычка, реальные
агенты так и делают (integrity-check).

### 19.2. Правило «GET → изменить → POST целиком»

⚠️ `POST /api/<section>/config` у b4 заменяет объект **целиком**, это не
merge. Наивный `POST {"dc_relay":"..."}` с одним полем затрёт секреты,
порт и всё остальное. Правильный цикл:

```
GET  /api/mtproto/config        → получили полный JSON
     (в памяти) поменяли ОДНО поле
POST /api/mtproto/config        → отправили ВЕСЬ объект обратно
```

MCP-путь (`b4_set_config_value`) этой проблемы не имеет — он меняет
одно значение атомарно и отчитывается старым значением. Ещё причина
по умолчанию предпочитать MCP.

### 19.3. WS-поток логов

```python
# ws://<host>:7000/api/ws/logs — живой хвост лога b4
# (websocket-клиент; авторизация — как у web-панели, если задана)
ws = create_connection("ws://192.168.1.1:7000/api/ws/logs")
while True:
    print(ws.recv())   # строки вида: TCP <src> → <dst> ip-set=<имя сета>
```

Приём «подписался на лог → дёрнул тестовый домен → увидел в потоке, какой
сет сматчил» — самый быстрый способ проверить, что перехват вообще
работает. ИИ делает это автоматически при любой проверке сетов.

## 20. Встроенные защиты b4: что ИИ не сможет сломать

b4 — редкий случай, когда защиту проектировали именно против
«энтузиаста-модели». Полный разбор в доках b4 (Settings → Integrations →
MCP server); выжимка:

**Жёстко отказано всегда (даже с Allow configuration changes = ON):**

| Отказано | Почему |
|---|---|
| Все креды (web, SOCKS5, MTProto, прокси апстримов) | секреты не для моделей |
| Настройки web-сервера (порт/bind/TLS) | ИИ не должен закрывать себе дверь и способ отката |
| Настройки MCP (токен, права) | ИИ не расширяет собственные полномочия |
| Движок захвата / TUN | переключение под живой сетью отрезает машину |
| Бекенд firewall | ошибочное значение = машина без правил |
| Метки пакетов / таблицы маршрутизации | несущая конструкция самого b4 |
| id сетов | на них ссылаются цепочки эскалации |
| Каталог логов, пути geo-файлов | файловые пути — только содержимое читаемо, не перемещаемо |

**Осторожности, о которых модель предупреждают сами ответы:**

- списки (домены сета и т.п.) **заменяются целиком**, не дополняются —
  ответ `b4_set_config_value` содержит предыдущее значение целиком, чтобы
  изменение можно было откатить руками;
- `b4_revert_last_change` шагает по истории изменений, сделанных **через
  MCP** с последнего старта b4; правки Web UI в историю не попадают,
  рестарт её очищает;
- «отказ пути ≠ отказ доступа»: например, логи читаются всегда, но
  переместить файл логов нельзя — принцип в том, что содержимое
  восстанавливаемо, а локация — нет.

**Browser-origins:** запросы с заголовком `Origin` принимаются только с
literal-IP/localhost самого b4 — посещённая веб-страница не достучится
до вашей панели через браузер. ИИ-приложения `Origin` не шлют и не
затронуты; hostname-доступ из браузера требует `allowed_origins` в
конфиг-файле.

Итого — модели доступна зона «видимые и обратимые изменения сетов».
Всё, что может отрезать вам путь назад (или украсть секрет), отрезано
на уровне бинарника b4, а не обещаний модели.

## 21. Автобан на нодах каскада: почему IP ИИ или роутера может попасть в бан

Если ваш ИИ-агент (или роутер) ходит мимо роутерного b4 ещё и на VPS с
Chimera (REST/MCP-доступ, пробы релеев, health-checkи), помните про
[AutoBan](SECURITY_BAN_FAQ.md) на этих нодах.

Симптом-легенда: «из внешнего мира все мои новые порты на VPS глухие, а
старые работают». Именно так выглядит бан автобана: ufw-правило
`deny from <IP>` встаёт **ниже** старых allow-правил (SSH/443) и **выше**
всех новых портов — старые сервисы продолжают отвечать, новые молча
дропаются. Кажется «порт-точечным фильтром провайдера», на деле это ваш
же защитник перестарался.

Механика: cron каждые 5 минут считает TLS-ошибки Xray по IP; порог
(например, 10 ошибок за 10 минут) — и IP улетает в ufw-deny. Обрывы
Wi-Fi, DPI-резеты на пути, агрессивные ретраи ИИ-клиента — всё это
«наследит» в error.log. У агентов привычка долбить endpoint ретраями —
идеальный кандидат.

Профилактика (на каждой ноде, куда ходит ИИ):

1. Вписать IP ИИ/роутера в **whitelist автобана** (TUI: Авто-бан →
   `[5] Управление whitelist`, или правкой `/var/lib/xray-installer/autoban.json`).
2. Whitelist автобана ≠ «белые списки» других модулей (ipban /
   user_ip_whitelist) — это разные хранилища, проверяйте именно
   autoban.json.
3. В REST-клиентах агента держать human-подобные ретраи: пауза 3–5 с,
   максимум 3–4 попытки, не штормить.

Лечение, если уже словили (на ноде):

```bash
sudo ufw status numbered                  # ПЕРВЫМ ДЕЛОМ при любой аномалии доступности
sudo ufw delete deny from <ваш-IP>        # снять бан
# и вписать себя в whitelist (см. выше), иначе вернётся
```

> **Урок на миллион:** при любой загадочной глухоте портов первым делом
> просите `ufw status numbered` — ответ там оказывается в половине
> случаев, и никогда не последним.

## 22. Гигиена: закрытие доступа и ротация токена

**Отзыв доступа ИИ — мгновенный, три уровня:**

| Уровень | Действие | Эффект |
|---|---|---|
| Токен | Web UI b4 → MCP → **Regenerate** (или очистить поле) | все сессии агента умирают в момент |
| Сеть | удалить firewall-правило / выключить nginx front | путь закрыт, токен невалиден в никуда |
| Сервис | выключить **Enable MCP server** | эндпоинт гаснет целиком |

**После завершения рабочей сессии с временным агентом** (разово позвали
помочь): Regenerate + удалить SSH-правило порта. Постоянному агенту
достаточно того, что порт открыт только с его IP.

**Регулярная гигиена:**

- сменён IP/подсеть ИИ → обновить Source IP в firewall-правиле (иначе
  агент «молча потерялся» — таймауты без ошибок);
- подозрение на утечку токена → Regenerate, обновить конфиги клиентов;
- ребут роутера «сломал» доступ → §23, пункт про runtime-правила;
- раз в квартал пересматривайте список whitelist'ов автобана на нодах —
  мёртвые IP вычищать (не копятся).

**Чего НЕ нужно:** отдельный токен под каждый инцидент (поле одно —
токен-то один, см. §12), паранойя вокруг read-агентов (они физически не
меняют данные), и тем более полный отказ от MCP из-за страха — read-only
режим даёт ИИ глаза без рук.

## 23. Диагностика подключений: типовые грабли

Симптом → причина → лекарство:

| Симптом | Причина | Лечение |
|---|---|---|
| curl висит и отваливается по таймауту | нет заголовка `Accept: application/json, text/event-stream` | добавить заголовок (§16) — №1 грабель |
| `401 Unauthorized` | неверный/отозванный токен | скопировать заново / Regenerate и обновить конфиги |
| Соединение таймаутится (весь путь) | firewall режет: Source IP-правило не совпало / порта нет в правилах | `ufw status numbered` (VPS) / правило роутера (§14); правило без `-s` открыть на время — для диагностики |
| `405 Method Not Allowed` на GET | так задумано (Streamable HTTP — только POST) | это не ошибка, шлите POST |
| Работало, после ребута роутера пропало | runtime iptables-правило умерло | персистенция `/jffs/scripts/firewall-start` (§14.3) |
| Работало, потом «само заглохло» новые порты на VPS, старые живы | автобан забанил IP (§21) | разбан + whitelist |
| Инициализация проходит, tools/call молчит | потерян `Mcp-Session-Id` (рестарт b4 / новая сессия) | заново initialize, сохранить свежий session-id |
| MCP «включён», но `/api/mcp` нет | выключен web-сервер b4 (порт 0) | включить web-сервер (Security), порт 7000 |
| ИИ видит инструменты, но изменения отклоняются | Allow configuration changes = OFF | это фича: включить осознанно (§11.4, §20) |
| TLS-ошибка при https-подключении | self-signed сертификат | импортировать CA в клиенте или согласиться с предупреждением; для CLI — `-k` на свой страх |

Порядок отсечения при «вообще не подключается»: порт слушает? (netstat
на хосте) → файрволл пускает? (правило/ufw status) → HTTP отвечает?
(curl без заголовков — соединение хотя бы устанавливается) → токен
верен? (401 vs зависание) → заголовки верны? (§16). Пять шагов, две
минуты, ноль гаданий.

## 24. Частые вопросы (Q&A)

**— Это безопасно? ИИ получит доступ ко всему?**
Нет, «всего» не будет. Read-only режим (по умолчанию) — ИИ только читает.
Режим записи ограничен сетами/подсистемами с откатом; креды, web-сервер,
MCP-настройки, движок захвата и firewall-бекенд запрещены на уровне
бинарника b4 (§20). Плюс токен действует только на `/api/mcp`.

**— Чем MCP лучше, чем просто дать ИИ REST с паролем?**
REST-пароль web-панели живёт сутки и сбрасывается при рестарте b4;
MCP-токен постоянный. REST «умеет» заменять конфиги целиком (§19.2) —
MCP меняет значения точечно с отчётом «было/стало» и откатом. Плюс
b4 сам рекламирует инструменты и описания настроек — модель не гадает.

**— Могу я пустить ИИ только посмотреть, без права что-то трогать?**
Да — это состояние по умолчанию (Allow configuration changes = OFF).
Диагностика при этом полноценная: статус, логи, соединения, метрики,
пробы дорог через REST.

**— Что если ИИ всё-таки накосячит в конфиге?**
Через MCP: «поставь как было» — b4_revert_last_change шагает назад по
истории; ответ изменения содержит старое значение целиком. Изменения
проходят ту же валидацию, что Web UI — невалидное просто не применится.

**— Обязательно ли открывать порт в интернет?**
Нет. Путь A (агент на домашнем ПК) вообще ничего не открывает. WAN нужен
только если агент живёт вне дома (§14–§15).

**— У меня динамический IP у агента. Что делать?**
Ограничивайте правилом подсеть (/24), либо путь C + авторизация на
nginx, либо периодически обновляйте Source IP. Не открывайте порт «на
все» — токен не заменяет файрволл.

**— Как закрыть доступ после сессии?**
Regenerate токена (мгновенно) + удалить firewall-правило. Выключение
MCP-сервера — для длительной паузы (§22).

**— Почему мой curl просто виснет?**
Нет заголовка `Accept: application/json, text/event-stream` (§16). Это
самая частая «поломка» протокола, и она притворяется таймаутом сети.

**— После перезагрузки роутера ИИ пропал.**
Runtime iptables-правило не пережило ребут — сделайте персистенцию в
`/jffs/scripts/firewall-start` (§14.3) или используйте GUI-правило.

**— Новые порты на VPS глухие, старые работают. Мой ИИ что-то сломал?**
Скорее ваш же автобан забанил IP (§21). Порядок действий: `ufw status
numbered` → разбан → whitelist.

**— ИИ и VLESS — что выбрать?**
Не «или». VLESS возит трафик, ИИ обслуживает систему. Сравнение и риски —
§9: там же список того, что даёт каждое и чем платите.

**— Можно подключить несколько ИИ-приложений?**
Да — несколько серверов в mcp.json/LM Studio, VS Code и Claude, каждый со
своим тумблером. Токен у них общий (один на b4) — Regenerate отзовёт
у всех разом.

**— Может ли ИИ подсмотреть секреты из ответов b4?**
Креды стрипаются из выводов инструментов по списку §18. Но `b4_diagnostics`
отдаёт hostname/интерфейсы/правила — рабочую карту сети. Если это
чувствительно — read-only не поможет (это чтение), поможет только
решение «не пускать» или локальный LLM.

**— b4 не сам вызывает ИИ-провайдеров? Нет скрытых звонков домой?**
b4 только обслуживает входящие HTTP-запросы на `/api/mcp`. Модель
работает в вашем приложении; исходящих подключений к ИИ-сервисам b4 не
делает и API-ключей не требует.

**— Подойдёт ли это для роутера без Merlin?**
b4 поддерживает несколько платформ; решение — платформенный firewall.
Пример для OpenWrt — §14.4, Keenetic/Mikrotik — по их штатным средствам.

**— Чем это лучше, чем я сам открою Web UI и посмотрю?**
Ничем, для одного взгляда. Смысл в масштабе: 200 строк лога, пять
гипотез, три пробы дорог и откат — это минуты ИИ и ваш вечер вручную.
Плюс скрипты остаются: завтра тот же инцидент закрывается одним
запуском.

**— Что ИИ НЕ сможет сделать через MCP в принципе?**
Сменить пароль/токены, переехать порт панели, выключить сам MCP,
переключить движок захвата или firewall-бекенд, изменить routing-таблицы
и метки, удалить/переименовать id сетов, переместить файлы логов и
geo-баз (§20). Всё это — «руками владельца».

**— Роутер — не перегружу ли я его запросами ИИ?**
MCP-запросы — это единицы REST-вызовов, на порядки легче одного
видеопотока через мост. Ограничение скорее в вашей дисциплине ретраев
(§21, автобан на пути).

**— Telegram показывает «Подключение…». С чего начать?**
Со §5–§6: сначала понять, что именно умерло (дверь или дорога), потом
лечить нужное. Практически: `POST /api/mtproto/test-ws {"dc":2}` —
живой срез всех дорог сразу; хвост WS-логов покажет, чей хендшейк
падает. Если «умерло всё» — это дороги, и чинится флипом `dc_relay`
(§8.3); если мертва одна дорога — кулдауны сами разберутся, ничего
делать не надо.

**— Обязательно ли городить весь эшелон из §8, или можно одним каналом?**
Можно одним — и большинство так живёт: мост с `auto`-апстримами уже
переключается между edge и CF-пулом сам. Эшелон из кейса §5 собран
потому, что там умерли ВСЕ WS-дороги разом; если у вас есть VPS с
прямым TCP до DC, socat-релей из «интересной опции» превращается в
спасательный круг за десять минут (§7.4).

**— tg://-ссылка «вечно подключается», хотя порт открыт. Что это?**
Почти всегда не Telegram. Чек-лист по частоте: (1) `ufw status
numbered` на прокси-сервере — нет ли DENY на ваш IP (автобан, §21);
(2) жив ли секрет — `secrets[].enabled=true` в конфиге после деплоя
через REST (§8.5, баг кейса); (3) доходит ли TCP вообще — probe-only
диал с роутера; (4) резолвится ли домен из `server=`. Самая коварная
причина — первая: бан сидит в середине списка правил, и «порт-точечная
глухота» выглядит как блок-лист цензуры.

## 25. Шпаргалка по командам

```bash
### включить/проверить MCP (Web UI: Settings → Integrations → MCP server)
curl -sS -m 10 -X POST "http://192.168.1.1:7000/api/mcp" \
  -H "Authorization: Bearer <TOKEN>" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"check","version":"1.0"}}}'

### firewall роутера (Merlin, SSH): открыть порт b4 только для IP ИИ
iptables -I INPUT -p tcp --dport 7000 -s 198.51.100.0/24 -j ACCEPT
# персистенция: /jffs/scripts/firewall-start (+x, JFFS custom scripts = On)

### OpenWrt
uci add firewall rule; uci set firewall.@rule[-1].src='wan' \
  && uci set firewall.@rule[-1].src_ip='198.51.100.50' \
  && uci set firewall.@rule[-1].dest_port='7000' \
  && uci set firewall.@rule[-1].proto='tcp' \
  && uci set firewall.@rule[-1].target='ACCEPT' \
  && uci commit firewall && /etc/init.d/firewall restart

### nginx front на VPS (путь C): меню Chimera
# Главное меню → 3 → Y → B → 8 → порт 9743 → 1 (LE-домен) / 2 (self-signed)

### инструменты MCP (ручной вызов — скрипт §16)
./mcp-call.sh b4_status '{}'
./mcp-call.sh b4_check_domain '{"domain":"youtube.com"}'
./mcp-call.sh b4_recent_connections '{"domain":"youtube.com"}'
./mcp-call.sh b4_logs_tail '{"lines":50}'
./mcp-call.sh b4_diagnostics '{}'
./mcp-call.sh b4_set_config_value '{"path":"sets.<id>.strategy","value":"extsplit"}'
./mcp-call.sh b4_revert_last_change '{}'

### REST: probe-only проба дорог (оверрайды НЕ сохраняются)
curl -sS -X POST "http://192.168.1.1:7000/api/mtproto/test-ws" \
  -H "Content-Type: application/json" -d '{"dc":2}'
curl -sS -X POST "http://192.168.1.1:7000/api/mtproto/test-ws" \
  -H "Content-Type: application/json" \
  -d '{"dc_relay":"<relay-host>:7007","upstream_mode":"tcp","cfproxy_enabled":false,"dc":3}'

### REST: правильный цикл изменения конфига (POST = ЗАМЕНА целиком!)
curl -sS http://192.168.1.1:7000/api/mtproto/config > cfg.json
# ...правим ОДНО поле в cfg.json...
curl -sS -X POST "http://192.168.1.1:7000/api/mtproto/config" \
  -H "Content-Type: application/json" -d @cfg.json

### VPS: автобан-не-моя-вина (§21)
sudo ufw status numbered            # ПЕРВЫМ делом при аномалиях
sudo ufw delete deny from <ваш-IP>  # разбан
# whitelist: TUI Авто-бан → [5], или /var/lib/xray-installer/autoban.json

### Telegram: проба дорог / флип моста (§7–§8)
# срез всех дорог DC2 (probe-only, в конфиг не пишется):
curl -sS -X POST "http://192.168.1.1:7000/api/mtproto/test-ws" \
  -H "Content-Type: application/json" -d '{"dc":2}'
# перевести мост на socat-релей VPS (Web UI: Settings → MTProto → DC relay):
#   поле = <relay-host>:7007, режим auto; очистить поле = вернуться на CF-пул
# обновить карту дата-центров ТГ:
curl -sS -X POST "http://192.168.1.1:7000/api/mtproto/refresh-dcs"

### закрыть доступ
# Web UI: MCP → Regenerate (токен умер) → удалить firewall-правило → (опция) MCP off
```
