# AutoBan / Honeypot / IP-Ban / GeoIP Block / РФ-блокировка — FAQ по защите Chimera

Это подробный гайд по пяти модулям Chimera, отвечающим за блокировку
входящего трафика от злоумышленников, сканеров портов и государственных
DPI-зондов. Описаны принципы работы, отличия, совместные комбинации,
типовые проблемы и их решения.

> **Краткая навигация:**
> - **AutoBan** — автоматическая блокировка IP по превышению порога
>   TLS-handshake ошибок в логе Xray (защита от перебора/зондирования).
> - **Honeypot-порт** — TCP-ловушка: открывает «фейковый» порт и
>   мгновенно банит любого, кто к нему подключится.
> - **IP-Ban** — ручной бан IP/CIDR/диапазона/ASN через `iptables/ipset`
>   с сохранением состояния и восстановлением после reboot.
> - **GeoIP Block** — блокировка по странам и интернет-сканерам на
>   уровне Xray routing rules (outboundTag=block + blackhole).
> - **Блокировка входящих из РФ** — закрытие Xray-порта для всех
>   российских подсетей через `iptables/ipset` (на уровне ядра, до Xray).

## 1. Зачем пять разных функций, если все банят IP

На первый взгляд — пять модулей делают одно и то же: добавляют правило
блокировки в firewall или routing. Но они решают **разные задачи**,
работают на **разных уровнях стека** и нормально функционируют только
вместе.

### AutoBan

Реагирует на **уже произошедшие** события: сканирует `error.log` Xray,
считает TLS-handshake ошибки по IP, и если за последние N минут их
накопилось больше порога — банит IP. Это **реактивная** защита: IP
попадает в бан только после того, как реально «наследил».

- Хорошо: ловит DPI-зонды, сканеры протоколов, ботов, подбирающих
  cipher-suites.
- Плохо: IP успевает сделать N-1 попытку до бана. Если N=10 —
  злоумышленник делает 9 бесплатных зондирований.

### Honeypot-порт

Работает **проактивно**: открывает порт, который не нужен ни одному
легитимному клиенту, и банит каждого подключившегося. Сканер портов
заглядывает на все TCP-порты подряд — попадается на первом же запросе
к honeypot-порту.

- Хорошо: банит ещё до того, как сканер дойдёт до реального порта
  Xray. Ловит даже тех, кто вообще не делает TLS-handshake.
- Плохо: ничего не знает про поведение на порту 443. Если злоумышленник
  подключается сразу к Xray и соблюдает «тихий» режим — honeypot его
  не увидит.

### IP-Ban

Не реактивный, не проактивный — **ручной**. Администратор сам
указывает, что забанить: один IP, подсеть, диапазон или целую ASN.
Применяется для превентивной блокировки известных плохих сетей
(РКН-инфраструктура, сканеры Censys, конкретные провайдеры).

- Хорошо: можно забанить сразу всю ASN со всеми её подсетями, не
  дожидаясь, пока каждый IP «засветится» в логах.
- Плохо: требует ручного решения. Список нужно поддерживать — ASN
  меняют префиксы, новые сканеры появляются.

### GeoIP Block

Работает **на уровне Xray routing** — добавляет в `config.json`
правила вида `{geoip: {country: [CN,RU]}, outboundTag: "block"}`.
Xray сам определяет страну клиента по GeoIP-базе и отправляет
соединение в `blackhole` outbound. Также умеет блокировать подсети
известных сканеров (Shodan, Censys) и отдельные ASN.

- Хорошо: работает на уровне приложения (Xray), не требует iptables.
  Можно включать/выключать без root. Поддерживает allowlist и
  blocklist по странам.
- Плохо: срабатывает **после** установления TLS-handshake — клиент
  успевает получить fake-сертификат и понять, что его блокируют.
  Не защищает от сканеров портов (они даже до Xray не доходят).

### Блокировка входящих из РФ

Работает **на уровне ядра** через `iptables/ipset`: DROP входящих
TCP-соединений на порт Xray с российских подсетей. Список подсетей
берётся из `delegated-ripencc-latest` (RIPE NCC), обновляется по cron.
Whitelist позволяет исключить конкретные IP (свой дом, клиенты с
РФ-IP через `user_ip_whitelist`).

- Хорошо: работает **до** Xray — соединение даже не доходит до
  приложения. Эффективно против всех РФ-IP сразу, включая РКН-инфра.
  Поддерживает IPv4 + IPv6.
- Плохо: закрывает **только конкретный порт** (по умолчанию 443).
  Другие порты (22, 80, 8443) остаются открытыми — там РФ-IP могут
  стучать и накапливать TLS-ошибки. Требует `ipset` (не всегда есть
  на Debian 13 без ufw).

### Аналогия

| Модуль | Реальная аналогия |
|---|---|
| AutoBan | Камеры наблюдения + автоматический турникет, который закрывается после 10 неудачных проходов |
| Honeypot | Фальшивая дверь рядом с настоящей. Кто за неё дёргает — выйти уже не может |
| IP-Ban | Чёрный список гостей у охраны. Не пустить конкретных людей, даже если они ещё ничего не сделали |
| GeoIP Block | Охрана проверяет паспорт на входе: «из Китая — не пускаем». Но клиент уже успел поздороваться |
| РФ-блокировка | Забор вокруг территории: из РФ-региона вообще не подойти к воротам |

## 2. Принципиальная разница: пять типов защиты

| Характеристика | AutoBan | Honeypot | IP-Ban | GeoIP Block | РФ-блокировка |
|---|---|---|---|---|---|
| **Тип** | реактивный | проактивный | ручной | geo-routing | kernel-drop |
| **Уровень** | ufw/iptables | ufw (systemd) | iptables+ipset | Xray config.json | iptables+ipset |
| **Когда банит** | после N ошибок | при 1 подключении | когда админ сказал | при подключении | при подключении |
| **Что анализирует** | `error.log` Xray | TCP-соединение | решение админа | GeoIP-база | RIPE delegated |
| **Порог** | 10 ошибок / 10 мин | 1 подключение | без порога | без порога | без порога |
| **Кого ловит** | активных зондировщиков | сканеры портов | кого укажет админ | страны / сканеры | все РФ-подсети |
| **Зависит от Xray** | да | нет | нет | да (routing) | нет |
| **Автоматический cron** | да (5 мин) | нет (systemd) | нет | да (через ru_subnets) | да (еженедельно) |
| **Хранение состояния** | `autoban.json` | `honeypot.json` | `ipban.json` + ipset | в `config.json` | `ingress_geoip.json` |
| **Восстановление после reboot** | через cron | через systemd | через `ipset-persist` | через Xray config | через systemd-unit |
| **Требует root** | да (ufw/iptables) | да (systemd+ufw) | да (iptables) | нет (только Xray) | да (iptables) |
| **Поддержка IPv6** | да | да | да | да (geoip6.dat) | да |
| **Telegram-уведомления** | да | да (при вкл.) | нет | да | да |

## 3. AutoBan — автоматический бан по TLS-ошибкам

### Как работает

```
       каждые 5 минут (cron /etc/cron.d/xray-autoban)
                    ↓
   /usr/local/bin/xray-autoban.sh
                    ↓
        парсит /var/log/xray/error.log
        за последние N минут (по умолчанию 10)
                    ↓
        считает TLS-ошибки по каждому IP
                    ↓
        if (errors[ip] >= threshold && ip not in banned):
                    ↓
        ban через ufw (или iptables fallback)
                    ↓
        запись в /var/lib/xray-installer/autoban.json
        запись в /var/log/xray-autoban.log
        запись в /var/log/xray-ban-report.txt
        Telegram-уведомление (если настроено)
```

### Что считается TLS-ошибкой

Модуль ищет в `error.log` строки, соответствующие регулярному выражению:

```
tls: handshake | tls: no supported versions | tls: no cipher
failed to read
invalid header
connection reset
broken pipe
```

Это **именно** паттерны активного зондирования: DPI-сканер подключается
к Xray-порту, инициирует TLS с неправильными параметрами (или сразу
рвёт соединение), и Xray фиксирует это как ошибку. Нормальные
клиенты таких ошибок не оставляют — у них handshake завершается
успешно.

### Порог по умолчанию

- **10 ошибок за 10 минут** (`_BAN_THRESHOLD_DEFAULT = 10`,
  `_BAN_WINDOW_MINUTES = 10`).
- Меняется через меню AutoBan → `[2] Изменить порог / окно`.

### Что AutoBan НЕ банит

- IP нод каскада (entry/exit) — cron каждый прогон резолвит домены
  нод через DoH и их IP попадают в рантайм-сет `auto_wl` (живает один
  прогон, пересчитывается каждые 5 минут, в файл не пишется — см.
  «Гигиена whitelist» ниже), чтобы не забанить собственную
  инфраструктуру.
- Собственные IP сервера (public + все интерфейсные) — тоже в
  `auto_wl`, определяются каждый прогон локально (`ip route`,
  `ip addr`) без сети.
- IP из `_BAN_WHITELIST_DEFAULT` (`127.0.0.1`, `::1`) и добавленные
  вручную через `[5] Управление whitelist` — это и есть весь
  «Пользовательский whitelist».
- IP, у которых ошибок меньше порога — даже если они ведут себя
  подозрительно. AutoBan не делает «подозрительный → бан», только
  «превышение порога → бан».

### Гигиена whitelist: авто-резолвы не оседают в списке (фикс 2026-09-21)

**Кейс <node-2>:** в «Пользовательском whitelist» меню `[5]` скопилось
~80 IP из 194.67.71.0/24, которые владелец не вносил. Атрибуция:
AS197695 REG.RU, парковочный кластер регистратора (ParkingCrew —
HTTP-проб отдавал `data-page-type="parking-crew"`). Домены каскада
жили на NS `ns1/ns2.reg.ru`; когда у имени нет A-записи в зоне, DNS
регистратора отвечает парковочными IP round-robin — каждый запрос
получает другой адрес из /24.

До фикса cron сливал результат резолва доменов каскада в
пользовательский `cfg['whitelist']` и персистил его — каждый резолв
навсегда оседал в списке. Домен без A-записи раз в 5 минут приносил
новый случайный парковочный IP; DDNS-ротация нод оседала всей
историей адресов. Побочные эффекты: дырка в автобане для ~80
shared-IP парковки (туда могут приземлиться чужие домены) и
бесконечный рост списка.

Теперь авто-IP живут в рантайм-сете `auto_wl`: защищают ровно один
прогон, пересчитываются каждые 5 минут, в файл не пишутся.
`cfg['whitelist']` = только ручные записи из меню [5]. Ноды по-
прежнему видны в меню `[5]` в секции «Автозащита — IP нод каскада»,
вычисляемой на лету.

**Чистка накопленного до фикса мусора** (один раз):

```bash
sudo cp /var/lib/xray-installer/autoban.json{,.bak}
sudo python3 -c "
import json
p = '/var/lib/xray-installer/autoban.json'
c = json.load(open(p))
c['whitelist'] = [ip for ip in c.get('whitelist', []) if not ip.startswith('194.67.71.')]
json.dump(c, open(p, 'w'), indent=2, ensure_ascii=False)
print('осталось:', len(c['whitelist']))"
```

По аналогии можно вычистить и старые IP мигрировавших нод
(Hoster-C/Hoster-B/Hoster-FI/…) — текущие IP нод вернутся сами через
«Автозащиту», не записываясь в пользовательский список.

После обновления кода нужно переустановить cron-скрипт, чтобы новый
шаблон лёг в `/usr/local/bin/xray-autoban.sh`: AutoBan → `[2] Изменить
порог / окно` → Enter/Enter (переустановит с теми же значениями),
либо `[1]` выключить/включить.

### Как включить

Главное меню → **Безопасность и автоматизация** → `[1] AutoBan** →
`[1] Включить авто-бан`.

При включении:
1. Создаётся `/etc/cron.d/xray-autoban` — cron каждые 5 минут.
2. Создаётся `/usr/local/bin/xray-autoban.sh` — встроенный Python-скрипт
   с захардкоженными порогом и окном.
3. State `autoban.json` обновляется: `enabled: true`.

### Миграция FW-порядка [F]

Пункт `[F] FW-порядок банов` переставляет deny-правила существующих
банов ПЕРВОЙ строкой `ufw-user-input` — выше allow-правил портов
(first-match-wins). Нужен один раз после обновления на фикс
2026-09-21, если баны были поставлены старым кодом (в конец цепочки).

**Батч-режим (фикс 2026-09-21, кейс vds14808):** миграция делает
**одну правку** `/etc/ufw/user.rules` + **один** `ufw reload` —
секунды. Раньше на каждый IP делалось два CLI-вызова `ufw delete` +
`ufw insert`, каждый из которых ре-апплит весь ruleset (1-3 с на
вызов) — 199 IP «висели» 10-20 минут без прогресса. Если быстрый
путь не удался (нет/не читается user.rules, упал reload) — автоматический
фолбэк на по-IP CLI с прогрессом каждые 20 IP. Повторный запуск
идемпотентен: если deny уже стоят сверху — мгновенное «199 из 199»
без единого вызова ufw.

Перед правкой создаётся бэкап `user.rules.chimera-bak`; при неудачном
reload файл откатывается из бэкапа. Проверка результата:

```bash
iptables -L ufw-user-input -n --line-numbers | head
# строки 1..N должны быть DROP для забаненных IP, ALLOW портов — ниже
```

### Разбан IP — батч-режим (в т.ч. «all»)

`[3] Разбанить IP` для **нескольких** IP (в т.ч. `all`) снимает
deny-правила **одной правкой** `/etc/ufw/user.rules` + **одним**
`ufw reload` (фикс 2026-09-21, кейс vds14808: 199 IP по-одному через
`ufw delete` висели ~5 минут — каждый вызов ре-апплит весь ruleset).
Удаляются все deny-строки целевых IP, включая дубли; чужие баны и
allow-правила не трогаются. Один IP — обычный CLI delete (быстро).
CLI-фолбэк с прогрессом — только если файловый путь не удался.

### История банов

В меню AutoBan → `[6] История банов` — отдельный список, который
хранит **все** баны (включая уже разбаненные). Ограничение: 500
записей, после чего старые отбрасываются.

**Очистка `[C]`:** удаляет и таблицу истории (state), и файл отчёта
`/var/log/xray-ban-report.txt`. До фикса 2026-09-21 очистка «не
работала»: миграция `banned → ban_history` в `_autoban_load()`
воскрешала историю при следующем открытии меню (cron за 5 минут
перебанивал пару активных сканеров → `banned` непуст → история
пересоздавалась из него), плюс файл отчёта под таблицей никто не
чистил. Теперь флаг `history_migrated` в state (ставится при первой
миграции ИЛИ при очистке `[C]`) гарантирует: очищенная история не
воскреснет. **Новые** баны по-прежнему записываются, пока работает
авто-бан — это нормально и останавливается только отключением
авто-бана `[1]`.

Запись в истории содержит:
- IP
- `banned_at` — дата/время бана
- `unbanned_at` — дата/время разбана (или `None` если активен)
- `count` — сколько ошибок накопилось
- `reason` — текстовая причина (например, `12 TLS errors in 10min`)
- `asn` / `isp` / `org` — ASN, провайдер и организация (с фикса
  2026-09-20, кейс vds14808: раньше cron-бан писал прочерки «без
  ASN-lookup»; теперь lookup выполняется в момент бана — ip-api.com
  + файл-кеш `/var/lib/xray-installer/autoban_asn_cache.json`, TTL
  7 дней — и значения сохраняются в запись). В таблице истории
  строка `↳ AS… · Провайдер` берётся из записи, для старых записей —
  lookup на лету.

### Полный лог

`/var/log/xray-ban-report.txt` — читаемый отчёт, ротация раз в 7 дней
(`_BAN_REPORT_TTL_DAYS = 7`). Содержит по одной строке на каждый бан
с ASN-информацией (ASN / Провайдер / Организация). Открывается через
`[6]` после таблицы истории. Записи, сделанные ДО фикса 2026-09-20,
останутся с прочерками — это статический текстовый лог.

### Плюсы

- **Полностью автоматический** — включил и забыл.
- **Не требует внешних зависимостей** — ufw или iptables, которые уже
  есть в системе.
- **Не портит конфиг Xray** — работает только на уровне firewall.
- **Уведомления в Telegram** — если настроен бот, приходит уведомление
  о каждом бане.
- **Whitelist для chain-нод** — автоматически резолвит домены exit-нод
  через DoH и добавляет их IP в whitelist, чтобы не забанить
  собственную инфраструктуру при смене IP ноды.

### Минусы

- **Не видит «тихих» сканеров** — если злоумышленник делает 9 попыток
  и останавливается, он не получит бан.
- **Реагирует с задержкой** — cron запускается раз в 5 минут. За это
  время сканер успеет сделать десятки зондирований.
- **Не работает без Xray** — если Xray остановлен, `error.log` не
  обновляется, AutoBan не имеет данных.
- **Ложные срабатывания** — если у реального клиента плохой интернет
  (много TCP-резетов), его IP может попасть в бан. Лечится добавлением
  в whitelist.

## 4. Honeypot-порт — ловушка для сканеров

### Как работает

```
   systemd-сервис xray-honeypot.service
                    ↓
        Python-скрипт /usr/local/bin/xray-honeypot.py
                    ↓
        слушает TCP-порт (по умолчанию 9999) через socket()
                    ↓
        кто-то подключился → accept() → conn.close()
                    ↓
        если IP не в whitelist:
                    ↓
        ufw deny from <ip> to any comment "honeypot"
                    ↓
        запись в /var/log/xray-honeypot.log
        запись в /var/lib/xray-installer/honeypot.json
```

### Принцип ловушки

Honeypot-порт — это **порт, который не нужен ни одному легитимному
клиенту**. Сканер портов (nmap, masscan, zmap) проверяет все порты
подряд — он обязательно зайдёт на honeypot-порт. Мгновенный бан.

Никакого протокола поверх TCP не поднимается — `accept()` сразу
закрывает соединение. Это нормально: сканеру достаточно знать, что
порт открыт, он идёт дальше. А мы уже запомнили его IP.

### Порт по умолчанию

`9999` — выбран как «неинтересный» порт, не пересекающийся с
популярными сервисами. Можно изменить через меню Honeypot → `[2]
Изменить порт`.

**Важно:** Honeypot не даст поставить себя на порт Xray или любой
другой занятый порт. Проверка делается через `state.json`.

### Что Honeypot НЕ ловит

- Целенаправленный сканер, который проверяет **только** конкретный
  порт (например, только 443). Если он не заходит на 9999 — Honeypot
  его не видит.
- «Тихий» злоумышленник, который подключается к Xray напрямую и
  ведёт себя нормально.
- DHCP-клиентов, у которых IP меняется каждые несколько часов —
  Honeypot забанил старый IP, новый у них уже другой.

### Как включить

Главное меню → **Безопасность и автоматизация** → `[P] Honeypot-порт** →
`[1] Запустить Honeypot`.

При включении:
1. Генерируется `/usr/local/bin/xray-honeypot.py` — автономный
   Python-скрипт с захардкоженными портом и whitelist.
2. Создаётся systemd-юнит `/etc/systemd/system/xray-honeypot.service`.
3. Сервис включается и запускается.
4. State `honeypot.json` обновляется: `enabled: true`.

### Whitelist

Whitelist **отдельный** от AutoBan. Это значит, что если IP в
whitelist AutoBan, но не в whitelist Honeypot — Honeypot его забанит.

В whitelist Honeypot нужно добавить:
- 127.0.0.1, ::1 (по умолчанию)
- IP всех серверов cascade (entry/exit), чтобы они не попали в бан
  при взаимной диагностике
- Свой домашний/рабочий IP — на случай если вдруг полезете на
  honeypot-порт из любопытства

### Лог и пойманные IP

- `/var/log/xray-honeypot.log` — текстовый лог: CONNECT / BAN / SKIP /
  ERROR. Ротации нет — следите за размером вручную.
- `honeypot.json` → `banned` — словарь пойманных IP с timestamp.
- В меню: `[4] Список пойманных IP`, `[6] Последние 30 строк лога`.

### Плюсы

- **Мгновенный бан** — IP попадает в чёрный список при 1 подключении,
  без порога.
- **Ловит даже тех, кто не делает TLS-handshake** — достаточно
  TCP-connect.
- **Не зависит от Xray** — отдельный systemd-сервис, работает даже
  когда Xray остановлен.
- **Очень дешёвый по ресурсам** — Python-сокет, без TLS, без логики
  протокола.
- **Эффективен против автоматических сканеров** (Censys, Shodan,
  Shadowserver) — они проверяют все порты, обязательно попадутся.

### Минусы

- **Ловит только «глупых» сканеров** — тех, кто проверяет все порты.
  Целенаправленный атакующий, знающий порт Xray, обойдёт honeypot.
- **Раздельный whitelist** — нужно поддерживать два списка (AutoBan +
  Honeypot), иначе можно случайно забанить свою инфраструктуру.
- **Не работает через NAT/прокси** — если сервер за NAT, honeypot
  видит IP NAT-шлюза, а не реальный IP клиента. На VPS этой проблемы
  нет.
- **Опасен для любопытного админа** — если случайно сделать
  `telnet server 9999` со своего рабочего IP, попадёшь в бан. Всегда
  добавляйте свой IP в whitelist перед включением.

## 5. IP-Ban — ручной бан IP/CIDR/ASN

### Как работает

```
   меню IP-Ban → [1] Добавить бан → ввод:
       1.2.3.4              — один IP
       10.0.0.0/24          — подсеть
       10.0.0.1-10.0.0.255  — диапазон
       AS12345              — вся ASN (RIPE Stat)
                    ↓
   если ASN: запрос к stat.ripe.net/data/announced-prefixes
                    ↓
   все CIDR добавляются в ipset:
       xray_manual_ban   (IPv4)
       xray_manual_ban6  (IPv6)
                    ↓
   iptables INPUT -m set --match-set xray_manual_ban src -j DROP
   ip6tables INPUT -m set --match-set xray_manual_ban6 src -j DROP
                    ↓
   сохранение в /var/lib/xray-installer/ipban.json
                    ↓
   ipset save → /etc/ipset.conf (через ipset-persist)
```

### Форматы ввода

| Формат | Пример | Что делает |
|---|---|---|
| Один IP | `1.2.3.4` | Банит один IPv4-адрес |
| Подсеть (CIDR) | `10.0.0.0/24` | Банит 256 адресов |
| Диапазон | `10.0.0.1-10.0.0.255` | Банит все IP между двумя указанными |
| ASN | `AS12345` | Скачивает все префиксы ASN через RIPE Stat, банит их все |
| IPv6 | `2001:db8::/32` | Банит IPv6-подсеть |

Можно вводить **несколько значений через запятую или пробел**:
```
1.2.3.4, 10.0.0.0/8, AS1234
```

### Бан ASN — отдельно

При вводе `AS61280` IP-Ban:
1. Запрашивает `https://stat.ripe.net/data/announced-prefixes/data.json?resource=AS61280`.
2. Получает список всех префиксов, анонсируемых этой ASN
   (для AS61280 — 12 префиксов, ~2304 IP).
3. Добавляет каждый префикс в ipset.
4. Сохраняет запись в `ipban.json` с пометкой `kind: "asn"`.

**Сетевой запрос** — если RIPE Stat недоступен, бан ASN не сработает.
Лечится повторной попыткой через несколько минут.

### Что IP-Ban НЕ затрагивает

- Конфиг Xray (никаких изменений в `config.json`)
- GeoIP-блокировку (`xray_ru_block` / `xray_ru_block6`)
- AutoBan (`xray-autoban`)
- Honeypot-порт
- Службы Xray, nginx, Telemt

Это **только** ручной ban-list, независимый от остальной защиты.

### Персистентность

`ipset` хранится в оперативной памяти. После reboot правила
пропадают. Для восстановления:

1. **`[4] Восстановить из state`** — перечитывает `ipban.json` и
   заново наполняет ipset.
2. **`[5] Сохранить ipset → /etc/ipset.conf`** — выгружает текущий
   ipset в файл, который восстанавливается при загрузке системы
   через `ipset-persist` (отдельный пункт меню `IP`).

**Рекомендация:** после каждого добавления банов делайте `[5]` —
тогда после reboot состояние восстановится автоматически.

### Как включить

Главное меню → **Безопасность и автоматизация** → `[IB] IP-Бан** →
`[1] Добавить бан** → введите IP/CIDR/ASN.

Сразу после применения правила активны. Никакого «включить/выключить»
не требуется — IP-Ban всегда активен, вопрос только в том, есть ли
записи в ipset.

### Плюсы

- **Банит всю ASN сразу** — не нужно ждать, пока каждый IP засветится.
- **Поддерживает IPv6** — отдельный ipset `xray_manual_ban6`.
- **Не зависит от других модулей** — можно включать без AutoBan и
  Honeypot.
- **Восстанавливается после reboot** — через `ipset-persist`.
- **Чистый iptables/ipset** — никакой логики в Python после применения,
  работает на скорости ядра.

### Минусы

- **Требует ручного обслуживания** — список плохих ASN нужно
  поддерживать.
- **RIPE Stat иногда тормозит** — при бане большой ASN запрос может
  занимать 5-15 секунд.
- **Список ASN устаревает** — провайдеры меняют префиксы, нужно
  периодически пересоздавать бан.
- **Можно случайно забанить легитимных пользователей** — если
  забанить крупную ASN (например, Ростелеком AS12389), отрубишь
  миллионы абонентов.

## 6. GeoIP Block — блокировка по странам в Xray routing

### Как работает

```
   клиент подключается к Xray (TCP+TLS на порт 443)
                    ↓
        Xray принимает соединение, делает TLS handshake
                    ↓
        Xray проверяет routing.rules в config.json
                    ↓
        правило {geoip: {country: [CN]}, outboundTag: "block"}
                    ↓
        если IP клиента в Китае → отправляем в blackhole outbound
                    ↓
        соединение закрывается (клиент получает TCP RST)
```

### Уровень работы

GeoIP Block работает **на уровне приложения** (Xray), а не на уровне
ядра. Это значит:
- Соединение **доходит** до Xray (TCP handshake + TLS handshake
  завершаются).
- Xray определяет страну клиента по `geoip.dat` / `geoip6.dat`.
- Если страна в blocklist — Xray отправляет соединение в `blackhole`
  outbound, который просто закрывает соединение.

Это **отличает** GeoIP Block от РФ-блокировки: последняя работает на
уровне `iptables` и режет соединение ещё **до** того, как оно дойдёт
до Xray.

### Режимы

| Режим | Что делает | Пример |
|---|---|---|
| **Allowlist** | Принимать только из указанных стран, всё остальное блокировать | `RU,KZ,BY` → остальное в block |
| **Blocklist** | Блокировать конкретные страны, остальное пропускать | `CN,IR,KP` → в block |
| **Scanner block** | Заблокировать подсети известных сканеров (Shodan, Censys, Shadowserver) | готовый список |
| **AS-маршрутизация** | Блокировать (или направлять в direct) конкретные ASN через RIPE Stat | `AS14061` (DigitalOcean) → block |
| **РФ подсети → direct** | Российские подсети направлять через direct outbound (не через exit-ноду) | защита от цензора |

### Что GeoIP Block НЕ делает

- **Не режет соединение до TLS handshake** — клиент успевает получить
  fake-сертификат REALITY и понять, что его блокируют. Это нормально:
  REALITY специально отдаёт «настоящий» сайт-заглушку.
- **Не защищает от сканеров портов** — сканер, проверяющий все порты,
  даже не доходит до Xray (его ловит Honeypot).
- **Не закрывает SSH/HTTP/другие порты** — работает только для трафика,
  проходящего через Xray.

### Как включить

Главное меню → **Безопасность и автоматизация** → `[2] GeoIP Block** →

- `[1]` Allowlist — ввести коды стран (например `RU,KZ,BY`)
- `[2]` Blocklist — ввести коды стран (например `CN,IR,KP`)
- `[3]` Заблокировать диапазоны сканеров (Shodan, Censys)
- `[4]` Удалить все правила
- `[5]` РФ подсети RIPE → direct (защита от цензора)
- `[6]` AS-маршрутизация (по ASN хостера/провайдера)
- `[7]` Управление AS-маршрутами

При применении:
1. Читается текущий `config.json` Xray.
2. Добавляются routing rules с `outboundTag: "block"`.
3. Создаётся/обновляется `blackhole` outbound.
4. Xray перезапускается.
5. При ошибке — откат к предыдущему конфигу.

### Плюсы

- **Не требует root** для изменения правил (только запись в `config.json`
  + restart Xray).
- **Гибкая настройка** — можно комбинировать страны, ASN, отдельные IP
  в одном правиле.
- **Allowlist и Blocklist одновременно** — например, allowlist `RU,KZ`
  + blocklist внутри них `AS61280` (ГРЧЦ).
- **Не конфликтует с iptables-правилами** — работает на другом уровне
  стека.
- **Авто-определение ASN хостинга** — при первом открытии меню Chimera
  определяет ASN вашего VPS-провайдера и предлагает добавить его в
  whitelist (чтобы не заблокировать сами себя).

### Минусы

- **Срабатывает после TLS handshake** — клиент видит, что его блокируют.
  Для полной невидимости используйте РФ-блокировку (kernel-level DROP).
- **Требует GeoIP-базы** (`geoip.dat`, `geoip6.dat`) — обновляются через
  отдельный пункт меню `[3] Управление GeoIP/GeoSite файлами`.
- **Перезапуск Xray при каждом изменении** — на 1-2 секунды обрывает
  активные соединения клиентов.
- **Не защищает другие сервисы** (SSH, nginx, Telemt) — только трафик
  через Xray.

## 7. Блокировка входящих из РФ — kernel-level DROP через iptables/ipset

### Как работает

```
   клиент из РФ подключается к порту 443
                    ↓
        iptables INPUT chain:
        -m set --match-set xray_ru_block src -j DROP
                    ↓
        ядро проверяет IP клиента в ipset xray_ru_block
                    ↓
        если IP в РФ-подсети → DROP (тихий сброс пакета)
                    ↓
        клиент получает TCP timeout (не RST, а именно timeout)
                    ↓
        до Xray соединение НЕ доходит
```

### Уровень работы

РФ-блокировка работает **на уровне ядра** (iptables + ipset). Это
самый ранний возможный уровень фильтрации:
- Пакет принимается сетевым интерфейсом.
- Проходит через `iptables INPUT` chain.
- Если IP в `xray_ru_block` ipset → ядро дропает пакет.
- До Xray (и до TLS handshake) дело не доходит.

Это **отличает** РФ-блокировку от GeoIP Block: последняя работает на
уровне приложения и срабатывает только после TLS handshake.

### Источник данных

Список российских подсетей берётся из **RIPE NCC delegated-ripencc-latest**:
```
https://ftp.ripe.net/ripe/stats/delegated-ripencc-latest
```

Это официальный реестр распределения IP-адресов по странам. Файл
обновляется RIPE NCC ежедневно, содержит ~5000-6000 российских
подсетей (IPv4 + IPv6).

Chimera кэширует файл в `/etc/xray/ru_subnets_ripe.txt` и обновляет
по cron (по умолчанию еженедельно, можно изменить на ежедневный).

### Реализация

Через `ipset` (эффективно для 5000+ CIDR):
```bash
# Создание ipset
ipset create xray_ru_block hash:net family inet
ipset create xray_ru_block6 hash:net family inet6

# Наполнение (5000+ CIDR)
ipset add xray_ru_block 5.3.32.0/19
ipset add xray_ru_block 5.45.192.0/18
# ... и т.д.

# Привязка к iptables
iptables  -A INPUT -p tcp --dport 443 -m set --match-set xray_ru_block  src -j DROP
ip6tables -A INPUT -p tcp --dport 443 -m set --match-set xray_ru_block6 src -j DROP
```

Если `ipset` недоступен — fallback на plain iptables (создаёт отдельное
правило на каждый CIDR, работает медленнее, но совместимо со всеми
системами).

### Whitelist

Whitelist **отдельный** — хранится в `ingress_geoip.json`. IP из
whitelist добавляются как `iptables -I INPUT 1 -s <IP> -j ACCEPT` —
**перед** DROP-правилом, поэтому имеют приоритет.

Дополнительно: модуль `user_ip_whitelist.py` создаёт ipset
`clients_wl_v4` / `clients_wl_v6` для per-user исключений. Это
позволяет клиентам с российскими IP подключаться к VLESS на 443, даже
если РФ-блокировка включена — но только если их IP в их личном
whitelist (управляется через User Portal).

### Что РФ-блокировка НЕ делает

- **Закрывает только конкретный порт** (по умолчанию 443 или
  `server_port` из `state.json`). Другие порты (22, 80, 8080, 8443)
  остаются открытыми для РФ-IP.
- **Не блокирует российские ASN точечно** — она блокирует все
  РФ-подсети оптом. Если нужно забанить конкретную ASN (например,
  ГРЧЦ), используйте IP-Ban.
- **Не работает без `ipset`** — на Debian 13 без ufw может не быть
  `ipset`, тогда fallback на plain iptables (медленно).

### Как включить

Главное меню → **Безопасность и автоматизация** → `[G] Блокировка
входящих из РФ**.

При включении:
1. Проверяется возраст RIPE-файла (если старше 7 дней — обновляется).
2. Скачивается `delegated-ripencc-latest`.
3. Парсится, извлекаются РФ-подсети (IPv4 + IPv6).
4. Создаются/обновляются ipset `xray_ru_block` / `xray_ru_block6`.
5. Добавляются iptables-правила с `--dport {port}`.
6. Применяется per-user whitelist (если установлен).
7. Сохраняется state в `ingress_geoip.json`.
8. Устанавливается cron для еженедельного обновления.
9. Устанавливается systemd-юнит для восстановления ipset при reboot.

### Плюсы

- **Самый ранний уровень фильтрации** — соединение не доходит до
  приложения. Клиент не видит даже TCP RST, только timeout.
- **Эффективно против всех РФ-IP сразу** — включая РКН-инфраструктуру
  (ГРЧЦ, ТСПУ), которой не нужно «наследить» в логах, чтобы попасть
  под блок.
- **Поддержка IPv4 + IPv6** — отдельные ipset для каждой версии.
- **Per-user whitelist** — клиенты с РФ-IP могут подключаться через
  `user_ip_whitelist` (отдельный ipset `clients_wl`).
- **Авто-обновление** — cron еженедельно скачивает свежий список от
  RIPE NCC.
- **Восстановление после reboot** — systemd-юнит восстанавливает ipset
  из `/etc/ipset.conf`.

### Минусы

- **Закрывает только один порт** — если на сервере открыто несколько
  портов (443 + 8443 + 22), РФ-IP могут стучать на остальные. Решение:
  использовать вместе с IP-Ban для конкретных ASN, или закрывать
  остальные порты через ufw.
- **Требует `ipset`** — без него fallback на plain iptables работает
  медленно (5000+ правил в INPUT chain).
- **Еженедельное обновление cron** — подсети могут устареть за неделю.
  Если нужна актуальность — измените cron на ежедневный.
- **BGP vs delegated расхождение** — иногда оператор получает блок от
  российского LIR, но анонсирует через зарубежный upstream. В BGP IP
  выглядит «не из РФ», и GeoIP-сервисы могут показать NL/FI. В этом
  случае блок может не сработать (см. раздел 16 «Диагностика»).

## 9. Сосуществование: не конфликтуют ли функции

**Не конфликтуют.** Каждый модуль использует свой «канал» бана:

```
                    iptables INPUT
                         │
        ┌────────────────┼────────────────────┬───────────────┐
        │                │                    │               │
   ipset:               ufw deny:        ipset:           Xray routing:
   xray_manual_ban      xray-autoban     xray_ru_block    outboundTag=block
                       honeypot                             (blackhole)
        │                │                    │               │
        └────────────────┼────────────────────┴───────────────┘
                         │
                         ↓
                       DROP / blackhole
```

- **IP-Ban** — отдельный ipset `xray_manual_ban(_6)`, никогда не
  пересекается с другими.
- **AutoBan** — отдельные правила ufw с комментарием `xray-autoban`.
- **Honeypot** — отдельные правила ufw с комментарием `honeypot`.
- **GeoIP Block** — routing rules в `config.json` Xray + `blackhole`
  outbound. Не трогает iptables.
- **РФ-блокировка** — отдельный ipset `xray_ru_block(_6)` +
  iptables-правила с комментарием `xray-ru-ingress-block`.

### Что это значит на практике

1. **Можно включить все пять одновременно** — никаких конфликтов.
2. **Разбан в одном модуле не снимает бан в другом.** Если IP попал
   одновременно в AutoBan, Honeypot и РФ-блокировку — нужно
   разбанивать в каждом месте отдельно.
3. **Whitelist у каждого свой.** Добавление IP в whitelist AutoBan
   не защищает его от Honeypot или от РФ-блокировки.
4. **GeoIP Block и РФ-блокировка дублируют функционал** — обе могут
   блокировать РФ-IP. Но РФ-блокировка делает это на уровне ядра
   (раньше, до TLS), а GeoIP Block — на уровне Xray (позже). Если
   включить обе, РФ-IP даже не дойдут до Xray — GeoIP Block для них
   не сработает никогда. Это нормально, просто избыточно.
5. **Очистка РФ-блокировки** (через меню «Блокировка входящих из РФ»
   → отключить) автоматически чистит ufw deny-правила
   AutoBan/Honeypot. Это мера против накопления устаревших банов.

### Если IP попал в несколько банов одновременно

В меню `[3] Разбанить IP` AutoBan или `[5] Разбанить IP` Honeypot —
разбан делает только свой модуль. Полный разбан:

1. AutoBan → `[3] Разбанить IP` → выбираете IP.
2. Honeypot → `[5] Разбанить IP` → выбираете тот же IP (если есть).
3. IP-Ban → `[2] Снять бан` → если IP там тоже есть.
4. РФ-блокировка → добавить IP в whitelist (если IP российский).
5. GeoIP Block → проверить routing rules, удалить правило для
   страны/ASN, если применимо.

После этого проверьте, что правил действительно нет:
```bash
iptables -L INPUT -n -v | grep <IP>
ipset list xray_manual_ban | grep <IP>
ipset list xray_ru_block | grep <IP>
ufw status | grep <IP>
# Для GeoIP Block — в config.json Xray
python3 -c "import json; c=json.load(open('/usr/local/etc/xray/config.json')); [print(r) for r in c.get('routing',{}).get('rules',[]) if r.get('outboundTag')=='block']"
```

## 10. Рекомендованные комбинации под разные сценарии

### Сценарий 1: Минимальная защита (только VPS для себя)

**Использовать:**
- ✅ AutoBan (включить, дефолтные настройки)
- ❌ Honeypot (не нужен — некому ловиться)
- ❌ IP-Ban (некого банить вручную)
- ❌ GeoIP Block (не нужен — нет целевых стран)
- ❌ РФ-блокировка (не нужна — вы единственный пользователь)

**Обоснование:** AutoBan достаточно. Сканеры стучатся редко, порог
10/10 ловит 99% случаев. Остальные модули — лишняя нагрузка на
администрирование.

### Сценарий 2: Несколько пользователей, публичный IP

**Использовать:**
- ✅ AutoBan (включить, порог 10/10)
- ✅ Honeypot (порт 9999, в whitelist — свой IP)
- ❌ IP-Ban (пока некого банить превентивно)
- ❌ GeoIP Block (не нужен)
- ❌ РФ-блокировка (не нужна — пользователи могут быть из РФ)

**Обоснование:** Honeypot ловит сканеры портов ещё до того, как они
дойдут до Xray. AutoBan добивает тех, кто подошёл к Xray напрямую и
начал зондирование. РФ-блокировка отключена, потому что у вас могут
быть пользователи из РФ.

### Сценарий 3: Сервер активно зондировали госструктуры (ГРЧЦ, ТСПУ)

**Использовать:**
- ✅ AutoBan (включить, порог понизить до 5/5)
- ✅ Honeypot (порт 9999, в whitelist — свой IP + IP нод каскада)
- ✅ IP-Ban:
  - `AS61280` (ФГУП ГРЧЦ)
  - `AS58067` (АО МЭНС)
  - `AS48148` (Связьатоминформ)
  - `AS60119` (Единый Оператор Связи)
  - `AS398324` (Censys Inc. — интернет-сканер)
- ❌ GeoIP Block (не нужен — РФ-блокировка ниже эффективнее)
- ✅ РФ-блокировка (если у вас нет клиентов из РФ)

**Обоснование:** После однократного визита ГРЧЦ нужно превентивно
закрыть все их подсети, чтобы при смене IP они не могли повторно
простучать. РФ-блокировка закрывает все российские подсети оптом
(включая те, что ещё не засветились). AutoBan с порогом 5/5 быстрее
ловит новые попытки. Honeypot ловит всех остальных сканеров. Если у
вас есть клиенты из РФ — не включайте РФ-блокировку, используйте
только IP-Ban для конкретных ASN.

### Сценарий 4: Защита от целенаправленной атаки на протокол

**Использовать:**
- ✅ AutoBan (включить, порог 3/5 — агрессивный)
- ✅ Honeypot (порт 9999 + порт 10000 + порт 31337 — несколько ловушек)
- ✅ IP-Ban (забанить все известные ASN сканеров)
- ✅ GeoIP Block (blocklist: `CN,IR,KP` + scanner block)
- ✅ РФ-блокировка (если нет клиентов из РФ)
- ✅ Дополнительно: **DPI-детектор** (`[D]` в меню безопасности) —
  ловит паттерны зондирования Reality/VLESS

**Обоснование:** При целенаправленной атаке злоумышленник знает порт
Xray, обходит honeypot. Нужен агрессивный AutoBan + DPI-детектор.
IP-Ban закрывает известные источники. GeoIP Block закрывает целые
страны. РФ-блокировка режет на уровне ядра. **Внимание:** порог 3/5
даёт много ложных срабатываний — внимательно следите за whitelist.

### Сценарий 5: Защита только от автоматических сканеров (Censys, Shodan)

**Использовать:**
- ❌ AutoBan (не нужен — Censys ведёт себя «тихо», не превышает порог)
- ✅ Honeypot (порт 9999 — Censys обязательно зайдёт)
- ✅ IP-Ban:
  - `AS398324` (Censys)
  - `AS46562` (Performive)
  - `AS14061` (DigitalOcean — если не используете сами)
- ✅ GeoIP Block (scanner block — готовый список Shodan/Censys/Shadowserver)
- ❌ РФ-блокировка (не нужна — сканеры обычно не из РФ)

**Обоснование:** Censys и Shodan делают по 1 запросу с каждого IP,
AutoBan их не видит. Honeypot ловит при первом же подключении.
IP-Ban закрывает всю их ASN. GeoIP Block добавляет готовый список
сканеров в routing Xray — двойная защита.

### Сценарий 6: Сервер для клиентов из РФ, но без сканеров из РФ

**Использовать:**
- ✅ AutoBan (включить, порог 10/10)
- ✅ Honeypot (порт 9999, в whitelist — свой IP)
- ✅ IP-Ban (AS61280 ГРЧЦ, AS398324 Censys, и т.д. — точечно)
- ❌ РФ-блокировка (НЕ включать — отрубите клиентов из РФ)
- ✅ Per-user IP whitelist (`user_ip_whitelist`) — для клиентов с
  фиксированными IP
- ✅ GeoIP Block (опционально, blocklist `CN,IR,KP`)

**Обоснование:** Если все ваши пользователи — из РФ, РФ-блокировку
включать нельзя. Вместо этого используете IP-Ban для точечного
закрытия известных госструктурных ASN. AutoBan ловит зондировщиков.
Honeypot ловит сканеров. Per-user whitelist позволяет клиентам с
российскими IP подключаться, даже если их IP случайно попал в бан.

### Сводная таблица комбинаций

| Сценарий | AutoBan | Honeypot | IP-Ban | GeoIP Block | РФ-блок |
|---|---|---|---|---|---|
| 1. Минимальная защита | ✅ | ❌ | ❌ | ❌ | ❌ |
| 2. Несколько пользователей | ✅ | ✅ | ❌ | ❌ | ❌ |
| 3. Зондировали госструктуры | ✅ (5/5) | ✅ | ✅ (ASN) | ❌ | ✅* |

## 11. Что использовать, а что — нет

### ✅ Использовать всегда

- **AutoBan с дефолтными настройками** — базовая защита, работает
  автоматически, не требует обслуживания. Включить на любом сервере
  с Xray.
- **Whitelist AutoBan** — обязательно добавьте:
  - `127.0.0.1`, `::1` (по умолчанию)
  - IP вашего cascade (entry + exit ноды)
  - Свой домашний/рабочий IP
  - IP любых мониторинг-сервисов (UptimeRobot, BetterStack) если
    используете
- **IP-Ban для конкретных IP и узких CIDR** — безопасно и полезно.
  Если в логах AutoBan или Honeypot вы видите повторяющихся
  нарушителей с одного IP или подсети — добавьте их в IP-Ban как
  постоянный запрет, который переживёт очистку AutoBan/Honeypot.
  Примеры безопасного применения:
  - Один IP: `142.248.80.152` — забанить конкретного нарушителя
    навсегда, чтобы AutoBan не «забыл» его при достижении лимита
    истории.
  - Узкая подсеть: `212.192.158.0/24` (256 адресов) — закрыть
    конкретный блок ГРЧЦ, который уже сканировал вас.
  - Диапазон: `5.129.188.10-5.129.188.50` — закрыть подсеть
    без указания CIDR.
- **РФ-блокировка** (`[G]` в меню безопасности) — если у вас **нет**
  пользователей из РФ. Закрывает все российские подсети на уровне
  ядра, эффективно против ГРЧЦ/ТСПУ/РКН-инфраструктуры. Не забудьте
  добавить свой IP в whitelist перед включением.
- **GeoIP Block → Scanner block** (`[2]` → `[3]`) — добавляет в
  routing Xray готовый список подсетей Shodan/Censys/Shadowserver.
  Безопасно: это специализированные сканеры, у них нет легитимных
  пользователей.

### ⚠️ Использовать с осторожностью

- **Honeypot-порт** — включать только если вы понимаете, что делаете.
  Обязательно добавьте свой IP в whitelist **до** включения, иначе
  первый же «telnet server 9999» из любопытства забанит вас.
- **IP-Ban для ASN небольших госструктур и сканеров** — безопасно
  для сетей с 7-20 префиксами (ГРЧЦ AS61280, Censys AS398324).
  Но любое добавление ASN означает потерю возможности зайти на
  сервер с IP из этой ASN — проверьте, нет ли там ваших клиентов.
- **Понижение порога AutoBan** (3/5 или ниже) — много ложных
  срабатываний. Реальные клиенты с плохим интернетом будут попадать
  в бан.
- **IP-Ban для средних ASN** (AS58067 МЭНС, AS48148 Связьатоминформ,
  AS60119 Единый Оператор Связи) — 7-20 префиксов, риск для
  легитимных пользователей невелик, но и клиент из этих сетей
  перестанет заходить. Баньте осознанно.
- **GeoIP Block → Allowlist по странам** — если укажете неправильный
  код страны или забудете свою — отрубите себе доступ. Always
  добавляйте свой IP в исключения перед применением allowlist.
- **РФ-блокировка при наличии клиентов из РФ** — отрубит всех
  российских пользователей. Используйте per-user IP whitelist
  (`user_ip_whitelist`) для клиентов с фиксированными IP, либо не
  включайте РФ-блокировку вообще.

### ❌ Не использовать

- **IP-Ban крупных российских операторов как ASN** (Ростелеком
  AS12389, МТС AS8359, Билайн AS3216/AS8402, МГТС AS25513, ТТК
  AS8342) — отрубите миллионы легитимных абонентов, в т.ч. возможно
  себя. Эти ASN закрываются через «Блокировку входящих из РФ»
  (`[G]` в меню безопасности), которая блокирует все РФ-подсети
  оптом.
  - **Нюанс:** если нужно закрыть **конкретную** подсеть крупного
    оператора (например, замеченный в сканировании блок
    `83.220.32.0/22` Ростелеком-бизнес) — это безопасно. Проблема
    только в бане ASN целиком, не в бане отдельных подсетей.
- **Honeypot на стандартных портах** (80, 443, 22, 8080, 8443) — вы
  сами заблокируете себе доступ к серверу. Honeypot ставится только
  на «неинтересные» порты: 9999, 10000, 31337, 12345.
- **Параллельные ручные ufw/iptables правила без комментариев** —
  модули Chimera не будут их видеть, при очистке они останутся как
  мусор. Всегда используйте меню Chimera для управления банами.
  - **Нюанс:** если нужно временное правило для отладки (например,
    временно закрыть порт для теста) — это нормально, но удаляйте
    его вручную после, не оставляйте «навсегда».
- **РФ-блокировка + GeoIP Block allowlist `RU` одновременно** —
  избыточно. РФ-блокировка режет на уровне ядра, до Xray дело не
  доходит, GeoIP Block никогда не сработает. Выберите что-то одно.
- **GeoIP Block для блокировки РФ** (blocklist `RU`) — если у вас
  есть клиенты из РФ, используйте РФ-блокировку с per-user
  whitelist вместо GeoIP Block. РФ-блокировка работает раньше (на
  уровне ядра) и поддерживает per-user исключения.

| Малая ASN (7-20 префиксов) | низкий | ✅ можно банить |
| Средняя ASN (50-500 префиксов) | средний | ⚠️ с проверкой |

## 12. Диагностика AutoBan: пустая История банов

### Симптом

На главном экране AutoBan видно `Забанено IP: 13`, список IP
присутствует. Но в `[6] История банов` — `История пуста`.

### Причина

До фикса (август 2026) cron-скрипт `xray-autoban.sh` банил IP и
записывал в `BAN_LOG`, но **не добавлял запись в `ban_history`**.
Только `_autoban_run_once()` (вызывается из меню `[4]`) писал в
историю. Поскольку cron — основной механизм — все баны делались без
записи в историю.

### Решение

В фиксе добавлено:
1. Cron-скрипт теперь пишет в `ban_history` при каждом бане.
2. `_autoban_load()` мигрирует существующие баны из `banned` в
   `ban_history` при первом открытии после обновления.

**Действие:** обновите Chimera до последней версии, откройте AutoBan
→ `[6] История банов`. Существующие баны автоматически перенесутся.
Новые баны от cron будут добавляться корректно.

### Проверка

```bash
# Проверить что в state есть ban_history
python3 -c "import json; d=json.load(open('/var/lib/xray-installer/autoban.json')); print('ban_history:', len(d.get('ban_history', [])))"

# Принудительно запустить автобан (создаст новые баны если есть нарушения)
# Меню AutoBan → [4] Запустить проверку прямо сейчас
```

## 13. Диагностика Honeypot: банит себя самого

### Симптом

Honeypot включён, и вы случайно подключились к порту 9999 с IP,

## 14. Диагностика IP-Ban: правила не восстанавливаются после reboot

### Симптом

После перезагрузки сервера правила IP-Ban не работают. `iptables -L`
показывает, что ipset пустой.

### Причина

`ipset` хранится в RAM. После reboot — пустой. Для восстановления
нужно:
1. Иметь выгруженный файл `/etc/ipset.conf` (через `[5] Сохранить`).
2. Иметь включенный `ipset-persist` (меню безопасности → `[IP]`).
3. Раньше iptables-правила (`-m set --match-set xray_manual_ban`)
   НЕ восстанавливались вовсе — `xray-ipset-restore.service`
   восстанавливает только сеты. С фикса 2026-09-21 при добавлении
   бана ставится собственный `xray-ipban-restore.service`, который
   при загрузке пересоздаёт сеты (`ipset create -exist`) и правила
   (`iptables -I INPUT 1 …`).

### Решение

1. **После каждого добавления банов** делайте `[5] Сохранить ipset → /etc/ipset.conf`.
2. Включите **`ipset Persist`** (`[IP]` в меню безопасности) — это
   создаст systemd-юнит, который при загрузке системы восстанавливает
   ipset из `/etc/ipset.conf`.
3. `[4] Восстановить из state` в меню IP-Ban — пересоздаёт сеты,
   правила (первой строкой INPUT) и boot-юнит.
4. Если после reboot правила всё равно не появились — вручную
   (правило — ПЕРВОЙ строкой, не `-A`!):
   ```bash
   ipset restore -! -f /etc/ipset.conf
   iptables -I INPUT 1 -m set --match-set xray_manual_ban src -j DROP -m comment --comment xray-manual-ban
   ip6tables -I INPUT 1 -m set --match-set xray_manual_ban6 src -j DROP -m comment --comment xray-manual-ban
   ```

### Проверка

```bash
# ipset должен содержать ваши CIDR
ipset list xray_manual_ban | head -20

# iptables должен иметь правило с --match-set ПЕРВОЙ строкой INPUT
iptables -L INPUT -n --line-numbers | head -5
```

> **Почему именно `-I INPUT 1`:** при включённом UFW (дефолт Chimera)
> пакеты на открытые порты принимаются внутри ufw-цепочек
> (`ufw-before-input → ufw-user-input → allow`) по принципу
> first-match-wins и никогда не доходят до правил в конце INPUT.
> Правило, добавленное `-A` (в конец), — декоративное. Это была
> причина кейса AS25369 (2026-09-21): бан ASN стоял, а сканеры
> продолжали долбить xray и попадать в историю автобана.

## 15. Диагностика GeoIP Block: правила не работают после рестарта Xray

### Симптом

Вы добавили правило GeoIP Block (например, blocklist `CN`), но после
рестарта Xray или перезагрузки сервера клиенты из Китая снова могут
подключаться.

### Причина 1: правила не сохранились в config.json

GeoIP Block пишет правила прямо в `/usr/local/etc/xray/config.json`
(или `/etc/xray/config.json`). Если после добавления правил был
запущен `reconfigure.py` или другой скрипт, перезаписывающий конфиг —
правила могли потеряться.

**Проверка:**
```bash
python3 -c "import json; c=json.load(open('/usr/local/etc/xray/config.json')); [print(r) for r in c.get('routing',{}).get('rules',[]) if r.get('outboundTag')=='block']"
```

Если список пуст — правила потеряны. Примените заново через меню
GeoIP Block.

### Причина 2: нет blackhole outbound

Для работы `outboundTag: "block"` в config.json должен быть
объявлен outbound с `tag: "blackhole"`:

```json
"outbounds": [
  ...,
  {
    "tag": "blackhole",
    "protocol": "blackhole"
  }
]
```

Если outbound отсутствует, Xray не сможет отправить соединение в
block и просто пропустит его.

**Решение:** меню GeoIP Block → `[4] Удалить все правила` → заново
применить. Chimera автоматически создаст blackhole outbound.

### Причина 3: устаревший geoip.dat

GeoIP-база скачивается в `/usr/local/share/xray/geoip.dat`. Если она
устарела (не обновлялась > 1 месяца), новые подсети могут не
определяться как принадлежащие к указанной стране.

**Решение:** меню → **Безопасность и автоматизация** → `[3]
Управление GeoIP/GeoSite файлами` → обновить.

### Причина 4: правила стоят в неправильном порядке

Xray применяет routing rules **по порядку**. Если правило blocklist
стоит **после** правила, разрешающего трафик — оно не сработает.

**Проверка:**
```bash
python3 -c "import json; c=json.load(open('/usr/local/etc/xray/config.json')); [print(i, r.get('outboundTag','?'), r.get('geoip',r.get('domain',''))) for i, r in enumerate(c.get('routing',{}).get('rules',[]))]"
```

Правила block должны стоять **до** catch-all правила (обычно
`outboundTag: "..."` без условий).

## 16. Диагностика РФ-блокировки: ГРЧЦ смог простучать

### Симптом

Включена «Блокировка входящих из РФ», подсети обновлены, cron
работает. Но в логах AutoBan появляются баны с российских IP —
например, AS61280 (ГРЧЦ).

### Причина 1: сканирование идёт на другой порт

РФ-блокировка закрывает **только один порт** — `server_port` из
`state.json` (обычно 443). Но на сервере открыто ещё минимум:

- 22 (SSH)
- 80 (HTTP, certbot standalone)
- 8443 (Telemt Panel, User Portal)
- 8080, 31337 (другие сервисы)

Если на этих портах тоже слушает Xray (например,Reality fallback,
port hopping) — ГРЧЦ мог подключиться туда, и РФ-блокировка не
сработала.

**Проверка:**
```bash
ss -tlnp | grep -E 'xray|nginx|sing-box'
```

Если открыто больше портов, чем нужно — закройте лишние через ufw:
```bash
ufw deny 8080/tcp
ufw deny 8443/tcp
# и т.д.
```

### Причина 2: BGP vs delegated расхождение

ГРЧЦ имеет свою AS61280, но сами IP они получают от более крупного
LIR. В `delegated-ripencc-latest` этот блок значится как RU. Но в
BGP-таблице IP может выглядеть «не из РФ», если ГРЧЦ анонсирует
через европейский upstream.

GeoIP-сервисы (MaxMind, IPinfo) тоже могут показать NL/FI для этого
IP. В этом случае РФ-блокировка не сработает по гео-признаку.

**Решение:** добавьте конкретную ASN ГРЧЦ в IP-Ban:
```
AS61280
```
Это закроет все их подсети независимо от того, как они анонсируются
в BGP.

### Причина 3: устаревший delegated-ripencc

Cron обновляет список еженедельно по умолчанию. Если ГРЧЦ получил
новый блок 2 дня назад — его ещё нет в локальном ipset.

**Решение:** измените cron на ежедневный:
```bash
# /etc/cron.d/xray-ingress-geoip
# Было: 0 3 * * 1  (понедельник 3:00)
# Стало: 0 3 * * *  (каждый день 3:00)
0 3 * * * root /usr/local/bin/xray-ingress-geoip-update.sh >> /var/log/xray-ingress-geoip.log 2>&1
```

Или запустите обновление вручную:
```bash
/usr/local/bin/xray-ingress-geoip-update.sh
```

### Причина 4: ESTABLISHED,RELATED пропускает пакеты до DROP

Правило РФ-блокировки ставится через `iptables -A` (в конец), а
правило `ESTABLISHED,RELATED -j ACCEPT` стоит раньше. Если ГРЧЦ
уже установил TCP-соединение до применения блокировки — пакеты
handshake идут как `ESTABLISHED` и обходят DROP.

**Решение:** это архитектурный компромисс (нельзя рвать активные
сессии легитимных клиентов). Лечится перезапуском Xray или
ожиданием таймаута соединения (обычно 2-3 минуты).

### Причина 5: IPv6

Если у сервера есть IPv6-адрес, и ГРЧЦ подключался по IPv6 — а блок
был применён только на IPv4. Проверьте, что IPv6-блок тоже активен:

```bash
ip6tables -L INPUT -n | grep xray_ru_block6
ipset list xray_ru_block6 | wc -l
```

Если список пуст — пересоздайте блокировку через меню Chimera,
убедившись, что IPv6 включён.

## 18. Whitelist: где он общий, а где раздельный

### Раздельные whitelist

У каждого модуля **свой собственный** whitelist:

| Модуль | Где хранится | Что исключает |
|---|---|---|
| AutoBan | `autoban.json` → `whitelist` | IP не попадает в автобан |
| Honeypot | `honeypot.json` → `whitelist` | IP не банится при подключении к honeypot |
| IP-Ban | нет whitelist | Любой IP в списке = бан (нельзя «не банить») |
| GeoIP Block | через routing rules в `config.json` | Можно добавить IP в allowlist-правило (исключение) |
| РФ-блокировка | `ingress_geoip.json` → `whitelist` + per-user `clients_wl` | IP не попадает под блокировку РФ-подсетей |

**Важно:** добавление IP в whitelist одного модуля НЕ защищает его от
других модулей. Если IP нужно исключить отовсюду — добавляйте во все
списки.

### Автоматический whitelist в AutoBan

AutoBan автоматически добавляет в whitelist IP всех нод каскада
(entry + exit) из `state.json`:

```
state.json → chain_nodes[] → для каждой ноды:
  если host — IP → добавить в whitelist
  если host — домен → резолв через DoH (1.1.1.1, 8.8.8.8)
                     → добавить IP в whitelist
```

Это **критично** — иначе при TLS-handshake ошибках между нодами
касакда они начали бы банить друг друга. DoH-резолв нужен, чтобы
не использовать локальный DNS-кэш (там может быть устаревший IP).

Дополнительно: AWG exit-host тоже резолвится и добавляется в
whitelist, если `awg_exit_enabled: true` и `install_mode: B`.

### Где смотреть whitelist

```bash
# AutoBan
python3 -c "import json; print(json.load(open('/var/lib/xray-installer/autoban.json')).get('whitelist', []))"

# Honeypot
python3 -c "import json; print(json.load(open('/var/lib/xray-installer/honeypot.json')).get('whitelist', []))"

# GeoIP block
python3 -c "import json; print(json.load(open('/var/lib/xray-installer/ingress_geoip.json')).get('whitelist', []))"
```

### Ротация логов

Только `xray-ban-report.txt` имеет автоматическую ротацию (7 дней,

    missingok
    notifempty

Или используйте модуль Chimera **logrotate** (`[L]` в меню
диагностики) — он настраивает ротацию для всех логов Chimera одним
действием.

### Очистка ban_history

AutoBan: `[6] История банов` → `[C] Очистить историю`. Это удаляет
**только** историю, активные баны в `banned` остаются.

Honeypot: `[5] Разбанить IP` — по одному, или через редактирование
`honeypot.json` напрямую.

IP-Ban: `[X] Снять ВСЕ баны` — flush + удаление ipset. После этого
