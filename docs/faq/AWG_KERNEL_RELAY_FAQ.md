## 1. Откуда это взялось: кейс Виталия

Дословно из чата сообщества (сообщение автора кейса, 26.11.2026):

> «в общем добрался до этой темы наконец-то. и сразу скажу, что два
> туннеля с условиями двусторонней блокировки 16к работать не будет.
> Причина: при согласовании ключей в рамках туннеля требуется
> двусторонний обмен, а его нет) проходят только первые 25 пакетов в
> каждую из сторон и потом блок. Блок может пробить только инициатор
> при помощи отправки i1. а это происходит только в одну сторону.
> а надо и в обратную. навайбокодил решение — туннель остается 1, но
> добавляется модуль ретрансляции, который устанавливает второе
> соединение в рамках 1 туннеля и пробивает блок в обратную сторону).
> у меня в бою работает почти сутки. еще наблюдаю. […] остается только
> подобрать датаграмму для i1, которая пробьет блокировку. в моем
> случае это датаграмма от днс-запроса.»

Что из этого важно понять:

1. **Двусторонний кат ≠ однонаправленный срез.** Split-direction (п.8)
   рассчитан на «отправить можем, принять нет» — короткие пакеты ходят в
   обе стороны, режется направление/объём. У Виталия поле резало ЛЮБОЙ
   флоу после ~25 пакетов **в каждую сторону**: даже handshake двух
   новых туннелей не сходился (обмен инициации требует встречных пакетов).
2. **Пробить кат может только инициатор** — отправкой первой датаграммы
   флоу (в терминах AWG — i1, init-пакет handshake'а). Инициатор — один;
   встречного «инициатора» у WG-ответчика нет.
3. **Решение автора кейса**: туннель ОДИН (тот же awg1, те же ключи,
   та же обфускация), но endpoint ядра переключается на локальный
   userspace-релей, который держит два внешних UDP-флоу и **сеет каждый
   первой DNS-датаграммой** — и тогда «инициатором» пробития становится
   каждое направление. ДNS-датаграмма выбрана потому, что резать DNS
   поле не может (базовая потребность сети).

Модуль оформляет эту схему штатно: меню, валидации, guarded-откат,
watchdog, TG-уведомления — то, чего «патчу нейрослопа для
исследовательских целей» не хватало.

## 2. Физика: один туннель, два флоу, DNS-прелеюдия

```
kernel awg1 (A, RU) ──► 127.0.0.1:loopA ──► relay A (userspace)
     ▲                                          │
     │                                          │ tx-флоу: A.extIP:A.tx ──► B:B.rx
     │                                          │ ПЕРВАЯ датаграмма флоу — DNS-запрос
     │                                          ▼
     │                                     relay B ──► 127.0.0.1:kernelB ──► kernel awg1 (B, exit)
     │                                          ▲
     └── 127.0.0.1:loopA ◄── relay A ◄──────────┘ rx-флоу: B.extIP:B.tx ──► A:A.rx
              (входящий)                          (сеется прелеюдией на B)
```

Ключевые точки:

1. **Ядро не меняется.** Kernel AWG продолжает видеть «пира» на
   `127.0.0.1:loop` — localhost-флоу не режется никогда. Релей — тупой
   датаграммный насос (select-loop) между localhost-парой сокетов и
   парой внешних. Приватные ключи релей не читает; конфиги `.conf` не
   трогает; меняется только runtime-endpoint одного пира.

2. **Каждое направление — свой флоу, и каждый отправитель СЕЕТ свой.**
   DPI классифицирует флоу (5-tuple) по первому пакету. Первая
   датаграмма каждого флоу — валидный DNS-запрос → флоу в белом списке
   → последующие WG-пакеты (handshake, keepalive, данные) едут по
   «белому» флоу в обе стороны. Это и есть «второе соединение в рамках
   одного туннеля» из кейса — на уровне проводного транспорта.

3. **Прелюдия отправляется ровно один раз** — до первого пакета ядра
   (лениво: реальный трафик AWG «выдавливает» её в флоу первой). Опция
   *refresh* (кастомизация) пере-сеивает флоу при простое: DPI-таблицы
   флоу живут ограниченно, а туннель без keepalive может молчать
   дольше их таймаута.

4. **Камуфляж флоу — целостный**: случайный высокий tx-порт источника
   («клиентский» вид) → 443/udp назначения (QUIC-вид) или 53/udp
   (DNS-вид). DNS-прелеюдия в 443-флоу выглядит как DoQ-эскалация, в
   53-флоу — как классический resolver-запрос. Дефолт меню — rx:443
   (боевой рецепт пилота; 53 у некоторых операторов перехватывается
   transparent-DNS-прокси — тогда флоу не доходит до провайдера
   датаграмм, см. §9).

5. **EPERM-семантика** (пилот): `send()` даной датаграммы с EPERM
   отбрасывает только её (жалоба в journalctl раз в минуту на
   направление); EPERM на прелюдии = выход стоит до вмешательства
   оператора, вход продолжает качать. Любая другая ошибка — честное
   исключение и рестарт-лестница watchdog'а.

## 3. Чем НЕ является: релей ≠ split-direction

| | Split-direction (п.8) | Kernel-relay (п.9) |
|---|---|---|
| Что добавляет | второй туннель + fwmark/connmark маршрутизация | userspace-релей поверх ТОГО ЖЕ туннеля |
| Требует от поля | короткие пакеты ходят в обе стороны | флоу пропускает «первую» датаграмму DNS |
| Лечит | однонаправленный срез (one-way-out), stream-cut | ДВУСТОРОННИЙ кат ~16к (кейс Виталия) |
| Чего требует | 2× handshake'ов, подсети, ключи | endpoint-переключение runtime |
| Отказ | e2e-гейт до переключения транзита | юнит+endpoint подтверждение до применения |
| Откат | снос правил + рестарт каскадного routing | guarded-restore endpoint (сверка identity) |

**Зонд плеча (меню каскада → 8 → 1) различает подслучаи**: вердикт
`one-way-out` теперь честно разделяет «направленный срез» (короткие
ходят в обе → split-direction) и «двусторонний кат ~25 пакетов»
(кейс Виталия → релей). Вердикт `udp-dead` релею не лечится — UDP
резаться целиком (нужен другой транспорт, см. RU_NODE_CASCADE_FAQ §9.1).

## 4. Прелюдии и порты: кастомизация камуфляжа

Меню релея → п.4 (или при включении):

| Пресет | Что шлёт | Кому |
|---|---|---|
| `dns-fixed` | DNS-запрос example.com A/IN, фикс-txid | **дефолт** — побайтово боевой пилот Виталия |
| `dns-rand` | то же, txid случайный на включение | свежий seed не выглядит дублем запроса |
| `custom-domain` | DNS-запрос вашего домена | флоу выглядит как резолв вашего ресурса |
| `custom-hex` | сырые байты hex'ом | эксперименты: снять рабочий запрос tcpdump'ом |
| `none` | ничего | поле, режущее только «непервые» датаграммы |

Порты: loop — любой свободный (меню подсказывает); tx — случайный
высокий (клиентский вид источника); rx — 443 (дефолт) или 53/любой;
remote_tx/remote_rx — порты напарника из его бокса плана (выводится
после включения на первой ноде). Keepalive-рецепт пилота: инициатор
25 с, ответчик off — остаётся в конфиге туннеля, релей его не трогает.

Refresh-интервал: 0 (выкл) — дефолт пилота; 300 с — пере-сеивать флоу
прелеюдией при простое туннеля (DPI-таблицы флоу не вечны).

## 5. Установка: два шага и окно простоя

Канон двухшагового TUI каскада: сначала одна нода, потом вторая; данные
передаются «боксом плана». Меню: **AWG → Каскад из 2 серверов → 9**.

**Требования**: выделенный kernel AWG с ровно одним пиром и уже
установленным прямым IPv4 endpoint'ом (обычно awg1 каскадного линка).
Модуль откажет на userspace-интерфейсе, multi-peer, пустом/loopback
endpoint, общем клиентском awg0. Нужен systemd с transient-юнитами и
DynamicUser; доступ динамической службы на чтение Python-модуля в дереве
установки; firewall должен пропускать точные UDP-пары (релей портов не
открывает).

**Шаг 1 — нода A** (пункт 1): iface, свой внешний IPv4, порты,
пресет прелюдии, поведение watchdog при исчерпании лестницы
(fail_action: откат / только уведомить — §6.1). После включения
печатается **бокс плана для B**: какие remote_tx/remote_rx вводить
напарнику (зеркальные ваши tx/rx).

**Шаг 2 — нода B** (тот же пункт 1): iface, свой IPv4, свои tx/rx,
remote_* из бокса плана A. Тот же пресет прелюдии.

**Окно простоя**: между включением A и B линк односторонен (ядро A
уже говорит с loop-релеем, а на B его rx-порт ещё никто не слушает) —
запускайте оба конца подряд, секундами. Пользователи каскада увидят
короткий лаг, не разрыв.

**Что НЕ меняется**: ключи, обфускация, версия протокола, конфиги
`.conf`, маршрутизация транзита, клиентский каскад, b4-сплит. Релей —
только проводной транспорт endpoint'а.

## 6. Watchdog: откат или «только уведомить» + автовосстановление после ребута

Пункт 5 включает таймер `awg-kernel-relay-watchdog.timer` (раз в
минуту, wrapper PYTHONPATH-safe — канон awg-cascade-failover).

Лестница тика (возврат строки-действия в лог):

- `ok` — юнит active и handshake свеж (rekey ~2 мин + keepalive 25 с
  держат возраст живого линка далеко ниже порога 300 с);
- флоу/юнит умер → **relaunch юнита** (новый transient-юнит = новый
  флоу = свежий DPI-бюджет); ожил → `recovered` + TG
  `awg_relay_dir_dead`;
- не ожил → `pending-N`; N=3 подряд → **авто-откат**: guarded-restore
  прямого endpoint + TG `awg_relay_off`;
- записи `/run` нет (ребут — tmpfs) → `restore_on_boot` (п.6 меню,
  default **off**) поднимет релей заново из state-бокса; выключен →
  режим снят с уведомлением (`lost`).

### 6.1. fail_action: «уведомлять И катать» или «ТОЛЬКО уведомлять»

Фичареквест Виталия (26.11, дословно): «добавить режим уведомлять но
не откатывать на прямой эндпоинт. Смысл: я и так знаю что прямой не
заработает, но в случае отключения или долгой перезагрузки одного из
узлов потом еще и режим работы восстанавливать надо будет».

Выбор делается **при активации** (п.1 спросит после прелюдии) и
меняется позже пунктом меню 7 («Watchdog-откат») — изменение вступает
в силу со следующего минутного тика (watchdog читает state каждый
тик, без рестарта таймера).

| | `rollback` (по умолчанию) | `notify_only` |
|---|---|---|
| 3 неудачи relaunch подряд | авто-откат на прямой endpoint | **режим держится**, relaunch продолжается каждую минуту |
| Что в TG | `awg_relay_dir_dead` ×3 → `awg_relay_off` | `awg_relay_dir_dead` до предела → **одно** `awg_relay_hold` → тишина |
| Напарник вернулся | (режим уже снят) | флоу оживёт сам → `awg_relay_recovered` |
| Кому нужно | «прямой работает, релей — временный обход» | «прямой мёртв» (двусторонний кат): откат — потеря режима + ручное восстановление после простоя |

Почему TG молчит выше предела: долгий простой ноды на 6 часов не
должен стоить 360 уведомлений — `awg_relay_hold` сообщает об
удержании один раз, ответ приходит с оживанием (`awg_relay_recovered`).
Спам-лимит не про «режим»: relaunch продолжается, счётчик неудач
растёт в state.

Парность с `restore_on_boot`: notify_only держит режим на ЭТОЙ ноде
(напарник ушёл в ребут); `restore_on_boot` возвращает режим на ТОЙ
ноде после её ребута. Для кейса Виталия включаются оба — тогда ни
одна сторона сценария «ребут/долгий простой одного из узлов» не
требует ручного восстановления.

События Telegram: `awg_relay_on` (включён), `awg_relay_dir_dead`
(флоу умирал: спас/не помог N/3), `awg_relay_off` (выключен: вручную /
авто-откат / потерян после ребута), `awg_relay_hold` (лестница
исчерпана — держим без отката), `awg_relay_recovered` (флоу ожил
после удержания). Все пять выключаемы из меню уведомлений
(tg_bot [5]→[3]).

## 7. Диагностика и откат

- **Пункт 2 (статус)**: режим, флоу, прелюдия, handshake-возраст,
  счётчики туннеля, наличие /run-записи, watchdog.
- **Пункт 7 (диагностика)**: journalctl юнита (EPERM живёт тут), `awg
  show` живым текстом, текущий endpoint.
- **Пункт 3 (выключить)**: стоп юнита → guarded-восстановление прямого
  endpoint (сверка ifindex/listen-port/pubkey и endpoint ∈
  {old,target}; дрейф = отказ с сохранением записи для разбора) → снятие
  записи → state + TG.
- EPERM на прелюдии в journalctl (`relay: EPERM prelude; output
  disabled`) — выход стоит: сменить пресет/порты (п.4), выключить (п.3),
  включить заново.
- Не совмещать релей с другими писателями endpoint'а (SaveConfig,
  смена пиров, повторная настройка каскада) — guarded-сверка честно
  откажет при дрейфе.

Автозапуска после ребута по умолчанию НЕТ (transient-юниты и /run —
tmpfs): это осознанная честная граница; включается п.6 при желании.

## 8. Честные границы: когда релей жив, а когда нет

Обещание модуля — не «работает у всех», а **«находит транспорт, если
поле пропускает первые датаграммы флоу, и честно откатывается, если
нет»** (канон §4 RU_NODE_CASCADE_FAQ).

- **Работает**, если: DPI классифицирует флоу по первому пакету и
  держит белые списки (DNS) стабильно; рез только «после N пакетов»
  (кат 16к/25 пакетов — кейс Виталия). Проверяется включением: юнит и
  endpoint применяются только после подтверждения; handshake-возраст
  виден в статусе.
- **Не поможет**, если: UDP режется целиком (`udp-dead` — зонд
  скажет); DPI ре-классифицирует флоу по каждому пакету (тогда WG-пакет
  после прелюдии вылетает из белого списка — refresh не лечит, лечит
  только другой транспорт); провайдер перехватывает UDP/53
  transparent-DNS-прокси (для rx:53 — используйте 443).
- **Дрейф поля**: ТСПУ обновляют правила волнами; watchdog ловит смерть
  флоу и откатывается на прямой endpoint с TG. Регулярные `awg_relay_dir_dead`
  — сигнал, что поле ушло: пора подбирать новую прелюдию (п.4) или
  переносить exit.
- **Инварианты для перепроверки** при странных потерях: keepalive 25 с
  на инициаторе (рецепт пилота); отсутствие конкурирующих писателей
  endpoint; оба конца включены (односторонний релей = односторонний
  линк, см. §5).

## 9. Частые вопросы

**Q: Можно включить релей только на одном конце?**
Нет. Входящее направление несёт tx-флоу НАПАРНИКА: без его релея
обратные пакеты идут напрямую и режутся тем же полем. Один конец =
односторонний линк (это и было «отправить можем, принять нет»).

**Q: Что с MTU?**
Релей — датаграммный насос: MTU туннеля не меняется (1280 в каскадном
каноне, TCPMSS-клампы транзита остаются прежними). Прелюдия меньше
MTU по определению (DNS-запрос ~30 байт).

**Q: Релей видит приватные ключи?**
Нет. Релей качает датаграммы endpoint↔wire; приватный ключ живёт в
конфиге ядра. systemd-юнит DynamicUser, капы только CAP_NET_BIND_SERVICE
(порты <1024), AF_INET/AF_UNIX only.

**Q: Юнит упал после включения — что будет?**
Watchdog (если включён, п.5): relaunch, не поможет ×3 → смотрите
fail_action: `rollback` — авто-откат на прямой endpoint + TG;
`notify_only` — одно TG-уведомление, режим ДЕРЖИТСЯ и relaunch
продолжается (§6.1). Без watchdog'а — п.3 вручную (guarded-восстановление
сверяет, что откатываем СВОЙ endpoint).

**Q: Почему 443, а не 53?**
53-й у части операторов перехватывается transparent-DNS-прокси —
флоу не дойдёт до провайдера датаграмм. 443/udp (QUIC-вид) — боевой
рецепт пилота Виталия. 53 работает там, где прокси нет — пункт меню
принимает любой порт.

**Q: Это то же, что пункт 8 (Split-direction)?**
