# VLESS — FAQ по установке и конфигурации

Полный гайд по установке VLESS (REALITY / xHTTP), каскадов, транспортов
и всех опций проекта Chimera. Написан для новичков — от аренды сервера
до финальной ссылки для клиента.

> **VLESS** — протокол проксирования Xray-core. В Chimera используется
> в двух вариантах: VLESS+TCP+REALITY (максимальная производительность)
> и VLESS+xHTTP+TLS (маскировка под HTTPS). Не путать с Telemt (MTProto
> для Telegram) — это отдельный протокол, см. [TELEMT_FAQ.md](TELEMT_FAQ.md).

## 1. Подготовка: аренда сервера и домен

### Сервер (VPS)

**Минимальные требования:**
- ОС: Debian 12/13 или Ubuntu 22.04/24.04
- RAM: 512 МБ (минимум), 1 ГБ (рекомендуется)
- Диск: 5 ГБ
- Сеть: публичный IPv4, желательно IPv6
- Права: root

**Где арендовать:**

| Сценарий | Где | Почему |
|---|---|---|
| Режим A (прямой) | Любой зарубежный хостинг (EU/US/Asia) | Клиент подключается напрямую |
| Режим B, Entry-нода (RU) | Российский хостинг (PQ.hosting, Aeza, и т.д.) | Низкая задержка для РФ-клиентов |
| Режим B, Exit-нода (EU/US) | Зарубежный хостинг (Hetzner, Contabo, и т.д.) | Доступ к заблокированным в РФ ресурсам |

> **Важно:** для Режима B нужно **два сервера** — один в РФ (Entry), один за
> рубежом (Exit). Exit-нода устанавливается первой (Режим A), потом Entry
> (Режим B) с параметрами от Exit.

### Домен

**Домен нужен ВСЕГДА** — и для REALITY, и для xHTTP TLS. Chimera
использует архитектуру **selfsteal** (маскировка под собственный сайт):

- Nginx слушает на 443 порту, терминирует TLS с **реальным Let's Encrypt
  сертификатом вашего домена**, и отдаёт сайт-заглушку.
- Xray REALITY использует этот же домен как `serverNames` (SNI), а
  `dest` указывает на unix-сокет Nginx — то есть REALITY маскируется
  **под ваш собственный сайт**, а не под чужой.
- DPI видит обычный HTTPS-трафик к вашему домену с валидным сертификатом.

> **Использовать чужой домен (microsoft.com, yahoo.com) нельзя!** В
> классической архитектуре REALITY (без selfsteal) чужой домен
> используется для `dest` — Xray подключается к чужому сайту для
> имитации TLS-handshake. Но в Chimera `dest` указывает на unix-сокет
> Nginx (ваш собственный сайт), а `serverNames` = ваш домен. Поэтому
> домен **обязательно должен быть вашим**, с A-записью на IP сервера.

**Где купить домен:**
- Любой регистратор (Namecheap, Porkbun, Cloudflare, Reg.ru, и т.д.)
- Цена: ~$1-15/год для `.com`/`.net`/`.org`/`.dev`/`.xyz`
- Дешевле всего: `.xyz` (~$1/год), `.click` (~$2/год)

**Настройка DNS:**
```
Тип:  A
Имя:  @ (или поддомен, например proxy)
IP:   <IP вашего сервера>
TTL:  3600 (1 час)
```

> **Исключение:** при AWG-транспорте в Режиме B (когда нет Nginx на
> Entry-ноде) REALITY использует чужой домен для `dest` (например
> `www.cloudflare.com`). Но это частный случай — AWG-транспорт
> настраивается отдельно, см. раздел 6.
> Для xHTTP домен покупать **обязательно**.

## 2. Запуск установки

### Быстрый старт (одной командой)

```bash
bash <(curl -fsSL https://gitlab.com/netwalker071778/chimera-project/-/raw/chimera-v5/bootstrap.sh)
```

Bootstrap скрипт:
1. Проверяет права root.
2. Устанавливает `python3`, `curl`, `git` если отсутствуют.
3. Клонирует репозиторий в `/opt/chimera`.
4. Запускает установщик.

### Ручная установка

```bash
git clone -b chimera-v5 https://gitlab.com/netwalker071778/chimera-project.git /opt/chimera
cd /opt/chimera
python3 verify.py    # проверить целостность
sudo python3 main.py # запустить
```

### Главное меню

После запуска `main.py` вы увидите главное меню:

```
[1] 🚀 Установить / Переустановить
[2] 🔀 Переключить режим (A↔B)
[3] 📦 Миграция (экспорт/импорт)
[4] ⚙️  Применить оптимизации sysctl/limits
[5] 🔄 Обновить Xray
[5b] ♻️ Перегенерировать конфиг Xray
[6] 🛠️  Аварийное восстановление

[8] 🧪 Запустить unit-тесты
[9] 🔀 Mieru Hybrid Addon
[W] 🌐 Веб-панель управления
```

Нажмите `[1]` для начала установки.

## 3. Режим A vs Режим B — что выбрать

### Режим A — одиночный сервер

```
Клиент ──VLESS/REALITY──► VPS (любая страна) ──► Интернет
```

- Один сервер выполняет роль точки выхода.
- Клиент подключается напрямую к серверу.
- **Простота:** одна установка, минимум настроек.
- **Минус:** если сервер в РФ — заблокированные сайты недоступны (нужен VPN
  на клиенте). Если сервер за рубежом — может быть блокировка по IP со
  стороны ТСПУ.

**Когда выбирать:** сервер за рубежом, клиенты могут напрямую к нему
подключаться (ТСПУ не режет прямые VLESS-соединения).

### Режим B — каскад Россия → Зарубеж

```
Клиент ──VLESS/REALITY──► Entry VPS (RU) ──транспорт──► Exit VPS (EU/US) ──► Интернет
```

- Два сервера: Entry (РФ) и Exit (зарубеж).
- Клиент подключается к Entry, трафик идёт через Exit в интернет.
- **Транспорт** между Entry и Exit: VLESS, AWG или Hysteria2 (см. раздел 6).
- **Плюс:** обходит блокировки ТСПУ (трафик до Entry — внутри РФ, быстрый;
  выход через Exit — за рубежом).
- **Минус:** сложнее настройка, два сервера.

**Когда выбирать:** сервер в РФ, клиенты в РФ, нужно обходить блокировки
ТСПУ для доступа к заблокированным ресурсам.

### Режим B Multi — мультикаскад с балансировкой

```
                              ┌──► Exit VPS 1 (EU) ──►┐
Клиент ──► Entry VPS (RU) ─── ┼──► Exit VPS 2 (US) ──►├──► Интернет
                              └──► Exit VPS 3 (AS) ──►┘
```

- До 10 exit-нод, трафик распределяется между ними.
- Стратегии балансировки: Round Robin / Least Ping / Least Load / Random / Smart Balancer.
- **Плюс:** избыточность (если одна exit-нода упадёт — трафик пойдёт через другие).

## 4. Протокол: REALITY vs xHTTP

При установке Chimera спрашивает: `[1] VLESS+TCP+REALITY` или `[2] VLESS+xHTTP+TLS`.

### VLESS + TCP + REALITY (рекомендуется)

```
Клиент ──TCP──► Nginx (unix socket) ──► Xray (REALITY)
                 TLS-handshake с маскировочным сайтом
```

- **Максимальная производительность** — аппаратное ускорение TLS.
- Маскировка: трафик выглядит как подключение к реальному HTTPS-сайту
  (указанному в SNI/dest).
- Архитектура **selfsteal**: REALITY маскируется под **ваш собственный**
  сайт (на Nginx, с Let's Encrypt сертификатом вашего домена).
- **Nginx** слушает на 443 порту, терминирует TLS, отдаёт сайт-заглушку,
  и проксирует VLESS-трафик через unix-сокет в Xray.
- **Домен обязателен** (ваш, с A-записью на IP сервера).

**Когда выбирать:** в большинстве случаев. Быстрее, проще. Домен нужен
(для selfsteal), но не нужен отдельный сертификат для протокола
(только для сайт-заглушки nginx, который получается автоматически).

### VLESS + xHTTP + TLS

```
Клиент ──HTTPS──► Nginx (TLS, Let's Encrypt) ──► Xray (xHTTP backend)
                   Реальный сертификат вашего домена
```

- Трафик выглядит как обычный HTTPS-поток (HTTP/2 или chunked-streaming).
- Обходит DPI через маскировку под реальный веб-сайт.
- **Домен обязателен** (ваш, с A-записью на IP сервера).
- **Let's Encrypt сертификат** — Chimera получает автоматически через certbot.
- Режимы xHTTP: `packet-up` / `stream-up` / `stream-one`.
- Дополнительные опции: xmux (мультиплексирование), padding, SSE/grpc заголовки.

**Когда выбирать:** если REALITY блокируется ТСПУ (редко), или нужна
максимальная маскировка под реальный HTTPS-сайт.

### Выбор порта

| Порт | Описание |
|---|---|
| **443** ★ | Стандартный HTTPS — меньше блокировок, рекомендуется |
| **8443** | Альтернатива — часто не блокируется |
| **Вручную** | Любой 1–65535 (избегайте 80, 22, 53) |

> **Рекомендация:** используйте **443** — это стандартный HTTPS-порт, его
> реже всего блокируют. Если 443 занят другим сервисом — используйте 8443.

## 5. Параметры установки (11 шагов)

После выбора режима и протокола, Chimera последовательно спрашивает
11 параметров:

### Шаг 1/11: UUID клиента

Уникальный идентификатор пользователя. Генерируется автоматически (опция `1`)
или вводится вручную (опция `2`).

> **Рекомендация:** `1` (сгенерировать автоматически). UUID можно добавить
> позже через меню "Управление пользователями".

### Шаг 2/11: ShortID (REALITY)

Короткий hex-идентификатор для REALITY-handshake. Генерируется автоматически
(8 hex-символов) или вводится вручную (2-16 hex, чётная длина).

> При xHTTP TLS — пропускается.

### Шаг 3/11: Ключи REALITY (x25519)

Пара ключей: Private Key (приватный) + Public Key (публичный).

- `1` — сгенерировать автоматически (рекомендуется). Ключи создаются после
  установки Xray-core.
- `2` — ввести вручную (если уже есть пара ключей).

> При xHTTP TLS — пропускается (используется TLS-сертификат Let's Encrypt).

### Шаг 4/11: SpiderX

Путь краулера REALITY (например `/abc123`). Генерируется автоматически или
вводится вручную (должен начинаться с `/`).

> При xHTTP TLS — пропускается.

### Шаг 5/11: Unix socket path

Путь к unix-сокету, через который Nginx передаёт трафик в Xray.

- Генерируется автоматически: `/dev/shm/<hex>.socket`
- Можно ввести вручную (абсолютный путь, заканчивается на `.socket`).

> При xHTTP TLS — пропускается (используется TCP backend, не сокет).
> При AWG-транспорте — пропускается (Xray слушает TCP напрямую).

### Шаг 6/11: Домен (SNI)

Доменное имя сервера. **Обязательный параметр.** Домен должен быть **вашим**
(с A-записью на IP сервера).

- Для **REALITY** и **xHTTP TLS**: Chimera использует архитектуру
  **selfsteal** — REALITY маскируется под **ваш собственный** сайт
  (Nginx + Let's Encrypt сертификат вашего домена). Использовать чужой
  домен нельзя.
- Для **AWG-транспорта** (Режим B без Nginx): REALITY использует чужой
  домен для `dest` (например `www.cloudflare.com`). Это частный случай.

### Шаг 7/11: Email для Let's Encrypt

Email для регистрации в Let's Encrypt (нужен для получения SSL-сертификата).
По умолчанию: `admin@<домен>`.

> Даже при REALITY (где сертификат не нужен для протокола) — email и
> сертификат нужны для сайт-заглушки nginx (порт 443).

### Шаг 8/11: Стратегия исходящих соединений (domainStrategy)

Как Xray резолвит DNS для исходящих соединений:

| Опция | Стратегия | Описание |
|---|---|---|
| `1` ★ | UseIPv6v4 | Сначала IPv6, fallback IPv4 (рекомендуется) |
| `2` | UseIPv4v6 | Сначала IPv4, fallback IPv6 |
| `3` | UseIP | Системный DNS |
| `4` | UseIPv4 | Только IPv4 |

> Если на сервере есть IPv6 — рекомендуется `1` (UseIPv6v4). Если IPv6
> нет — `4` (UseIPv4).

### Шаг 9/11: Шаблон сайта-заглушки

Какой веб-сайт покажется, если кто-то зайдёт на ваш сервер в браузере по
доменному имени (или IP:443). Это маскировка — сервер выглядит как обычный
веб-сайт, а не прокси.

15 шаблонов на выбор:
1. TechHub — IT-портал
2. NexCloud — serverless SaaS
3. Holm & Oak — homeware store
4. Ember & Grain — wood-fired bistro
5. NexHub — community + storage
6. ByteForge — developer forum
7. Lumen Architects — architecture studio
8. Verdant Botanical — plant shop
9. Northwind Coffee — coffee roastery
10. Solstice Wellness — spa & wellness
11. Atelier Meridian — design studio
12. Harborline Logistics — shipping & freight
13. Quietude Library — digital library
14. Mensara Consulting — strategy consulting
15. Cascade Analytics — analytics SaaS
0. Случайный

> **Рекомендация:** выберите `0` (случайный) или любой понравившийся.
> Все шаблоны — статичные HTML/CSS/JS, не нагружают сервер.

### Шаг 10/11: DNSCrypt-proxy

| Опция | Описание |
|---|---|
| **Y** ★ | Установить DNSCrypt-proxy — шифрует DNS-запросы, защищает от слежки провайдера |
| **N** | Использовать публичные DNS напрямую (1.1.1.1 / 8.8.8.8) |

> **Рекомендация:** `Y` (установить). DNSCrypt шифрует DNS-запросы, что
> важно для приватности. Добавляет ~5 МБ RAM, но защищает от DNS-leak.

### Шаг 11/11: TLS Fingerprint (uTLS)

Определяет, под какой браузер маскируется TLS-хендшейк клиента. Влияет
на обход DPI. **Должен совпадать в клиенте и на сервере.**

| Опция | Fingerprint | Описание |
|---|---|---|
| `1` ★ | chrome | Google Chrome (наиболее распространённый, рекомендуется) |
| `2` | firefox | Mozilla Firefox |
| `3` | safari | Apple Safari (desktop) |
| `4` | edge | Microsoft Edge |
| `5` | random | Случайный из реальных браузеров (выбирает Xray при старте) |
| `6` | randomized | Рандомизированный при каждом хендшейке (uTLS randomized) |

> **Рекомендация:** `chrome` — самый распространённый, меньше всего
> привлекает внимание. Если используете клиент на Firefox — выберите
> `firefox`. **Важно:** fingerprint в клиенте Xray/v2rayNG должен
> совпадать с выбранным на сервере.

## 6. Транспорт в Режиме B: VLESS / AWG / Hysteria2

При выборе Режима B Chimera спрашивает, **как трафик будет выходить**
с RU-сервера (Entry) через зарубежный (Exit):

```
Клиент ──► Entry VPS (RU) ──???──► Exit VPS (EU) ──► Интернет
                               ↑
                        Что здесь?
```

### Опция 1: VLESS (стандарт)

```
Entry ──VLESS/REALITY──► Exit
```

- Классический каскад через VLESS-протокол.
- На Exit-ноде должен быть установлен Chimera в Режиме A.
- Нужны параметры от Exit-ноды: IP, порт, UUID, Public Key, ShortID, SNI, fingerprint.
- Параметры берутся из VLESS-ссылки, которую выдаёт Exit-нода после установки.

**Плюсы:** простота, совместимость.
**Минусы:** VLESS-трафик между Entry и Exit может детектиться DPI.

### Опция 2: AmneziaWG 2.0 (рекомендуется)

```
Entry ──AWG (UDP, обфусцирован)──► Exit
```

- Зашифрованный UDP-туннель (AmneziaWG = модифицированный WireGuard с
  обфускацией).
- Устойчив к DPI — обфусцированные пакеты не похожи на WireGuard.
- **Не требует VLESS на Exit-ноде** — Chimera сама установит AWG-сервер
  на Exit через SSH.
- Нужен: IP Exit-сервера, SSH-доступ (пароль или ключ).

**Плюсы:** устойчивость к DPI, не требует ручной настройки Exit.
**Минусы:** UDP-трафик (некоторые сети режут UDP), чуть больше overhead.

### Опция 3: Hysteria2 (QUIC/UDP)

```
Entry ──Hysteria2 (QUIC/UDP)──► Exit
```

- Транспорт на базе QUIC (UDP) — высокая скорость, устойчивость к потерям.
- **Не требует VLESS на Exit-ноде** — Hysteria2-сервер ставится через меню 7.
- Настройка в два шага: (1) установка H2 на Exit, (2) активация на Entry.

**Плюсы:** высокая скорость, устойчивость к потерям пакетов.
**Минусы:** UDP-трафик, нужен отдельный порт для H2.

### Сравнение

| Транспорт | Протокол | DPI-устойчивость | Скорость | Настройка |
|---|---|---|---|---|
| VLESS | TCP/TLS | Средняя | Высокая | Ввод параметров от Exit |
| AWG 2.0 | UDP (обфусцирован) | Высокая | Высокая | SSH-доступ к Exit |
| Hysteria2 | UDP (QUIC) | Высокая | Очень высокая | Меню 7 (2 шага) |

> **Рекомендация:** для РФ — **AWG 2.0** (опция 2). Устойчив к DPI,
> простая настройка через SSH. Если UDP режется — VLESS (опция 1).

## 7. Каскад и мультикаскад: порядок установки

### ВАЖНО: домены для каждой ноды

В каскаде **каждый сервер должен иметь свой домен**, связанный A-записью
со своим IP. Архитектура selfsteal требует, чтобы Nginx на каждом сервере
имел реальный Let's Encrypt сертификат для своего домена — без этого
REALITY не сможет маскироваться, и клиенты/каскад не подключатся.

| Сервер | Домен | A-запись → IP | Зачем |
|---|---|---|---|
| Entry (РФ) | `entry.example.com` | IP сервера в РФ | selfsteal REALITY для клиентов |
| Exit 1 (EU) | `exit1.example.com` | IP сервера в EU | selfsteal REALITY для Entry→Exit |
| Exit 2 (US) | `exit2.example.com` | IP сервера в US | selfsteal REALITY для Entry→Exit |
| Exit 3 (AS) | `exit3.example.com` | IP сервера в AS | selfsteal REALITY для Entry→Exit |

**Правила:**
1. **Каждый домен → A-запись → IP своего сервера.** Нельзя указать
   домен Exit 1 на IP Exit 2 — Let's Encrypt не получит сертификат,
   REALITY не заработает.
2. **Можно использовать поддомены одного домена.** Например:
   `proxy.example.com` → Entry (РФ), `eu.proxy.example.com` → Exit 1,
   `us.proxy.example.com` → Exit 2. Это дешевле — один домен, много
   поддоменов.
3. **Нельзя использовать один домен для нескольких серверов.** A-запись
   указывает на один IP — если два сервера отвечают на один домен,
   Let's Encrypt получит сертификат только для первого.
4. **Для AWG-транспорта** домен на Entry не нужен (AWG не использует
   REALITY/Nginx на Entry). Но на Exit — нужен (там Chimera в Режиме A).
5. **Для Hysteria2-транспорта** домен на Entry не нужен. На Exit
   нужен домен для H2 (или можно использовать IP — но домен лучше для
   маскировки).

> **Пример минимальной настройки (1 Entry + 1 Exit, VLESS-каскад):**
> 1. Купить домен `example.xyz` (~$1/год).
> 2. Создать A-запись: `proxy.example.xyz` → IP Entry-сервера (РФ).
> 3. Создать A-запись: `exit.example.xyz` → IP Exit-сервера (EU).
> 4. При установке Exit (Режим A): домен = `exit.example.xyz`.
> 5. При установке Entry (Режим B): домен = `proxy.example.xyz`,
>    а параметры Exit-ноды (SNI = `exit.example.xyz`) — из VLESS-ссылки.

### Порядок установки для Режима B (VLESS-транспорт)

```
Шаг 1: Установить Chimera на Exit-сервере (Режим A)
        ↓ Получить VLESS-ссылку и параметры
Шаг 2: Установить Chimera на Entry-сервере (Режим B)
        ↓ Ввести параметры от Exit-ноды
Шаг 3: Получить VLESS-ссылку для клиентов (от Entry-сервера)
```

### Подробно по шагам

#### Шаг 1: Установка Exit-ноды (Режим A)

1. Арендуйте зарубежный VPS (EU/US/Asia).
2. Запустите установку Chimera: `bash <(curl -fsSL ...)`.
3. Выберите **Режим A** (Одиночный сервер).
4. Выберите протокол (**REALITY** рекомендуется).
5. Введите параметры (домен/SNI, UUID, и т.д.).
6. Дождитесь завершения установки.
7. **Сохраните** параметры из финального экрана:
   - VLESS-ссылка (в файле `/root/vless_link.txt`)
   - UUID
   - Public Key
   - ShortID
   - SNI/домен
   - Порт (обычно 443)

#### Шаг 2: Установка Entry-ноды (Режим B)

1. Арендуйте российский VPS.
2. Запустите установку Chimera.
3. Выберите **Режим B** (Каскадный прокси).
4. Выберите протокол (**REALITY** рекомендуется).
5. Введите параметры Entry-ноды (домен/SNI, UUID, и т.д.).
6. Выберите транспорт: **VLESS**, **AWG** или **Hysteria2**.

**При выборе VLESS-транспорта:**

7. Введите параметры **каждой exit-ноды** (см. ниже).
8. Для каждой ноды нужно указать:
   - **IP или домен** exit-сервера
   - **Порт** (обычно 443)
   - **UUID** (из финального экрана exit-сервера)
   - **Public Key** (pbk, из финального экрана)
   - **ShortID** (hex, из финального экрана)
   - **SNI** (домен exit-сервера)
   - **Fingerprint** (должен совпадать с exit-сервером)

> **ВНИМАНИЕ!** Параметры от exit-сервера нужно вводить **аккуратно**.
> VLESS-ссылка, которую выдаёт exit-сервер, содержит все параметры, но
> в формате URL. **Обязательно прогоните ссылку через ИИ (ChatGPT/Claude/
> любой LLM) или соберите параметры вручную**, удалив все лишние переносы
> строк, пробелы и спецсимволы. Если вставить ссылку с переносами или
> пробелами — **ничего работать не будет**, и ошибка будет неочевидной
> (Xray просто не подключится к exit-ноде).

**Пример VLESS-ссылки от exit-сервера:**
```
vless://12345678-1234-1234-1234-123456789abc@203.0.113.50:443?encryption=none&flow=xtls-rprx-vision&security=reality&sni=example.com&fp=chrome&pbk=ABCDEF1234567890...&sid=abcdef12&spx=%2Fabc123&type=tcp&headerType=none#Exit-EU
```

**Как извлечь параметры:**

| Параметр | Где в ссылке | Пример |
|---|---|---|
| IP/домен | После `@` и до `:` | `203.0.113.50` |
| Порт | После `:` и до `?` | `443` |
| UUID | После `vless://` и до `@` | `12345678-1234-1234-1234-123456789abc` |
| Public Key (pbk) | `&pbk=...&` | `ABCDEF1234567890...` |
| ShortID (sid) | `&sid=...&` | `abcdef12` |
| SNI | `&sni=...&` | `example.com` (домен exit-сервера) |
| Fingerprint (fp) | `&fp=...&` | `chrome` |

8. При вводе **нескольких exit-нод** (мультикаскад) — повторите для каждой.
   Можно добавить от 1 до 10 нод. После ввода всех нод выберите стратегию
   балансировки (Round Robin / Least Ping / Least Load / Random / Smart Balancer).

**При выборе AWG-транспорта:**

7. Введите IP exit-сервера и SSH-доступ (пароль или ключ).
8. Chimera сама подключится по SSH, установит AWG-сервер на Exit,
   и настроит туннель. **Вручную вводить параметры exit-ноды не нужно.**

**При выборе Hysteria2-транспорта:**

7. Установка H2 на Exit происходит **после** основной установки, через
   меню 7 (Hysteria2 транспорт). Во время установки просто выбирается
   транспорт — параметры вводятся позже.

#### Шаг 3: Получение ссылки для клиентов

После завершения установки Entry-сервера, финальный экран покажет:
- VLESS-ссылку для клиентов (в файле `/root/vless_link.txt`)
- QR-код (в файле `/root/vless_qr.png`)
- Все параметры

**Клиентам нужно давать ссылку от Entry-сервера** (не от Exit).

### Стратегии балансировки (мультикаскад)

При 2+ exit-нодах Chimera спрашивает стратегию:

| Опция | Стратегия | Описание |
|---|---|---|
| `1` ★ | Round Robin | Подключения по кругу: нода1→нода2→нода1→... |
| `2` | Least Ping | Xray замеряет RTT, выбирает самую быструю |
| `3` | Least Load | Учитывает RTT + количество соединений |
| `4` | Random | При каждом подключении нода выбирается случайно |
| `5` | Smart Balancer | Авто: задержка + нагрузка + пропускная способность, cron каждые 5 мин |

> **Рекомендация:** `1` (Round Robin) — простой и надёжный. Если ноды
> разной мощности — `5` (Smart Balancer).

## 8. Раздельное туннелирование (Split Tunneling)

### Что это

```
Без split tunnel:    Весь трафик клиента → через VPN (Entry → Exit → Интернет)

С split tunnel:      Заблокированные в РФ ресурсы → через VPN (Entry → Exit → Интернет)
                     Остальной трафик (банки, Госуслуги, маркетплейсы) → напрямую
```

- Списки заблокированных ресурсов берутся из `geosite:runetfreedom`
  (github.com/itdoginfo/runetfreedom — регулярно обновляемый список
  доменов, заблокированных в РФ).
- Дополнительно можно указать свои домены и IP/CIDR.

### Включение

Во время установки Chimera спрашивает:
```
Включить раздельное туннелирование? [Y/N]
```

- **Y** — заблокированное через VPN, остальное напрямую.
- **N** — весь трафик через VPN.

При `Y` можно дополнительно ввести домены/IP через запятую:
```
Дополнительные домены/IP: blocked-site.com, 203.0.113.0/24
```

### Когда включать

| Сценарий | Включать? |
|---|---|
| Сервер в РФ (Режим B), клиенты в РФ | ✅ Да — банки/Госуслуги должны идти напрямую |
| Сервер за рубежом (Режим A) | ❌ Нет — весь трафик через VPN, нет проблемы с РФ-сайтами |
| Сервер за рубежом, но клиенты в РФ | Зависит — если нужны РФ-банки напрямую, включите |

### Управление после установки

Меню → **Управление раздельным туннелированием**:
- Включить/выключить.
- Добавить/удалить домены/IP.
- Обновить списки geosite/geoip (авто-обновление через cron).

> **Важно:** split tunnel работает на стороне Xray (routing rules). Клиент
> должен быть настроен на "проксировать весь трафик" (не "только заблокированные"
> — это делается на стороне сервера, не клиента).

### ВАЖНО: серверная маршрутизация в каскадном режиме

В **каскадном режиме (Режим B)** вся маршрутизация трафика выполняется
**на Entry-ноде** (РФ-сервер) — благодаря связке split tunneling
(домены из geosite:runetfreedom) + РФ-подсети RIPE (CIDR, см. раздел 14).

```
Клиент ──весь трафик──► Entry VPS (RU)
                          │
                          ├─ РФ-домены (geosite:runetfreedom) → direct (напрямую)
                          ├─ РФ-IP (RIPE CIDR)                → direct (напрямую)
                          └─ Остальной трафик                  → Exit VPS (EU) → Интернет
```

**Клиенту не нужно настраивать раздельное туннелирование на своём
устройстве.** Клиент просто подключается к Entry-серверу (режим "весь
трафик через VPN" в клиентском приложении), а сервер уже сам разделяет
трафик:
- Заблокированные/зарубежные сайты → через Exit-ноду (обход блокировок).
- Российские сайты (банки, Госуслуги, маркетплейсы) → напрямую с
  Entry-сервера (быстро, без лишнего хопа, банки видят вход из РФ).

**Плюсы серверного разделения:**
- **Не нужно настраивать каждый клиент.** Split tunneling включается
  один раз на сервере — все клиенты сразу получают разделённый трафик.
- **Не нужен специальный клиент.** Работает в любом клиентском
  приложении (v2rayNG, Shadowrocket, Nekobox, и т.д.) — достаточно
  режима "проксировать весь трафик".
- **Списки обновляются на сервере.** geosite:runetfreedom и RIPE CIDR
  обновляются автоматически (cron/systemd timer) — клиентам не нужно
  ничего обновлять.
- **Нет утечек.** Поскольку разделение происходит на сервере (а не на
  клиенте), невозможно случайно пропустить трафик мимо VPN — все
  решения принимает Xray на Entry-ноде.

## 9. DNSCrypt-proxy

### Что это

DNSCrypt-proxy — зашифрованный DNS-резолвер. Шифрует DNS-запросы между
сервером и DNS-провайдером (Cloudflare, Google, Quad9), защищая от
перехвата и подмены DNS-запросов провайдером.

### Как работает

```
Без DNSCrypt:    Сервер ──DNS (plaintext UDP:53)──► DNS-провайдер
С DNSCrypt:      Сервер ──DNSCrypt (encrypted)────► DNS-провайдер
```

Xray отправляет DNS-запросы на `127.0.0.1:5300` (локальный DNSCrypt),
который шифрует и перенаправляет на публичный DNS-сервер.

### Включение

Во время установки (шаг 10/11):
```
Установить DNSCrypt-proxy? [Y/n]
```

- **Y** (рекомендуется) — установить DNSCrypt.
- **N** — использовать публичные DNS напрямую (1.1.1.1 / 8.8.8.8).

### Когда не нужен

- Низкая память (< 512 МБ) — DNSCrypt добавляет ~5 МБ RAM.
- Тестовая установка — проще без лишних компонентов.

## 10. Сайт-заглушка (маскировка)

### Что это

Когда кто-то (или DPI) заходит на ваш сервер в браузере по
`https://<домен>:443` — он видит **обычный веб-сайт**, а не прокси.
Это маскировка: сервер выглядит как легитимный веб-ресурс.

### Как работает

```
Браузер/DPI ──HTTPS:443──► Nginx ──► Статичный HTML-сайт (заглушка)
                                      (15 шаблонов на выбор)
Клиент VLESS ──TCP:443──► Nginx ──► Xray (REALITY/xHTTP)
                                   (прозрачно, не мешает сайту)
```

Nginx на 443 порту:
- Для обычных HTTPS-запросов — отдаёт статичный сайт (заглушку).
- Для VLESS-клиентов — проксирует трафик в Xray через unix-сокет (REALITY)
  или TCP-backend (xHTTP).

### Шаблоны

15 готовых шаблонов (см. шаг 9/11). Все — статичные HTML/CSS/JS с
анимациями, выглядят как реальные сайты:
- IT-портал, SaaS, homeware store, bistro, community, developer forum,
  architecture studio, plant shop, coffee roastery, spa, design studio,
  logistics, library, consulting, analytics.

> **Рекомендация:** выберите `0` (случайный). Все шаблоны качественные.

## 11. SSL-сертификаты Let's Encrypt

### Когда нужны

- **REALITY** — сертификат нужен **всегда**. В архитектуре selfsteal Nginx
  терминирует TLS с реальным сертификатом вашего домена, а REALITY
  маскируется под этот же сайт. Без сертификата selfsteal не работает.
- **xHTTP TLS** — сертификат **обязателен** для протокола. Nginx терминирует
  TLS с реальным сертификатом вашего домена.

### Как получается

Chimera автоматически получает сертификат через **certbot** (Let's Encrypt ACME):
1. Nginx настраивается на временный HTTP:80 (для ACME-challenge).
2. Certbot запрашивает сертификат для указанного домена.
3. Let's Encrypt проверяет, что домен указывает на этот сервер.
4. Сертификат сохраняется в `/etc/letsencrypt/live/<домен>/`.
5. Nginx перенастраивается на HTTPS:443 с этим сертификатом.
6. Настраивается авто-обновление (cron / systemd timer).

### Требования

- Домен с A-записью на IP сервера.
- Порт 80 (HTTP) открыт — для ACME-challenge.
- Порт 443 (HTTPS) открыт — для сайт-заглушки и VLESS.

> Если порт 80 закрыт файрволом — certbot не сможет получить сертификат.
> Откройте 80 и 443 перед установкой.

## 12. TLS Fingerprint (uTLS)

### Что это

uTLS (uTLS = µTLS) — библиотека, которая маскирует TLS ClientHello под
конкретный браузер. DPI анализирует ClientHello и определяет, какой
браузер его отправил. Если ClientHello не похож на реальный браузер —
DPI может заблокировать соединение.

### Как работает

```
Без uTLS:    ClientHello = стандартный Go TLS (легко детектится)
С uTLS:      ClientHello = Chrome / Firefox / Safari / Edge (копия реального)
```

Fingerprint **должен совпадать** на сервере и в клиенте:
- На сервере: параметр установки (шаг 11/11).
- В клиенте: настройка `fingerprint` в Xray/v2rayNG/Shadowrocket/etc.

### Опции

| Fingerprint | Описание | Когда использовать |
|---|---|---|
| `chrome` ★ | Google Chrome | По умолчанию (самый распространённый) |
| `firefox` | Mozilla Firefox | Если клиент на Firefox |
| `safari` | Apple Safari | Если клиент на Safari/macOS |
| `edge` | Microsoft Edge | Если клиент на Edge |
| `random` | Случайный из реальных | Для разнообразия |
| `randomized` | Рандомизированный | Максимальная анонимность (непредсказуемый) |

> **Рекомендация:** `chrome` — самый распространённый, меньше всего
> привлекает внимание. **Важно:** если на сервере `chrome`, то и в клиенте
> (v2rayNG, Shadowrocket, Nekobox) нужно выставить `chrome`.

> **Ограничения REALITY (важно для Xray-core 26.9.8+ на сервере):**
> `random`/`randomized` для REALITY запрещены гардом Chimera (сервер не
> извлекает auth-proof из рандомизированного Hello — соединение молча
> уходит в декой); `ios` не содержит key_share X25519MLKEM768 и
> отвергается ядрами 26.9.8+ даже настоящим Xray-клиентом; для
> mihomo-семейства против 26.9.8+ работает только `chrome` + флаг
> `support-x25519mlkem768` (рецепт B — генераторы Chimera пишут его
> автоматически). Полная матрица — [§18](#18-совместимость-клиентских-ядер-и-версий-xray-core-гейт-версий-x25519mlkem768).

## 13. Гео-блокировка (Ingress blocking)

### Что это

Блокировка входящих подключений с определённых стран/IP-диапазонов.
Защищает сервер от сканирования с российских IP (если сервер за рубежом)
или от зарубежных IP (если сервер в РФ).

### Как работает

iptables + ipset:
- Создаётся ipset-набор с подсетями страны (например `xray_ru_block`).
- iptables-правило: `iptables -A INPUT -p tcp --dport 443 -m set --match-set xray_ru_block src -j DROP`.

### Управление

Меню → **Гео-блокировка**:
- Добавить страну (по коду: RU, CN, IR, и т.д.).
- Удалить страну.
- Список заблокированных стран.

> **Не путать с split tunneling!** Гео-блокировка блокирует **входящие**
> подключения (кто может подключиться к серверу), а split tunneling
> маршрутизирует **исходящие** подключения (куда идёт трафик).

## 14. РФ подсети RIPE → direct (защита от цензора)

### Что это

Это **маршрутизация** — правило в конфиге Xray, которое направляет
трафик к российским IP-адресам **напрямую** (минуя VPN-каскад), а весь
остальной трафик — через exit-ноду.

```
Клиент ──► Entry VPS (RU) ──┬──► РФ-сайты (банки, Госуслуги, маркетплейсы) → напрямую (direct)
                             └──► Заблокированные/зарубежные сайты → Exit VPS (EU) → Интернет
```

### Чем отличается от Split Tunneling

| | Split Tunneling | РФ подсети RIPE → direct |
|---|---|---|
| Что маршрутизирует | **Домены** (по geosite:runetfreedom) | **IP-подсети** (по RIPE NCC) |
| Источник данных | github.com/itdoginfo/runetfreedom (список доменов) | ftp.ripe.net (delegated-ripencc-latest — официальные подсети РФ) |
| Как работает | Xray routing по доменным правилам | Xray routing по IP/CIDR правилам |
| Можно использовать вместе | ✅ Да — дополняют друг друга | ✅ Да |

**Рекомендуется использовать оба** — split tunneling для доменов, РФ-подсети
для IP. Они не конфликтуют: Xray применяет первое совпавшее правило.

### Как работает

1. Chimera скачивает `delegated-ripencc-latest` с `ftp.ripe.net` —
   официальный реестр всех IP-блоков, делегированных RIPE NCC (европейский
   региональный интернет-регистратор). Из него извлекаются все подсети
   РФ (country code = RU) — количество CIDR зависит от актуальности
   реестра, на момент написания документа в реестре было 13563 CIDR.
2. Подсети сохраняются в `/etc/xray/ru_subnets_ripe.txt`.
3. В конфиг Xray добавляются routing-правила: для каждого блока до 500
   CIDR — одно правило с `outboundTag: "direct"` (или `"direct-local"`
   при AWG-транспорте, чтобы обойти fwmark).
4. Xray применяет правила: трафик к РФ-IP идёт напрямую (через
   системный роутинг), остальной — через VPN-каскад.

### Зачем нужно

**Без РФ-подсетей:** весь трафик клиента идёт через VPN-каскад
(Entry → Exit → Интернет). Это значит, что российские сайты (Сбербанк,
Госуслуги, Яндекс, маркетплейсы) тоже идут через зарубежный Exit — что
может:
- Привести к блокировке аккаунта (банк видит вход из-за границы).
- Замедлить доступ (лишний хоп через Exit).
- Привлечь внимание цензора (трафик к РФ-сайтам через VPN).

**С РФ-подсетями:** трафик к российским IP идёт напрямую с Entry-сервера
(минуя Exit), остальной — через Exit. Банки видят вход из РФ, доступ
быстрый, цензор не видит VPN-трафика к РФ-сайтам.

### Когда включать

| Сценарий | Включать? |
|---|---|
| Режим B (каскад), сервер в РФ | ✅ Да — обязательно |
| Режим A, сервер за рубежом | ❌ Нет — весь трафик и так через сервер |
| Режим A, сервер в РФ | ❌ Нет — весь трафик напрямую |

### Как включить

Меню → **Гео-блокировка** → `[5] РФ подсети (RIPE NCC) → direct**:

```
[1] Скачать/обновить подсети из RIPE NCC и применить в Xray
[2] Применить из сохранённого файла (без загрузки)
[3] Настроить время авто-обновления (systemd timer)
[4] Отключить авто-обновление (удалить timer)
[5] Удалить правила РФ подсетей из Xray
[6] Показать первые 20 подсетей из файла
[7] Просмотр всех routing-правил Xray
```

- `[1]` — скачать актуальные подсети (количество CIDR зависит от
  актуальности реестра RIPE, на момент написания — 13563) и применить.
  Занимает
  30-60 секунд (загрузка ~10 МБ файла с RIPE).
- `[3]` — настроить systemd timer для ежедневного авто-обновления.
  Подсети РФ меняются (добавляются/удаляются), важно обновлять регулярно.
- `[5]` — удалить все правила из Xray (отключить direct-маршрутизацию).

### Авто-обновление

Рекомендуется включить `[3]` (systemd timer) — подсети RIPE обновляются
ежедневно. Timer запускает `python3 main.py --update-ru-subnets` в
заданное время, скачивает свежий файл и применяет правила в Xray.

### Проверка

```bash
# Сколько правил в Xray
grep -c "ru_subnets_ripe" /etc/xray/config.json

# Должно быть ~13000+ CIDR в файле (зависит от актуальности реестра)
wc -l /etc/xray/ru_subnets_ripe.txt

# Статус timer
systemctl list-timers xray-ru-subnets.timer
```

### Совместимость с AWG-транспортом

При AWG-транспорте (Режим B) РФ-подсети используют `outboundTag:
"direct-local"` (а не `"direct"`) — это специальный outbound без fwmark,
чтобы трафик шёл через системный дефолт-роут (минуя AWG-туннель). Chimera
делает это автоматически при применении правил.

## 16. Ссылки для клиентов

### Где взять

После установки:
- `/root/vless_link.txt` — VLESS-ссылка (текст).
- `/root/vless_qr.png` — QR-код (для мобильных клиентов).
- `/root/vless_qr_ipv4.png` — QR-код (IPv4, для Режима A).

### ВАЖНО: в каскадном режиме — ссылка от Entry-сервера

В **Режиме B (каскад)** клиенту нужно выдавать ссылку **только от
Entry-сервера** (РФ-нода, Режим B) — **НЕ от Exit-сервера**.

```
Клиент ──VLESS-ссылка от Entry──► Entry VPS (RU) ──► Exit VPS (EU) ──► Интернет
                                  ↑
                          Ссылка отсюда, не от Exit
```

- Ссылка от Entry содержит домен/IP Entry-сервера, ключи REALITY
  Entry-сервера, порт Entry-сервера.
- Exit-сервер используется только как промежуточный узел — клиенты
  подключаются к нему **не напрямую**, а через Entry (каскад).
- Если дать клиенту ссылку от Exit — он подключится напрямую к
  зарубежному серверу, минуя каскад. Это может не работать (ТСПУ
  блокирует прямые VLESS-соединения из РФ) и лишает смысла весь каскад.

> **В Режиме A** (одиночный сервер) — ссылка выдаётся от единственного
> сервера, проблем нет.

### Использование домена в ссылке (рекомендуется)

В VLESS-ссылке адрес сервера может быть указан как **IP-адрес** или как
**домен**:

```
По IP:     vless://UUID@203.0.113.50:443?...
По домену: vless://UUID@proxy.example.xyz:443?...
```

**Рекомендуется использовать домен**, а не IP. Преимущества:
- **При смене IP** (переезд сервера) — достаточно обновить A-запись в DNS,
  клиентам не нужно перевыдавать ссылки.
- **CDN/Cloudflare** — если домен проксируется через Cloudflare, можно
  скрыть реальный IP сервера.
- **SNI совпадает с адресом** — при использовании домена в ссылке SNI
  и адрес совпадают, что выглядит естественнее для DPI.
- **IPv6** — домен резолвится в AAAA-запись, клиенты с IPv6 подключаются
  по IPv6 без отдельной ссылки.

> Chimera по умолчанию генерирует ссылку с доменом, если он указан при
> установке. Если ввести IP вместо домена — ссылка будет с IP.

### Формат ссылки

```
vless://<UUID>@<АДРЕС>:<PORT>?encryption=none&flow=xtls-rprx-vision&security=reality&sni=<SNI>&fp=<FINGERPRINT>&pbk=<PUBKEY>&sid=<SHORTID>&spx=<SPIDERX>&type=tcp&headerType=none#<NAME>
```

Где `<АДРЕС>` — домен (рекомендуется) или IP сервера.

### Добавление пользователей

Меню → **Управление пользователями**:
- Каждый пользователь получает свой UUID.
- Ссылка генерируется для каждого отдельно.
- Можно настроить лимиты трафика и TTL-пользователей.

> Все пользователи подключаются к одному порту (443). Различение — по UUID.

## 17. Частые вопросы

### Q: Какой режим выбрать — A или B?

**A:** Если сервер за рубежом и клиенты могут напрямую к нему подключаться —
Режим A. Если сервер в РФ и нужен обход блокировок — Режим B (каскад:
Entry в РФ → Exit за рубежом).

### Q: Нужен ли домен для REALITY?

**A:** Да. В Chimera REALITY использует архитектуру **selfsteal** —
маскируется под **ваш собственный** сайт (Nginx + Let's Encrypt
сертификат вашего домена). Домен нужен **всегда**. Использовать чужой
домен нельзя (исключение: AWG-транспорт в Режиме B без Nginx).

### Q: Какой порт выбрать?

**A:** 443 (стандартный HTTPS) — меньше всего блокировок. Если 443 занят — 8443.

### Q: Какой fingerprint выбрать?

**A:** `chrome` — самый распространённый. **Важно:** должен совпадать в
клиенте и на сервере.

### Q: Что делать, если VLESS-ссылка от exit-ноды с переносами строк?

**A:** Прогоните ссылку через ИИ (ChatGPT/Claude) или соберите параметры
вручную, удалив все переносы строк, пробелы и лишние символы. Вставка
ссылки с переносами — самая частая причина неработающего каскада.

### Q: Можно ли добавить несколько exit-нод?

**A:** Да, до 10 нод. При установке Режима B введите параметры каждой
ноды. Трафик будет распределяться по выбранной стратегии (Round Robin /
Least Ping / и т.д.).

### Q: В чём разница между AWG и VLESS-транспортом в каскаде?

**A:** VLESS — TCP/TLS-туннель между Entry и Exit. AWG — UDP-туннель с
обфускацией (устойчивее к DPI). AWG не требует VLESS на Exit — Chimera
сама установит AWG-сервер через SSH.

### Q: Как обновить Xray после установки?

**A:** Меню → `[5] Обновить Xray`. Или `python3 main.py --update-xray`.

### Q: Как пересоздать конфиг Xray без переустановки?

**A:** Меню → `[5b] Перегенерировать конфиг Xray`. Или через аварийное
восстановление: `[6] Аварийное восстановление`.

### Q: Что делать, если Xray не запускается?

**A:** Проверьте лог: `journalctl -u xray -n 30`. Проверьте конфиг:
`xray run -test -config /etc/xray/config.json`. Если конфиг невалиден —
перегенерируйте: `[5b]` или `[6]`.

### Q: Как включить split tunneling после установки?

**A:** Меню → Управление раздельным туннелированием → Включить. Можно
добавить свои домены/IP.

### Q: Как сменить fingerprint после установки?

**A:** Меню → `[2] Управление пользователями` → Fingerprint manager.
Или вручную в `/etc/xray/config.json` → `fingerprint` в `realitySettings`.

### Q: Можно ли использовать и REALITY, и xHTTP одновременно?

**A:** Нет, при установке выбирается один протокол. Сменить можно через
переустановку (меню → `[1]`).

### Q: Как полностью удалить Chimera?

**A:** Меню → `[7] Удалить установку`. Останавливаются и удаляются все
сервисы (xray, nginx, dnscrypt), конфиги, скрипты. Данные пользователей
и сертификаты Let's Encrypt сохраняются.

### Q: Что значит "Redirect 6" в iptables?

**A:** `6` — номер протокола TCP (IPPROTO_TCP = 6). Флаг `-n` (numeric)
в iptables делает протокол числом вместо текста `tcp`. Это нормально.

### Q: Nyamebox / Karing пишет «reality verification failed» — что делать?

**A:** У этих клиентов ядро sing-box. Против сервера на Xray-core
26.9.8+ они не работают в принципе: sing-box не отправляет key_share
X25519MLKEM768 в ClientHello, а сервер такой хендшейк отвергает
(конфигом не лечится). Варианты: mieru-подписка Chimera, клиент
mihomo/Xray-семьи или даунгрейд сервера до 26.7.28 — пункт меню
`[5c]` пропишет `minClientVer="1.8.0"` автоматически. Полная матрица
и рецепты —
[§18](#18-совместимость-клиентских-ядер-и-версий-xray-core-гейт-версий-x25519mlkem768).

## 18. Совместимость клиентских ядер и версий Xray-core (гейт версий, X25519MLKEM768)

### Что случилось

В сентябре 2026 после обновления серверного Xray-core до 26.9.8/26.9.9
у части клиентов отвалился VLESS+REALITY:

- клиенты на ядре **sing-box** (Nyamebox, Karing, Hiddify, SFM) —
  `reality verification failed` на каждом соединении;
- клиенты семейства **mihomo** без «рецепта B» — TCP до сервера жив,
  но туннеля нет (Timeout: соединение молча уводится в декой).

Расследование (локальный стенд 2026-09-10: серверы 26.6.27 / 26.7.28 /
26.9.9 × гейты unset / `""` / `1.8.0` / `2.0.0` × клиенты sing-box 1.14.0,
mihomo 1.19.30, Xray 26.6.27/26.7.28/26.9.9 — плюс живые пробы против
RU1/RU2/PL) вскрыло **две независимые серверные механики Xray-core**,
сломавшие клиентскую совместимость. Конфиги Chimera при этом корректны:
лечение — на стороне клиентов, либо временный даунгрейд сервера
(см. «Рецепты» ниже).

### Эпохи серверного Xray-core

| Эпоха | Версии сервера | Гейт версий (minClientVer) | Требование X25519MLKEM768 в ClientHello |
|---|---|---|---|
| До-гейт | ≤ 26.6.27 | нет | нет |
| Гейт-эпоха | 26.7.11–26.7.28 | unset/`""` → **дефолт-гейт 26.3.27** (в логе предупреждение «The default minimal client version is Xray-core v26.3.27») | нет |
| MLKEM-эпоха | 26.9.8, 26.9.9 | unset/`""` → **гейт ВЫКЛ** (дефолт убран; непустые пороги работают) | **да** — CH без MLKEM или с MLKEM не первой позицией key_share отвергается |

> Релизов между 26.7.28 и 26.9.8 **не существует** (нет ни 26.8.x, ни
> 26.9.0–26.9.7) — v26.7.28 это ровно «последняя версия до MLKEM».
> Все теги начиная с 26.4.x помечены на GitHub как Pre-release (поэтому
> releases/latest ведёт на v26.3.27); флот Chimera работает на 26.9.9.

### Кто что отчитывает в REALITY-хендшейке

| Клиентское ядро | ClientVer в хендшейке |
|---|---|
| Xray-core (Incy, v2rayNG, Xray-CLI) | реальная версия ядра, напр. `[26, 9, 9]` |
| mihomo (Clash Verge, FlClash, OpenClash) | `[1, 8, 2]` — версия XTLS-реализации mihomo |
| sing-box (Nyamebox, Karing, Hiddify, SFM) | `[1, 8, 1]` — версия XTLS-реализации sing-box |

Важно: mihomo и sing-box версию **отчитывают** (кто не знал — ClientVer
это XTLS-версия, а не «версия Xray»). Xray-клиент в ClientVer кладёт
версию своего ядра — поэтому любой непустой порог ≤ его версии он
проходит.

### Матрица совместимости клиент ↔ сервер

| Клиент \ Сервер | ≤ 26.6.27 | 26.7.11–26.7.28 | 26.9.8+ (флот Chimera) |
|---|---|---|---|
| **sing-box 1.14.x** (Nyamebox, Karing, Hiddify, SFM) | ✅ работает из коробки | ⚠️ только с явным `minClientVer="1.8.0"` (рецепт podkop); с unset/`""` дефолт-гейт 26.3.27 валит `[1,8,1]` → декой/Timeout | ❌ **не работает и не заработает конфигом** — не шлёт key_share X25519MLKEM768: `reality verification failed` при любом гейте и любом fp |
| **mihomo 1.19.x** (Clash Verge, FlClash, роутеры) | ✅ (флаг MLKEM не нужен; с флагом — тоже работает) | ⚠️ только с `minClientVer` ≤ `"1.8.2"` (mihomo отчитывает `[1,8,2]`: пороги `"1.8.0"`/`"1.0.0"` проходит, `"2.0.0"` — нет); с unset/`""` дефолт-гейт валит | ✅ **только «рецепт B»**: `fp=chrome` + `reality-opts.support-x25519mlkem768: true` — генераторы Chimera пишут это автоматически (с 10.09.2026); без флага или с firefox/ios/edge — ❌ (502/Timeout) |
| **Xray-core** (Incy, v2rayNG, Xray-CLI) | ✅ | ✅ (отчитывают реальную версию ≥ 26.3.27 — дефолт-гейт проходят) | ✅ при fp=chrome/firefox/safari и достаточно свежем ядре (клиент 26.6.27 проверен — OK); ❌ при fp=ios; очень старые ядра без MLKEM упадут так же, как sing-box |

Все клетки матрицы покрыты экспериментом (стенд 2026-09-10). Успешные
хендшейки против 26.9.9 сервер логирует (при `show: true`) строкой
`is using X25519MLKEM768 for TLS' communication: true`.

### Причины совместимости и несовместимости (по клеткам)

**sing-box × 26.9.8+ — несовместим в принципе.** Требование MLKEM зашито
в серверную библиотеку xtls/reality (PR #6507); поля конфига, которое
отключает проверку, не существует — RPRX в issue #6477 прямо пишет, что
сервер «смотрит прямо на отпечаток». TLS-стек sing-box не генерирует
key_share X25519MLKEM768: официальный sing-box 1.14.0 (31.08.2026,
uTLS 1.8.7) и форк shtorm-7/sing-box-extended 1.14.0-extended-2.7.1 дают
одинаковый отказ (живой тест против RU1/RU2). PQ-фингерпринты
(`chrome_pq`) sing-box сам удалил ещё в 1.10.0 как несовместимые с
REALITY. Вывод: лечится только апдейтом sing-box выше по течению —
следить за SagerNet/sing-box. Обходные пути: mieru-подписка Chimera
(nyamebox / `mierus://` / Karing-JSON) или клиент mihomo/Xray-семьи.

**sing-box/mihomo × 26.7.11–26.7.28 (с дефолтом) — гейт версий.** Сервер
требует ClientVer ≥ 26.3.27; mihomo шлёт `[1,8,2]`, sing-box `[1,8,1]` —
оба ниже порога, REALITY молча уводит соединение в декой (в клиенте —
Timeout, в логе сервера — rejection). Лечится явным
`minClientVer="1.8.0"` (рецепт podkop): 1.8.2/1.8.1 ≥ 1.8.0, оба
проходят. Это и есть «эпоха фикса podkop» — их чат-рецепт валиден ровно
для серверов 26.7.11–26.7.28.

**mihomo × 26.9.8+ — совместим только с рецептом B.** mihomo умеет
строить ClientHello с X25519MLKEM768 первой позицией key_share, но
MLKEM-заготовка у него одна — хром (HelloChrome_Auto), и включается она
флагом `support-x25519mlkem768`. Поэтому для REALITY против 26.9.8+
fp форсирован в `chrome` и нужен флаг; с firefox/ios/edge в ClientHello
нет MLKEM key_share → отвержение (502/Timeout). Против старых ядер
(≤ 26.7.28) связка chrome+флаг тоже работает — флаг безвреден.

**Xray-клиенты × 26.9.8+ — совместимы.** Отчитывают реальную версию ядра
(любой разумный порог проходят), MLKEM в ClientHello умеют давно —
июньский клиент 26.6.27 проходит против 26.9.9 (проверено). Единственный
провал — `fp=ios`: у iOS-заготовки нет key_share MLKEM, сервер отдаёт
настоящий сертификат декоя, клиент пишет `REALITY: received real
certificate`. Точная нижняя граница «свежести» ядра не пинилась, но
весь 26.x-ряд с chrome/safari/firefox проходит.

### Почему мы сами ошибались раньше (честная записка)

Ранняя правка «выключен гейт версий» (10.09.2026, утро) считала, что
mihomo «не отчитывает версию и не проходит НИКАКОЙ непустой порог,
включая 1.0.0». Стенд показал обратное: mihomo отчитывает `[1,8,2]` и
проходит пороги ≤ "1.8.2". Тесты того времени шли без флага MLKEM
(рецепта B ещё не было) — соединения валил MLKEM-чек ядра 26.9.8+, а не
гейт версий; симптом один и тот же (Timeout), причину спутали. Лекарство
(`""`) при этом осталось верным: на 26.9.8+ дефолт-гейт убран, и пустое
значение = «гейт выключен». Комментарии в коде и меню 5b переписаны под
факты в тот же день (см. CHANGELOG).

### Рецепты

**Флот Chimera (Xray 26.9.8+, конфиги уже правильные):**
- mihomo-клиенты: ядро ≥ 1.19.29 + подписка mihomo из Chimera (рецепт B
  уже в конфиге) — работает;
- Xray-клиенты (Incy, v2rayNG): fp=chrome/safari/firefox — работает
  (fp=ios — нет);
- sing-box-клиенты (Nyamebox, Karing): на VLESS не заведутся —
  используйте mieru-подписку Chimera (nyamebox / `mierus://` /
  Karing-JSON) или переходите на mihomo/Xray-семью.

**Если очень нужны sing-box-клиенты именно на VLESS (даунгрейд):**

С 11.09.2026 даунгрейд — одно действие из панели: «Установка и
Система» → пункт `[5c] Даунгрейд ядра Xray`. Панель сама: скачает
ядро через download manager (10 зеркал + SHA256-верификация),
забэкапит бинарник (/var/backups/xray/binaries), прогонит тест
конфига новым ядром (провал = автоматический откат), выставит
minClientVer под эпоху (state.json + все REALITY-инбаунды живых
конфигов), предложит отключить таймер автообновления и перезапустит
Xray. На выходе печатается матрица «клиент → работает?». Целевые
версии — ровно две:

| Цель (пункт 5c) | Эпоха | Авто-конфиг | Xray | sing-box | mihomo |
|---|---|---|---|---|---|
| `v26.7.28` — последний пререлиз до MLKEM («оптимум») | гейт | `minClientVer="1.8.0"` | ✅ | ✅ [1,8,1] ≥ 1.8.0 | ✅ [1,8,2] ≥ 1.8.0 |
| `v26.3.27` — последний стабильный релиз GitHub | до-гейт | `minClientVer=""` | ✅ | ✅ | ✅ |

Даунгрейда на 26.9.8 в списке нет: это та же MLKEM-эпоха, что и
26.9.9 — конфиг не меняется, sing-box всё равно не работает.
Возврат на актуальное ядро — пункт `[5]`: он мигрирует
эпоха-управляемое значение обратно в `""` автоматически (кастомное
значение, выставленное вручную, не трогается).

Ручной путь (если панели нет под рукой):
1. Даунгрейд Xray-core до **v26.7.28** — последняя версия до MLKEM:
   скачать `Xray-linux-64.zip` с
   `github.com/XTLS/Xray-core/releases/tag/v26.7.28`, заменить
   `/usr/local/bin/xray`, `systemctl restart xray`, проверить
   `xray version`;
2. Выставить явный **`minClientVer="1.8.0"`** (без этого дефолт-гейт
   26.3.27 продолжит валить mihomo/sing-box): пункт `[5b]` →
   подтвердить перегенерацию (`y`) → ответить `y` на «Выставить
   minClientVer?» → Enter. Значение хранится в `state.json`
   (`min_client_ver`), генераторы читают его оттуда — конфиг
   переживёт любые rebuild/ротации кредов. Сброс в `""` — там же,
   введя `-`;
3. Цена решения: сервер остаётся в гейт-эпохе без апдейтов 26.9.x;
   пункт меню `[5] Обновить Xray-core` вернёт 26.9.x — и sing-box снова
   отвалится. Не обновляйте ядро, пока sing-box не добавит MLKEM.

Тонкости:
- таймер `xray-autoupdate.timer` сравнивает версии только на
  РАВЕНСТВО с GitHub-stable (v26.3.27): после даунгрейда его скрипт
  молча перетянет ядро на v26.3.27, даже если та старше — пункт 5c
  предлагает таймер отключить (вернуть: `[5]` →
  «Включить автообновление»);
- mihomo-конфиги менять не нужно: рецепт B (chrome + флаг) безвреден
  на всех эпохах;
- exit-ноды цепочки (режим B) получат значение при следующей
  перегенерации их конфигов (генераторы читают state.json);
- серверных «MLKEM-полей» не существует — поведение зашито в бинарник
  ядра, меняется только сменой версии.

> Даунгрейд до «стабильного релиза» в смысле GitHub (releases/latest =
> v26.3.27) тоже заставит sing-box работать (до-гейт эпоха, правки не
> нужны), но это мартовское ядро: есть прецедент, что на старых ядрах
> DPI режет REALITY-ногу entry→exit (см. CHANGELOG, инцидент
> 29.08.2026). Оптимальный даунгрейд — 26.7.28 + `minClientVer="1.8.0"`.

**Ждать апстрим:** когда sing-box добавит X25519MLKEM768 и Nyamebox/
Karing подтянут ядро — совместимость вернётся без серверных жертв.

### Диагностика — как понять, что у вас именно это

| Симптом | Где видно | Что означает |
|---|---|---|
| `reality verification failed` | лог sing-box-клиента | сервер 26.9.8+, ClientHello без MLKEM отвергнут |
| Timeout, TCP до сервера жив | mihomo-клиент | декой: гейт (26.7.x с дефолтом) или MLKEM (26.9.8+ без рецепта B) |
| `REALITY: received real certificate` | лог Xray-клиента | CH отвергнут как «не REALITY» (fp=ios, random/randomized, неверные pbk/sid) |
| `authentication failed or validation criteria not met` | лог сервера 26.9.x | REALITY-аут не прошла (MLKEM/гейт/креды) |
| `is using X25519MLKEM768 ... : true/false` | лог сервера (show: true) | true = CH с MLKEM (26.9.8+ примет), false = без (26.9.8+ отвергнет) |
| `The default minimal client version is Xray-core v26.3.27` | лог сервера 26.7.x при старте | сервер в гейт-эпохе: unset/`""` = дефолт-гейт |
