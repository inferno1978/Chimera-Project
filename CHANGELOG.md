# Changelog new entry — fix(dns): DNS-watchdog двусторонний AGH-aware — redirect 53→dnscrypt ставится ТОЛЬКО при мёртвом AGH и СНЯТ при живом; prod-инцидент «нулевые счётчики AGH при живом трафике» (redirect в nat OUTPUT, поставленный до-AGH версией модуля, уводил локальный DNS Xray мимо AGH прямо в dnscrypt) (13 Nov 2026)

## Контекст: prod-инцидент 13.11 (основная нода, AGH v0.107.79): клиент подключён по VLESS и смотрит YouTube — трафик живой, а счётчики AGH нули, querylog пуст («висит один запрос»); контрольная нода с тем же стеком показывает растущие счётчики и запросы к потоковым серверам YouTube. Цепочка диагностики: stats/querylog напрямую не читаются (bbolt + буфер в памяти) → API /control/querylog → эксперимент транспортами (loopback UDP/TCP не логируются, DoH и публичный сокет — логируются) → единственное объяснение — перехват до AGH → tcpdump port 53/5300 закрыл вопрос: запросы Xray на 127.0.0.1:53 перехватывались правилом iptables nat OUTPUT REDIRECT --to-ports 5300 (udp+tcp, комментарий chimera-dns-fix) — поставленным 24.10 СТАРОЙ (до-AGH) версией resolv_conf_fix (AGH на ноде тогда не стоял; на контрольную ноду правило не ставилось — потому там счётчики росли) и с тех пор живущим в живых iptables + /etc/iptables/rules.v4 + telemt-warp-rules.v4; всё, что резолвилось через системный resolv.conf (127.0.0.1:53 — sniffing-резолв Xray для direct-ветки YouTube), тихо уходило мимо AGH прямо в dnscrypt; DoH :31443 redirect не ловит — потому «один висящий запрос». Вторая половина причины: живой watchdog (шаблон версии 24.10) был ОДНОСТОРОННИМ — AGH он знал только как «рестартнуть, если :53 мёртв», владельца :53 не проверял: проба во время рестарта AGH проваливалась → watchdog молча ставил redirect «навсегда»; apply-скрипт chimera-dns-fix-apply.py и одноимённая служба к тому моменту уже были AGH-aware (снимают redirect при живом AGH) — слепым оставался только таймерный скрипт (60 с).

## Решение: resolv_conf_fix._watchdog_script_content() — двусторонняя AGH-aware синхронизация В НАЧАЛЕ генерируемого скрипта (до пробы, идемпотентно): agh_serves_53() (systemctl is-active AdGuardHome + ss -ulnp видит слушателя adguard на udp :53) → del_redirect_all() (цикл: nat -S OUTPUT | grep chimera-dns-fix → -D, пока правил не останется; сбой удаления не роняет скрипт) + logger «AGH owns :53 — redirect снят». Лестница self-heal прежняя: двойная проба :53 (транзиент — не смерть) → рестарт AGH (владелец :53) → dnscrypt-рестарт + redirect как страховка на случай мёртвого AGH; возврат AGH → следующий проход таймера снимет redirect. Шапка скрипта: TAG/PROBE_DOMAIN и чтение порта dnscrypt из TOML (PORT_TOML) вынесены до функций — нужны и AGH-aware-блоку, и лестнице; докстринг переписан (шаг 0 — AGH-AWARE sync, 0.5 — проба), заголовочный комментарий скрипта дописан двусторонней семантикой. Интерфейс скрипта не менялся (probe → ladder), apply-скрипт/служба/юниты не тронуты; сгенерированный скрипт совпадает с вылеченной прод-нодой (diff по некомментным строкам пуст).

# Changelog new entry — fix(b4): установка b4 качала зашитую v1.78.0 вместо последнего release — install_b4 теперь резолвит свежий стабильный релиз через GitHub API с фолбэком на проверенную константу (11 Nov 2026)

## Контекст: живой лог установки свежей ноды 11.11: «[youtube_b4] [INFO] Скачиваю b4 v1.78.0 для linux-amd64...» → «[OK] b4 установлен и запущен!» → через 27 секунд «[INFO] b4 latest: release=1.90.1, pre-release=1.87.0rc2 (кэш обновлён)» → «[INFO] Обновление: 1.78.0 → 1.90.1» → «[OK] Обновлено: 1.78.0 → 1.90.1». B4_VERSION = "1.78.0" прибита гвоздями в dpi_bypass.py и youtube_b4.py (модули-близнецы: централизованный «DPI Bypass» + зеркало «YouTube через B4», один binary, один общий state), _download_b4_binary() собирает URL releases/download/v{B4_VERSION} — при том что механизм узнавания свежего релиза в модуле УЖЕ есть (_detect_latest_version → GitHub /releases/latest; им пользуются авто-обновление и кэш шапки меню). Итог каждой чистой установки: устаревший 24-МБ binary скачивается, тут же скачивается ещё раз актуальной версией, сервис перезапускается — двойная загрузка, лишний рестарт и окно между «установлен» и «обновлён», где state и меню честно показывают 1.78.0 при живом 1.90.1.

## Решение: (1) новый хелпер _resolve_install_version(timeout=10) в ОБОИХ модулях (зеркально, идентичный исходник): спрашивает GitHub /releases/latest через существующий _detect_latest_version — только стабильные релизы, pre-release установке сознательно не предлагается; 'v'-префикс снимается гардой (URL собирается как v{version}, двойное «vv» исключено); мусорный ответ отбрасывается ключ-гардом _b4_version_key (пустые числовые компоненты → фолбэк); GitHub недоступен → WARN «ставлю проверенную v{B4_VERSION}» и фолбэк — установка не должна падать из-за метаданных. (2) _download_b4_binary(version="") параметризован: пустая версия — прежняя B4_VERSION (прямая совместимость любых вызовов), непустая — фактическая версия в URL и в логе «Скачиваю b4 v{version}...». (3) install_b4(): резолвит версию ДО скачивания, передаёт в _download_b4_binary и пишет в общий state ФАКТИЧЕСКИ установленную версию («version»: version) — не константу; авто-обновлению сразу нечего делать, двойная загрузка и лишний рестарт исчезают. Авто-обновление (release/pre-release), кэш шапки меню, REST-интерфейс и сеты не тронуты; B4_VERSION остаётся фолбэком и парой синхронизации близнецов (тест test_shared_b4_version прежний).

На dev-боксе этих файлов нет — тесты зелёные, регресс не был виден (подтверждено на RU1: те же 2 падения и на коде b7f55f2 ДО фикса cb6ebb9). Побочно: непатченный _tw_log писал WARN/SKIP-строки прогонов тестов в боевой /var/log/xray-exit-traffic-watcher.log на нодах.
