# Changelog new entry — FIX(config-owner): владелец конфига после патчей модулей = канон _core 640 root:xray вместо битого root:root (репорт клиента 04.11: «после добавления outbound и отправки на него RU-подсетей владельцем config файла стал root, xray не смог прочитать конфиг» — чинил вручную chgrp xray; повторилось и при добавлении routing-правила)

## Контекст: клиент на 138x (systemd User=xray/Group=xray, конфиг /etc/xray/config.json, канон установщика root:xray 0640) добавил кастомный outbound + направил на него РФ-подсети, затем добавил routing-правило — оба флоу падали одинаково: xray не стартовал (permission denied), владелец конфига после патча становился root:root. Причина: три модуля-фичи (routing_rules, dns_rules, custom_outbounds) несли устаревшие приватные копии _set_config_owner с жёстким shutil.chown root:root, тогда как канон _core._set_config_owner давно правильный (640 root:xray, числовой GID, fallback 0644). При исходных 0640 root:xray смена группы на root лишала сервис group-read → рестарт xray падал. На части нод баг маскировался world-readable дрейфом (138x root:root 0644, 91x nobody:nogroup 0644 — следы того же бага).

## Решение: во всех трёх модулях приватная копия _set_config_owner заменена на тело канона _core (без импорта _core — модули standalone, circular): os.chown(0, grp.getgrnam("xray").gr_gid) + os.chmod 0640; KeyError группы xray → fallback chmod 0644 (xray читает как other); прочие ошибки — no-op (write_text и так сохраняет владельца, chown — идемпотентное доведение до канона). Побочно apply теперь ИСЦЕЛЯЕТ дрейфовавшие права: 138x root:root 0644 → root:xray 0640 (world-read с конфига снят — там REALITY-приватки).

## Тесты: test_routing_rules 35 OK, test_dns_rules 31 OK, test_custom_outbounds 57 OK, test_tui 26 OK — 149 без изменений. E2E на 138x (прод): (1) прямой тест всех трёх копий функции на probe-файле → root:xray 0640; (2) реплей бага клиента: конфиг принудительно в битое root:root 0640 → _rr_apply_to_xray(restart=True, validate=True) с инертным правилом ownfix-e2e (домен ownfix-e2e-test.invalid → direct) → конфиг исцелён root:xray 0640, xray ACTIVE, правило в конфиге; (3) runuser -u xray xray run -test — конфиг читается и валиден ОТ ИМЕНИ сервиса; (4) cleanup: пустой state → правило удалено, xray ACTIVE, права root:xray 0640 остались. 13/13 OK. (04 Nov 2026)

# Changelog new entry — FIX(tui): стрелки ↑↓ убивали меню выбора — _getch_raw не видел хвоста ESC-последовательности (sys.stdin.read(1) затягивал [B в буфер Python мимо select); раунд-2: всплеск-чтение + парсер CSI/SS3 + _KEY_PENDING (04 Nov 2026)

## Контекст: репорт владельца 04.11 (скриншот): «не срабатывают стрелочки в меню, где есть выбор пунктов. Как только нажимаю на стрелку вниз или вверх, сразу появляется надпись "Нажмите Enter…"» — любые терминалы, обычные и NumPad-стрелки; «в меню DPI Detector из Chimera стрелочки работают» (то меню на input() в cooked-режиме — стрелки там безвредны, потому и «работают»). Диагноз по скриншоту: под меню «Куда направить трафик РФ-подсетей?» видно «Нажмите Enter… ^[[B^[[B^[[B^[[A^[[A^[[A» — литеральные ESC-последовательности стрелок печатаются в терминал мусором. Разбор: tui_select/tui_form/tui_input (меню выбора: routing_rules/dns_rules/_core, формы) читают клавиши через _getch_raw; тот читал первый символ через sys.stdin.read(1) — TextIOWrapper одним сисколом затягивал в буфер Python ВЕСЬ хвост последовательности ([B приходит из SSH одним пакетом), где его не видит select(2) на fd → таймаут 50 мс → «голый» ESC → tui_select трактовал его как Esc-отмену и закрывал меню, остаток [B эхом печатался. Воспроизведено pty-пробой на 138x до патча: _getch_raw([B) → '' (должен быть KEY_DOWN), tui_select(↓+Enter) → None (меню убито первым же байтом).

## Решение — два раунда, оба вскрыты pty-тестами на реальном терминале (как в SSH-сессии). Раунд-1: чтение через os.read(fd, 1) по байту из kernel-буфера — select сразу видел хвост, стрелки заработали; но pty-прогоны показали наследника: восстановление cooked-режима между нажатиями съедало байты, пришедшие ОДНИМ всплеском со стрелкой (↓+Enter одним пакетом: '
' повисал в kernel-очереди на границе raw→cooked→raw, второй _getch_raw блокировался навсегда), плюс SS3-стрелки (OB, application mode) не разбирались вовсе — ранний обрыв хвоста по isalpha ловил модификатор 'O' как финал ('O' вместо KEY_DOWN), дефект, наследованный от исходного кода. Раунд-2 (итоговая схема): _getch_raw читает ВЕСЬ всплеск одним raw-сеансом (блокирующий os.read + дочитывание до 50 мс тишины), первый кейстрок разбирает отдельный парсер _parse_key (CSI: ESC [ params до финала-буквы/~; SS3: ESC O финал — ровно 3 байта; UTF-8: продолжения по lead-байту 0xC0-0xF7 → 2-4 байта, кириллица в формах; / → KEY_BACKSPACE, 	 → KEY_TAB), остаток всплеска хранится в _KEY_PENDING и отдаётся следующим вызовам БЕЗ обращения к терминалу — все байты живут в Python, границы raw/cooked их не трогают. Одинокий Esc — всплеск из одного байта → '' (честная отмена, 50 мс тишины). Маппинг последовательностей и коды клавиш — без изменений; EOF/поведение — паритет со старым кодом.
