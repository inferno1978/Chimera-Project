# Changelog new entry — fix(rkn-guard): диагностика UFW-рековери — подсчёт правил ruleset в WARN/ERR (доп. инцидента 24.11: юзер <blw> насчитал ~63к мусорных «DROP all»-строк в iptables; после чистки установка прошла) (24 Nov 2026)

## Контекст: доп-данные инцидента 24.11 (запись ниже): юзер прислал скрины — живая ufw-before-input без jump (откатное состояние после FTL: обёртка демонтировала блок), сама цепочка SCANNERS-BLOCK корректна (conntrack-RETURN → LOG → DROP match-set), iptables v1.8.10 (nf_tables), и итоговое «откуда-то было 63к мусорных записей, после чистки всё установилось» (скрин успешной переустановки). Ответ владельцу на «и всё же — про лимит»: 63к — это ИНДИВИДУАЛЬНЫЕ iptables-правила (пер-IP DROP от стороннего бан-скрипта), НЕ списки rkn-guard: у rkn-guard 4–6 правил на семейство (jump + conntrack-RETURN + LOG + DROP match-set), вся масса адресов в ipset (hash:net maxelem 65536 на сет на семейство; при превышении бинарник честно отказывается «превышает 65536 подсетей на семейство»; 5 базовых списков ~4.4k CIDR — запас 15x). В iptables лимита на число правил нет вовсе; совпадение 63к ≈ 65536 случайно (iptables-строки, не записи ipset). Усугубляющая механика провала: на backend nf_tables каждая команда iptables обрабатывает ruleset ЦЕЛИКОМ → при 63k правил ufw reload и чтение цепочек медленные → окно гонки reload→verify широкое, писатель мусора успевает встать выше jump в живой ufw-before-input. После чистки операции быстрые — установка прошла.

## Решение: WARN повторного провала _rg_cli_mutate_ufw_safe и [ERR]-подсказка _rg_install_flow дополнены: (1) подсчёт правил `iptables-save | grep -c '^-A'` («всего правил; тысячи/десятки тысяч — мусор от сторонних пер-IP банов» — раздутие ruleset видно сразу); (2) причина расширена «внешняя система перегенерирует правила ИЛИ ruleset раздут»; (3) докстринг-механика шапки дополнена усугубляющим фактором (nf_tables → ruleset целиком → широкое окно гонки; после чистки мусора вставало) — для будущей диагностики кейсов этого класса. Логика авторековери не менялась: ремонт позиции jump + один повтор покрывают и этот сценарий (мусор ниже jump ремонту не мешает).

# Changelog new entry — fix(rkn-guard): UFW-jump авторековери — переустановка на ноде с внешним антидосом падала FTL «Не удалось сохранить правила iptables error="ufw-before-input: SCANNERS-BLOCK is not the first rule"» (инцидент 24.11: скрин юзера <blw>, «длинный список из drop all в iptables»; доп-скрин — живая цепочка SCANNERS-BLOCK при этом корректна) (24 Nov 2026)

## Контекст: вопрос сообщества (дословно, скрин каскад-меню): «почему-то не работает разделение трафика, как будто 7-й пункт всегда включен» + «не работает, проверял через ifconfig.me, 2ip. ozon палит что впн включен. при ручном указании приложений все отлично». Диагноз по скринам: пункт 7 выключен (split-tunnel), а весь клиентский трафик уходит через exit (RU-сайты видят exit-IP); диф iptables юзера корректен (FORWARD-ACCEPT по ipset появляется/исчезает вместе с пунктом 7) — румблер режима работает, сломано НЕВИДИМОЕ в `iptables -L`: mangle-таблица и наполнение ipset. Первопричина: mark-правило каскада `-m set ! --match-set awg_ru_networks dst` по ПУСТОМУ множеству матчит ВСЁ: set существует, но без записей → весь клиентский v4 маркируется → table 2000 → awg1 → exit — поведенчески неотличимо от включённого exit-all при выключенном пункте 7. Прежний комментарий сетапа описывал только противоположный сценарий («пустой ipset = весь клиентский трафик уйдёт НАПРЯМУЮ» — верно лишь для ОТСУТСТВУЮЩЕГО set'а, когда '-m set'-правило не добавляется вообще) и вводил в заблуждение. Три пути к поломке: (1) установка при недоступных зеркалах ru.zone — download_ru_zone при провале писал ПУСТОЙ файл, установка продолжалась с варнингом; (2) МИНА cron: еженедельное обновление при провале зеркал ЗАТИРАЛО рабочий ru.zone пустым файлом — сплит молча умирал после ближайшего ребута (boot-скрипт пересоздавал set пустым); (3) set ОТСУТСТВУЕТ → mark-правило не добавляется → весь клиентский трафик напрямую с entry (каскад молча не каскадирует, E2E-кейс из докстрингов).

## Решение: гард по всем трём сценариям + самолечение. (1) awgs_cascade_download_ru_zone: провал зеркал больше НЕ трогает прежний НЕпустой ru.zone (честный варнинг «сохранён прежний, N сетей»; пустой файл — только при его полном отсутствии, контракт load_ipset сохранён). (2) Новые хелперы: awgs_cascade_ipset_entries (парсер Number of entries, 0 при отсутствии), _awgs_cascade_ensure_ipset (create -exist — set обязан СУЩЕСТВОВАТЬ до '-m set'-правил, лечит сценарий «missing set»), _awgs_cascade_restore_ipset_from (общий pipe-restore из файла CIDR-списка), awgs_cascade_install_fallback_snapshot (assets/awg/ru.zone.fallback → /etc/awg-cascade/ru.zone.fallback при каждой перегенерации routing-скрипта), awgs_cascade_ipset_seed_if_empty — лестница самолечения: перечитать ru.zone → fallback-снимок → create-пустым + ERROR в лог с дословным симптомом («ведёт себя как включённый пункт 7, хотя он выключен; лечение: пункт 3»). Ключевое свойство самолечения: split-форма mark-правила НЕ меняется — при наполнении set'а (cron/пункт 3) та же форма правила оживает без переустановки правил. (3) Новый ассет assets/awg/ru.zone.fallback — реальный снимок ru.zone primary-зеркала (11 482 сети, снят в день фикса; '#'-шапка с провенансом игнорируется обоими загрузчиками): RU-entry без доступа к зеркалам получает рабочий RU-список вместо пустоты (устаревший список лучше пустого: RU-сети меняются медленно, свежесть возвращает cron/пункт 3 при первом же успехе). (4) awgs_cascade_load_ipset: при пустом/отсутствующем ru.zone set СОЗДАЁТСЯ (хотя бы пустым) — правила обязаны ставиться. (5) _awgs_cascade_apply_iptables: ensure-set ДО применения правил (обе ветки) + в split-режиме гард после (entries==0 → seed + ERROR). (6) Boot-скрипт (обе формы — обычная и LB): раздел 1.5 — подсчёт entries, seed из fallback-копии, при неудаче echo-варнинг в stderr юнита + logger daemon.warning (молчать нельзя: со стороны неотличимо от exit-all); гард стоит ДО раздела 2.1 (mark-правило). LB-хук диспетчера тоже матчит по awg_ru_networks — гард покрывает и его. (7) awgs_cascade_update_ru_zone (cron/пункт 3): после загрузки контроль entries, seed при нуле, INFO с числом сетей. (8) awgs_cascade_setup_awg0: seed после загрузки ru.zone, честный многострочный варнинг при пустоте (дословный симптом «Ozon/2ip поднимут флаг впн») + исправлен вводящий в заблуждение комментарий (теперь оба зеркальных сценария). (9) Статус-экран (пункт 4): entries<100 — жёлтая строка «подозрительно мало сетей»; 0 в split-режиме — КРАСНЫЙ блок «RU-сплит ФАКТИЧЕСКИ НЕ РАБОТАЕТ: весь клиентский трафик через exit — выглядит, как будто пункт 7 включён, хотя он выключен. Лечение: пункт 3» (в exit-all пустой set — законное состояние, без блока) + новая диагностика формы mark-правила: `iptables -t mangle -S PREROUTING`, blanket-марка без RU-исключения в split-режиме (конкурирующий хвост от прежнего режима/версии) → красная строка с лечением systemctl restart awg-cascade-routing (проверка только вне LB-режима — там свой диспетчер).

# Changelog new entry — feat(nginx): волна nginx.org — HTTP/2-синтаксис без deprecation-варнингов (генераторы + мигратор 5e) + модуль-обновлялка nginx_updater (меню 5f + хук конца установки; CVE-2026-123633/123007) (19 Nov 2026)

## Контекст: двумя частями. (1) Косметика владельца после nginx-марафона (перевод 7 нод живого флота на nginx.org 1.30.7 ради CVE-2026-123633/123007, HTTP/2 RCE): «варнинги listen … http2 is deprecated в генерируемых конфигах сайтов — лечится в panel_nginx_front.py (перевод на отдельную директиву http2 on;), руками не трогал» + «давай потрогаем на всём флоте». Живые vhost'ы генерировались во времена дистрибутивных nginx (1.18/1.24), где inline-параметр listen был единственным вариантом; на 1.30.7 каждый nginx -t/reload сыплет «the "listen ... http2" option is deprecated». Порог директивы — 1.25.1, НЕ 1.25 (на 1.25.0 «http2 on;» = unknown directive → nginx -t падает): три гейта версии в nginx_setup.setup_nginx_final проверяли major.minor без patch и пропустили бы 1.25.0. (2) Вопрос владельца: «как сделать так, чтобы при установке Химеры дефолтный nginx, который с багами, обновлялся до самой последней доступной версии? Даже при переустановке с нуля версия останется дефолтной. Может, в меню ещё какую-то обновлялку сделать для nginx отдельным пунктом? Естественно, учтя все мины» — setup_nginx_temp ставит nginx из репо дистрибутива (Ubuntu 24.04 = 1.24.0, обе CVE открыты), свежая нода с чистой установкой остаётся на уязвимой сборке.

## Решение: (1а) Генераторы: panel_nginx_front._nginx_supports_http2_on() (nginx -v → кортеж, порог (1,25,1); любая ошибка → False — старый inline-синтаксис валиден на ВСЕХ версиях, консервативный дефолт не ломает ни одну ноду) + параметр http2_on у _generate_vhost (≥ 1.25.1: «listen … ssl;» + отдельная «http2 on;» после последней listen-строки блока, в т.ч. dual-stack [::]; старее — прежний inline), caller panel_nginx_front_install детектит один раз; nginx_front_portal — то же (делегирует установку общему генератору, локальный _generate_vhost API-совместим, дефолт False = обратная совместимость ассертов test_port_registry). Реальный кейс той же сессии: у домашнего клиента есть IPv6-префикс /64; в INPUT (v4 и v6) ДО ufw стоят ручные цепочки защиты — port-knocking на :443, manual-ban (автобан сканера), блокировка входящих из РФ; whitelist ingress-блокировки (ingress_geoip, blanket-ACCEPT первым в INPUT, сразу обе семьи адресов) — единственное место, где домашний префикс пробивается сквозь ВСЕ слои разом; без него симптом «по v6 с дома не подключается, по v4 всё работает» выглядит загадочно (UFW-правила для TLS/DoT-портов формально открыты, но пакеты не доходят до ufw). Нюанс, отражённый в напоминании: смена домашнего /64 провайдером (перезагрузка роутера) требует обновить запись в whitelist.

## Решение: (1) _core.py do_full_install() — после генерации клиентских ссылок, гард IS_IPV6_AVAILABLE (напоминание печатается только когда у сервера есть v6): четыре INFO понятным языком — «Дома есть IPv6? Тогда добавьте ваш домашний IPv6-диапазон в белый список сервера — иначе защита (блокировка входящих из РФ, port-knocking) может отклонять подключения по IPv6, хотя по IPv4 всё будет работать»; путь по меню: 5 «Безопасность и Автоматизация» → G «Блокировка входящих из РФ» → 4 «Управление whitelist» → «+» (проверено по фактическому UI: пункты _box_item в _core/ingress_geoip); формат — префикс целиком: «первые 4 группы вашего IPv6 + ::/64», пример 2001:db8:1234:5678::/64 («под правило попадут все устройства домашней сети, а не один компьютер»); где узнать свой IPv6 — 2ip.ru или ifconfig.me, открытые с домашнего компьютера. (2) aghome_setup.finalize_aghome_config() — после финальных INFO-ссылок, гард _get_public_ipv6() (домен DoH/DoT/DoQ резолвится и в AAAA — клиенты с домашним v6 пойдут к AGH по v6): то же напоминание двумя строками «AGH: …» с путём меню и форматом префикса; обёрнуто try/except — печать напоминания не может сломать финализацию.
