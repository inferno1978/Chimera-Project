# Telemt (MTProto Proxy) — FAQ по установке и диагностике

Это подробный гайд по установке Telemt в проекте Chimera. Описаны все
режимы, нюансы xray-интеграции, типовые проблемы и их решения.

> **Telemt** — Telegram MTProto Proxy на Rust/Tokio. Позволяет
> пользователям Telegram подключаться через ваш сервер, обходя
> блокировки. Не путать с VLESS/Reality — Telemt работает только для
> Telegram, отдельный протокол.

## 1. Быстрый старт

Перед установкой ответьте себе на один вопрос:

> **Блокирует ли мой хостер / провайдер Telegram?**

- **Нет** (большинство зарубежных хостеров) → Middle Proxy, ME-pool
  поднимется сам, xray-каскад опционален как fallback.
- **Да** (РФ, РКН режет ME-серверы `91.108.x.x` / `149.154.x.x`) →
  Direct Mode, xray-каскад обязателен.

Если не знаете — попробуйте `curl -v --connect-timeout 5
https://91.108.4.100:8888`. Если `Connection refused` или `timeout` —
ME заблокирован. Если `connection reset` после TLS-handshake — ME
доступен.

## 2. Режимы работы

Telemt может работать в двух режимах подключения к Telegram:

### Middle Proxy (`use_middle_proxy = true`)

```
Клиент Telegram → ваш сервер (Telemt) → ME-серверы Telegram → DC Telegram
                    185.x.x.x:5000      91.108.x.x:8888      149.154.x.x:443
```

- Telemt подключается к **ME-серверам** Telegram (Middle Endpoint,
  порт 8888/80/443/8443).
- ME-серверы — это «официальные» прокси-пулы Telegram, они сами
  маршрутизируют трафик к DC (Data Centers).
- `me runtime ready: ON` — ME-pool поднят, всё работает.
- **Требует**: хостер НЕ блокирует ME-серверы.

### Direct Mode (`use_middle_proxy = false`)

```
Клиент Telegram → ваш сервер (Telemt) → DC Telegram напрямую
                    185.x.x.x:5000      149.154.x.x:443
```

- Telemt подключается **напрямую** к DC Telegram (порт 443/8443).
- `me runtime ready: OFF` — ME-pool не поднимается (это нормально в РФ).
- `route mode: direct` в веб-панели.
- **Требует**: либо хостер не блокирует DC, либо xray-каскад (трафик
  Telemt → xray → exit-нода → DC).

### Гибридный fallback (рекомендуется если хостер не блокирует ME)

```
Клиент → Telemt → ME-серверы (primary)
                   ↓ (если ME упал)
                  DC напрямую (fallback через xray cascade)
```

- `use_middle_proxy = true` + xray-tproxy включён.
- Если ME-pool падает — Telemt автоматически переключается в Direct Mode,
  и трафик к DC идёт через xray cascade → exit-ноду.
- `me runtime ready: ON` в норме, `OFF` + `reroute active: ON` при
  fallback.

## 3. Xray-интеграция и кнопка [R]

### Что такое xray-tproxy-интеграция

```
Telemt → iptables REDIRECT → dokodemo :10811 (xray) → cascade → exit VPS → Telegram
```

Telemt запускается под root и сам инициирует соединения к Telegram.
Без xray-интеграции эти соединения идут **напрямую** с entry-ноды. Если
хостер блокирует TG-DC — Telemt не может подключиться.

Xray-интеграция перехватывает трафик Telemt к TG-подсетям через
`iptables -t nat -A OUTPUT -d <TG-подсеть> -j REDIRECT --to-port 10811`
и отправляет в `dokodemo-door` inbound xray, который уже проксирует через
cascade (VLESS или AWG) на exit-ноду.

**Доступна только в Режиме B** (cascade с exit-нодой). В Режиме A
(прямой интернет) xray-tproxy включать нельзя — нет exit-ноды для
каскада.

### Кнопка [R] — "Маршрут DC/ME трафика"

В меню xray-интеграции (Telemt → XRAY ИНТЕГРАЦИЯ → `[R]`).

**Что делает:**
1. Добавляет `After=xray.service` в `telemt.service` — Telemt стартует
   **после** xray (когда iptables-правила уже применены).
2. Добавляет `RETURN`-правило для UID xray — чтобы xray не попал в
   собственную REDIRECT-петлю.

**Зачем нужно:**
- Без `[R]` Telemt может стартовать раньше xray, установить прямые
  соединения к TG-DC (минуя REDIRECT), и эти ESTABLISHED-соединения
  не будут перехвачены даже после применения правил.
- С `[R]` Telemt стартует после xray → все новые соединения попадают
  под REDIRECT → идут через cascade.

**Правило:** `[R]` включать **всегда**, если `[1]` (xray-интеграция)
включена. Без `[1]` кнопка `[R]` бесполезна.

### ME-исключения из REDIRECT

Telemt сам делает RPC handshake к ME-серверам на портах `:8888`, `:80`,
`:443`, `:8443`. Эти порты **НЕ должны** перехватываться REDIRECT, иначе
ME-handshake проваливается (xray отдаёт plain TCP вместо MTProto-протокола).

Chimera автоматически добавляет `RETURN`-правила для этих портов в обеих
таблицах (`iptables` для IPv4 + `ip6tables` для IPv6) при включении
xray-интеграции:

```
iptables  -t nat -I OUTPUT -p tcp --dport 8888 -j RETURN
iptables  -t nat -I OUTPUT -p tcp --dport 80  -j RETURN
iptables  -t nat -I OUTPUT -p tcp --dport 443 -j RETURN
iptables  -t nat -I OUTPUT -p tcp --dport 8443 -j RETURN
# то же для ip6tables
```

Эти правила стоят **выше** REDIRECT-правил для TG-подсетей, поэтому
ME-трафик идёт напрямую, а TG-DC трафик (`:443` к DC, а не к ME) — через
xray.

> **Важно:** порт `:443` используется и ME, и TG-DC. Исключение `:443`
> из REDIRECT означает, что TG-DC трафик тоже идёт напрямую (НЕ через
> xray). Это нормально, когда ME работает (telemt не обращается к TG-DC
> напрямую, ME-серверы делают это внутри себя). Если ME упадёт и
> включится Direct Mode fallback — TG-DC трафик пойдёт напрямую, что
> может не работать если хостер блокирует TG-DC.

## 4. Пошаговая установка

### Шаг 1. Главное меню Chimera → Telemt (MTProto Proxy)

Выберите пункт установки Telemt. Укажите порт (по умолчанию 5000).

### Шаг 2. Вопрос о регионе

```
Telegram заблокирован на этом сервере? [Y/n]
```

| Ответ | Что произойдёт | Когда выбирать |
|---|---|---|
| **N** (Нет) | `use_middle_proxy = true`, ME-pool поднимется сам | Хостер НЕ блокирует ME |
| **Y** (Да) | `use_middle_proxy = false`, Direct Mode | РФ / РКН блокирует ME |

### Шаг 3. Xray-интеграция (после установки)

Меню Telemt → **XRAY ИНТЕГРАЦИЯ**:

1. `[1]` Включить интеграцию — добавляет `dokodemo-door` в xray +
   iptables REDIRECT для TG-подсетей + ME-исключения.
2. `[R]` ВКЛЮЧИТЬ "Маршрут DC/ME трафика" — `After=xray.service` +
   RETURN для UID xray.

**Правило:** если `[1]` включён → `[R]` тоже включаем. Всегда.

### Шаг 4. Дождаться инициализации ME (если выбрали N)

После установки подождите 60 секунд. Telemt поднимает ME-pool не сразу —
нужно время на RPC handshake к 12+ ME-серверам.

### Шаг 5. Проверить статус

```bash
systemctl reload telemt
sleep 60
journalctl -u telemt -n 30 | grep -i "middle\|ME\|runtime"
```

Должны увидеть `RPC handshake OK addr=...:8888` — значит ME работает.

## 5. Проверка после установки

### TUI Chimera (меню Telemt → Статистика)

Показывает трафик через iptables-цепочки `TELEMT_STATS_IN/OUT`. Это
надёжный источник, не зависит от telemt API.

### Веб-панель Telemt Panel (если установлена)

Показывает трафик через telemt API (`127.0.0.1:9091`). Берёт данные из
внутренних счётчиков telemt.

### Таблица состояний

| `me runtime ready` | `reroute active` | `route mode` | Ситуация |
|---|---|---|---|
| ON (зелёный) | OFF | middle | ✅ **ИДЕАЛ**: ME работает, fallback не нужен |
| OFF | ON | direct | ✅ **РФ**: Direct Mode через xray cascade |
| OFF | OFF | middle | ⚠️ ME не работает, fallback не сработал — проверьте логи |
| ON | ON | direct | ⚠️ ME упал, перешли в Direct Mode — проверьте ME-серверы |

### Проверка iptables-правил

```bash
# Должно быть 4 RETURN-правила (80, 443, 8443, 8888) в каждой таблице
iptables  -t nat -L OUTPUT -n | grep -E 'dpt:(80|443|8443|8888)'
ip6tables -t nat -L OUTPUT -n | grep -E 'dpt:(80|443|8443|8888)'

# Должны быть REDIRECT-правила для TG-подсетей
iptables  -t nat -L OUTPUT -n | grep REDIRECT
ip6tables -t nat -L OUTPUT -n | grep REDIRECT
```

## 6. Пользователи и ссылки

### Добавление пользователей

Меню Telemt → **Управление пользователями** → Добавить.

Каждый пользователь получает:
- **username** — имя (латиница, цифры, `_`, `-`).
- **secret** — 32-значный hex-секрет (генерируется автоматически).

### Ссылка для клиента

После добавления пользователя TUI выдаёт ссылку вида:

```
tg://proxy?server=185.x.x.x&port=5000&secret=dd1234567890abcdef...
```

Эту ссылку даёте пользователю. Он открывает её в Telegram — и
подключается к вашему прокси.

### Несколько пользователей

- Все пользователи подключаются к одному порту (например 5000).
- Секрет у каждого свой — telemt различает пользователей по секрету.
- Можно создать сколько угодно пользователей.

## 7. iOS Fix (второй порт)

### Зачем нужен

У iOS-клиентов Telegram другой TLS ClientHello, и DPI (ТСПУ) может
блокировать именно iOS по JA4-фингерпринту. `client_mss` фрагментирует
TLS ClientHello для **всех** клиентов — но если фрагментация нужна
только iOS, лучше использовать отдельный порт.

### Как работает

```
iOS-клиент → порт 5001 → iptables TCPMSS-clamp → REDIRECT → порт 5000 (Telemt)
Android    → порт 5000 → напрямую (без TCPMSS)
```

- Создаётся второй внешний порт (например 5001).
- iptables TCPMSS-clamp на SYN-пакетах для порта 5001.
- iptables REDIRECT с 5001 на 5000.
- iOS-клиентам даёте ссылку с `port=5001`.
- Android/Desktop — ссылку с `port=5000`.

### Включение

Меню Telemt → **iOS Fix** → Включить. Укажите внешний порт (по умолчанию
основной +1) и MSS (по умолчанию 92).

> **Важно:** iOS Fix и `client_mss` в конфликте. Если включаете iOS Fix —
> `client_mss` будет удалён из конфига (с согласия пользователя).

## 8. Статистика трафика

### TUI Chimera (меню Telemt → Статистика)

Считает трафик через **iptables-цепочки** `TELEMT_STATS_IN/OUT`:
- `TELEMT_STATS_IN` — входящий трафик на порту Telemt (rx).
- `TELEMT_STATS_OUT` — исходящий трафик (tx).
- Cron сбрасывает счётчики в 00:00, суточные данные накапливаются в
  `/var/lib/telemt/stats.json`.
- Per-user распределение — пропорционально числу сессий (из journalctl).

**Плюсы:** не зависит от telemt API, работает даже если API не считает
трафик.
**Минусы:** per-user трафик приблизительный (пропорционально сессиям, а
не по факту).

### Пункты меню статистики

| Пункт | Что делает |
|---|---|
| `[1]` Обновить | Пересчитать статистику сейчас |
| `[2]` Real-time | Обновление каждые 5 секунд |
| `[3]` Включить iptables | Переинициализировать цепочки учёта |
| `[4]` Сбросить | Очистить всю накопленную статистику |
| `[5]` Диагностика API | Проверить почему веб-панель может показывать 0 |

## 9. Веб-панель Telemt Panel

### Что это

`telemt_panel` — отдельный Go-бинарник с React-фронтендом
([github.com/amirotin/telemt_panel](https://github.com/amirotin/telemt_panel)).
Общается с telemt через HTTP API (`127.0.0.1:9091`, секция `[server.api]`
в `telemt.toml`).

### Установка

Меню Telemt → **Telemt Panel** → Установить. Chimera:
1. Создаёт системного пользователя `telemt-panel`.
2. Включает `[server.api]` в `telemt.toml` (через `mtproto.ensure_api_enabled()`).
3. Скачивает бинарник панели.
4. Генерирует конфиг панели (`/etc/telemt-panel/config.toml`).
5. Устанавливает systemd-юнит.

### Важно про источники трафика

| Источник | TUI Chimera | Telemt Panel |
|---|---|---|
| Где берёт трафик | iptables-цепочки `TELEMT_STATS_IN/OUT` | HTTP API telemt (`127.0.0.1:9091`) |
| Зависит от telemt API | ❌ Нет | ✅ Да |
| Надёжность | Всегда работает (если iptables настроен) | Зависит от internal telemt counters |

**Если TUI показывает трафик, а Panel — 0:**
1. Telemt был недавно перезапущен (uptime < 10 мин) — внутренние счётчики
   обнулились. iptables-счётчики НЕ обнуляются. Подождите 5-10 минут.
2. `build profile: unknown` в System Info панели — бинарник telemt может
   быть собран без stats-feature.
3. Баг upstream telemt — API не считает трафик в этой версии.

### Диагностика

Меню Telemt → Статистика → `[5]` Диагностика Telemt API — проверяет:
- Секцию `[server.api]` в `telemt.toml`.
- HTTP-доступность API на `127.0.0.1:9091`.
- Uptime telemt (если < 10 мин — рекомендация подождать).
- Даёт рекомендации по результатам.

## 10. Диагностика: me runtime ready OFF

### Сценарий 1: РФ, ME заблокирован (нормально)

Если вы выбрали "Y" (Да, заблокирован) — `me runtime ready: OFF` это
**нормально**. Telemt работает в Direct Mode, `route mode: direct`.
Ничего чинить не нужно.

### Сценарий 2: ME НЕ заблокирован, но OFF (проблема)

Если вы выбрали "N" (Нет, не заблокирован), но `me runtime ready: OFF` —
что-то мешает ME-pool подняться.

**Проверка 1: xray-tproxy перехватывает ME-трафик**

```bash
# Проверить RETURN-исключения для ME-портов
iptables  -t nat -L OUTPUT -n | grep -E 'dpt:(80|443|8443|8888)'
ip6tables -t nat -L OUTPUT -n | grep -E 'dpt:(80|443|8443|8888)'
```

Должно быть 4 RETURN-правила (80, 443, 8443, 8888) в каждой таблице,
стоящие **выше** REDIRECT-правил. Если их нет — переустановите
xray-интеграцию:

```bash
python3 -c "
import sys
sys.path.insert(0, '/opt/chimera')
from chimera.modules.mtproto import xray_disable_tproxy_for_telemt, xray_enable_tproxy_for_telemt
print(xray_disable_tproxy_for_telemt())
print(xray_enable_tproxy_for_telemt())
"
systemctl reload telemt
```

**Проверка 2: логи telemt**

```bash
journalctl -u telemt -n 50 | grep -i "middle\|ME\|runtime"
```

- `RPC handshake OK addr=...:8888` — ME-handshake проходит, пул должен
  подняться.
- `All ME servers for DC failed` — все ME-серверы для этого DC
  недоступны. Возможно, хостер всё-таки блокирует часть ME.
- `ME pool is not ready yet; retrying` — telemt продолжает попытки,
  подождите ещё 1-2 минуты.

**Проверка 3: доступность ME-серверов**

```bash
# Тест TCP-соединения к ME-серверу (если connection refused/timeout — заблокирован)
curl -v --connect-timeout 5 https://91.108.4.100:8888 2>&1 | head -5
```

**Проверка 4: дубли iptables-правил**

Если RETURN-правил несколько (дубли) — это не проблема (iptables берёт
первое). Но если вы случайно удалили все — ME-pool упадёт. Переустановите
через скрипт выше (он гарантирует ровно одно правило на порт).

## 11. Диагностика: трафик не считается

### В TUI Chimera (меню Telemt → Статистика)

**"Accounting: нет (journalctl)"** — iptables-цепочки не созданы.

Решение: `[3]` Включить / переинициализировать учёт iptables. Если
показывает "iptables-учёт НЕ активирован" — проверьте лог:

```bash
grep "mtproto_stats.setup_iptables_accounting" /var/log/chimera.log
```

Возможные причины:
- Контейнер без `CAP_NET_ADMIN` — iptables не может создавать цепочки.
- Ядро без netfilter-модуля.
- Конфликт iptables-nft vs iptables-legacy.

### В веб-панели Telemt Panel

**Total Traffic: 0 B** — telemt API возвращает 0.

1. Меню Telemt → Статистика → `[5]` Диагностика Telemt API.
2. Если "API отвечает: ✗" — проверьте `systemctl status telemt`,
   `ss -tlnp | grep 9091`.
3. Если uptime < 10 минут — подождите, счётчики обнулились при рестарте.
4. Если `build profile: unknown` — попробуйте другую версию telemt.

> **TUI Chimera** (через iptables) — надёжный источник. Если TUI видит
> трафик, а Panel — нет, проблема в upstream telemt, не в Chimera.

```
│ НЕ заблокирован  │ [N] (без xray)   │ ME: ON, без fallback        │
│ ЗАБЛОКИРОВАН     │ [Y] + [1] + [R]  │ ME: OFF, Direct через xray  │
│ ЗАБЛОКИРОВАН     │ [Y] (без xray)   │ Telegram НЕ РАБОТАЕТ        │
└──────────────────┴──────────────────┴─────────────────────────────┘

[N] / [Y] — ответ на вопрос "Telegram заблокирован?" при установке
[1]       — пункт [1] в меню xray-интеграции (Включить)
[R]       — пункт [R] в меню xray-интеграции (Маршрут DC/ME трафика)

ПРАВИЛО: [R] включать ТОЛЬКО если [1] включён.
         Без xray-интеграции [R] бесполезен.
```

## 13. Частые вопросы

### Q: Я нажал [3] в меню статистики несколько раз. Теперь дубли правил?

**A:** Нет. Начиная с версии после коммита `1e54bc6`, Chimera использует
`_ipt_ensure_single_return_rule()` — цикл удаления всех дублей перед
добавлением одного правила. Гарантируется ровно одно RETURN-правило на
порт на таблицу. Но если вы чистили правила вручную — лучше
переустановить через скрипт (см. раздел 10, Проверка 1).

### Q: "Redirect 6" в выводе iptables — что это за цифра?

**A:** `6` — это номер протокола TCP (`IPPROTO_TCP = 6`). Флаг `-n`
(numeric) в iptables делает протокол числом вместо текста `tcp`. Это
нормальный вывод, не баг.

### Q: `me runtime ready` загорелся OFF после перезагрузки сервера

**A:** Проверьте, что xray-tproxy-правила применились после ребута.
Chimera сохраняет их через `netfilter-persistent save` или
`iptables-save > /etc/iptables/rules.v4`. Если после ребута правил нет —
выполните `[1]` Переприменить в меню xray-интеграции.

### Q: Можно ли использовать Telemt без xray-интеграции?

**A:** Да, если хостер не блокирует ни ME, ни TG-DC. В этом случае:
- Выберите "N" (Нет, не заблокирован) при установке.
- Не включайте xray-интеграцию.
- Telemt будет работать через Middle Proxy напрямую.
- `me runtime ready: ON`, `reroute active: OFF`.

Минус: нет fallback на Direct Mode через xray. Если ME упадёт — Telemt
переключится в Direct Mode, но без xray-каскада трафик к TG-DC пойдёт
напрямую (может не работать если хостер блокирует DC).

### Q: iOS Fix ломает статистику трафика в веб-панели?

**A:** Нет, iOS Fix работает через iptables NAT REDIRECT (внешний порт →
основной порт). Telemt видит соединение на основном порту — статистика
считается корректно и в TUI, и в веб-панели (если API telemt работает).

### Q: Как обновить список TG-подсетей?

**A:** Меню Telemt → XRAY ИНТЕГРАЦИЯ → `[N]` Обновить подсети Telegram +
переприменить iptables. Chimera скачает актуальный список с GitHub и
переустановит REDIRECT-правила.

### Q: Telemt пишет "Middle Proxy warmup timeout exceeded" в логах

**A:** Это значит ME-pool не успел инициализироваться за `warmup_timeout`
(по умолчанию 45 секунд). Если после этого `me runtime ready: OFF` —
проверьте:
1. Доступность ME-серверов (см. раздел 10, Проверка 3).
2. RETURN-исключения для ME-портов (см. раздел 10, Проверка 1).
3. Логи на `All ME servers for DC failed` — если все ME заблокированы,
   переключитесь в Direct Mode (ответ "Y" при установке).

### Q: Можно ли сменить порт Telemt после установки?

**A:** Да, через переустановку (меню Telemt → Удалить → Установить заново
с новым портом). При этом:
- Секреты пользователей сохранятся (в `telemt.toml`).
- Ссылки клиентам придётся перевыдать с новым портом.
- iptables-цепочки `TELEMT_STATS_IN/OUT` и REDIRECT-правила
  переустановятся автоматически.

### Q: Как полностью удалить Telemt?

**A:** Меню Telemt → Удалить. Chimera:
1. Останавливает и удаляет systemd-юнит `telemt.service`.
2. Удаляет бинарник `/usr/local/bin/telemt`.
3. Удаляет конфиг `/etc/telemt/telemt.toml`.
4. Удаляет iptables-цепочки и REDIRECT-правила.
5. Отключает `[server.api]` (если была включена).

Веб-панель Telemt Panel удаляется отдельно (меню Telemt → Telemt Panel →
Удалить).

## 14. client_mss — фрагментация TLS ClientHello против DPI (JA4)

### Что это и зачем

С 1 апреля 2026 г. ТСПУ (часть АСБИ) развернул правила **JA4-фингерпринтинга**
— распознавание MTProxy Fake-TLS по уникальному паттерну TLS ClientHello.
DPI (Deep Packet Inspection) на стороне провайдера анализирует первый пакет
TLS-handshake и сравнивает его с известными сигнатурами MTProxy. Если
совпадает — соединение блокируется.

**Механизм обхода:** объявление малого TCP MSS (Maximum Segment Size) в
SYN/ACK. Клиент вынужден фрагментировать ClientHello по нескольким TCP-сегментам.
Ключевые поля для JA4 (ALPN, signature_algorithms) попадают во 2-й / 3-й сегмент
— одно-пакетный экстрактор ТСПУ видит неверный хэш и пропускает соединение.

```
Без client_mss:                     С client_mss = 92:
┌─────────────────────┐             ┌──────┬──────┬──────┬───┬───┐
│ ClientHello (1 пак.)│             │ Seg1 │ Seg2 │ Seg3 │...│Sn │
│ ALPN + sig_algs     │             │      │ ALPN │ sig_ │   │   │
│ JA4 = E5b0_...      │             │      │      │ algs │   │   │
│ → ТСПУ блокирует    │             │ JA4  │ JA4  │ JA4  │   │   │
└─────────────────────┘             │ =??? │ =??? │ =??? │   │   │
                                    └──────┴──────┴──────┴───┴───┘
                                    ТСПУ видит только Seg1 → пропускает
```

### Как работает

`client_mss` — параметр в секции `[server]` файла `telemt.toml`:

```toml
[server]
port = 5000
client_mss = "tspu"    # или "92", "256", "512", и т.д.
```

Telemt ≥ 3.4.15 читает этот параметр и объявляет указанный MSS в SYN/ACK для
**ВСЕХ** входящих соединений. На более ранних версиях поле игнорируется без
ошибки.

### Пресеты

| Клавиша | Value | MSS | Название | Описание |
|---|---|---|---|---|
| `1` ★ | `tspu` | 92 | TSPU Stealth | Нативный пресет против ТСПУ JA4. Дробит ClientHello на 5–7 сегментов. **Рекомендуется по умолчанию.** |
| `2` | `2in8` | 256 | 2-in-8 Split | Умеренная фрагментация. ClientHello в 3–4 сегмента. Меньше overhead. |
| `3` | `512` | 512 | Half-MSS | Лёгкая фрагментация. Снижает нагрузку на CPU, слабее обходит JA4. |
| `4` | `extreme-low` | 88 | Extreme Low | Максимальная фрагментация. Если `tspu` не помогает. |
| `5` | `1024` | 1024 | Soft Split | Минимальная фрагментация. Для линий с высокой потерей пакетов. |
| `6` | `768` | 768 | Balanced | Баланс между фрагментацией и overhead. |
| `7` | `336` | 336 | 3-in-3 Split | ClientHello в ~3 сегмента. Компромисс для мобильных. |
| `8` | `176` | 176 | Deep Fragment | Глубокая фрагментация. Эффективен против реассемблирующего DPI. |
| `9` | `128` | 128 | Micro Segment | Очень мелкая нарезка. Высокий overhead, высокая антидетект-надёжность. |
| `0` | (пусто) | ~1460 | Без изменений | MSS выбирает ядро. `client_mss` не пишется в конфиг. |

> **Рекомендация:** начните с `tspu` (MSS 92). Если ТСПУ всё равно блокирует —
> попробуйте `extreme-low` (88). Если фрагментация ломает подключение на плохих
> мобильных сетях — `2in8` (256) или `336`.

### Когда НЕ нужно включать client_mss

- **Сервер НЕ в РФ** — ТСПУ не действует, JA4-дактилоскопия не применяется.
  `client_mss` добавит лишний overhead без пользы.
- **Используете iOS Fix** — iOS Fix делает свою фрагментацию через iptables
  TCPMSS на отдельном порту. `client_mss` в конфиге конфликтует с ним
  (два разных MSS на один сокет). См. раздел 15.

### Как включить/сменить

**При установке:** мастер установки спросит про MSS-пресет (через
`telemt_mss_selector.mss_select_interactive()`). Выберите пресет — он
запишется в `telemt.toml`.

**После установки:** `telemt_mss_selector.py` не имеет отдельного меню —
`client_mss` меняется через:
1. Ручную правку `telemt.toml` → `systemctl reload telemt`.
2. Переустановку Telemt (меню Telemt → Удалить → Установить заново).
3. iOS Fix (если нужен только для iOS — см. раздел 15).

## 15. iOS Fix — точечная фрагментация для iOS-клиентов

### Проблема

У iOS-клиентов Telegram другой TLS ClientHello, и ТСПУ может блокировать
именно iOS по JA4-фингерпринту. При этом Android и Desktop через тот же
порт работают нормально.

`client_mss` (раздел 14) фрагментирует ClientHello для **ВСЕХ** клиентов —
даже тех, кому фрагментация не нужна. Это добавляет overhead (лишние пакеты,
латентность) для Android/Desktop.

### Решение

iOS Fix создаёт **отдельный внешний порт** для iOS-клиентов. На этом порту
iptables TCPMSS-clamp фрагментирует ClientHello «на лету», а трафик
прозрачно редиректится на основной порт Telemt.

```
iOS-клиент → порт 5001 → iptables TCPMSS (MSS 92) → REDIRECT → порт 5000 (Telemt)
                                                                ↑
Android/Desktop → порт 5000 → напрямую (без TCPMSS) ────────────┘
```

- iOS-клиентам даёте ссылку с `port=5001`.
- Android/Desktop — ссылку с `port=5000`.
- Secret и IP — те же для всех; меняется только port= в ссылке.

### Как работает (механизм)

Два iptables-правила:

```
# 1. mangle/PREROUTING — TCPMSS-clamp на SYN для внешнего порта
iptables -t mangle -A PREROUTING -p tcp --dport 5001 \
    --tcp-flags SYN,RST SYN \
    -m comment --comment telemt-ios-mss-fix \
    -j TCPMSS --set-mss 92

# 2. nat/PREROUTING — REDIRECT с внешнего порта на основной
iptables -t nat -A PREROUTING -p tcp --dport 5001 \
    -m comment --comment telemt-ios-mss-fix \
    -j REDIRECT --to-port 5000
```

Первое правило клампит MSS только на SYN/SYN-ACK для внешнего порта — на
установленные соединения и остальные порты не влияет. Второе — прозрачно
подменяет порт назначения на основной порт Telemt до локальной доставки
пакета.

### ВАЖНО: конфликт с client_mss

`client_mss` в конфиге задаёт MSS на **ВСЕ** соединения сразу. Если он
включён, два механизма будут спорить за MSS одного и того же сокета.

**При включении iOS Fix:**
1. Chimera читает `telemt.toml` и проверяет, есть ли `client_mss`.
2. Если есть — предупреждает: "client_mss задан — конфликтует с MSS-clamp
   для iOS-порта."
3. Спрашивает: "Убрать client_mss из конфига и продолжить? [Y/n]"
4. При согласии — `client_mss` **удаляется из конфига** (`_strip_client_mss()`).
5. Telemt перезапускается (`systemctl restart telemt`).

**После этого фрагментация продолжает работать, но ТОЛЬКО для iOS-клиентов**
(через iptables TCPMSS на внешнем порту 5001). Android/Desktop, подключающиеся
на основной порт 5000, получают **нормальный MSS** (без фрагментации).

> **Это правильное поведение**, а не баг. Смысл iOS Fix — точечная
> фрагментация только для iOS, без overhead для остальных. Если хотите
> фрагментацию для всех — не включайте iOS Fix, используйте `client_mss`.

### Когда использовать iOS Fix вместо client_mss

| Ситуация | Что выбрать |
|---|---|
| ТСПУ блокирует ВСЕХ клиентов (Android + iOS + Desktop) | `client_mss` (фрагментация для всех) |
| ТСПУ блокирует ТОЛЬКО iOS, Android/Desktop работают | iOS Fix (точечная фрагментация) |
| Не знаете кого блокирует | Начните с `client_mss`. Если Android/Desktop жалуются на медленность — переключитесь на iOS Fix. |

### Включение

Меню Telemt → **iOS Fix** → `[1]` Включить / изменить параметры.

1. Укажите **внешний порт** (по умолчанию основной +1, например 5001).
2. Укажите **MSS** (по умолчанию 92 — соответствует пресету `tspu`).
3. Если `client_mss` задан — подтвердите удаление из конфига.
4. Chimera применяет iptables-правила, перезапускает Telemt.
5. Выдайте iOS-пользователям ссылку с `port=5001`.

### Выключение

Меню Telemt → **iOS Fix** → `[2]` Выключить и удалить правила.

Chimera удаляет iptables-правила (TCPMSS + REDIRECT), помеченные
`--comment "telemt-ios-mss-fix"`. Основной порт Telemt продолжает работать
как обычно.

> **Важно:** при выключении iOS Fix `client_mss` НЕ возвращается
> автоматически — он был удалён из конфига при включении. Если хотите
> фрагментацию для всех — установите `client_mss` заново (ручная правка
> `telemt.toml` или переустановка).

### Проверка статуса

```bash
# Проверить iptables-правила iOS Fix
iptables -t mangle -L PREROUTING -n -v | grep telemt-ios-mss-fix
iptables -t nat -L PREROUTING -n -v | grep telemt-ios-mss-fix

# Проверить client_mss в конфиге
grep client_mss /etc/telemt/telemt.toml
# Если строка есть → client_mss задан (конфликт с iOS Fix)
# Если строки нет → client_mss удалён, фрагментация через iOS Fix
```

## 16. SYN Limiter — защита от SYN-флуда и зависаний "Подключение..."

### Что это и зачем

**Симптом:** клиент Telegram у части пользователей зависает в статусе
"Подключение..." на неопределённое время, либо подключается и затем рвётся.

**Причина:** ретрай-шторм SYN. Клиент в нестабильной сети (мобильный
интернет, агрессивный NAT) не получает SYN/ACK вовремя и шлёт повторные
SYN, которые накладываются на старое полуоткрытое соединение. Сервер видит
лавину SYN с одного IP и:
- тратит ресурсы на обработку дублей;
- conntrack/backlog не успевает;
- клиент закономерно не может завершить handshake.

> **Важно:** `client_mss` (раздел 14) здесь НЕ помогает — это другая
> проблема. `client_mss` решает детект DPI по TLS-фингерпринту. SYN Limiter
> решает ретрай-шторм SYN на уровне TCP-рукопожатия.

### Как работает

iptables `hashlimit` — секционирование SYN-трафика по клиентскому IP:

```
# Правило 1: пропустить SYN в пределах лимита на src-IP
iptables -A INPUT -p tcp --dport 5000 --syn \
    -m hashlimit --hashlimit-name telemt_syn \
    --hashlimit-mode srcip --hashlimit-srcmask 32 \
    --hashlimit-upto 1/sec --hashlimit-burst 1 \
    --hashlimit-htable-expire 10000 \
    -j ACCEPT

# Правило 2: отбросить всё, что превысило лимит
iptables -A INPUT -p tcp --dport 5000 --syn -j REJECT --reject-with tcp-reset
```

- Первое правило пропускает SYN в пределах лимита на src-IP (через скрытую
  hash-таблицу ядра).
- Второе — отбрасывает всё, что превысило лимит для данного IP, сразу с
  TCP RST (а не тихим DROP), чтобы клиент не ждал таймаут и реконнектился
  мгновенно.
- Не-SYN пакеты (уже установленные соединения) правило не трогает.

### Пресеты

| Пресет | Rate | Burst | Описание |
|---|---|---|---|
| **Жёсткий** ★ | 1/sec | 1 | Рекомендуется по умолчанию. Один SYN в секунду с IP, без bursts. |
| Средний | 1/sec | 3 | Допускает короткие всплески (3 SYN подряд). |
| Мягкий | 2/sec | 5 | Для нестабильных сетей с частыми ретраями. |
| Свой | — | — | Произвольные rate/burst. |

> **Рекомендация:** начните с **жёсткого** (1/sec, burst 1). Если
> пользователи жалуются на сложности с подключением — смягчите до среднего.

### Когда включать

- Пользователи жалуются на "Подключение..." зависания.
- В логах `journalctl -u telemt` много `connection reset` / `SYN flood`.
- Много пользователей с мобильного интернета (нестабильный NAT).

### Когда НЕ нужно

- Мало пользователей (< 10) — SYN-шторм маловероятен.
- Все пользователи на стабильных каналах (домашний интернет, Ethernet).

### Как включить

Меню Telemt → **SYN Limiter** → `[1]` Включить / изменить пресет.

1. Выберите пресет (жёсткий / средний / мягкий / свой).
2. Chimera применяет iptables-правила, помеченные
   `--comment "telemt-syn-limit"`.
3. Правила сохраняются через `netfilter-persistent save` / `iptables-save`.

### Выключение

Меню Telemt → **SYN Limiter** → `[2]` Выключить.

Chimera удаляет ТОЛЬКО правила с тегом `telemt-syn-limit` — не трогает
REDIRECT-правила xray/tproxy (другая chain/match, другой тег), не трогает
TCPMSS-правила iOS Fix (другой тег).

### Проверка

```bash
# Проверить правила SYN Limiter
iptables -L INPUT -n -v | grep telemt-syn-limit

# Должно быть 2 правила:
# 1. ACCEPT с hashlimit (пропуск в пределах лимита)
# 2. REJECT --reject-with tcp-reset (отброс превышения)
```

### Совместимость

- **Не конфликтует с xray-tproxy** — SYN Limiter работает в цепочке `INPUT`
  (входящие SYN), а xray-tproxy — в `nat/OUTPUT` (исходящий трафик telemt).
  Разные chain, разный match, не пересекаются.
- **Не конфликтует с iOS Fix** — iOS Fix работает в `mangle/PREROUTING` +
  `nat/PREROUTING`, SYN Limiter — в `INPUT`. Разные chain.
- **Не конфликтует с iptables-учётом трафика** — учёт работает в
  `TELEMT_STATS_IN/OUT` цепочках, SYN Limiter — в `INPUT`.

| ✅ | ❌ | ❌ | ✅ | ТСПУ блокирует всех, ME заблокирован (Direct через xray) |
| ❌ | ✅ | ❌ | ❌ | ТСПУ блокирует только iOS, ME не заблокирован |
| ❌ | ✅ | ❌ | ✅ | ТСПУ блокирует только iOS, ME заблокирован |
| ✅ или ❌ | ✅ или ❌ | ✅ | любое | SYN-шторм от нестабильных клиентов |

> **Примечание:** `client_mss` и iOS Fix **взаимоисключающи** — при включении
> iOS Fix `client_mss` удаляется из конфига. Фрагментация продолжается через
> iptables TCPMSS, но только для iOS-клиентов на внешнем порту.
